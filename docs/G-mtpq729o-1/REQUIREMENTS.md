3. 覆盖完整性以 §2.5 功能域基线 + 功能索引对账为准（R-3）；将军可抽测模块主路径。

**明确不做什么（scope out）**
- 🚫 不写内部架构/源码导读（workbench/README、scrum/README 已有）；不逐行复述 API 实现。
- 🚫 首版不做多语言/网页版/截图集。
- 🚫 不删除 README 中仍承担总览/快速开始/排障职责的内容（去重时迁移而非丢弃）。

**验收口径（可测语句）**
- AC-R1-1 存在性：main（或待 promote 分支）存在 docs/FEATURES.md（或将军裁决的路径），文件为有效 Markdown，标题含「功能使用介绍 / 使用手册」语义。

- AC-R1-3 覆盖对账：§2.5 功能域基线中将军确认保留的每个域，在手册中均有对应章节或小节，章节锚点可在文档内跳转（对账方法见 R-3 AC-R3-1）。

### R-3（P0）功能索引（feature index）：机器可提取的完整性对账基准

**背景**：没有功能清单，「完整」就无法度量，新增功能是否漏更也无法自动判断。T-098 machcheck 与 T-107 stage.docs 证明仓库已有「可机器核对的结构化文档」先例。

**目标**：功能手册内置**功能索引段**（独立小节，固定表格格式），每行 = 功能名 | 章节锚点 | 入口 | 状态（已上线/迭代中/遗留）；该段可被脚本稳定提取，作为完整性对账与新增功能检出的基准。

**做什么（scope in）**
1. 定义索引格式（coder 定稿，breaker 校验可解析性）：建议每行四段 | 分隔、首列为功能 ID（如 F-01）。
2. 索引覆盖 §2.5 功能域基线中将军确认的全部功能（域级即可，不必到按钮级——粒度 D-6）。
3. 提供最小解析器/断言样例供 test-designer 转用例（可放 docs/T***-evidence/machcheck 风格脚本或 CI 阶段，R-5 统一）。

**明确不做什么（scope out）**
- 🚫 不承诺自动穷举源码生成索引（可选增强 D-6）；首版索引为人工整理 + 机器校验格式与锚点。
- 🚫 索引不做版本化 UI/网页（纯 Markdown 段即可）。

**验收口径（可测语句）**
- AC-R3-1 可提取：用脚本（样例：正则按行首 F-[0-9]{2} 提取功能索引行）能从 docs/FEATURES.md 提取出索引表，行数 ≥ §2.5 基线功能域数 - 将军删除项，0 解析异常（缺段/坏列）。
- AC-R3-2 锚点有效：索引中每个「章节锚点」在文档内存在对应标题（提取 #… 并比对全文标题，0 失效）。
- AC-R3-3 无空壳：索引中每条功能对应正文小节非空且含「入口」或「操作」字样内容（抽样 3 条人工复核 + 脚本断言小节行数 ≥ 5）。
- AC-R3-4 双向引用：README §3 模块导航能索引到功能手册对应章节（配合 AC-R2-2）。

### R-4（P0）持续自动更新机制：流水线契约（功能触发 → 文档同步强制携带）

**背景**：goal 的核心是「持续性」。若只交付首版手册，下个功能一来文档又烂尾。需要在**本仓库自己的功能交付流水线**里建立强制规则：凡用户可见功能变化，链上必须带「文档同步」。

**目标**：功能触发类目标/任务在其生命周期内**自动携带文档同步义务并验收**：拆解默认生成「文档同步」切片或验收项（更新功能手册对应功能小节 + 功能索引 + README 引导段），缺失时任务有明确提示/被打回；新功能合入 main 时文档已同步合入。

**做什么（scope in）**
1. 定义触发判定（§8 D-5）：用户可见行为变化的合入触发；纯重构/测试不触发。
2. 接入点（researcher 选型，至少一处落地）：
   - breaker 拆解模板/守护注入：凡 feature 类任务链，自动附「doc-sync」验收项或切片（文件域 = docs/FEATURES.md + README.md 对应段），或
   - roles.json/stage-standards 为 coder/devops 增加「用户可见行为变更须同步功能手册 + README」验收项，或
   - 新增轻量规则文档 + 守护提示词注入（与 LEGION.md 纪律呼应并机器化其一）。
3. 文档同步最小义务：改对应功能小节（或新增小节）+ 更新功能索引行 + README 对应引导（如 README 本就只留引导，多数情况仅加一行/链接）+ 同步登记为该任务产出文档（复用 T-107 产物登记链路，可选）。
4. 首版生效方式：以一次真实/模拟功能迭代做试点（用当前在途或将军指定的下一个功能目标），验证机制走通。

**明确不做什么（scope out）**
- 🚫 不做运行期自动生成文档。
- 🚫 不强制**非功能类**任务（bug 修复但无行为变化/纯重构）更新文档（D-5 例外口径）。
- 🚫 不做跨目标/跨空间文档同步（只约束本仓库主功能文档）。

**验收口径（可测语句）**
- AC-R4-1 模板生效：按现状生成一条**功能类**目标链（发布一个「给 Legion 加一个用户可见小功能」的测试目标，或用将军指定目标），breaker 拆解产物（docs/G-mtpq729o-1/TASK_BREAKDOWN.md）中**存在**显式文档同步切片或带 doc-sync 验收项的任务（文件域含 docs/FEATURES.md 或 README.md）。
- AC-R4-2 缺失即提示：模拟该链某任务**未做**文档同步直接提交 → 任务停在 in_review 且有明确「需同步功能文档」类提示（守护评论/验收项不满足），将军可打回；补上后通过。
- AC-R4-3 试点闭环：试点功能合入 main 后，docs/FEATURES.md 与 README.md 出现该功能对应内容，功能索引新增该功能行（AC-R3 校验通过）；试点全程 0 次人工提醒（文档同步由机制携带，非将军逐任务叮嘱）。
- AC-R4-4 非功能不误伤：对一条**纯重构/测试类**任务（样例：只改内部实现不改行为），其链不要求文档同步（无 doc-sync 验收项或该项标注 not-applicable），流程不被卡。
- AC-R4-5 回归：既有 stage.docs 产物登记/预览（T-107）不受影响；roles.json 若被改动仅限新增字段/模板，岗位职责语义不变。

### R-5（P1）文档新鲜度机器校验（CI/脚本门禁）

**背景**：让 R-4「可被自动验证」，避免纪律停留在散文。仓库已有 run-ci.mjs 六阶段与 T-098 machcheck 先例，扩展成本低。

**目标**：提供可运行的文档校验（脚本或 CI 阶段）：索引可提取且 0 异常、索引锚点有效、README↔功能手册互链有效、README 快速开始关键项不丢（对应 AC-R2/AC-R3 的机器化子集），作为发布门禁可选项接入。

**做什么（scope in）**
1. 实现校验脚本（样例形态：node scripts/ci/check-docs.mjs 或扩展 run-ci.mjs 加 doc 阶段），检查项 = AC-R2-1/2/3 + AC-R3-1/2/3 的机器子集。
2. 接入方式（researcher 定）：发布 CI 默认跑或可跳过开关；失败输出到具体行。
3. 与 T-098 machcheck 先例的关系：可复用其断言风格，不重复造轮子（D-4 若将军只选流程规则，本需求降 P2 或仅留脚本不进 CI）。

**明确不做什么（scope out）**
- 🚫 不校验文档「语义是否准确」（那靠 tester 抽测 + 将军验收），只校验结构与链接/索引一致性。
- 🚫 不把校验做成必须联网/装依赖（仓库禁联网下依赖，脚本零依赖 Node 即可跑）。

**验收口径（可测语句）**
- AC-R5-1 脚本存在且零依赖可跑：node scripts/ci/check-docs.mjs（或等价）在仓库根直接运行 exit 0（当前文档满足时）；含 --help 或阶段说明。
- AC-R5-2 正向用例：故意在 docs/FEATURES.md 插入一个失效锚点链接 → 脚本 exit ≠ 0 且报错含文件与锚点行。
- AC-R5-3 覆盖项：脚本覆盖 AC-R2-2（README→手册锚点）、AC-R3-1（索引提取）、AC-R3-2（索引锚点）至少三项；AC-R2-1 段落去重与 AC-R2-3 关键项可用脚本或人工清单二选一。
- AC-R5-4 门禁接线（若接 CI）：run-ci.mjs 文档阶段 PASS/FAIL 正确反映（全绿 PASS，注入坏链接 FAIL），证据输出可查。

## 6. 端到端验收总口径（happy path + 关键边界，供将军快速验收）

1. **首版交付验收**：将军打开 docs/FEATURES.md（或裁决路径）→ 目录完整、功能索引在、README 收敛并互链 → 按手册快速开始走通三分钟循环，再抽 3 个功能域按手册复现成功 → 检查 README 与手册无整段重复（R-1/R-2/R-3 AC 全绿）。
2. **持续机制验收（试点）**：将军发布一个**用户可见小功能**目标（或指定在途功能）→ 链的拆解自动带文档同步切片（R-4）→ coder 合入时手册+README+索引同步更新 → CI 文档校验通过（R-5）→ main 上该功能「手册可查、README 有引导」。全程将军不需逐任务叮嘱「记得更文档」。
3. **不误伤边界**：一条纯重构任务不被文档要求卡住（R-4 AC-R4-4）。
4. **缺失提示边界**：故意不做文档同步的任务停在 in_review 且有明确提示，可打回（R-4 AC-R4-2）。
5. **机器门禁边界**：注入失效链接/坏索引 → 校验脚本失败并指明位置（R-5）。

## 9. 关键澄清结论（给将军的速览）

1. **目标 = 双交付**：① Legion 平台一份**结构化完整功能使用手册**（新文档，README 收敛为总览并互链去重）；② **持续机制**——本仓库每次用户可见功能新增/迭代，流水线强制携带文档同步并可被机器校验（R-1~R-5）。
2. **产品对象**：本仓库 Legion 平台自身（software 空间历史目标一致），非外部软件（A-1，D-1 待确认）。
3. **「自动」的落点**：不承诺运行期自动生成；落地为「拆解默认注入 doc-sync + 缺失即提示/打回 + CI/脚本新鲜度校验」（R-4/R-5），与既有守护/产物链（T-107 stage.docs）复用。
