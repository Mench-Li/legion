### 2.2 数据面现状（team-hub chat：会话/消息/AI 回复状态机）

- 表：conversations（scope 分区）、messages（conv_id/scope/author/kind/body/meta）、chat_reply_settings（per-scope 开关/模型/身份/systemHint）；meta JSON 列承载 AI 状态（零迁移扩展）。
- 发送即入队：postMessage 在回复开关开且发送者非本空间回复方身份时给消息标 meta.aiStatus=awaiting（server.mjs:996-1008）；回复方身份默认 ＜scope＞-assistant（replyIdentityFor，可被 settings.identity 覆盖，chat.test.mjs S9 TC-S9-05）。
- 回复设置默认 **enabled=true**（getReplySettings 未设置行即返回默认开，server.mjs≈:1046-1056；live 库 chat_reply_settings 为空表 = 默认开生效中，§2.5）。
- 队列/回写：GET /api/chat/replies 拉 awaiting（含最近上下文、limit 上限、跨空间隔离）；POST /api/chat/replies/answer|retry|fail CAS 回写 awaiting→replied/failed，重复/并发幂等不产生第二条回复（server.mjs:1101-1215、:2643-2690）；超龄（> CHAT_REPLY_TIMEOUT_MS）兜底标 failed（:1084-1098）；retry = failed→awaiting 重新入队（:1183-1187）。
- 测试锚定：node team-hub/chat.test.mjs **本次实测 23 tests / 23 pass / 0 fail / exit 0**（suites 14，duration 约 0.9s），覆盖 S1 会话/消息契约 + S9 AI 回复数据面（TC-S9-01..13：默认开、awaiting 状态机、身份不自我触发、队列/上下文/limit、CAS 幂等回写、超龄兜底、retry、HTTP 路由非法入参 400）；CI 阶段 chat 契约在 run-ci.mjs:190 登记，历史全绿。
- **结论**：数据面「发送 → awaiting →（守护执行）→ replied/failed」闭环契约可用且绿；本目标缺口**不在数据面**。

### 2.3 回复执行层现状（plugins chat-responder，故障点候选）

- 守护每轮 sweep 调 sweepChatReplies()（plugins/src/index.ts:2500）：拉本 scope awaiting → 逐条 answerChatMessage（:2389-2475）→ 经 ctx.subagents.start 起**轻量子代理**直答（无仓库工具、不访问文件/网络；提示词 = 空间对话助手角色 + systemHint + 会话历史，plugins/src/chatResponder.ts buildChatAnswerPrompt）。
- 模型解析链：settings.model → agent_models 表 role≈assistant 行 → 守护当前选择模型（config/currentSelection）→ 子代理 agentOptions；**未知/不可用模型 → 子代理 stopReason=error → 回写 failed + 笼统 error 文案**（测试 TC-S10-06 即定义此路径「不崩溃」，但 aiError 对用户**不可行动**——live 失败正是该形态，§2.5）。
- 运行前提（默认假设）：**守护进程在线 + 模型解析成功 + foreman 可用 + 回复预算 ≤120s**（budgetMs = min(workerTimeoutMs, 120000)）；任一不满足 → awaiting 停留或 failed。UI 对「守护没在跑/模型没配」**无预防性提示**。
- **结论**：R-1 的主战场 = 执行层（模型/守护/子代理出站失败的可诊断、可行动化与恢复），并给出「配置不可用时的明确提示」，把笼统「回复子代理未完成（error）」升级为可读原因。

### 2.4 UI 面现状（ChatView + api.ts）

- 守卫与死路：hub 模式守卫 ChatView.tsx:237（「需要中枢」卡片）；**scope 守卫 ChatView.tsx:250-257：未选具体空间（含「全部空间」默认视图）→ 只显示「请先选择具体工作空间…（全部空间视图不可发消息）」卡片，无「选择工作空间开始对话」入口**——用户落在默认「全部空间」时对话中心**看起来不可用**（与 goal「对话功能不可用」的部分观感吻合，但 live 证据证明将军实际已进入 software 空间并发送成功，主因仍为 AI 不回复，§2.5）。

- **结论**：UI 缺「上下文输入面」（选空间入口、文件上传）与「回复设置面」；失败文案/预防提示可行动性不足。

**背景**：goal 第 1 条「对话功能不可用，无法回答」。live 证据（§2.5）：software 空间会话 msg2 发送后 awaiting→failed（aiError「回复子代理未完成（error）」），全程无回复；数据面 23/23 测试全绿（§2.2）→ 故障点在执行层（守护/模型解析/子代理出站）。另 UI 对「未选空间（全部空间视图）」直接不可发起会话（§2.4），且失败文案/预防提示不可行动。

**目标**：默认运行前提（守护在线 + 模型可解析 + 回复开）下，用户在具体空间会话发消息后能在时间窗内收到回复方消息；模型/守护不可用等失败场景给出**可读、可行动**的原因与恢复路径（重试可用、修复配置后新消息即正常）；「无法回答」死胡同消失。

**做什么（scope in）**
1. 复现与根因定位（researcher/coder 执行）：在**隔离实例/临时库**上按 §2.5 现场复现同型失败（发送 → awaiting → failed「回复子代理未完成（error）」），定位 stopReason=error 的具体根因（模型解析链 settings.model→agent_models→守护默认模型哪个环节失效/提供方不可用/子代理 start/预算/foreman 等），修复并记录复现命令。
2. 可行动失败文案：failed 时 aiError 按根因分类给**可行动提示**（如「未配置可用模型：请在模型配置中选择 assistant 可用模型后重试」「回复超时（守护未响应）」），不再出现笼统 error；UI ❌ 气泡与原因展示沿用并增强。
3. 运行前提可见化：对话中心对「守护不可达 / 模型不可用 / 回复开关状态」提供可见状态或预防性提示（形态 researcher 定：状态条/开关位/帮助文案，至少不静默）。
4. 入口可用性（与 R-2 重叠部分按 D-2 落地）：未选空间（全部空间视图）不再是无解释死路——有「选择工作空间开始对话」引导入口。
5. 设置面（按 D-4 默认采纳）：对话中心暴露每空间「AI 回复」开关（至少开关，身份/模型可选），接线 api.ts:611-617 既有函数；开关关 → 零出站、人-人消息正常；同步收敛 §2.6 文档不一致。
6. 历史遗留消息口径（按 D-5 默认）：升级后仅新消息进入回复流程；对现存无状态/awaiting/failed 消息不自动轰炸回填（策略见 D-5）。
7. 测试与回归：数据面 23 例不回归；新增「真实执行」验证路径（守护在线时 L1：发送→replied；模型不可用时：failed + 可行动原因）与 CI chat 阶段对齐（run-ci.mjs:190）。

**明确不做什么（scope out）**
- 🚫 不替换/不新增 LLM 通道与提供方（模型来源与运行契约留给 researcher，默认沿用现有 DSH 模型解析链）。
- 🚫 不做流式/打字机回复；不改人-人收发与存储语义。
- 🚫 不保证守护离线时也能回复（守护在线 = 运行前提，文档化 + 失败可行动化，而非魔法保活）。
- 🚫 不做语音/富媒体等新会话形态。

**验收口径（可测语句）**
- AC-R1-1 复现锚定：存在一份隔离环境复现记录（命令+输出），发送消息后进入 awaiting 且最终（≤120s 或配置窗）得到 replied 或 failed；复现不触碰 live 库（§4.2）。
- AC-R1-2 可回答主路径：守护在线 + 模型可用 + 回复开（默认）→ 发送 → 时间窗内会话出现回复消息（author=配置身份/＜scope＞-assistant、body 非空、同一会话、有 audit chat:message），源消息 meta awaiting→replied。
- AC-R1-3 失败可行动：模拟模型不可用/守护离线 → failed 且 aiError 是**分类可行动文案**（包含「如何恢复」语义，测试断言不含裸 error/undefined 样式文案），UI 呈现 ❌ + 原因 + 「↻ 重试」。
- AC-R1-4 重试闭环：failed 消息点重试 → 回 awaiting →（模型修复后）replied；重复回写不产生第二条回复（幂等，TC-S9-08/11 不回归）。
- AC-R1-5 设置开关（D-4 默认采纳时）：对话中心可见每空间「AI 回复」开关；关 → 发送无 awaiting/零出站、人-人消息正常；再开恢复；设置持久化（per-scope，GET/POST /api/chat/reply-settings 契约 TC-S9 不回归）。
- AC-R1-6 入口可用：从「全部空间」视图进入对话中心 → 出现「选择工作空间开始对话」入口，点击后进入该空间可发消息状态（浏览器驱动冒烟）。
- AC-R1-7 数据面回归：node team-hub/chat.test.mjs exit 0（≥23 例）；CI chat 阶段 PASS；既有 chat-l1-smoke/chat-s2-smoke 不回归。
- AC-R1-8 遗留消息口径（D-5 默认）：升级后对 msg1 型无状态旧消息不自动产生回复/标记（断言或人工核对口径一致），新发送消息按 R-1 流程走。

### R-2（P0）对话上下文输入 · 关联工作空间

**背景**：goal 第 2 条前半「对话支持输入上下文，比如关联工作空间」。现状：回复方提示词只有「会话历史 + systemHint」，**没有所关联工作空间的真实内容**（chatResponder.ts 明示无工具/不访问文件）；对「当前指挥台还缺什么功能」「仓库里有什么」类问题只能空答或拒绝（live msg1 即此类问题，§2.5）。同时「全部空间」视图对话中心不可用（§2.4）。

**目标**：用户可在对话中心内选择/切换对话所关联的具体工作空间（含从全部空间视图一键进入）；回复方在会话历史之外可依据**该空间的只读上下文**（空间元数据 + 绑定仓库目录/规范/代表性文件等，具体取数由 researcher 落定）作答——「关于该空间自身」的问题能被真实内容支撑而非幻觉/空答；空间身份与审计随关联正确。

**做什么（scope in）**
1. 入口闭环：对话中心（含全部空间视图）提供「选择工作空间 / 开始对话」入口与空间列表（复用 GET /api/spaces），选定后进入该空间会话态；会话头部展示当前关联空间并可切换（切换后按新空间加载会话/身份，防串显沿用 R-A5 守卫）。
2. 空间上下文口径（默认，D-2）：回复方每次作答的上下文 = 会话历史 + 该空间「只读上下文摘要」（候选：空间元数据、绑定仓库根关键文件（README/FEATURES/LEGION 等）、文件目录概要、该空间规范；精确取数与摘要机制 researcher 选型）；上下文来源与生成时间在 UI 或消息上可见（可选增强）。
3. 身份/审计随关联正确：author=＜scope＞-assistant/settings.identity、audit scope 字段与当前关联空间一致（既有纪律延续，TC-S9-05 不回归）。
4. 护栏接入 R-4：空间上下文的长度预算、注入失败时的降级（无上下文也可回复或明确说明缺什么）。
5. 测试：入口冒烟 + 上下文有效性抽测（用绑定仓库真实事实出题，回答能引用真实内容）。

**明确不做什么（scope out）**
- 🚫 不给回复方任意文件读写/工具权限（上下文为**只读、显式、预算内**提供；默认不做「回复方可自由操作仓库」）。
- 🚫 不做跨空间聚合上下文（一次会话只关联一个工作空间，D-2 例外需将军明示）。
- 🚫 空间上下文具体取哪些文件/摘要/注入深度 = researcher 选型，本需求只钉「有真实上下文且可测其效果」。

**验收口径（可测语句）**
- AC-R2-1 入口：全部空间视图打开对话中心 → 存在可点的「选择工作空间开始对话」入口，选择 software 后进入可发消息会话态（浏览器驱动冒烟）。
- AC-R2-2 关联正确：会话头部/状态能标识当前关联空间；切换空间后会话列表/消息/回复身份随新空间（无串显——R-A5 守卫断言沿用）。
- AC-R2-3 上下文生效：在绑定仓库的 software 空间会话中，向回复方提「用一句话说明仓库里有哪些顶层目录/README 讲的产品是什么」类事实题 → 回复内容与仓库真实结构一致（tester 用真实内容抽测 ≥2 题，断言关键实体出现且无编造目录名）。
- AC-R2-4 降级不崩：仓库无绑定/读不到上下文 → 回复方明确说明「无法读取工作空间内容」或按历史回答，不报错不冒充（断言文案）。
- AC-R2-5 身份审计：回复消息 author=software-assistant（或设置身份）、audit 含 chat:message 且 scope=software；R-1 AC-R1-7 数据面回归全绿。

### R-3（P0）对话上下文输入 · 上传文件

**背景**：goal 第 2 条后半「…上传文件等方式」。现状：对话编辑器纯文本（ChatView.tsx:442-455），无任何附件能力；messages 无附件数据面；回复方只能看到会话文字。将军要给 AI「看个文件再答」无处下手。

**目标**：用户在对话中可**选择/上传文件**随消息发送；该文件内容作为回复方的回答上下文（连同会话历史）；上传的文件在会话消息上有可见标识；超限/非法类型有可读拒绝；文件内容**不写入消息正文**（安全），仅作上下文并经审计可见。

**做什么（scope in）**
1. 数据面（默认 D-3/D-6，机制 researcher 定）：消息 meta 携带附件引用（文件名/大小/内容引用或内联文本），kind 仍为 text（或新增 kind 需过服务端白名单，二选一由 researcher 定）；附件随**当条消息**进入回复上下文，不形成跨消息持久知识；上下文字符预算见 R-4。
2. UI 面：编辑区提供「📎 添加文件/上传」入口（单选/多选按 D-6），发送前可移除；发送后该消息旁展示附件标识（文件名/大小）；附件内容不进 draft/body。
3. 边界与安全（R-4 护栏）：类型/大小/数量限制（D-6 默认）、超限可读错误、纯文本提取失败（二进制/图片）提示「不支持作为上下文」、上传文件仅该会话可见、操作留 audit。
4. 测试：上传→基于文件内容提问→回答引用正确；无附件行为不回归；拒绝路径断言。

**明确不做什么（scope out）**
- 🚫 不把上传文件做成「全局知识库/长期记忆」（默认仅当次回复上下文，D-3）。
- 🚫 不做图片/音视频多模态理解（非文本文件可上传但默认提示不可作上下文，D-6 例外需将军扩展）。
- 🚫 不做文件跨会话共享/转发；不做回复方可自由下载/编辑上传文件（只读上下文）。
- 🚫 存储介质/落盘位置/生命周期 = researcher 选型（可复用文件中心写纪律或临时面），本需求钉用户可感知行为。

**验收口径（可测语句）**
- AC-R3-1 上传可发送：编辑区存在附件入口；选择一个文本文件（如 README.md）随消息发送成功；消息旁出现附件标识（文件名+大小）；messages 数据面携带附件引用且 body 不含文件全文。
- AC-R3-2 基于文件作答：上传内容含独有事实（tester 用带特定编号/术语的测试文件）→ 提问 → 回复引用了该独有事实（断言关键串出现）；不带上传文件时同问 → 无该事实（对照断言，证明上下文真实生效）。
- AC-R3-3 拒绝路径：超大小上限/超数量/二进制或超大文件 → 发送前或发送时给出可读错误，消息不进队列（或进队列但回复明确「无法读取该附件」），UI 不崩。
- AC-R3-4 移除与取消：发送前可移除附件；移除后不随消息发送（断言请求不含附件）。
- AC-R3-5 安全回归：消息正文仍纯文本渲染、无 dangerouslySetInnerHTML（既有 S2 安全断言不回归）；审计含附件操作（chat:message detail 可断言文件名/大小）；附件仅属该会话（跨会话不可见）。
- AC-R3-6 无附件回归：不带附件的人-人/AI 消息行为与 R-1 验收一致（AC-R1-2/3 不回归）。

### R-4（P1）上下文输入护栏与公共规则（横切 R-2/R-3）

**背景**：R-2/R-3 引入「外部内容进入回复上下文」，必须钉住公共边界，避免泄漏/超预算/文档失真。

**目标**：一套可测的公共护栏，同时约束空间上下文与上传文件上下文。

**做什么（scope in）**
1. 上下文预算：单次回复可注入的外部上下文总字符预算（默认：空间摘要 + 附件合计 ≤ 约 8000 字符量级，具体由 researcher 定并暴露配置），超限截断并提示（不静默丢弃关键部分）。
2. 内容边界：只接受文本类（UTF-8）；上传文件类型白名单/黑名单可配置（默认黑名单含可执行/压缩/图片等，D-6）；路径/仓库内容只读。
3. 可见性与审计：附件/空间上下文在该会话可见；chat:message 等 audit 携带来源（文件名/大小/空间）可断言；**文件内容不进消息 body**（防泄漏进人-人面）。
4. 失败与降级：上下文读取失败 → 明确提示并降级（仅按会话历史回答），不冒充读取成功。
5. 清理策略：上传上下文不跨消息/会话持久（D-3），保留策略 researcher 定并文档化。

**明确不做什么（scope out）**
- 🚫 不做敏感内容扫描/脱敏引擎（默认仅显式提供 + 审计 + 预算；内容治理如需要由将军另立目标）。
- 🚫 不把护栏做成运行期联网能力（零外网依赖纪律延续）。

**验收口径（可测语句）**
- AC-R4-1 预算断言：构造超预算附件 → 回复仍完成或明确截断提示；不抛未定义错误。
- AC-R4-2 类型断言：黑名单类型上传被拒（可读文案）；文本类型成功。
- AC-R4-3 泄漏断言：带附件消息的 messages.body 不含文件正文片段（正则断言）；附件引用只存在于 meta/附件字段。
- AC-R4-4 审计断言：附件/上下文操作留 chat:* audit，detail 含文件名+大小+scope。
- AC-R4-5 降级断言：上下文读取失败路径的回复文案明确（R-2 AC-R2-4 同断言族）。
- AC-R4-6 清理断言：新会话/新消息不带上一消息附件上下文（隔离断言）。

## 6. 端到端验收总口径（happy path + 关键边界，供将军快速验收）

1. **可回答主路径**：选中 software 空间 → 新建/打开会话 → 输入「你好」→ 守护在线+模型可用时 ≤120s 内收到 software-assistant 回复；消息状态 ⏳→✅（R-1 AC-R1-2）。
2. **上下文输入 · 工作空间**：全部空间视图可一键选择工作空间开始对话；在 software 会话问「指挥台顶层有哪些目录/README 说了什么」→ 回答引用仓库真实内容（R-2）。
3. **上下文输入 · 上传文件**：上传一个含独有事实的文本文件并提问 → 回答引用该事实；不传时无此事实（R-3 对照断言）。
4. **失败可行动**：模型配置不可用 → ❌ + 「如何恢复」文案 + 重试按钮；修复配置重试后成功（R-1 AC-R1-3/4）。
5. **不误伤回归**：人-人收发、无附件消息、数据面 23 例、CI chat 阶段全绿；live 库零写入（R-1/R-4）。
6. **文档一致**：FEATURES §3.9 / README 与实现一致，含失败排查与上下文操作说明（R-5）。

## 9. 关键澄清结论（给将军的速览）

1. **goal 第 1 条是真实缺陷，且现场就在 live 库**：目标创建前 4 分钟（2026-09-07T10:30:57Z），software 空间会话消息「hi」被回写 failed / 回复子代理未完成（error），全程无回复（§2.5）；数据面 23/23 测试全绿（§2.2）→ **故障在执行层**（守护 chat-responder → 模型/子代理出站），需求 = 复现定位 + 修复 + 失败可行动化 + 入口可用性（R-1）。
2. **「对话中心」= Legion workbench 💬 对话中心**（含 team-hub chat 后端 + 守护链路），与历史目标一致；现场会话「software 工作空间对话」为直接证据（D-1）。
3. **goal 第 2 条 = 给 AI 回复方喂「真实上下文」**：现状回复方只有会话历史、无仓库/文件可见性（chatResponder 明示无工具）——①关联工作空间（R-2：选/换空间 + 空间只读内容为上下文 + 打通全部空间死路）②上传文件（R-3：显式文本附件为当次回复上下文）。「等方式」开放，本期只做示例两种（O-2）。
4. **三处「文档/UI 不一致」一并收口**：回复设置「每空间可开关」无 UI 入口（§2.6）；「全部空间」视图对话中心无解释死路（§2.4）；故障排查表缺「AI 不回/失败怎么办」——分别由 R-1/R-2/R-5 按 D-4 裁决落地。
5. **给下游的自由度**：LLM 通道、上下文注入机制、附件存储、守护/模型运行契约、预算配置形态——均留给 researcher/breaker/coder 落定；本文钉用户可感知行为与可测验收。
