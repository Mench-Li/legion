# 提交纪律与违规记录

本文件记录**流程违规**（不是代码缺陷 —— 那类在 `docs/bugs/`），以及它们暴露出的机制缺口。
写下来的理由只有一条：**违规如果不留下可查的账，它下一次会以同样的形态再发生一次。**

---

## 规矩（业主 2026-10-12 复述）

> **不允许直接提交到 `main`，只允许通过功能分支合并到 `main`。**

配套动作（本仓既有的做法）：功能分支 → `git merge --no-ff` 进 `main` → `git push origin main`；
推送被拒时 `git fetch` + 合并 `origin/main` 后重试（并发同事很频繁）。

## 违规记录

### ① 2026-10-04 ｜ `3f48b02c` ｜（业主已裁决"接受并记录"）

`fix(workbench): /hub 代理的转发身份要分三种…（BUG-019）` —— 直接落在 `main` 上。

### ② 2026-10-12 ｜ `5e21263e` ｜（业主已裁决"接受并记录，下次绝不允许再犯"）

`fix(plugin): 影子对账读 Legion 目录漏了 includeSecretRefs=1 —— 那扇门开不了的根因`

**怎么发生的**（机制，不是态度）：

```powershell
git checkout -b fix/shadow-fetch-include-secretrefs   # ← 该分支名已存在（上一次尝试留下的）⇒ 失败
git add -- …                                          # ← 没有检查上一条的返回值
git commit -F .msg                                    # ← 于是提交落在 main 上
```

两次尝试的**第一次**是被 PowerShell 的多行提交信息解析搞坏的（提交没成，但分支建好了）；
第二次我用了消息文件——**却没有先确认自己还在哪个分支**。

**为什么现有流程没拦住**：`git commit` 落在哪个分支只取决于**当前**分支，
而"当前分支是 `main`"这件事在那条命令里**不可见**。整条链上没有任何东西会问一句
"你现在在 main 上，确定吗"。

  > 一个"我在功能分支上"的假设，与一个"我刚才那条命令失败了"的事实，
  > 在提交成功的那一刻是同一个读数 ——
  > 直到推上去，而那时**变更已经进了 main**。

## 防再犯（三条，按成本从低到高）

| # | 动作 | 现在能不能做 |
| --- | --- | --- |
| 1 | **提交前先问自己现在在哪**：`git branch --show-current` 的输出里出现 `main` ⇒ 停，先建分支 | ✅ 立即可用（已写进本文件） |
| 2 | **不把多条 shell 命令串成一串**：`checkout -b` 与 `commit` 分两次执行，**逐条看返回值** | ✅ 立即可用 |
| 3 | **机器判据**（见下） | ⚠ 需要一次裁决 |

### 关于第 3 条（机器判据）——实测之后我不建议现在做，理由如下

可以设想的判据是"`main` 的第一父链上不许新增非 merge 提交"。
但实测（2026-10-12）：

```
git log --first-parent main | wc -l           → 1176
其中「非 merge」的提交                          → 945
```

也就是说**直提在历史上是常态而不是例外**（这 945 里既有真的直提，也有"快进合并"留下的痕迹
—— 两者在提交图上**无法区分**）。于是：

- 这道闸门一旦加上，会**立刻**把一大批历史与同事的既有做法判红；
- 而它分不清"直提"与"快进合并"，所以它报的**不是它想报的那件事**；
- 更要紧的是：它是**全仓策略**，不该由一次事故顺手立起来 ——

  > 一道"顺手加上去"的闸门，如果它拦的是别人的既有做法，
  > 那么它下一次被讨论的原因会是"它太吵"，而不是"那件事有多严重"。

⇒ 建议：先靠上面 1、2 两条（它们覆盖了这次事故的**全部**成因），
等业主明确要求"把这条纪律也做成闸门"（并接受它会红在历史与并发做法上）时再做。
届时的正确形状是**棘轮**：把当时的读数记成基线，只对**新增**报红
（与 `dsh-boundary.mjs`、`reachability.mjs` 同一套做法）。
