# P4-6 白板房间目录的单实例守卫 —— 验证证据

> 任务来源：`docs/REMAINING-TASKS.md` 候选 **#5**（= `docs/STATUS.md` 已知限制 #11 中的
> 「多实例共享存储未实现」）。原话：「白板多实例共享存储未实现（P3-1 已登记）：当前是单实例多房间；
> ADR-0008 记录了被否方案与『转 v2』的触发条件（真正需要横向扩展时再启动）」。

## 1. 先把「候选要什么」和「该做什么」分开

候选的字面意思是「实现多实例共享存储」。但 **ADR-0008 明确否决了这个方向**，并写明
「满足任一触发条件即重新评估，**不提前做**」；三条触发条件（单实例连接数持续超 200/50、
需要跨机房共享同一房间、可用性要求高于单点）**当前一条都不成立**（单团队、单机自托管）。

所以本切片**没有**去实现多实例（那会与 ADR 冲突，且需要外部 DB/Redis，与「零第三方依赖」冲突）。
转而问一个可测、且答案必然有用的相邻问题：

> **今天如果有人（误）把两个实例指向同一个 `WB_ROOMS_DIR`，会发生什么？**

因为 `rooms.mjs` 第 7 行只有一句注释「本模块假设唯一进程持有这些文件」，**没有任何守卫**。
若答案是「静默把数据搞坏」，那它就是一个真实缺陷——无论多实例是否被否决。

## 2. 实测：旧行为是**静默的数据分裂**（这是本切片的全部理由）

真起两个服务进程、指向同一 `WB_ROOMS_DIR`、各自画图（读数取自 `main` 上的实现）：

| 步骤 | 实例1 视图 | 实例2 视图 | 房间真值 |
| --- | --- | --- | --- |
| 实例1 画 red-1 | **1** 个元素 | 404（房间还没在实例2 打开） | 1 |
| 实例2 画 blue-1（其 `welcome.doc` 长度 = **0**，看不到 red-1） | **1**（只有 red-1） | **1**（只有 blue-1） | **2** |
| 两边各再画一笔 | **2**（red-1/red-2） | **3**（blue-1/blue-2/…） | **4** |
| 两侧日志中的错误 | **无** | **无** | — |

**两个实例的视图永久分裂，且谁都不等于真值 4；两侧日志一个字都没有。**
根因不在 SQLite 的并发能力，而在应用层设计：每个实例各持一份内存 doc，
且 `snapshot()` 会 `DELETE FROM ops`——实例 A 落快照可能删掉实例 B 尚未读到的 op（**永久丢失**）。

## 4. 守卫的行为读数（真实进程）

### 4.1 第二个实例必须**启动即失败**

```
[whiteboard] 房间目录已被另一个白板实例占用：<dir>（占用者 pid 6204（端口 24301），自 2026-09-11T06:05:55.039Z 起）
  白板是单实例设计（ADR-0008 决策 1）：两个实例共享同一 WB_ROOMS_DIR 会**静默分裂数据**
  （各自一份内存 doc，且落快照时会删掉对方尚未读到的 op）。
  处置：① 停掉那个实例；② 或为本实例指定独立的 WB_ROOMS_DIR；③ 若确认那个进程已不存在，删除锁文件后重启：<dir>\.whiteboard.lock
```

实测：实例1 起来（`up=true`）→ 实例2 **`up=false` 且以非零码退出**，输出即上面这段；
并且**实例1 完全不受影响**（`/healthz` 仍 200）——守卫不误伤正在服务的那个。

### 4.2 崩溃不能把服务锁死（**接管陈旧锁**）

| 步骤 | 读数 |
| --- | --- |
| SIGKILL 实例1（不走关闭路径） | 锁文件**仍在**（必然残留） |
| 起新实例 | **能起来**，并在日志留下 `[whiteboard] 接管了陈旧目录锁（上一个进程未优雅退出）：…` |
| 新实例能否服务/写入 | 能：`/api/rooms/<id>` 200、画一笔后 `elements: 1` |

这一条是必需的：只做拒绝而不做接管，一次 SIGKILL 就会让服务再也起不来——**比原缺陷更糟**。
接管同时写审计 `lock_takeover` 与启动告警，避免「静默接管」掩盖上一次崩溃。

### 4.3 一次性边界：优雅退出释放锁

`registry.closeAll()` 会 `release()`（用例断言锁文件消失，且随后的新注册表能重新独占——
**既有用例** `rooms.test.mjs`「重启注册表后按房间恢复」正是这个用法，未受影响）。
**未在真实进程上验证 SIGTERM**：Windows 上 `child.kill('SIGTERM')` 是**强制终止**、不执行 JS 处理器，
因此探针里「优雅退出后锁仍在」是**测试手段的平台限制**，不是代码缺陷（服务端确实注册了
`SIGINT`/`SIGTERM` 处理器 → `close()` → `closeAll()`）。锁残留本身由 §4.2 的接管兜底。

### 5.1 覆盖的边界（均在用例里）

| 场景 | 断言 |
| --- | --- |
| 空目录获取 | 锁文件含 pid/端口/起始时间（能把「谁占着」直接告诉运维） |
| 已被**活着的**进程占用 | 拒绝、如实报出占用者、**不覆盖**别人的锁 |
| **陈旧锁**（pid 不存在） | 接管成功，且 `tookOverFrom` 落盘留痕 |
| **锁文件损坏**（非法 JSON） | 按陈旧处理接管，服务不被卡死 |
| release 归属 | 只删自己的锁（pid + startedAt 双匹配），**不得删掉接管者的锁** |
| release 幂等 / 目录不可写 | 二次释放为空操作；不可写报 `unwritable`（不伪装成「被占用」） |
| 内存存储 | **不加锁**、不创建锁文件、多注册表共存（测试与 bench 依赖这一点） |
| 被拒时的副作用 | `open()` 返回 `storage_busy` + 错误里含 `WB_ROOMS_DIR` 与占用者 pid；**不建房间、不碰存储文件** |
| 显式逃生阀 | `lockDir:false` 可关掉守卫（`lockStatus().mode === 'disabled'`） |
| 真实双进程 | 第二个启动即失败且非零退出；第一个不受影响；强杀后可接管并正常服务 |

## 6. 未覆盖 / 已知边界（诚实登记）

1. **本切片没有实现多实例共享存储**（那是 ADR-0008 明确否决、且当前触发条件不成立的方向）。
   本切片做的是**让单实例约束可执行**：把静默数据分裂换成一条明确的启动错误。
2. **锁是建议性的（advisory）**：它只在本服务内部生效。绕过它（改代码、删锁文件后立刻起第二个、
   或用 `lockDir:false`）仍能复现旧的分裂行为。它防的是**误操作**，不是恶意规避。
3. **判活依赖 pid**：理论上存在 pid 复用导致「误判为活着」的窗口（于是错误地拒绝启动）。
   概率极小，且后果是「启动被拒 + 明确提示」，不是数据损坏——比反向误判安全得多。
4. **SIGTERM 优雅释放未在真实进程上验证**（见 §4.3 的 Windows 限制）；Linux 上预期成立但未实测。
5. **锁不覆盖审计目录**：`audit.jsonl` 仍可被两个实例同时追加（追加写本身不易损坏，
   但会造成事件交错与轮转竞态）。本切片只锁房间目录（数据完整性风险所在）。
   这也是为什么**所有测试启动器都用内存房间**（`DB_PATH=':memory:'` → 不加锁），否则并行测试会互相拒绝。
6. **`DB_PATH=':memory:'` 会连带把房间也切成内存**（`index.js:74`）。本探针最初因此测了个空
   （房间里根本没有文件、结论无效），已刻意不设该变量。该语义此前未有文档记录，属**既有**行为，
   本切片未改动——但值得知道：想「只把白板主库放内存、房间仍落盘」是做不到的。
7. **未做多实例的「正确」实现评估**：ADR-0008 被否方案 A 里补记了「`storage.mjs` 接口不足以支撑共享存储」
   （缺订阅/通知通道，且 `snapshot()` 的 `DELETE FROM ops` 会跨实例误删），但**没有**给出完整设计。
   真到触发条件满足时，应从该 ADR 重新评估，而不是照本切片改几行。
8. **`lockDir:false` 逃生阀无审计**：关掉守卫时不会记录任何事件。当前只用于测试；
   若将来要在生产用它，应先补审计。
