## 1. ★★ 段首说明里有一个**过期数字**，而"逐字保真"会把它一起搬走

原文那段开头写着：

```
// 五条路由，刻意把**写**与**投影**分开：
//   · `GET  /api/automation/calendar`  纯投影，不写任何行
//   · `GET  /api/automation/schedules` 计划清单
//   · `POST /api/automation/schedules` 建计划
//   · `POST /api/automation/schedules/update` 改计划（含启停）
//   · `POST /api/automation/tick`      显式物化
//   · `GET  /api/automation/runs`      运行历史
//   · `GET  /api/automation/summary`   汇总
```

说「五条」，紧接着列了 **7** 条。这是搬运**之前**就有的笔误。

> 一个"逐字保真"的搬运，与一个"把原件的笔误一起保真"的搬运，
> 在原文对的时候是同一个东西。

**处置**：不改原文（零改写是纪律），而是让生成器**数一遍、报出来**，
并在搬过去的那一段**之前**加一行"生成器核实"的更正说明。生成日志：

```
⚠ 段首说明说「五条路由」，实测 **7** 条 —— 原文这处数字过期
```

★ 这条检测只在**段首说明自称了条数**时才生效（认 `N条路由`，中文数字与阿拉伯数字都认）；
没自称就只打印一行"无法交叉核对"。它是"逐字保真必须配一道交叉核对"的第一个实例。

## 2. ★ 装置缺陷一：破验脚本的锚点在**缩进**上失配（5/15 条）

生成器把函数体整体缩进 +2。我按原文缩进写的锚点整批失配，
第一轮 15 条里 **5** 条报"锚点没命中"。

改了一次（忽略行首缩进）之后，**还**有失配：`if (sched === null) { json(res, 404,`
这种**行首片段**仍然不匹配 —— 我的匹配器要求**整行相等**，而它只是那一行
（后面还跟着模板字符串）的前缀。

> 一个"锚点没命中"的测试装置，与一个"没有缺口"的测试装置，
> 在报告里都是一句"没咬住"—— 除非你去看那句话是**哪一种**。

**修法**：按"去掉行首空白后的整段文本"做**子串**定位（默认要求唯一，
声明 `{ all: true }` 时打中多处），再按字符坐标回到原文替换、
替换文本套上**原地缩进**。这样锚点写不写缩进、是不是整行都对。

★ 与切片 6 的 K6 是**同一条教训的第二次**：报"锚点没命中"与报"漏网"
退出码相同、含义相反。所以这一版的失败信息里直接带上锚点原文。

## 3. ★★ 用例缺陷一：`calendar` 的"纯投影"判据依赖计划**恰好在点**

破验 K1（"calendar 从纯投影变成顺手落库"）第一轮**没被咬住**。
既有用例 ① 确实盯着这条性质（"打 50 次，运行表一行都不多"），
但它用的计划是 `{ kind: 'daily', hour: 9, minute: 0 }` ——
`nextRunAtMs` 在**未来**，于是 `materializeDue({ nowMs: Date.now() })` **什么都不物化**。
那一次 tick 是个**空操作**。

> 一个"从不写库的投影"，与一个"每次都调一次写库、只是恰好没东西可写"的投影，
> 在测试用的那条计划**不在点**的时候是同一个东西。

**修法**：判据不再依赖"这条计划恰好在不在点"，而是**直接问**
"这一条路由碰过任何写方法吗"——注入桩 + 与计划到不到点无关的断言：

```js
assert.deepEqual(names(s.calls).filter((n) => WRITES.includes(n)), [])
assert.equal(names(s.calls).includes('automationTick'), false)   // 它就是那个会落库的门
```

★ 这是**该用例本身的缺口**，不是新代码的 bug：既有 9 例一条都没说过
"投影端点不许碰写方法"这件事。

## 4. ★★ 用例缺陷二：`requireString` 的判据只喂过"值写错"，没喂过"整个没给"

破验 K6/K7（把 `scope` / `timezone` 的 `requireString` 去掉）第一轮**没被咬住**。
既有用例 ③ 喂的是"时区**值**写错"，那条路径走的是**仓储**的具名拒绝；
它从没喂过"时区**整个没给**"。于是 `undefined` 被静默交给仓储，
而**没有任何用例说过这件事**。

> 一个"字段写错被拒"，与一个"字段没写也被拒"，
> 在用例只喂过前者的时候是同一个东西。

**修法**：逐个删掉一个必填字段 ⇒ 必须 400 `MISSING_PARAM`，且**一次仓储调用都不能发生**；
再配一条**正面控制**（四字段齐全必须建得成），否则"一律拒绝"也能让四条通过。

## 5. ★ 用例缺陷三：只验了"调了哪个方法"，没验"**传进去的是什么**"

破验 K15（`runs` 的 `scheduleId` 空串不再折成 `null`）第一轮没被咬住：
原判据只验 `runsOf` 被调用，没验参数。于是 `scheduleId: scheduleId`
（不折 null）照样全绿，而空串会被当成一个真的计划 id 去筛。

**修法**：对 `scheduleId` / `scope` / `state` 三条都断言"空串 ⇒ `null`"，
并断言 `limit` 缺省 200、给值时按值传。
