## 1. ★★ 生成器的两个判据都被 `...` 展开骗过（一个假绿、一个假红）

第一个假象：核对报出一个**不存在的依赖**

```
✖ 有未登记的名字 …  experience  ← /api/experience/export
```

`'content-disposition': 'attachment; filename="legion-experience.json"'` ——
扫描器直接在**原始文本**上找"标识符 + `.`"，于是字符串里的 `experience.json`
被读成了一次成员访问。

> 一个"读进字符串内容"的扫描器，与一个"这个族真的引用了那个名字"的扫描器，
> 在报告里都是同一行"未登记的名字"——区别只在有没有人去看那个名字是什么。

前七族没暴露它，纯粹因为**没有哪一族的路由体里恰好有个 `词.词` 在字符串里**。

修掉之后立刻露出**第二个**（这回是假红）：`...appendExperienceRecord({` 这种
**展开一个独立函数**的写法，前导字符是 `.`，于是被同时当成"成员访问"：

- 在"未登记的名字"核对里 ⇒ **漏检**（本该报却没报，假绿）；
- 在"注入项都被用到"核对里 ⇒ 三个真依赖被报成"没被用到"（假红）。

> 一个"按前导字符判断这是不是独立引用"的扫描器，
> 与一个"真的分得清 `foo.bar` 和 `...foo`"的扫描器，
> 在只遇到前一种写法的时候是同一个东西。

**修法**：核对之前先把**字符串、注释、展开运算符**抹掉（定长替换成空格，
所以行列坐标不变、报错时指的行不会漂）。`db,` 这种"作为参数原样传下去"的用法
也一并被正确识别（旧判据要求 `dep.` 或 `dep(`，会把 `db` 误报成没用）。

## 2. ★★ 段首说明的"过期数字"核对器本身报了一个**假数字**

experience 那段写着「**四条**路由」而列了 5 条 —— 真过期数字，该报。但它同时报了：

```
⚠ 段首说明说「一条路由」，实测 **5** 条
```

对应的是这一句：

```
// ★ 处置单独一条路由（而不是往记录流里 POST 一条 `promote`）：
```

这是**叙述**（"处置单独用一条路由"），不是"本族有几条路由"的声明。
第一版匹配句中任意 `N条路由`，于是把叙述读成了声明。

> 一个"在句子里找数字"的核对器，与一个"核对这族有几条路由"的核对器，
> 在恰好只有前一种句子的那些族里是同一个东西。

**修法**：收紧成"这一行**以** `N条路由` 开头"（`// 四条路由，全部围绕…` 才是声明）。
收窄是刻意的：**宁可漏报，不要报假**。回归确认 `automation` 那段
「五条路由 / 实测 7 条」仍被正确报出（它是真正的规模声明）。

## 3. ★★★ 破验的"没咬住"有三种，处置完全不同

14 条变异，第一轮 **7 咬住 / 7 漏网**。逐条查完之后，那 7 条分成**三类**：

| 类 | 变异 | 判定 | 处置 |
| --- | --- | --- | --- |
| ① **真缺口** | K2 空 id / K3 百分号编码 / K10 空白 scope / K13 后缀判据 / K14 精确匹配 | 用例从没喂过那个输入 | **补判据**（5 条） |
| ② **可证等价** | K11 `sinceSeq ?? 0` / K12 `atMs : Date.now()` | 我改坏的那处与原文**在任何输入上同结果** | **不补判据**，只记录证明 |
| ③ 已覆盖 | K1/K4/K5/K6/K7/K8/K9 | 既有用例咬住了 | 不重复 |

> 一个"我改坏了但行为没变"的变异，与一个"我没测出来"的变异，
> 在破验报告里都是同一行"没咬住"。

### 3.1 补判据后 12/14 咬住，剩下的 2 条就是那两条**等价**

- **K11**：`optionalIntParam` 缺参返回 `null`；store 的签名是 `sinceSeq = 0`
  **默认参数** + SQL 里 `Number(sinceSeq) || 0`。`null` 不是 `undefined` ⇒
  默认参数不生效，但 `Number(null) || 0 === 0` ⇒ `0` 与 `null` 落到**同一个 SQL 参数**。
- **K12**：store 里是 `atMs: atMs ?? nowMs`，而 `nowMs = Date.now()` 是默认参数
  ⇒ 路由端给 `undefined` 与给 `Date.now()` 是同一个时刻来源。

★ **这两条不能被判据"修好"** —— 它们不是缺口，是等价。硬写一条断言
（比如"传给 store 的 `sinceSeq` 实参必须是 `0`"）只会把**实现细节**钉死，
而下一个合理的重构会因此无辜变红。所以改成：
① 用可执行的等式把等价性写下来；
② 顺手钉住 **store 端的前提**（`sinceSeq = 0` / `Number(sinceSeq) || 0` / `atMs ?? nowMs`
   还在不在）——**前提一变，这两条就会红**，那时才真的需要补路由端判据。

这是"把一次不可判定的观察，换成一个可判定的前提"：等价性本身依赖下游，
而下游的具体写法是可以用一条断言盯住的。

### 3.2 五条真缺口的具体内容

| 缺口 | 用例为什么没发现 |

## 8.1 ★ 记一笔我自己的复发缺陷：把带管符的片段**原样复述**进台账

写这片的台账记录时，护栏报了：

```
Error: 追加后管符数变了
```

原因是我在正文里**原样引用**了 store 的 SQL 片段 `Number(sinceSeq) || 0` ——
那个 `||` 是**两个表格列**，于是整行的列数从 4 变成 10。

> 一条记录如果原样复述了某个含管符的片段，它自己就破坏了那张表。

★ 这已经是**第三次**：切片 4、5 各一次（`Number(e?.statusCode) || 400`、
`=== null || length === 0`），这次是 `Number(sinceSeq) || 0`。
三次都是"我要引用一段真实的代码来证明我说的是真的"，而**那段代码正好含 `|`**。

每次的形式不同、机制完全一样，所以处置也不是"下次小心"，而是：
**台账正文里不复述含管符的代码片段，改成描述它**（"SQL 里把 `Number(sinceSeq)`
的结果再兜一次 0"）。护栏继续留着——它是唯一能把这件事变成**响亮失败**的东西，
而不是一个悄悄多出六列的表格。
