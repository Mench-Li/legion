## 1. ★★★ 既有用例里那条"看不见搬家"的测试

`connector-http.test.mjs` 的 ⑤ 原本是：

```js
const src = readFileSync(new URL('./server.mjs', import.meta.url), 'utf8')
for (const route of ["path === '/api/connectors'", …]) {
  assert.equal(src.includes(route), true, `源码里找不到字面量守卫：${route}`)
}
const f21 = src.slice(src.indexOf('F-21 连接器登记表'), src.indexOf('F-15 用量汇总'))
assert.equal(/\/\^\\?\/api\//.test(f21), false, 'F-21 里出现了正则路由守卫')
```

搬家之后 `server.mjs` 里只剩一行 `router.dispatch`，于是：

- 五条 `src.includes(...)` **如实变红**（它确实搬走了）—— 这一点是好的信号；
- 而 `slice(indexOf('F-21 连接器登记表'), indexOf('F-15 用量汇总'))` 这一句
  **一直是空的检查**。

★★★ **一个必须先核实、不能想当然的地方**：我第一反应是"搬家把两个端点错开了"。
量了一下才看清：那两个 `indexOf` 命中的**根本不是路由段的分段标题**，
而是**仓库层（store layer）的 JSDoc**：

```
L649:  * F-21 连接器登记表。
L651:  * 两张表，都是**只追加**：`connector_registrations` …
L940:  * F-15 用量汇总（§4.4）。
```

于是那个切片是**第 649–940 行**（约 9393 字符）—— 是 schema 与 doc，
里面**一个 `path === '…'` 字面量都没有**。

再往前核历史（`git show <ref>:team-hub/server.mjs`）
⇒ 切片长 **9393 字符、0 个路由字面量**，在 `db8e2cc`（切片 1）、
`77711ba`（切片 10）、`51082a8`（切片 11）**全都一样**。

⇒ **这条正则断言从一开始就是空的**，与本次搬家无关：
它写着"F-21 里没有正则守卫"，扫的却是一段 **F-21 根本不在里面**的区域。
`/\/\^\\?\/api\//` 在一个无关区域上判否，于是"没有正则守卫"
以"检查了一个无关区域"的方式通过。

> 一条"扫错区域"的断言，与一条"扫了正确区域且结论为否"的断言，
> 在它通过的时候是同一个东西 —— 而它已经这样通过了很多片。

★ 这一条只因为**前五条如实变红**才被翻出来：红了以后我才有理由去读这一句，
才有机会发现它一直是空的。**一条诚实的红，顺手暴露了旁边一条不诚实的绿。**

**修法（把判据改硬，而不是改软）**：不再比对字符串，改成**问抽取器本人**：

```js
const { extractDeclaredRoutes, findOpaqueRouteGuards } =
  await import('../scripts/prt/baseline-snapshot.mjs')
const seen = extractDeclaredRoutes(mod)   // mod = routes/connectors.mjs
```

实测 `extractDeclaredRoutes(模块)` 恰好回那 5 条（`POST /api/connectors/` 计进去），
`findOpaqueRouteGuards(模块)` 回 `[]`。★ 这样一来，
测试标题说的那件事（"对**基线抽取器**可见"）第一次**真的被断言了** ——
原来那句 `src.includes("path === '/api/connectors'")` 只是它的一个**替身**。

另外加了一句**切片长度自检**（`f21.length > 1000`）：切片指错地方时，
那条正则断言会恒真，而"恒真"与"真的没有"在输出上一样。
★ 本次这个自检**不会**报警（9393 > 1000）—— 它挡不住"指到了一段很长但无关的区域"，
这一种只能靠**在正确的文件上取正确的锚**来防（现在是 `mod.slice(indexOf('F-21 连接器登记表'))`，
在模块里它后面**就是**那五条路由）。

**★ 改硬之后单独验过它真的会咬**（`.worktrees/_prt-handoff/verify-connector-test5.mjs`）——
三种注入各跑一次，并且**只看 ⑤ 这一条**红没红：

| 注入 | 整份套件 | ⑤ 是否咬住 |
| --- | --- | --- |
| 基线 | 绿 | 否（应当如此） |
| 把列表路由改成**正则守卫** | 红（16 条失败） | ✅ 咬住 |
| 把 `path` 换成**常量** | 红（36 条失败） | ✅ 咬住 |
| 删掉 export 路由 | 红（6 条失败） | ✅ 咬住 |

> "整份套件变红"与"这条测试咬住了"，在只看退出码的时候是同一个东西。

★ 三条注入下 ⑤ 都红，说明它现在**真的**在核对标题说的那件事，
而不是像原来那样对着一段无关区域判否。

## 2. ★★★ 破验 21/21 —— 第二次零漏网、零等价

第一轮 15 咬住 / **6** 漏网，六条**全是真缺口**，而且集中在**同一类**：

> 一个"收了参数并把它传下去"的路由，与一个"收了参数然后丢掉"的路由，
> 在没有用例问过那个参数的效果的时候，是同一个东西。

| 缺口 | 真行为差异 | 既有用例为什么没发现 |
| --- | --- | --- |
| **K3** 顶层 `body.version` | store 里是 `version ?? declaration?.version` ⇒ 顶层**覆盖**声明内 | 既有用例的 `version` **一律写在 `declaration` 里面**，顶层那个从没出现过 ⇒ 优先级从未被喂过 |
| **K4** 顶层 `body.frozenAtMs` | 路由是 `Number.isInteger(x) ? x : Date.now()` | 从来没传过 `frozenAtMs` |
| **K5** 列表 `version` 过滤 **`records`** | 带 `version` 查询时 `records` 必须只剩那一版 | 既有用例带 `version` 时**只看 `registration.declaration`**，`records` 只验过形状与条数 |
| **K9** 回显的 `scope` | 读的是哪一格的唯一凭据 | 断言过 `records`/`registration`/`counts`，**唯独没断言 `scope`** |
| **K11** incidents 的 `sinceSeq` | 事件面也支持增量读 | 增量读**只验过登记那一侧**（`/api/connectors`），事件那一侧没验 |
| **K13** `decodeURIComponent` | 编码过的 id 也要能对上 | 既有用例的 id **全是纯字母数字** |

★ **K5 最重**：模块里那段长注释讲的正是这件事 ——
> "不传 version = 最新"这条默认**静默地覆盖了每一次带版本的查询 …… 
> **答案来自另一版，而响应里没有任何地方提示这件事**。

那段注释警告的是**登记面**，而 `records` 那一侧的同一处过滤从没被问过。

★ 六条与切片 11 的三条**完全同族**（K6 空串 / K8 严格布尔 / K2 `table`），
也与切片 8/9/10 同族：**用例只喂过"刚刚好正确"的输入**
（参数恰好给了值、id 恰好是纯字母数字、字段恰好没人看）。

★ 六条补判据后 **21/21**，且**全部走真 HTTP**（不用替身）—— 它们验的都是
"这个参数到底有没有影响响应"，这一点在真 hub 上最直接。
每条契约用一个**全新的 `connectorId`**，因此与前面用例的库状态无关。

## 3. ★★★ 我自己的三个错，都是"前提没有被核对"

这一片我写坏了三处，三处**形状相同**：

1. **K13 的用例没用到它的前提。** 我算出 `encoded` 却拿 `id` 去发请求 ⇒
   这条用例在"代码不解码"的实现上**也是绿的**。
   > 一条自己没用到那个前提的用例，与一条前提根本不成立的用例，
   > 在它通过的时候是同一个东西。

2. **词表照"我以为的"写。** 我把事件种类写成 `circuit_open` / `circuit_half_open`，
   真实是 `circuit-opened` / `circuit-closed`，熔断状态是 `half-open`（连字符）。
   这是**第四次**栽在"照着脑子里的实现写断言"（切片 9 两次、切片 11 一次）。

3. **`scope` 读错了位置。** 写面的 `scope` 从 **body** 读，我把它挂在 POST 的 URL 上
   ⇒ 那份声明落进了 `default`。而下面那条"teamA 里没有"的断言**照样是绿的**
   （因为 `teamA` 本来就一直是空的）—— **一条绿得毫无意义的断言**。

★ 第 3 条最值得记：它不是我写错了期望值，而是**我压根没走到我以为是的那条路径**，
而那条错误的路径**恰好也让断言通过**。
