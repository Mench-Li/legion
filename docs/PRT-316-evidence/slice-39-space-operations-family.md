# PRT-316 切片 39：第三十七族 = 工作空间的运维面（3 条）

> 这一片第一次撞上「**一个族不可能是一个区间**」——
> `/api/spaces` 下那 5 条**从来没挨在一起过**。
> 也是第一族要碰 **node 内建**（前 36 族一个都没用过）。

## 1. 本族长什么样

「工作空间的运维面：删除预检（影响面，只读）/ 开通 / 删除（含附件目录清理）」——

## 2. ★★★ 新形状：`/api/spaces` 的 5 条**从来没挨在一起过**

`group-remaining` 报「5 条 / 分段 3」，把每一对相邻路由的**间隔**数出来才看清：


`wire-family` 删的是**一段连续区间** —— 所以「一个族 = 一个前缀」在这里**不成立**。
本族取其中**唯一连续的 3 条**（L5754–L5923），这条区间里**一条外来路由都没有**；
上下界分别是 `POST /api/pipeline` 与 `POST /api/goal`（都是别人的活路由，切片 38 也是这种上界）。

> 一个「`/api/spaces` 是一族」的印象，
> 与一个「这 5 条**从来没挨在一起过**、中间隔着 5 条别人的路由」的事实，
> 在我把每一对相邻路由的**间隔**数出来之前是同一个东西。

★ 剩下两条（`POST /api/spaces` 在 L5688、`POST /api/spaces/` 在 L6028）**仍在 `server.mjs` 里**，
留给后面的片。本片把它们写成**判据**（§6 ⑤）。

## 5. ★★★ `POST /api/spaces/delete` 是**三重闸**的破坏性操作

实测（本片**不修**，只钉）：

| 闸 | 不满足时 |
|---|---|
| ① `by`（`handleWrite` 的操作者身份） | 400「缺少操作者身份 by」 |
| ② `confirm` **必须点名那个 id**：`delete-space:<id>` | 400「缺少确认：confirm 须为 delete-space:…」 |
| ③ **只允许 `general`** 执行（或 `body.forceGeneral === true`） | 400「删除空间仅允许 general 执行」 |
| ④ 受保护空间 `software` / `default` **一律拒绝** | 400「受保护空间 X 不可删除」 |

★★ 而且闸门拦住之后**什么都不许发生** —— 本片把这一条写成了判据
（`③`/`③b`：被拒之后那个空间必须**还在**）。

★ 破验证实这四条**都有人看着**（M4 / M5 / M6 全咬住），所以它们**不是**缺口 ——
记在这里是因为它们是这一族真正的重量所在。

## 6. ★★★ `provision` 是**诊断**，不是查询

| 输入 | 结果 |
|---|---|
| 缺 / 非法 id | 400「空间 id 非法（字母/数字/下划线/连字符，≤64 字符）」 |
| **不存在的**合法 id | ★★★ **200** + `ok:false` + `checks[]` |

不存在的空间**不是 404**，因为它的工作就是"告诉你这个空间缺什么"，
而"这个空间根本没注册"**正是它要报告的第一条**（`space-missing`，warn）。
`ok` 由 `!checks.some(c => c.level === 'error')` 推出。

```
[warn]  space-missing       空间 probe-sp 未注册（spaces 表无记录）…
[warn]  roster-empty        该空间编队为空…
[error] pipeline-missing    该空间未配置流水线…
[warn]  runtime-disabled    该空间执行配置未开启…
[error] daemon-offline      该空间没有守护实例…
```

★★ `level` 的取值是 **`ok` / `warn` / `error`** 三种（**有 `ok`**）—— 我第一版判据只写了
`info/warn/error`，**当场红了**。

★★ 另有一条**实测的不一致**（本片不修）：`impact` 用 `/^[a-z0-9][a-z0-9-]{0,63}$/`（**不认**下划线），
`provision` 用 `SCOPE_KEY_RE`（**认**下划线）—— 同一个前缀下**两套 id 校验**。判据把这个事实钉住了。

## 8. ★★ 我自己的三处错（都在判据里，不在源码里）

1. `level` 只写了 `info/warn/error`，实际有 **`ok`**。
2. `delete` 的回复形状是 `{ok, task:{id, removed}}`（`handleWrite` 的统一信封），
   我按 `{id, removed}` 断言 ⇒ 实际 `undefined`。
3. ★★★ **桩比真东西宽松**：`handleWrite` 的桩无条件调回调，
   而真的 `handleWrite` 在缺 `confirm` 时**直接拒**（不调回调）⇒ `delete` 的 `run` 在无 body 时抛错。
   已把桩改成**照实**拒。

★ 第 3 条最值得记：**一个"桩只要把回调调起来就行"的印象，
与一个"桩比被测对象宽松，于是测出来的是桩的行为"的事实，是同一个东西。**

★★ 另有一处**流程**问题：M11 的锚点带反引号/模板串，我自己写的转义没命中 ⇒
