# BUG-011｜流水线把「每个 tester 环都产出可部署物」当公理 —— 判定型/分析型任务推 done 会派出一整个 devops 环去部署一个不存在的东西

> 状态：**只记账，未修**（将军 2026-10-05 裁决：本条先记账，T-179 用 `canceled` 一次性收尾）。
> 发现于复核 BUG-010 的停摆读数时 —— 那条读数对 T-179 报了一次**空洞命中**，
> 顺着"为什么它会命中"往下走，才走到这里。

## 0. 先把"每个环交给下一环的是什么东西"说准

`roles.json` 的 software 流水线（实测，含 `docs` 与 `artifact` 声明）：

| 环 | label | `next` | `artifact`（机器闸门要的文件） | `docs`（写进 prompt 的产物） |
| --- | --- | --- | --- | --- |
| requirement | 需求澄清 | researcher | `docs/REQUIREMENTS.md` | — |
| researcher | 方案搜索 | breaker | `docs/RESEARCH.md` | — |
| breaker | 任务拆解 | test-designer | （无） | — |
| test-designer | 测试用例设计 | coder | （无） | — |
| coder | 编码实现 | reviewer | （无） | — |
| reviewer | 代码审查 | tester | （无） | — |
| tester | 测试执行 | devops | （无） | `docs/TEST_REPORT.md` |
| devops | 部署与 CI/CD | **null** | （无） | `docs/DEPLOY.md` |

**只有前两环有 `artifact`。** 其余六环（含 tester）都**没有**"这一步必须产出某个文件"的机器判据 ——
也就是说，从机器的角度看，**一个 tester 环可以不产出任何文件变更就合法地走到 done**（它只要把结论写成评论）。

这不是疏漏，而是刻意的：tester 的价值是**跑测试并说结论**，测试全绿时它**本来就什么都不该改**。
问题出在下一步。

## 1. 缺陷

`plugins/src/handoff.ts` 的 `advancePipeline`（第 181–287 行）是「阶段 → 阶段」的唯一出口。
它的全部前置闸门都是**关于身份与状态**的，没有一条是**关于交接内容的**：

| 行 | 闸门 | 问的是 |
| --- | --- | --- |
| 182 | `pipeline() === null && reviewWorkflow === undefined` | 这是流水线任务吗 |
| 185 | `agentSelectionSnapshot?.source === 'goal-agent-workflow'` | DAG 是否已预建 |
| 190 | `doneTask.slice != null` | 切片束的下一环是否另有编排 |
| 191 | `doneTask.fixOf != null` | 是不是回炉任务 |
| 192 | `role === SLICE_ANALYSIS_TAIL && isSliceGoalTask(...)` | 是不是分析前缀尾 |
| 215–226 | 目标 `done`/`canceled` | 目标是否已收口 |
| 240–242 | `stage.next` / `nextStage` 存在 | 角色链上还有下一环吗 |
| 249–254 | `hasSuccessor` | 后继是否已建过（幂等） |

于是：**只要角色链上还有下一环，任务一 done，后继就被建出来**，与"前序这一环到底交付了什么"无关。
tester→devops 是链上唯一一个**下游的开场白就是"去部署/构建"**的交接，所以它把这个缺陷放大成了可见的形状：

> 一个测试全绿、什么都没改的 tester 环 → done → 建出一个
> **【部署与 CI/CD】**任务，description 写着「[前序阶段] 测试执行（tester）已完成：…」，
> 而 devops 的 prompt 是「编写 CI/CD 流水线、构建与部署配置（Dockerfile、workflow、脚本），
> 输出部署与发布说明到 `docs/DEPLOY.md`」。

**它的上下文里没有任何东西可部署，而它的职责说明要求它产出部署配置。**
代价不只是"浪费一轮 agent"——一个被要求"写出部署物"的 agent，面对一个没有交付物的前序阶段，
最坏的结果是**为了满足任务而制造出部署物**（为不存在的东西写 Dockerfile / workflow）。
（这一句是**推理，不是实测**：本条只记账、没有真的把 T-179 推 done 去跑那一环。）

### 1.1 一个同形但更常见、更无害的入口

tester 之外也成立，只是下游的措辞不像 devops 那么刺眼：

- **coder 什么都没改**（判定"现有实现已满足"，只留评论）→ done → 建出 reviewer 环，
  而它**没有 diff 可审**；
- 这一类的共同形状是：**流水线的每个环都默认前序留下了东西，而"没留东西"是一个合法结果。**

### 1.2 与 BUG-009-a 的分工（必须说清楚，否则会低估本条）

T-179 的具体成因（声明域 `["scratch/"]`、`scratch/` 被 gitignore ⇒ 产出交付不了 ⇒ 分支 0 提交）
**已经被 BUG-009-a 在任务创建面拦住了** —— 直接问它一下就能看到，它的文案里就写着 T-179：

```
$ judgeFileDomain(['scratch/'], ignoredFileDomainEntries(...))
{ ok: false, code: 'DOMAIN_ALL_IGNORED',
  message: '声明的文件域全部被 .gitignore 忽略（scratch/）—— 这样的切片**交付不了**：
            它的产出不会进版本库，分支永远 0 提交（实测 T-179：干完 5 小时、报告烂在 scratch/ 里）。…' }
```

所以**本条与 BUG-009-a 不是同一个缺陷的两个名字**，而是分工：

| | 问的问题 | 覆盖的成因 |
| --- | --- | --- |
| BUG-009-a | 这个域**能不能**交付？ | 域全是 gitignored ⇒ **永远** 0 提交（配置错） |
| **BUG-011（本条）** | 这个环**实际**交付了吗？ | 域合法，但这一环**本来就没什么要交**（设计使然） |

§1.1 那两条（tester 全绿 / coder 判定无需改动）**不在 BUG-009-a 的射程内** —— 它们的域完全合法。
这就是为什么本条不能靠"已经拦住了 T-179 的成因"了结。

### 1.3 与 BUG-010 的关系：同一件事实的两面

「0 提交的切片」在流水线里是一类**特殊对象**，而流水线一直没有它的名字：

- **BUG-010 §2.3** 是它作用在**读数面**的后果：停摆判据只看 `main...w/<id>` 是否为空，
  于是零改动分支天然是 HEAD 的祖先 ⇒ 每轮报一次假停摆。修法是加一道 `own.length === 0` 前置闸门。
- **本条**是它作用在**流转面**的后果：`advancePipeline` 不问交接内容 ⇒ 零改动的环照建下游。

两条合起来说明：**"这一环交付了 0 个文件"是一个应当被显式命名的事实** ——
它在读数面需要一个"不必报警"的出口，在流转面需要一个"不必建下游"的出口。
两条都只是各自绕开，**没有一个地方真的把它命名出来**。

## 2. 修法（未实施，三个选项）

### 选项 A（推荐）—— 在**任务创建面**加"这一环产不产得出交接物"的前置判据

与 BUG-009-a 同形、同一个闸门位置（`createTask` / `insertGoalTask`）：

```
切片任务的 fileDomain 必须覆盖本阶段声明的交接物路径
（如 tester 的 docs/TEST_REPORT.md）—— 否则这一环**不可能**产出可交付物，
不该建成"切片 <role>"，而应建成一个**结论型任务**（没有下游环）。
```

为什么必须在**创建面**做：到了 `done` 那一刻，切片分支已经被 `autoPromote` 删掉
（`git branch -D w/<id>`），**判据所需的信息那时已经不存在了**。

### 选项 B（窄修，只治部署环）

`advancePipeline` 在创建 `devops` 后继前，若前序是 tester 且**它没有自己的提交**，
则跳过并记一条 activity。困难：这个读数必须在 `done` **之前**存下来
（`sourceCommit` / 冻结提交是现成的挂钩点，但它记的是"基线"不是"改了几个文件"）。

### 选项 C（治本，最大）—— 给每个 stage 声明「交接物类型」

`code` / `docs` / `conclusion` 三态。`conclusion` 型（判定、调研、验收结论）的环
**done 即收口**，不建下游。这是唯一一个把 §1.3 那个"0 交付"事实**命名出来**的选项，
但它改的是流水线语义（8 环的 `next` 链要从"角色链"变成"角色链 + 交接物类型"），
应当单独立项，不要顺手做。

**为什么不建议顺手做 C**：`roles.json` 的 `next` 链被 `handoff.advancePipeline`、
切片编排、目标预建链（`blockedBy`）三处同时读。改它的含义会影响三处，
而这三处的失败方向不同（漏建 = 链断、多建 = 凭空长任务，见 handoff.ts 里 T-156 那整段注释）。

| 将来要钉的 | 形态 |

| ③ | 前序有交付 ⇒ 行为与今天完全一致（防止"顺手收紧"把真流转也拦掉） |
| ④ | 反向验证：把判据拆掉的变异必须让 ② 变红 |

## 4. 边界与一次性处置

- **T-179 的处置（一次性，不靠本条的修法）**：它的判定报告已由将军搬运到被跟踪路径
  （`docs/bugs/T-179-12-red-suites-judgment.md`，源文在 `scratch/t179/JUDGMENT.md`，
  `scratch/` 被 gitignore ⇒ 分支永远 0 提交），故任务本身**没有可部署物**。
  将军裁定：T-179 标 **`canceled`**（而不是 `done`）—— 因为 `done` 会按上面的机制
  派出一个部署环去部署不存在的东西，而 `canceled` **不会被派下游**：
  `advancePipeline` 的唯一调用点是"4. 流水线 done 补流转"那道扫单，
  而它只取 `status === 'done'` 的任务，`canceled` 根本进不了那一步。
- **本条不改 `roles.json`**（理由见选项 C 的"为什么不建议顺手做"）。
- **本条不碰 BUG-010 的读数**：那道的 `own.length === 0` 闸门是"不必报警"，
  与本条的"不必建下游"是两件事，各自在自己的面上成立。
