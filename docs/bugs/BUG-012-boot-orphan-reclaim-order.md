# BUG-012｜守护重启时「按时间猜」的回收跑在「按重启确定」的回收**前面** —— 越老的孤儿越会被冻结，整个空间停摆等人工解锁

> 发现于 2026-10-06，起点是将军的「已重启」——我在复验 BUG-010 的读数时，
> 顺手打开了守护自己的日志（`~/.dsh/super-injector/dsh-scrum-worker.log`），
> 看到它在**每 30 秒**重复同一句失败，已经重复了 7 小时。
> 本条**未修**：先记账 + 给出修法；现场由 §5 的一条人工恢复解开。

## 1. 缺陷：两条回收路径的**先后顺序**把权威的那条饿死了

守护每轮跑两条回收（`plugins/src/index.ts:3653-3654`，注释自称 `// 0.` 与 `// 0.5`）：

```ts
await reclamation.reclaimStaleLeases(byId)      // 0.   按「多久没进展」猜
await reclamation.reclaimBootOrphans(tasks, byId)  // 0.5 按「本进程刚重启」确定
```

两条的**判据强度完全不同**，而它们的处理方式也**故意不同**（`team-hub/server.mjs` 里逐字写着理由）：

| 路径 | 判据 | 它知道什么 | 预约处理 |
| --- | --- | --- | --- |
| 0. `/api/release-stale`（**无** `ids`，按 `olderThan`） | `claimedAt`/`expiresAt` 超龄 | 只知道"很久没进展" —— **慢 worker 可能还在写** | **冻结** `reconciling`（`cancelled: true`，`server.mjs:6191-6205`） |
| 0.5 `/api/release-stale`（**带** `ids`） | 本进程刚重启 + 任务 `in_progress` 且 soldier 是自己 | 执行者**已随上一轮进程消失** | **真释放**（`cancelled: false`，`server.mjs:6153-6169`） |

`server.mjs` 那段注释把"冻结"的代价写得很清楚，而且已经踩过：

> 冻结会与这句评论**自相矛盾**：任务确实回到 todo，但下一次 claim 会撞 `RECONCILING`…而永久卡死
> ——"自动重新认领续做"成了一句空话。**实测代价：同一形态在本仓把三个任务卡死过（T-173 线、T-174、T-177）**，
> 每一次都要人工调 `/api/tasks/:id/reservation/confirm-stopped` 才能解开。

也就是说：**"冻结"是被有意留下的正确选择**（宁要人工解锁，不要两个写者 —— T-170 的核心不变量），
**"带 ids 的真释放"是后来补的修复**。缺的不是这两条里任何一条，缺的是**它们的次序**：

```
0.  按时间猜  →  T-189 已 in_progress 8 小时 > staleMinutes 60  ⇒ 命中 ⇒ 冻结 + 任务回 todo
0.5 按重启确定 →  过滤条件是 status === 'in_progress'  ⇒ 而 T-189 刚被 0. 改成了 todo ⇒ 看不到它 ⇒ 什么都不做
```

`0.5` 的过滤条件与 `0.` 的副作用**正好错开**，而这个错开是必然的，因为两者读的是**同一批对象**：

```ts
// index.ts:3608 —— Map 的值就是 tasks 数组里的那些对象本身
const byId = new Map(tasks.map(t => [t.id, t]))

// reclamation.ts:150 —— 0. 在 byId 上把状态改掉，tasks 数组里那个对象跟着变
const t = byId.get(id)
if (t) { t.status = 'todo'; t.soldier = null; t.claimedAt = null }
```

**所以缺陷的形状是**：

> **越老的孤儿，越一定拿到"错误"的那条处理。**
> 因为"老"正是 `0.` 的命中条件，而 `0.` 一旦命中就顺手把 `0.5.` 的入口关掉了。
> 而这两件事在语义上毫无关系 —— 任务活了 8 小时，与"宿主刚重启所以旧 worker 必然已死"无关；
> 后者才是**确定的知识**，前者只是**猜测**，而猜测先跑。

顺带一提这条缺陷的自我印证：**T-190 的任务标题就是它自己** ——
「【代码审查】worker 超时后写入预约不释放：守护两套机制互锁，任务每 40 分钟卡死（需人工解锁）」。
那一条审查任务，正被它所审查的互锁堵在门外。

## 2. 为什么此前没被发现

1. **它在日志里长得像正常重试**。`认领失败（可能已被他人认领）` 这句文案本身就在说"别担心，下轮会好"，
   而它每 30 秒出现一次、连出 850 次。**一条撒谎的文案比一条缺失的读数更坏** —— 后者会让人去找，前者让人安心。
2. **它只在"重启 + 任务比 `staleMinutes` 还老"时出现**。而 worker 超时预算是 45 分钟
   （`workerTimeoutMs: 2700000`）、`staleMinutes: 60`，所以"一个任务活过 60 分钟"在长任务上很常见；
   偏偏长任务正是宿主重启时最可能被孤儿化的那一类。
3. **它把"需要人工"伪装成了"等下一轮"**。守护没有任何读数在说"这个空间现在全停摆了"
   —— 与 BUG-010 同形：**静默的停摆**。

## 3. 修法（**已按选项 A 实施**，代码见 §7）

### 选项 A（推荐）—— 交换次序：权威的先跑

```ts
await reclamation.reclaimBootOrphans(tasks, byId)   // 0.5 先：重启是**证明**
await reclamation.reclaimStaleLeases(byId)          // 0.  后：超龄是**猜测**
```

- **安全性不变**：`0.5` 只处理「`in_progress` + `soldier` 是自己 + `!hold` + `!mediating`」，即**本守护自己认领的**任务；
  交换后 `0.` 仍会在**同一轮**里处理剩下的 `in_progress`（人类手动在办的、`hold` 的、`mediating` 的），
  它们拿到的仍是"冻结"——那正是 `0.` 存在的理由。
- **不会放过任何该冻结的**：`0.5` 的集合是 `0.` 集合的子集；先跑子集只是让"已被证明死掉的"用更准确的语义处理。
- **代价**：一次调用顺序的改动，加一段注释说明"为什么证明必须在猜测之前"。
- **判据**：新增一条**回归**用例，钉住"重启后，一个比 `staleMinutes` 还老的孤儿被**真释放**（`released`，不是 `reconciling`）"。

#### 为什么现有判据拦不住它：**两半各自是绿的，组合是坏的**

`team-hub/claim-reservation.e2e.test.mjs` 第 ⑯ 组把两件事都钉住了，而且钉得很仔细：

| 用例 | 它造的现场 | 它调用 | 断言 |
| --- | --- | --- | --- |
| ⑯①（L138-150） | `T-boot-orphan`，**刚**认领（`claimedAt` = 现在） | `release-stale` **带** `ids` | `released`（不是 `reconciling`），且能立即重认领 |
| ⑯②（L153-166） | `T-stale-frozen`，`claimedAt` 被**推老 1 小时** | `release-stale` **不带** `ids` | `reconciling`（不许放开），要 `confirm-stopped` 才能重认领 |

两半都对，而且都是有意为之。但**没有任何一条用例把"老"与"重启孤儿"放在同一个任务上，
再按生产的顺序把两条路径都跑一遍** —— 而生产恰恰只在这种组合下出错：

```
⑯① 的孤儿是**刚认领**的  ⇒ 就算 0. 先跑，超龄判据不命中 ⇒ 只有 0.5 能看见它 ⇒ 绿
⑯② 的任务**不是**孤儿   ⇒ 就算 0.5 先跑，claimedByUs/ids 也不含它 ⇒ 只有 0. 能看见它 ⇒ 绿
生产：孤儿的 `claimedAt` 是 8 小时前 ⇒ 两条**都能**看见它，且 0. 先跑 ⇒ 红
```

**"两条路径各自正确"与"两条路径按这个次序合起来正确"是两件事**，
而用例的现场把每条路径的候选集切得只让自己看得见 —— 于是次序这件事在测试里**不可表达**。
（与我此前记过的"干净夹具掩盖生产形状"同形：夹具越干净，越测不出组合。）

**所以新用例必须做的事只有一件**：让任务**同时**是"老"和"孤儿"，然后按 `index.ts` 的真实次序跑完两条。

### 选项 B —— 让 `0.` 在重启后的第一轮跳过"0.5 将要处理的那批"

逻辑等价于 A，但把"次序敏感"变成了显式条件，可读性略好、改动面略大（要跨模块传一个"本轮是首轮且这批归 0.5"的集合）。

### 选项 C（治本，最大）—— 让"证据强度"成为回收接口的一等参数

把 `/api/release-stale` 的 `ids` 从"可选的白名单"提升为"证据声明"：
调用方必须说明它凭什么知道执行者已停止（`restart` / `operator` / `timeout-confirmed`），
而**只有** `restart`/`operator`/`timeout-confirmed` 允许 `cancelled: false`；`age`/`ttl` 一律冻结。
这样可以彻底消灭"同一批量按不同证据混合处理"的可能，但改动面覆盖路由、store、守护三处，应当单独立项。

**不建议顺手做 C**：`/api/release-stale` 同时被守护、调解员、以及若干端到端测试调用，
把它的参数语义变严会波及一圈调用方；而 A 能用一行顺序改动拿下同一件事。

## 5. 现场处置（与 §3 的修法无关的一次性动作）

T-189 的预约是 `reconciling` + 任务 `todo` ⇒ 正好满足人工恢复端点的全部前置
（`team-hub/routes/write-intent.mjs:172-186` 要求 `by === 'general'`、`confirm === 'stopped:<id>`、
任务处于 `todo/blocked/canceled`、且存在一条 `reconciling` 预约）：

```bash
curl -X POST http://127.0.0.1:8787/api/tasks/T-189/reservation/confirm-stopped \
  -H 'content-type: application/json' \
  -d '{"by":"general","scope":"software","confirm":"stopped:T-189"}'
```

**证据（"执行者确实已停止"这件事，凭什么成立）**：

- 预约冻结于 `2026-10-05T16:04:14.016Z`，即**上一次宿主启动的那一秒**（该实例的守护日志首行在 `16:04:0x`）；
- 此后宿主**又重启过一次**（`23:07Z`，当前 PID 14620 起于本地 `07:07:01`）；
- 全机进程列表里**没有任何**来自那个时代的进程：唯一的两个 `node.exe` 是 `07:09:59` 起的（本次重启之后），
  其余全是系统进程或本次启动的 `DeepSeek Harness`；
- worker 由守护以**子进程**方式 spawn（`provider: spawn`），父进程两次重启之间没有"守护已死而 worker 还活着"的路径可走。

**这一步是人的affirmation，不是机器的推论** —— 这正是该端点要求 `by: "general"` 的原因：
放开的下一秒就可能出现两个写者（T-170 的核心不变量）。故本条现场处置**待将军确认后执行**。

`confirm-stopped` 只解开 T-189 一条；T-190 的 `FILE_CONTENTION` 会随之自行消失（它没有自己的预约，全库只有 T-189 这一条活跃）。

## 6. 边界

- **本条不改 `staleMinutes` / `workerTimeoutMs`**：那两条的关系是 BUG-009-b 的领域，
  而本条与"阈值设成多少"无关 —— 任何阈值下，只要 `0.` 先跑，老的孤儿就会被冻结。
- **本条不碰 BUG-010 的停摆读数**：那条说的是"停在 `in_review` 却没往下走"，
  而本条里任务根本不进 `in_review`（它卡在 `todo` + 冻结预约上）——**两处的静默是两种静默**，
  合起来说明这个系统缺的不是某一条读数，而是一条**"这个空间现在有没有在动"**的读数。
- **`reason` 字段的取值 `task-cancelled` 有误导性**：它来自 `finishTaskReservationInTx(id, { cancelled: true })`
  的调用点，而本次的调用方是**超龄回收**，不是"任务被取消"。诊断时必须靠 `state` + 上下文，不能信这个字符串。
  （本条记下来，不顺手改：改 `reason` 的取值会影响审计与既有测试。）

### 7.3 写这条判据时踩的三次"锚不唯一"（**同一形状，值得单独记**）

三条都是同一个病：**断言的目标在文件里不唯一** —— 于是变异发生了，用例照样绿。

| # | 症状 | 根因 | 修法 |

| 1 | M3（`byId` 改深拷贝）下 ③ 仍绿 | 断言写的是 `/const byId = new Map\(tasks\.map\(/` —— 只锚到**前缀**，而 `{ ...t }` 的深拷贝同样满足它 | 锚到**闭括号**：`…\[t\.id, t\]\)\)` |
| 2 | 收紧后 M3 **仍然**绿 | 紧邻的注释里**原样引用**了那一行代码（注释在解释"不能反过来"，自然要写出它）⇒ 断言被**注释**满足 | 新增 `codeOnly()`：要钉"代码里必须这么做"的断言，一律在**去注释**的源码上做 |
| 3 | M5（删掉小节标题）下 ⑤ 仍绿 | 断言只匹配那句**话**，而它在文件里出现三次：一处是小节标题，另两处只是**引用它**（"理由见文件头「…」"） | 锚到**标题本身**：`/^\/\/ ## ★ 次序是语义的一部分/m` |

这与 BUG-010 用例 ① 的「切片范围比断言对象大」、BUG-009-a 的「探测器问错了问题」是**同一族**：
缺陷不在被测代码里，在**判据自己**身上；而它的表现形式永远是"绿的"。
**唯一可靠的发现方式是变异测试** —— 这三条里有两条是变异跑出来才看见的，
