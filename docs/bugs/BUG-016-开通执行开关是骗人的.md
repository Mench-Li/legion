# BUG-016｜「开通执行」开关是骗人的：它写在守护从不读的那张表上

> 状态：**已修**（开关那一条；同族的「派 AI 执行」仍未接线，见 §7）
> 发现：2026-10-10，业主实测「在软件流水线工作区发布了新目标，没有自动认领开转」
> 影响面：`team-hub/routes/exec.mjs`（开关读写）、`workbench`（发布目标后的提示）

## 0. 现象与一句话根因

将军在「软件流水线」空间发布了一个目标。界面回「🎯 已发布目标」，8 条链任务
（T-195…T-202）也真的建出来了 —— 然后**全部停在 `todo`、`soldier=null`，十几个小时没动**，
界面上没有任何一句话解释为什么。

查到最后是**三个原因叠加**，而其中两个的开关都是"看起来已经在界面上打开了"的：

| # | 原因 | 证据（本机实测） | 性质 |
| --- | --- | --- | --- |
| 1 | 守护服务的**不是这个空间** | 唯一活着的心跳 `scrum/daemon.json` 写着 `scope: "default"`；`daemon-software.json` 最后写入是 4 天前 | 部署面配置（`scope` / `scopes`） |
| 2 | 该空间**未开通执行** | `GET /api/pipeline?scope=software` → `runtime.enabled=false`，而守护的 `planSpaceRunners` 明确 `if (!s.enabled) continue` | 数据面开关（本可点） |
| 3 | **★ 界面上那个开关根本不接这条线** | `POST /api/exec` 写 `exec_state`；守护读 `space_runtime.enabled`。**两张表** | 本 BUG |

第 3 条的特别之处在于它**不是"少了一个功能"，而是"多了一个会说谎的控件"**：

```
将军点开「⚡ 持续执行编排」→ 界面显示「已开启」→ 守护压根不看这张表 → 任务一动不动
```

> 一个"写在没人读的表上"的开关，
> 与一个"根本没有这个开关"，在将军那边是同一个东西——
> 只不过前者会让他以为已经开好了。

## 1. 为什么它会存在这么久

`exec_state` 与 `space_runtime` 各自看起来都自洽：

- `exec_state` 是 PRT-316 切片 25 从旧 `server.mjs` 逐字搬过来的，有 21 条判据守着
  （读、写、严格 `=== true`、关得掉、`by` 必填、方法位……）——**全绿**。
- `space_runtime` 是 SP-P0 引入的，守护读它，开通预检报它，`planSpaceRunners` 按它跳过空间——**也对**。

两边都没错，错在**它们是两张表**。而那 21 条判据问的一直是"开关存下来了吗"，
从来不是"**守护会因此改变行为吗**"：

> 判据问错了问题，就会一直绿着，直到有人在真机上发一个目标。

`docs/SPACE-DAEMON-RUNBOOK.md` §5 第 3 行其实**早就登记了**这件事
（「只写 hub `exec_state`，守护侧从不读 → 建议接线到守护或下线该控件」），
但它躺在"已知限制"表里，而界面上没有任何一处把这个限制告诉将军。

## 2. 修了什么

### 后端：开关读写 `space_runtime`（守护读的那张表）

`team-hub/routes/exec.mjs`：

- `GET /api/exec?scope=` → 读 `space_runtime`；回执带 `source: 'space_runtime'`
  （**回执自己说清读的是哪张表**，好让下一个读代码的人不必再追一遍）。
  另附 `maxWorkers` / `isolate`，界面因此能说清"这个空间会以什么形态跑"。
- `POST /api/exec` → upsert `space_runtime.enabled`；**只改这一列**，
  `maxWorkers` / `isolate` / `review_workflow` 原样保留
  —— 拨一下开关就把并发/隔离重置掉，是那种"看起来只是开了一下"却把跑法换掉的改动。
- `exec_state` **不再写、不再读**；表保留（历史行 + 空间删除的级联照旧），
  它记的从来就不是守护读过的东西。

### 前端：发布目标之后立刻说清"这个空间现在不会自动开工"

`workbench/src/App.tsx` 的发布流程在成功之后读一次服务端的**开通预检**
（`GET /api/spaces/provision`，那是权威口径），有 `error` 级阻塞项时**不说**「已发布目标」，
改说：

> ⚠ 目标已发布，但**这个空间现在不会自动开工**：〈阻塞项原话〉 → 修复：〈预检给的命令〉
> （链任务已建好，开通执行 / 守护上线后会自动认领，不必重发）

三条纪律：

1. 判定**不在这里另写一套** —— 两套判定迟早给出不同答案，而将军只能看到其中一个；
2. 预检拿不到时**当没有阻塞项**（目标确实已经发布成功，两件事分开说，不吓唬人）；
3. 说清"不必重发" —— 否则将军会把同一目标再发一遍，链任务翻倍。

## 3. 这次修正**不是**什么

- **不是**把 `exec_state` 的表删了（历史行与级联还在）。
- **不是**给旧 `exec_state` 里的值做迁移回填：那张表里的 `enabled=1` 从来没让任何任务跑起来，
  把它当"将军的意图"回填成真的执行，会**静默打开**几个他以为早已关掉的空间。
  现在的读数是真话，哪怕它与界面上曾经显示的相反。
- **不是**修「派 AI 执行」（见 §7）。

## 4. 判据（`team-hub/exec-routes.test.mjs`）

原来的 21 条是钉**旧形状**的，本次把它们改成钉新形状，并补了 4 条**问到点上**的：

| 用例 | 它问的问题 |
| --- | --- |
| ㉒ | 开关写的是 `space_runtime` 吗？`exec_state` 里**还有没有**新行？ |
| ㉓ | 拨开关**会不会**顺手重置 `maxWorkers` / `isolate` / `review_workflow`？ |
| ㉔ | 读回来的形态与写进去的是**同一行**吗（读写同源）？ |
| ㉕ | 审计里点名写进了哪张表吗（下一个人不必再追一遍）？ |

前端一组 5 条在 `workbench/scripts/goal-stall-warning.test.mjs`：判定来自预检 /
有 `error` 时说的人话**不是**"已发布目标" / 说清不必重发 / 预检拿不到时不吓唬人 /
开关读数就是守护读数。两条都已登记进 `scripts/ci/run-ci.mjs`。

**反向验证 7/7 全部按预期变红**，其中三条是"变异本身不成立"的教训，值得记下来：

- 第一次为了验 ㉓，把 `INSERT` 的**值**改成默认值 —— 没红。原因是 `ON CONFLICT` 只更新
  `enabled`，那三列对既有行根本没被写。**变异不改变行为 ⇒ 判据不可能红**，
  这时"没红"说明的是变异写错了，不是判据不行。
- 第二次只改 `ON CONFLICT` 子句、值仍带着旧值 —— 还是没红（`excluded.maxWorkers` 取的就是旧值）。
- 第三次把**两处同时**改成默认值（这才是"真的会把跑法换掉"的写法）⇒ ㉓ 立刻红。
- 前端那条一开始用 `lastIndexOf` 比较位置 ⇒ 抓不住"提前多弹一条成功提示"；
  改成**首次出现的位置 + 出现次数必须为 1** 才咬得住。

## 5. 这次为什么会漏（判断句）

> 一个开关的判据若只问"我存下来了吗"，
> 那么它写在**任何**一张表上都是绿的 —— 包括守护永远不会读的那一张。

推而广之：任何"界面写的"与"消费者读的"分处两地的东西，都要有**一条**判据把两者**对上**
（本 BUG 的 ㉒ 就是这一条），否则它会一直绿到真机上出事。

## 6. 激活与验收（本机）

1. **部署面**（`~/.dsh/profiles/desktop/cordis.patch.yml` 的 `dsh-scrum-worker`）：
   `scope: 'default'` + 未设 `scopes` ⇒ 只服务一个空间。改为
   `scopes: 'auto'`（接管所有"已开通执行 + 已配流水线"的空间）后**需要重启宿主**
   （配置在插件激活时读一次）。
2. **数据面**：`space_runtime.enabled=true`（本机已为 `software` 打开）。
   这一项**不需要重启**：监督者每 `max(intervalMs, 15s)` = 30s 重新对齐，
   下一轮就会挂载该空间的子实例。
3. 验收读数：
   - `~/.dsh/super-injector/dsh-scrum-worker-software.log` 出现 `[+] 空间 software 已挂载`；
   - `GET /api/spaces/provision?id=software` 的 `daemon-offline` / `queue-stalled` 变 `daemon-online`；
   - 8 条链任务里第一环（`requirement`）从 `todo` 转 `in_progress`。

## 7. 未做（与本 BUG 相邻，但**不是**同一件事）

1. **「🤖 派 AI 执行」那条通道仍未接线**：`POST /api/exec/request` 写 `exec_requests`，
   `/api/exec/queue` 列自动队列 —— 守护侧同样**从不读**（本次只接了开关那一条）。
   两条路要么接、要么下线，不能继续留着"点了没反应"。
2. **`exec_state` 表的归宿**：现在它只剩历史行与级联清理。可以择机删表 + 迁级联清单，
   但那要动 `spaces.test.mjs` 的计数断言与备份/恢复的兼容夹具，属于独立一刀。
3. **§5 第 1/2 条**（两个实例抢写 `daemon.json`、「⏸ 全局暂停」跨空间生效）：
   本机实测已随 `scopes:'auto'` 的按空间状态文件与日志缓解；`control.json` 仍是全局共享的
   （BUG-016 期间顺手删掉了它的**写入方**——那个按钮属于已取消的 v1 看板，见 BUG-015），
   故这条待办现在**没有写入方**，需要时再按空间重建。
4. **手机远程指挥**：`legion-si.online` 目前是一台**独立的空库**（四个空间 goals/tasks 全 0），
   不是通往本机的隧道；本机也没有任何隧道进程。正确形态是反代/隧道指向本机 8787
   **并同时给中枢设 `TEAM_HUB_TOKEN`**（否则等于把指挥台公开）。这一步在服务器侧配置，不在本仓。
