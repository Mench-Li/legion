# BUG-017｜多空间守护一个空间都不接管，而且**一声不响**

> 状态：**已修**（读取形状 + 空视图喊话 + 夹具改成真实形状）
> 发现：2026-10-10，追查「发布目标后没有自动认领」时挖到（BUG-016 的下游）
> 影响面：`plugins/src/index.ts`（`fetchSpaceViews` + `reconcile`）、
> `plugins/tests/multi-space*.test.mjs`（判据与夹具）

## 0. 一句话根因

`fetchSpaceViews` 读 `GET /api/spaces` 时**只认数组**，而真实中枢返回的是**对象**
`{ spaces: [...] }`：

```js
const list = await res.json()
for (const item of Array.isArray(list) ? list : []) {   // ← 真实响应是 {spaces:[…]}，循环一次都不转
```

于是 `views` 恒为空 ⇒ `planSpaceRunners` 算出 **0 个子实例** ⇒ **一个空间都不接管**。
而更坏的是**它一声不响**：`skipped`（"未接管的空间"）也是空的，
所以那行 `log('未接管空间（…）：…')` 也不打。

监督者看起来"活着"——每 30 秒准时跑、准时读、准时算出 0 个执行器，**日志里一行都没有**。

> 一个"读错了响应形状"的读取器，
> 与一个"这台机器上没有空间"的读取器，在下游是同一个东西——
> 只不过前者会在每一轮都安静地重犯一次。

## 1. 现场证据（本机实测）

| 读数 | 值 | 说明 |
| --- | --- | --- |
| `GET /api/spaces` 顶层类型 | **object**，键 `spaces` | 不是数组 |
| `dsh-scrum-worker.log` 最后两行 | `多空间首次编排失败：TypeError: fetch failed`（11:40:43、11:40:47） | 宿主刚起来时中枢还没监听；首轮失败是**正常**的 |
| 之后的日志 | **一片空白**（2 分钟 = 4 轮，一行都没有） | 每轮都"成功"地算出 0 个执行器 |
| `scrum/daemon-software.json` | 停在 4 天前 | 子实例从未挂载 |
| `scrum/daemon.json` | 停在 11:02（上一次宿主） | 监督者本身不写它（那是子实例的事） |

修好之后用真函数 + 真中枢验证：

```
修复前：fetchSpaceViews → 0 个空间        planSpaceRunners → 挂载（无）
修复后：fetchSpaceViews → 4 个空间        planSpaceRunners → 挂载 ozon、software
        default(off) gf001(off,3环) ozon(on,11环) software(on,8环)
```

## 2. 为什么它活了不知多久（一半的原因）

同一个仓里 `/api/spaces` 有**三个**读取者，另外两个写的是对的：

| 文件 | 写法 | 对不对 |
| --- | --- | --- |
| `plugins/src/workspace.ts`（`refreshSpaceBinding`） | `const data = await res.json(); data.spaces ?? []` | ✅ |
| `plugins/src/mediation.ts`（`refreshSpaceRepos`） | `for (const s of data.spaces ?? [])` | ✅ |
| `plugins/src/index.ts`（`fetchSpaceViews`） | `Array.isArray(list) ? list : []` | ❌ **就这一处** |

而且它**从来没有判据**：`multi-space.test.mjs` 测的是纯函数 `planSpaceRunners`
（喂进去的 `views` 是手工造的数组），唯一能覆盖 I/O 的端到端套件
`multi-space-supervisor.test.mjs` 的假 hub 喂的也是**裸数组**：

```js
if (href.includes('/api/spaces')) return jsonResponse(state.spaces.map(s => ({ id: s.id })))  // ← 夹具喂错了形状
```

> 一组夹具喂进去的是"我以为中枢会返回的形状"，
> 与一组夹具喂进去的是"中枢真的返回的形状"，在两者都绿的时候是同一个东西——
> 差别只在真机上那一次。

## 3. 修了什么

1. **形状**（`fetchSpaceViews`）：两种都收 —— 数组（兼容老夹具/老数据面）+
   `{spaces:[...]}`（真实数据面）；认不出的形状得到空数组而不是崩（fail closed）。
   导出以便单测（它是这一族里唯一做 I/O 的一环）。
2. **不许再静默**（`reconcile`）：`views.length === 0` 时打一行带 hub 地址的定位信息，
   并**只喊一次**（每 30s 重复喊会把日志淹掉；喊过一次就够定位）。
3. **夹具改成真实形状**（`multi-space-supervisor.test.mjs` 的 `stubHub`）：让那 6 条端到端用例
   真正覆盖真机形状 —— 它们现在能抓住这个缺陷（实测：变异回去后 6/7 红）。

## 4. 判据

新增 6 条（`plugins/tests/multi-space.test.mjs`，全部用替身 fetch）：

| 用例 | 它问的问题 |
| --- | --- |
| ★ TC-SP-P1-12 | 喂**真实形状** `{spaces:[…]}` 时读得到 3 个空间吗？（原缺陷的直接回归判据） |
| ★ TC-SP-P1-13 | 裸数组形状仍然收吗？（兼容） |
| ★ TC-SP-P1-14 | 认不出的形状 → 空数组且不抛吗？（fail closed） |
| ★ TC-SP-P1-15 | `hubUrl` 为空 → 一个请求都不发吗？ |
| ★ TC-SP-P1-16 | 同一仓三个读取者都认得 `spaces` 字段吗？（静态判据：下次谁再只认数组就红） |
| ★ TC-SP-P1-17 | 空视图**说出来**吗？而且只喊一次吗？（静态判据：静默不许回来） |

**反向验证 3/3 全部按预期变红**：
① 形状改回"只认数组" ⇒ 单元 TC-SP-P1-12 红 + 端到端 **6 条**红（含 TC-SP-P1-20「首次对齐」）
② 去掉空视图喊话 ⇒ TC-SP-P1-17 红
③ `workspace.ts` 改成只认数组 ⇒ TC-SP-P1-16 红

> 变异 ① 第一次没跑成：我的锚匹配到了文件里**更早**的一处 `const list`，
> 删掉了一大段、构建失败，于是测的是旧 lib（"红了但红得没意义"）。
> 教训：变异要**确认它真的改了目标那段**（打印被替换的原文），
> 而且本仓检出是 **CRLF** —— 多行锚必须容忍 `\r?\n`。

## 5. 判断句

> 一个把 I/O 读进来的读取器，若它的形状假设没有被**真实形状**喂过一次，
> 那么它其实只被验证过"我以为对面会说什么"。

更具体地：**任何跨进程/跨模块的响应形状，都要有一条判据用真实载荷喂进去**，
否则"没报错"只是"没人查过"。

## 6. 与 BUG-016 的关系

两件事叠在一起才让业主看到的现象变成"完全没反应"：

- **BUG-016**：开关写在守护不读的表上 ⇒ 空间明明"已开通"却永远是 `enabled=false`；
- **BUG-017**：监督者读错形状 ⇒ 就算数据面写着 `enabled=true`，它也一个空间都不接管、且不报。

两条都已修。BUG-016 的修法是"让开关真的接上"，BUG-017 的修法是"让读取器真的读到"。
