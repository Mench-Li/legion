# BUG-018｜"手机操控这台电脑的任务"这条路，缺的是入口而不是能力

> 状态：**已修**（配置面 + 代令转发的洞 + 操作手册）
> 背景：将军的原话 —— **"我就是要我手机能够在物理离开电脑时，可以操控电脑任务进程"**
> 影响面：`services-plugin`（配置面）、`workbench/scripts/serve.mjs`（`/hub` 代理的令牌转发）

## 0. 一句话结论

**能力早就有了，缺的是入口**，而且缺两个：

| # | 缺的东西 | 后果 |
| --- | --- | --- |
| 1 | 手机面/身份/远程门禁的三个开关，本插件**只注入 PORT/HOST/TOKEN** —— `identityKey`/`remoteAuth` 没有任何配置入口 | 只能去改系统环境变量；改错了没有任何东西会响（与 BUG-016 同类） |
| 2 | `/hub` 代理**只在 `desktopMode` 下**才附中枢令牌 | 一旦为了远程访问给中枢设 token，**本地面板当场读不出任何数据**（`desktopMode=false` 是本机现状） |

## 1. 这条路本来长什么样（已核实到代码）

手机端**已经写好**：`workbench/mobile/` 是一个 PWA（app/board/timeline/sw/manifest+图标），
由中枢自己在 `/mobile` 托管，它把请求打到 `location.origin`（即托管它的那台中枢）——
设计是对的：**手机连哪台中枢，就操控哪台电脑**。

"操控"这条链也是通的（逐行核实）：

```
手机 POST /api/agent-messages { intent: 'create_task', agentId, scope, body }
  → agent-conversations.mjs send() 第 217 行
  → createTask({ by, scope, role, status: 'todo' })
  → 任务进入该空间的 todo
  → 本机守护（订阅同一台中枢）在下一轮扫单时认领 → 派 worker → 在隔离 worktree 里执行
  → 进度/评论/问询按 SSE 回到手机的时间线
```

也就是说：**"手机派活 → 电脑执行"不需要任何新代码**，只需要手机能连上这台电脑的中枢。

## 2. 那三个开关（以及为什么必须一起设）

正本在 `team-hub/config-schema.mjs`：

| 键 | 环境变量 | 语义 |
| --- | --- | --- |
| `identityKey` | `LEGION_IDENTITY_KEY` | **手机面总开关**：>=16 字符 ⇒ 注册 `/mobile` 静态资源 + 身份系统；留空 ⇒ `/mobile` 404 |
| `remoteAuth` | `LEGION_REMOTE_AUTH` | `'1'` ⇒ 除公开白名单外全部 `/api/*` 要求**用户访问令牌**（登录） |
| `token` | `TEAM_HUB_TOKEN` | 机器令牌（读写鉴权） |

★ **只设 token 保护不到读面**：读面的门禁是 `readAuthRequired() = !isLoopback && token !== ''`，
而中枢按设计**始终绑回环**（隧道/反代在它前面）⇒ 那个门是关着的 ⇒ 不带令牌也能读全部数据。
读面要靠 `remoteAuth=1` 那套（要求登录用户）。

★ **token 留空时 `remoteAuth` 是空门**：门禁里的 `legacyAuthorized` 取 `authorized(req)`，
而它在 `TOKEN === ''` 时**返回 true**（源码原话：`if (TOKEN === '') return true`）。
所以 `remoteAuth=1` + 空 token = 依然全放行。

> 两个开关的名字都不说谎，但**它们的组合**才决定安不安全 ——
> 而组合关系没有任何地方写着，只能靠读源码得出。

**因此顺序是**：先设 token + identityKey + remoteAuth（重启宿主）→ **再**开隧道。
反过来，在那段窗口里中枢是公开且无鉴权的。

## 3. 修了什么

### ① 配置面（`services-plugin`）

新增两个字段与向 team-hub 的注入声明：

- `teamHubIdentityKey`（env `LEGION_IDENTITY_KEY`，标 `sensitive`）
- `teamHubRemoteAuth`（env `LEGION_REMOTE_AUTH`）

`buildTeamHubEnv()` 增加这两个参数，并且**只在有值时才注入** ——
注入空串会把宿主环境里配好的值盖掉，而"没配"与"配了个空的"在下游是同一句话。

### ② `/hub` 代理的令牌转发（`workbench/scripts/serve.mjs`）

原来：

```js
...(CFG.values.desktopMode ? { ...hubAuthHeaders(), ... } : {})   // ← 非 desktop 就不带令牌
```

现在**始终**附上中枢令牌（没配就是空对象，行为与从前一致）。判据见
`workbench/scripts/desktop-auth.test.mjs` 新增的那条（非 desktop + 中枢配了令牌 ⇒ `/hub` 仍 200）。

## 4. 判据与反向验证

- `services-plugin/index.test.mjs` 新增 4 条：能注入 / 空值不注入 / **接线处真的传了** / 配置面声明齐（含 `sensitive`）。
- `desktop-auth.test.mjs` 新增 1 条：非 desktop 部署的 `/hub` 代理仍带中枢令牌。
- **反向验证 6/6 全部按预期变红**：接线处不传密钥 · 空值也注入 · 配置面缺键 · injects 缺声明 ·
  密钥不标 sensitive · 代理回到"只在 desktopMode 带令牌"。

## 6. 与 BUG-016 / BUG-017 的同一条判断句

这三件事是**同一个形状**：功能都在，而"让它生效的那个入口"不在。

> 一个"写在没人读的表上"的开关（BUG-016）、
> 一个"读错了响应形状"的读取器（BUG-017）、
> 一个"只在某个模式分支里才接线"的转发（本 BUG）——
> 三者都会让"我明明配好了"与"它怎么不动"同时成立。
