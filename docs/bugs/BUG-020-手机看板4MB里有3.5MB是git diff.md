# BUG-020｜手机看板要下 4MB，其中 3.5MB 是手机永远不看的 git diff

> 状态：**已修**（`?compact=1` + 手机端带参）
> 发现：2026-10-10，手机远程连通后量"首屏到底要多久"时挖到
> 影响面：`team-hub/routes/read-models.mjs`（`/api/board`）、`workbench/mobile/app.mjs`

## 0. 现象

手机打开看板要 **15–45 秒**，有一次直接 **120 秒超时失败**。
第一反应是"中枢慢"，实测**不是**。

## 1. 实测（同一天、同一台机器）

| 读数 | 值 |
| --- | --- |
| 本机 `GET /api/board?scope=software` 响应体积 | **4071.6KB** |
| 其中 `patches` | **3498KB（86%）** —— 每个任务存着完整 git diff |
| 其中 `comments` | 211KB |
| 本机生成它要多久 | **330ms** |
| 过隧道传到手机（完整） | 15–45 秒；实测一次 120 秒**超时失败** |
| 手机看板真正读的字段 | `id/title/status/role/soldier/priority`（7 个） |

> 一个"把 git diff 也发给手机看板"的接口，
> 与一个"手机看板要 45 秒才出来"，是同一件事的两面。

诊断的顺序值得记下来：**先量本机耗时，再量体积**。
如果先怀疑中枢，就会去优化一个只花 330ms 的东西。

## 2. 改法

- `team-hub/routes/read-models.mjs`：`/api/board` 支持 `?compact=1`，
  按**白名单**只回看板字段（`id/title/status/role/soldier/priority/scope/blockedBy/hold/version`）。
  默认（不带参数）**逐字不变**。
- `workbench/mobile/app.mjs`：手机取看板时带 `compact=1`。
  **只改这一处**；任务详情那条路径不许被顺手改掉（详情要的就是 patches/comments）。

**为什么用白名单而不是黑名单**：黑名单会随"哪天又有个大字段长回来"静默失效；
白名单的失效方式是"少显示一点"——可见、可修。

## 3. 效果

| | 完整 | 精简 |
| --- | --- | --- |
| 响应体积 | 4071.6KB | **44.9KB**（缩小 **90.8 倍**） |
| 本机 | 149ms | 72ms |
| 过隧道（手机真实路径） | 120s 超时失败 | 约 1.4–10.8 秒 |

## 4. 判据

- `team-hub/read-models-routes.test.mjs` ⑫b：造一条带 200KB patches 的任务，
  断言默认响应**仍带** patches、`compact=1` 只剩几百字节、白名单外一律不带
  （白名单本身也被钉住：改了就要复核手机端）；⑫c：`compact` 与三个过滤参数**正交**。
- `workbench/scripts/mobile-board-parity.test.mjs`：源码级两条 ——
  手机必须带 `compact=1`；任务详情**不许**按精简口径取。

## 5. 判断句

> 一个只按"链路慢"去优化的排查，
> 与一个先量"到底传了多少字节"的排查，在响应是 45KB 还是 4MB 时是两件事。

## 6. 遗留

`patches` 有 3498KB 说明**库里存着大量 git diff**（162 个任务）。
这是数据增长问题，不是接口问题：真要控制体积，该考虑 diff 的保留策略
（例如只留最近 N 轮的 patch、或把 diff 落到 artifacts 文件里）。
本次**没动**——它会影响证据/审计口径，需要单独决策。
