# BUG-022｜提醒**根本不会响**：没选空间就不弹，且不说"为什么停在这"

> 状态：**已修**（web/桌面端 + 手机端）
> 发现：2026-10-10，将军原话「T-199 我没看到弹框」
> 影响面：`workbench/src/App.tsx`（弹框 effect）、`workbench/src/notify.ts`（`popupReason`）、
> `workbench/mobile/app.mjs`（`refreshPopups`）、`workbench/mobile/popup.mjs`（`popupReason`/`reasonFromTask`）

## 0. 现场

BUG-021 修完之后，将军仍然没收到 T-199 的弹框。而审计里那条**是有的**：

```
10:01:11  coder  transition  {"to":"in_review"}   ← 高优先级，按判据应当弹
```

所以这次不是"没做提醒"，而是**提醒被两个条件悄悄挡住了**。

## 1. 根因一：`!scope` 早退 ⇒ "全部空间"视图一个弹框都没有

BUG-021 那个 effect 的第一行是：

```ts
if (!hubMode || !scope) { setNotifyUnread(0); popupSeqRef.current = 0; return }
```

于是**没选中具体空间时，提醒整段不工作**。而"我现在没选空间"与"我不想被提醒"
毫无关系 —— 将军当时就停在这个视图上。

> 一个"要先挑一个空间才开始提醒"的提醒，
> 与一个"不提醒"的提醒，在用户还没挑空间时是同一个东西。

**改法**：`scope === null` 时**不过滤**地取审计（`fetchHubActivity({ scope: scope ?? undefined })`），
游标走 `__all__` 那一把（`popupSeqKey` 本来就支持 null）。点弹框时会先切到**那条任务所在的空间**
再打开通知中心 —— 跨空间提醒不该把人送到看不见它的地方。

手机端同一处（`refreshPopups` 里的 `if (state.scope === null) return`）一起修。
手机端平时会自动选第一个空间，所以这个空档少见；但"还没有任何空间"时它同样会静默。

## 2. 根因二：只说状态，不说**为什么停在这**

修好①之后弹框会说：

```
⏳ T-199 待你验收（编码工程师）
```

而 T-199 的真实原因是（任务最新评论）：

```
⚠ 编码实现完成，但自动合入主分支失败（可能冲突），改动保留在分支 w/T-199。请人工合入并推进：…
```

**"等你验收"和"等你解冲突"是两个不同的动作。** 只说前者会把人送去做错的事
（去点验收，而不是去解冲突）。

**改法**：`popupReason(commentText)` —— 从任务**最新一条**评论里抽第一行，
且**只认"出了状况、要人介入"的语气**（失败/冲突/等待人工/拒绝/无法/错误/超时/受阻/人工核对/人工处理）。
纯进展播报与常规的"请将军人工验收"都返回 `null`（后者是闸门的日常，主文案已经说了「待你验收」）。

★ 第一版门槛写宽了：「请将军」也被当成关键词，于是**常规验收评论被当成"原因"糊在弹框上**——
判据当场变红。这条记在这里：**漏掉一次补充说明，用户仍然会被弹框叫到；多糊一句，用户下次就不看了。**

## 3. 顺手补的一处"它到底在工作吗"

首次接入、且当下确实没有要提醒的事时，明确说一句：

```
🔔 提醒已就绪：有任务等你处理时，会在这里弹出来
```

只对每个浏览器说一次（`legion.notify.popuparmed` / `legion.mobile.popuparmed`）。
否则用户分不清"它没在工作"与"确实没事" —— **那正是这次投诉的根源**：
将军无法从界面上判断提醒是否已经武装好。

## 4. 验收

- `workbench/scripts/notify-popup.test.mjs`（34 例）：新增 BUG-022 两组 ——
  `popupReason` 用**真实那条挡住 T-199 的评论**断言能抽出来、纯进展播报返回 null、
  取第一行、超长带省略号、空/非字符串安全；接线判据断言 `App.tsx` 里
  **不再有 `!scope` 早退**、**确实在取任务原因**、**跨空间要切空间**。
- `workbench/mobile/popup.test.mjs`（21 例）：新增 `popupReason` **两端逐字一致**（含真实评论、null、数字、超长），
  以及"常规验收/进展播报两端都不当成原因"。
- **真实数据端到端**（本机中枢 + 运行中的服务）：

  ```
  不带 scope 拉审计（"全部空间"视图走的正是这条）：200 条   ← 从前这里根本不会走到
  T-199 进 in_review 的事件：seq 59966
  桌面弹框：⏳ T-199 待你验收（编码工程师） —— ⚠ 编码实现完成，但自动合入主分支失败（可能冲突）…
  手机弹框：与桌面**逐字相同**（同一个判据、同一条评论）
  ```

## 5. 判断句

> 一个"要你先挑一个空间、且只说状态"的提醒，
> 与一个"没在响"的提醒，在用户最需要它的时候是同一个东西。

## 6. 遗留

- 手机端的系统通知仍只在页面还活着时有效（见 BUG-021 §6，要 Web Push 才能覆盖"关掉页面"）。
- 弹框的"原因"要读一次任务详情（至多 3 次请求/轮，弹框本来就少）。若日后弹框变频繁，
  应改为让中枢在审计行里直接带上原因，而不是客户端回读。
