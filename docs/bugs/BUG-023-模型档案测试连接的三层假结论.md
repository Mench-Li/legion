# BUG-023｜模型档案「测试连接」连着说了**三句假话**

> 状态：**三层都已修**（布局闸门 / URL 拼接 / 读错口子）；**剩下的是一处数据问题**（见 §5）
> 发现：2026-10-10，将军报 `FJD · deepseek-v4-flash-openai`
> 「503：无法测试连接：产品目录布局未确定，因此不知道密钥库在哪里。**这次没有探测过**」
> 影响面：`product/paths.mjs`、`team-hub/secret-admin.mjs`、`team-hub/probe-service.mjs`、
> `runtime/probe/http.mjs`、`runtime/probe/index.mjs`、`runtime/contracts/model-probe.mjs`、
> `team-hub/routes/model-profiles.mjs`

## 0. 顺带回答：模型档案是什么

**模型档案（ModelProfile）= 一条"用哪个供应商的哪个模型、从哪拿钥匙"的登记**，
存在 team-hub 库里，面板「模型库」看的就是它：

| 字段 | 含义 |
| --- | --- |
| `id` / `displayName` | 档案标识与显示名 |
| `provider` / `model` | 供应商与模型 id（如 `fjd-ds` / `deepseek-v4-flash-openai`） |
| `endpoint` | API 基址（如 `https://fjbigmodel.fjdac.cn/v1`） |
| `secret_ref` | **只是引用名**（如 `FJD_DS_API_KEY`），密钥本体在操作系统密钥库（DPAPI）里，**库里永不存明文** |
| `reasoningEffort` / `limits` | 推理档位与限额 |

它同时是**派生 DSH 配置的源头**（见 `docs/DECISION-legion-owns-model-config.md`）：
Legion 是唯一真相，DSH 的配置由它算出来。所以"这条档案能不能用"直接决定 Agent 能不能跑。

「测试连接」= 拿 `secret_ref` 去本机密钥库取钥匙，向 `{endpoint}/v1/models` 发一次**几乎不花钱**的
`GET`，再核对模型 id 在不在清单里（见 `runtime/probe/http.mjs` 开头那段：不发起真实推理，
所以这个按钮才敢反复点）。

## 1. 第一层（BUG-023）：布局闸门拦了一件与密钥库无关的事

```
503 无法测试连接：产品目录布局未确定，因此不知道密钥库在哪里
```

**而密钥库好好的**：`GET /api/secrets` 正常列出凭据。这台机器上唯一的 `error` 级诊断是
`WORKSPACE_NOT_CONFIGURED`（"还没选项目工作区"）—— 与"密钥库在哪"毫无关系。

根因是一条规则被**抄成了两份**：

- `team-hub/secret-admin.mjs`（写凭据）——2026-10-10 已改成"**点名**密钥库真正依赖的那几个码"；
- `team-hub/probe-service.mjs`（测连接）——**还是**"任何 error 级都拒"。

先修了前一份，后一份没跟着改，于是同一台机器上"填密钥能用、测连接不能用"，
而两份代码各自看都"很对"。

> 一条被抄成两份的规则，
> 与一条只写了一份的规则，在**只修好其中一份**的那天之前，是一样的。

**改法**：集合与判据搬到 `product/paths.mjs`，导出 `SECRETS_BLOCKING_DIAGNOSTICS` 与
`secretsBlockingDiagnostics(diagnostics)`，两个调用方各 `import` 同一份；
报错时把**是哪几条**列出来（只说"布局未确定"等于没说）。
另加一条判据直接读这两个文件的源码，钉住它们不许再各自写一套。

## 2. 第二层（BUG-024）：`/v1` 拼了两遍 ⇒ 404 ⇒「供应商不认这个模型标识」

修好第一层后，判定变成「**供应商不认这个模型标识**：请核对模型 id」——**方向完全错了**。

```
档案 endpoint        = https://fjbigmodel.fjdac.cn/v1     ← OpenAI 兼容的 base_url 惯例就是含版本段
DEFAULT_MODELS_PATH  = '/v1/models'                       ← 又带一个 /v1
朴素拼接 = https://fjbigmodel.fjdac.cn/v1/v1/models  →  404
正确地址 = https://fjbigmodel.fjdac.cn/v1/models      →  200，清单里三个模型 id **全都在**
```

> 一个"把 /v1 拼两遍"的实现，
> 与一个"模型 id 填错了"的实现，在界面上说的是同一句话。

**改法**：`joinModelsUrl(base, modelsPath)` —— 只在**同一段紧挨着出现两次**时去掉一次
（`base` 不以该段结尾时**逐字不变**，如 `https://api.example.com` + `/v1/models`）。
判据里既钉"不重复"，也钉"既有形状不许被动过"。

## 3. 第三层（BUG-025）：路由把**脱敏视图**喂给了要用密钥的那段代码

修好第二层后，判定变成「**凭证已成功解析**，但供应商拒绝：请更换密钥」——**还是假话**，
而且这次把人送去供应商控制台。

`model-store.mjs` 一直备着**两个**读取口，注释甚至点名了这个用途：

```
get(id)          → descriptor，**不含 secretRef**（给 UI/API）
internalGet(id)  → 内部对象，**含 secretRef** ——「只在需要真的用凭证时调用（如 PRT-504 连通性测试）」
```

而探针路由读的是 `get()`。于是探针拿到的档案**没有 `secretRef`** ⇒ 一个 `Authorization`
头都不发 ⇒ 供应商回 401 ⇒ 判定写成"凭证已成功解析"。

> 一条"为了安全而脱敏"的读口，
> 与一条"把脱敏视图喂给要用密钥的那段代码"的读口，
> 在只看类型签名的时候是一模一样的。

**改法**：探针路由改读 `internalGet`（保留原有的 404 / 409 墓碑语义）。
另把"这次到底带没带凭证"作为**观测的一部分**报出来（`credentialSent`），
让判定层在 401 时能区分"钥匙被拒"与"根本没带钥匙"——后者不再说那句假话。

## 4. 为什么整套用例都没抓到（两次"夹具共盲点"）

1. `probe-service.test.mjs` 那条"布局不合法 ⇒ UNAVAILABLE"的夹具用的是
   `SECRETS_INSIDE_DATA_DIR` —— **在**点名集合里，所以修前修后都绿；
2. `model-routes.test.mjs` 的 `profile()` 夹具**没有 `secretRef`**，
   而它 stub 的正是脱敏口 `modelStore.get()` —— 夹具与实现**共享同一个盲点**。

> 一个"喂给被测代码的夹具"与"被测代码本身"共有的盲点，
> 是唯一一种连变异测试都很难发现的盲点：改哪一边都还是绿的。

所以补的判据里有两条是**入口级**的：一条用带 `secretRef` 的档案断言"探针真的拿到了引用名"，
一条断言"带 `secretRef` 而取不到钥匙时必须是 `SECRET_UNAVAILABLE`"。

## 5. 验收与**剩下的那一件事**

修完之后，真机判定（`POST /api/model-profiles/<id>/probe`）：

```
fjd-ds-deepseek-v4-flash-openai   HTTP 200  SECRET_UNAVAILABLE  「取不到 FJD_DS_API_KEY」
fjd-ds-deepseek-v4-pro-openai     HTTP 200  SECRET_UNAVAILABLE  同上
```

**这是真话了**，而它指向一个真实的数据问题：

```
三条 fjd-ds-* 档案的 secret_ref = FJD_DS_API_KEY
密钥库里的两条        = SVEA_DS_API_KEY · SVEA_DS_1_API_KEY     ← 没有 FJD_DS_API_KEY
而 model_providers.fjd-ds.credential_configured = 1             ← 面板据此显示「已配置凭证」
```

**用现有的任一把 SVEA 钥匙实测**（同一个 `base_url`）：`GET /v1/models` → 200，
清单里 `deepseek-v4-flash-openai` / `deepseek-v4-flash-vision-openai` / `deepseek-v4-pro-openai`
**三个都在**；用修好的 URL 跑完整探测 → `ok=true, capabilities={chat:true}`。

所以有两条路（**待将军裁决，见提交说明**）：

- **甲**：把 `FJD_DS_API_KEY` 补进密钥库（面板「凭证」里加，或在档案里改引用名）；
- **乙**：把这三条档案与 `fjd-ds` 供应商行指向**已存在的** `SVEA_DS_API_KEY`（实测可用）。

★ 顺带记一笔：`credential_configured` 是**从 DSH 导入的标记**，不是"核验过钥库里真的有"。
所以「已配置凭证 · 版本 1」这句话在钥匙缺失时**也是假话**。本次未改（它属于"该不该在
面板上做一次真实核验"的产品决定），但已在此登记。

## 6. 判断句

> 一个"报了个错但方向是错的"的按钮，
> 与一个"什么都不报"的按钮，在用户按下它十次之后，是同一个东西。
