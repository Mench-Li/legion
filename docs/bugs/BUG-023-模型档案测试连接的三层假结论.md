# BUG-023｜模型档案「测试连接」连着说了**三句假话**

> 状态：**三层已修**，并**收敛了"连接信息存两份"**（见 §6）
> 发现：2026-10-10，将军报 `FJD · deepseek-v4-flash-openai`
> 「503：无法测试连接：产品目录布局未确定，因此不知道密钥库在哪里。**这次没有探测过**」
> 影响面：`product/paths.mjs`、`team-hub/secret-admin.mjs`、`team-hub/probe-service.mjs`、
> `runtime/probe/http.mjs`、`runtime/probe/index.mjs`、`runtime/contracts/model-probe.mjs`、
> `team-hub/routes/model-profiles.mjs`、`team-hub/model-resolution.mjs`（新）、
> `team-hub/credential-status.mjs`（新）、`team-hub/routes/model-providers.mjs`、
> 面板 `DshProvidersPanel.tsx` / `ModelProfilesPanel.tsx` / `modelSettings.ts`

## 0. 模型档案是什么

**模型档案（ModelProfile）= 一条"哪个供应商的哪个模型"的登记**，同时也是
**派生 DSH 配置的源头**（Legion 是唯一真相，DSH 的配置由它算出来）。

| 字段 | 含义 |
| --- | --- |
| `provider` / `model` | 供应商与模型 id（`fjd-ds` / `deepseek-v4-flash-openai`） |
| `endpoint` | API 基址（**可空**，留空即继承供应商） |
| `secret_ref` | **只是引用名**（**可空**，留空即继承供应商）；密钥本体在操作系统密钥库（DPAPI） |
| `reasoningEffort` / `limits` | 推理档位与限额 |

**它与供应商不是同一件事的两遍**：

- 供应商 = 一个端点 + 一把钥匙 + **N 个模型**（`models_json`）；
- 档案 = 从里面**挑定一个**，好被岗位绑定（`employee_model_bindings` 的键是
  `(scope, 岗位) → primaryProfile + fallbackProfiles + perRunBudget`）、
  好写进每一次 Run 的历史（`modelProfileRef`，因此档案的删除是**墓碑**）。

「测试连接」= 拿 `secret_ref` 去本机密钥库取钥匙，向 `{endpoint}/v1/models` 发一次
**几乎不花钱**的 `GET`，再核对模型 id 在不在清单里（刻意不发起真实推理）。

## 1. 第一层：布局闸门拦了一件与密钥库无关的事

这台机器上唯一的 `error` 级诊断是 `WORKSPACE_NOT_CONFIGURED`（还没选项目工作区），
与"密钥库在哪"毫无关系。根因是**同一条规则被抄成两份**：`secret-admin.mjs`（写凭据）
上一轮已改成"点名密钥库真正依赖的码"，`probe-service.mjs`（测连接）**还是**"任何 error 都拒"。

> 一条被抄成两份的规则，
> 与一条只写了一份的规则，在**只修好其中一份**的那天之前，是一样的。

**改法**：集合与判据搬到 `product/paths.mjs`（`SECRETS_BLOCKING_DIAGNOSTICS` +
`secretsBlockingDiagnostics`），两个调用方 import 同一份；报错时列出**是哪几条**。

## 2. 第二层：`/v1` 拼了两遍 ⇒ 404 ⇒「供应商不认这个模型标识」

```
endpoint = https://fjbigmodel.fjdac.cn/v1   ← OpenAI 兼容的 base_url 惯例含版本段
DEFAULT_MODELS_PATH = '/v1/models'          ← 又带一个 /v1
朴素拼接 → /v1/v1/models → 404 → 被翻译成"不认模型 id"（而三个 id 供应商全认）
```

**改法**：`joinModelsUrl()` —— 只在**同一段紧挨两次**时去重；不含该段时**逐字不变**。

## 3. 第三层：路由把**脱敏视图**喂给了要用密钥的那段代码

`model-store` 一直备着两个读口（注释点名了本用途）：`get()` = 不含 `secretRef`；
`internalGet()` = 含 `secretRef`「只在需要真的用凭证时调用（如 PRT-504 连通性测试）」。
探针路由读的是 `get()` ⇒ 拿不到引用名 ⇒ **一个 `Authorization` 头都不发** ⇒ 供应商 401
⇒ 判定写成「**凭证已成功解析**，但供应商拒绝」。

> 一条"为了安全而脱敏"的读口，
> 与一条"把脱敏视图喂给要用密钥的那段代码"的读口，
> 在只看类型签名的时候是一模一样的。

**改法**：路由改读 `internalGet`；transport 报出 `credentialSent`，401 时区分
"钥匙被拒"与"根本没带钥匙"。

## 4. 为什么整套用例都没抓到（两次"夹具共盲点"）

1. `probe-service.test.mjs` 的布局用例夹具用的是**在**点名集合里的码（修前修后都绿）；
2. `model-routes.test.mjs` 的 `profile()` 夹具**没有 `secretRef`**，而它 stub 的正是脱敏口。

> 一个"喂给被测代码的夹具"与"被测代码本身"共有的盲点，
> 是唯一一种连变异测试都很难发现的盲点：改哪一边都还是绿的。

## 5. 诊断链上每一句都必须指向**真动作**

修完之后真机是 `SECRET_UNAVAILABLE / SECRET_NOT_FOUND`（真话），但那时它说的是
「无法访问或解密本机凭证库：请检查密钥库与当前 **Windows 账户作用域**」——
而库好好的，只是**没有这个引用**。两个动作完全不同：
一个去查 DPAPI/账户，一个去补钥匙。

> 一句"请检查密钥库作用域"，
> 在**库好好的、就是没有这个引用**的那次失败上，
> 与一个指向供应商控制台的错误一样，都是把人送去错误的地方。

**改法**：`SECRET_NOT_FOUND` 单独一条文案（"引用的凭证不在本机密钥库里…
不必去供应商控制台"）；打不开库时仍然是原来那句（那条是对的）。

## 6. 收敛：连接信息**只该存一份**（DECISION §6 的下半句）

实测两条记录：

```
model_providers.fjd-ds   base_url = https://fjbigmodel.fjdac.cn/v1   secret_ref = FJD_DS_API_KEY
model_profiles.<三条>    endpoint = https://fjbigmodel.fjdac.cn/v1   secret_ref = FJD_DS_API_KEY  ← 又一份
```

而 `docs/DECISION-legion-owns-model-config.md` §6（将军自己写的）早已定了方向：

> 建议（P1 一并做）：新增 `model_providers` 表…`model_profiles.provider` 引用它；
> **`api` 协议与 `base_url` 从"每行都有"上移到"每个供应商一份"**。

**表建了（P1 做了），"上移"只做了一半**：供应商有了 `base_url`，档案那份没删。
下游也没兑现"可选"——`probe-service` 见到空 `endpoint` 直接判「这个档案没有填 endpoint」。
还有一个证据说明这是"没做完"：`runtime/contracts/model.mjs:139` 明写
"endpoint **可选**"，理由给的是"本地模型可以合法地没有 endpoint 也没有凭证"。

**改法（`team-hub/model-resolution.mjs`）**：档案里的值是**可选覆盖**，
留空 ⇒ 从点名的供应商取；写了 ⇒ **逐字用它**（真实偏离必须活下来）。
这样不必再做一次数据迁移：**留空的档案自动就是"上移后"的形态**，
而已经写满的那三条行为**逐字不变**（它们本来就等于供应商的值）。

面板据此显示「（地址与凭证继承自供应商 fjd-ds）」，
并在**逐字等于**供应商的值时提示「可以留空」——**只提示，不拒绝**：
"留空"与"写成一模一样"在行为上等价，所以没有任何正确性理由去挡用户。

## 7. 假话的另一半：「已配置凭证」

面板那句「已配置凭证」来自两个**都不是核验**的来源：

- 供应商行 `model_providers.credential_configured` —— **P1 从 DSH 导入的标记**；
- 档案行 `hasCredential` —— 只表示 `secret_ref` **非空**。

> 一个"引用了某个名字"的条目，
> 与一个"那把钥匙真的在库里"的条目，在界面上说的是同一句话——
> 而它们的修法完全不同（一个要补钥匙，一个什么也不用做）。

**改法（`team-hub/credential-status.mjs`）**：核验真问密钥库，四态
`none | ready | missing | unavailable`；**一次列表只读一遍库**；
**读不出来 ⇒ `unavailable`，绝不降级成 `missing`**（把"我不知道"说成"没有"
会让用户去补一把他可能早就存过的钥匙）。

真机对照（修复后）：

| 供应商 | 导入标记 | ★ 核验 |
| --- | --- | --- |
| `fjd-ds` | true | **missing** |
| `deepseek-official` | true | **missing** |
| `svea-ds` | true | ready |
| `deepseek-account` | false | none（本就不需要凭证） |

## 8. 验收

- 判据：`model-resolution` 11 例 · `credential-status` 9 例（含"读不出来 ≠ 没有"）·
  路由级新增 5 例（供应商列表带核验状态 / 档案留空继承 / 写了不被覆盖 / 缺引用文案）；
  受影响 11 个套件 **252/252 绿**；四道门禁全绿；
  变异验证：把旧写法放回去，新增判据立刻变红。
- 真机：面板从此显示**核验过的**状态；三条 fjd 档案显示「凭证缺失：引用了名字，
  但钥匙**不在**本机密钥库里」，以及「地址与凭证引用与供应商逐字相同 —— 可以留空」。

## 9. 仍未做的（诚实登记）

- `credential_configured` 那个导入标记**仍然保留在响应里**（别的消费者还在用），
  只是界面不再据它下结论；
- `model_profiles.provider` **没有外键约束**，档案可以指向不存在的供应商
  （`providerMissing` 会报出来，但不阻止保存）；
- 把三条档案的 `endpoint`/`secret_ref` 真正**清空**（改为继承）属于一次数据变更，
  面板会提示"可以留空"，但**不代用户改数据**。

## 10. 判断句

> 一个"报了个错但方向是错的"的按钮，
> 与一个"什么都不报"的按钮，在用户按下它十次之后，是同一个东西。
