# BUG-026｜模型档案不该手工新建 —— 它该从「供应商 + 模型」派生

> 状态：**已修**（派生计划 + 具名端点 + 面板按钮）
> 提出：2026-10-10，将军原话
> 「那我还有必要新建档案嘛，**直接来源于模型与供应商才对啊**」
> 影响面：`team-hub/profile-derivation.mjs`（新）、`team-hub/routes/model-providers.mjs`、
> `team-hub/server.mjs`、`team-hub/config-schema.mjs`、面板 `DshProvidersPanel.tsx` /
> `ModelProfilesPanel.tsx` / `index.css`

## 0. 先把问题说准：档案有必要，**手工新建**没必要

这两件事原来被混在一起了。分开看：

| | 供应商 | 模型档案 |
| --- | --- | --- |
| 回答 | 我能连上谁 | **我选了哪一个** |
| 内容 | 一个端点 + 一把钥匙 + **N 个模型**（`models_json`） | 从那张清单里挑定**一个** |
| 为什么不能合并 | —— | 岗位绑定的键是 `(scope, 岗位) → 主档案 + 备选链 + 单次预算`（`employee_model_bindings`）—— 你得能"把**一个模型**绑给编码岗"，而供应商是"有 3 个模型的一坨"；另外每次 Run 都记 `modelProfileRef`，所以档案删除是**墓碑** |

**所以档案必须存在**（岗位绑定与运行历史要一个稳定的引用）。

**但手工新建是不该需要的**：档案的 `provider` / `model` / `displayName` / `id`
全都能从"供应商 + 它清单里的第几个模型"算出来 —— 而那个算法**本仓早就有了**：
`model-migration.mjs` 的 `profileIdFor(provider, model)`。

> 一个"把 (供应商, 模型) 折叠成 id"的函数，
> 在**只有一次性迁移那一条路调用它**的时候，
> 与一个"界面上仍然要用户手打 8 个字段"的产品，是可以同时存在的。

实测确认它确实只有那一条路在用：`modelStore.create` 的调用方只有**迁移**、
**配置包导入**、以及**面板的手工表单**；供应商的建/改路径**完全不碰档案表**。

## 1. 那个"早就有"的算法与库里现状**不一致**（这是最要紧的一条）

```
库里：fjd-ds-deepseek-v4-flash-openai          ← 连字符
规则：fjd-ds.deepseek-v4-flash-openai          ← 点号
```

于是**如果按 `id` 认身份**，"保存供应商时顺手派生"会一次**多建三条重复档案**，
而它们看起来完全正常（同样的 provider、同样的 model、同样的清单）。
真机 dryRun 的读数就是这条判据的现场：

```
新增 0 / 已存在 3 / 冲突跳过 0
    已存在 fjd-ds-deepseek-v4-flash-openai（← 就是这个模型，不动它）
```

> 一个"按 id 认身份"的派生器，
> 与一个"按 id 认身份、但库里 id 恰好等于派生规则"的派生器，
> 在**换一台机器/换一次导入**之后就分开了。

**改法**：身份是 **`(provider, model)`**，`id` 只是一个名字。

## 2. 三条纪律（都写进了 `profile-derivation.mjs` 的文件头）

1. **身份是 `(provider, model)`，不是 `id`** —— 见上。
2. **只建缺的，绝不改已有的。** 已存在的档案带着用户的真实选择（推理档位、限额、
   以及可能的偏离地址/另一把钥匙）。派生**连 `version` 都不动**。
3. **绝不自动删除。** 供应商清单里去掉的模型，对应档案只**报出来**（`orphaned`）。
   自动打墓碑是不可逆方向的动作，该由人决定；而且那条档案可能正被某个岗位绑定引用着。
   读数里因此写"**未动**"，而不是"已清理"。

另外一条来自既有纪律的沿用：**`runtimeType` 不猜**。供应商里没有这个信息，
库里也不该猜（与 `MIGRATION_RUNTIME_TYPE_REQUIRED` 同一条理由）——
所以它是请求里的**必填字段**，面板把它显示出来并预填 `dsh`
（`runtime/adapters/` 目前只有 `dsh` 一个适配器），而不是让服务端默默用一个默认值：
那会让"我没选过运行时"与"我选了 dsh"在读数上同形。

## 3. 派生的档案**天然就是"连接信息只存一份"的形态**

派生的档案把 `endpoint` / `secretRef` 写成 **`null`** —— 即"留空 ⇒ 从供应商继承"
（`team-hub/model-resolution.mjs`，见 BUG-023 §6）。所以：

- 不会为新档案再造一份供应商连接信息的拷贝；
- 供应商改地址/换钥匙时，这些档案自动跟着走。

> 一个"派生时顺手把供应商的地址抄进档案"的实现，
> 与 BUG-023 修掉的那个重复，是同一件事的第 N 次复发。

## 4. 接口与界面

- `GET /api/model-providers`：每个供应商多一列
  `profiles: { existing, missing, orphaned }` —— 面板据此说"生成 N 个档案"。
  **读不到档案表时不给这一列**（一个"还缺 0 个"的读数会被读成"都建好了"）。
- `POST /api/model-providers/<id>/derive-profiles`
  body `{ actor, runtimeType, dryRun? }` → 计划 / 执行结果（`created` / `failed` /
  `existing` / `conflicts` / `orphaned` / 一句话 `summary`）。
  - **具名端点而不是"保存供应商时顺手建"**：与 `/import` 同一条理由 ——
    供应商该不该长出一堆档案是一次**用户的决定**，不是一个副作用。
  - **位置**必须排在通配 `prefix` 路由之前，否则 id 会变成 `<id>/derive-profiles`
    （`/discover` 踩过同一个坑，判据里钉住了）。
  - `dryRun` 让面板**先展示"将新建 N 条"与它们的 id 再落笔**（与 P3 物化同一套）。
  - 逐条记账：一条写失败不该把已经建好的说成没建。
- 面板：「模型」页每个供应商行，缺档案时出现描边的「生成 N 个档案」；
  点开先 dryRun 预览，确认才写。孤儿档案显示「N 条档案已不在清单里」（并说明**没有动它们**）。
  档案页的手工表单保留给**真正的偏离**，并加了一句指路。

## 5. 验收

- 纯模块 `profile-derivation` **11 例**：按 `(供应商,模型)` 认身份（含"库里用连字符 id
  已存在 ⇒ 一条都不建"这条）、只建缺的、幂等、id 被别的模型占用 ⇒ 报冲突跳过、
  墓碑 id ⇒ 报冲突跳过、孤儿只报不删、`runtimeType` 必填、坏输入、读数含"未动"。
- 路由级 **9 例**（`model-providers-routes.test.mjs` ⑱–㉕）：列表带对账列、
  dryRun 一条都不写、真跑后 `endpoint`/`secretRef` 为 `null`、幂等（连 `version` 都不动）、
  缺 `runtimeType` 400 且不写、路由顺序（错误信息里不许出现 `derive-profiles`）、
  冲突不覆盖别人的档案、孤儿不自动删。
- 真机：#3 条既有 fjd 档案 ⇒ dryRun「新增 0 / 已存在 3」，真跑后档案数**仍是 3**。
- 四道门禁全绿（`scan.mjs` 把四个新错误码登记成 `nonEnvLiterals`，它们只是长得像 env 名）。

## 6. 仍未做的（诚实登记）

- 派生**只覆盖"供应商清单 → 档案"这一个方向**；把档案的偏离（另一个网关/另一把钥匙）
  反映回供应商**不做**——那是两个不同的轴，合并会丢掉"同一个供应商的某个模型走别的网关"
  这条真实可能。
- 孤儿档案的清理仍然**只能手工**（面板只提示）。要不要提供一个"批量打墓碑"的动作，
  属于一次产品决定（它不可逆，且可能影响岗位绑定）。
- `model_profiles.provider` 仍然**没有外键约束**，档案可以指向不存在的供应商
  （`model-resolution.mjs` 的 `providerMissing` 会报出来）。

## 7. 判断句

> 一份"要用户手打 8 个字段"的登记表，
> 与一台"这些字段全都已经知道"的机器，在**只有一个模型**的时候，差别只是麻烦；
> 在**供应商有 20 个模型**的时候，差别是这件事根本不会被做对。
