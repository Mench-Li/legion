# BUG-026｜模型档案由供应商与模型**自动生成**，不再手工新建

> 状态：**已完成**（保存即自动生成 / 面板去掉手工新建 / 运行时上移到供应商一份）
> 提出：2026-10-10，将军原话（两次，第二次把要求说全了）
> 第一次：「那我还有必要新建档案嘛，**直接来源于模型与供应商才对啊**」
> 第二次：「档案必然由供应商与模型来，且**添加完自动生成**供应商档案，而不是：
> 1.需要手工点生成；2.在模型档案这要手工填写」
> 影响面：`team-hub/profile-derivation.mjs`、`team-hub/provider-store.mjs`、
> `team-hub/routes/model-providers.mjs`、`runtime/contracts/model.mjs`、
> `team-hub/model-migration.mjs`（未改，被复用）、面板 `DshProvidersPanel.tsx` /
> `ModelProfilesPanel.tsx`、`index.css`

## 0. 先把问题说准：档案有必要，**手工新建**没必要

| | 供应商 | 模型档案 |
| --- | --- | --- |
| 回答 | 我能连上谁 | **我选了哪一个** |
| 内容 | 一个端点 + 一把钥匙 + **N 个模型**（`models_json`） | 从那张清单里挑定**一个** |
| 为什么不能合并 | —— | 岗位绑定的键是 `(scope, 岗位) → 主档案 + 备选链 + 单次预算`（`employee_model_bindings`）—— 你得能"把**一个模型**绑给编码岗"；另外每次 Run 都记 `modelProfileRef`，所以档案删除是**墓碑** |

**所以档案必须存在**（岗位绑定与运行历史要一个稳定的引用）。

**但手工新建是不该需要的**：档案的 `provider` / `model` / `displayName` / `id`
全都能从"供应商 + 它清单里的第几个模型"算出来 —— 而那个算法**本仓早就有了**
（`model-migration.mjs` 的 `profileIdFor`），只是此前**只有一次性迁移**在调用它。

> 一个"把 (供应商, 模型) 折叠成 id"的函数，
> 在**只有一次性迁移那一条路调用它**的时候，
> 与一个"界面上仍然要用户手打 8 个字段"的产品，是可以同时存在的。

## 1. 上一版只做到"点一下补齐"，那还是把机器知道的事交给用户点

上一轮（本次改动的第一版）加了「生成 N 个档案」按钮。它解决了"要手打 8 个字段"，
但没解决将军说的第 1 点：**需要手工点生成**。

现在的分工：

- **保存 / 修改供应商 ⇒ 立刻自动生成**（`routes/model-providers.mjs` 的 `deriveForProvider`）；
- **导入（从运行环境收进来）⇒ 同样自动生成**（否则引导导入之后"目录一堆、档案为空"——
  那正是将军那台机器上的那一幕：4 个供应商、档案只有 3 条）；
- 「补齐」端点保留，但**退化成修复/补历史那条路**（幂等，多点一次没有代价）。
  面板上它只在 `missing > 0` 时出现，措辞是「**补齐**」而不是「生成」——
  因为那意味着"那次没跑成"（历史数据，或某个模型的档案 id 被占用）。

## 2. 自动生成缺的那个信息：`runtimeType`（这一条决定了做法）

派生需要 `runtimeType`（"这批模型按哪种协议跑"）。它原来**每条档案各写一遍**，
而它是"**跟这个供应商说话**的方式" —— 与 `baseURL` / `secretRef` 同一条轴，
所以同一次"上移"把它一起移到了**供应商行**上（新增 `model_providers.runtime_type` 列）。

于是模型档案那页**不需要填它**（留空即继承），而供应商编辑页里它是一个**预填好的下拉**
（选项由服务端给，见下）。

### 为什么"预填"不是"猜"

`model-migration.mjs` 有一条纪律：runtimeType 不许猜，"猜错会让请求以错误的协议发出去"。
它仍然成立。区别在于**唯一性**：

- `runtime/contracts/model.mjs` 新增 `SUPPORTED_RUNTIME_TYPES = ['dsh']` ——
  它不是"我们支持的协议清单"（那是开放的声明空间），而是"**Legion 真能跑起来的**运行时"，
  依据是代码里**唯一**的分派点 `team-hub/server.mjs` 的 `resolveFrozenAgentModelConfig`
  （`profile.runtimeType !== 'dsh'` ⇒ 409）与 `runtime/adapters/` 里唯一的适配器。
- `resolveRuntimeType()` 的规则是：**只有恰好一个候选时**才允许替用户定
  （`from: 'only-supported'`）；供应商自己声明过就用它的（`from: 'provider'`）；
  请求里给过就用请求的（`from: 'request'`）；**有第二个候选就拒绝**
  （`DERIVE_RUNTIME_TYPE_AMBIGUOUS`）。

> 一个"挑第一个候选"的默认值，
> 与一个"只有一个候选，所以选它"的默认值，
> 在今天**是同一个东西** —— 而它们在上第二个适配器的那一天分开。

判据里有一条专门钉住这件事：把 `supported` 换成 `['dsh', 'codex']`，必须**拒绝**
（`profile-derivation.test.mjs` ⑮）。

### 面板的下拉选项来自服务端

`GET /api/model-providers` 现在返回 `runtimeTypes`，面板渲染下拉时用它 —— 不写死一个 `dsh`：

> 面板里写死的那一份，会在**加上第二个适配器的那天**静默落后，
> 而它的表现是"新运行时永远选不到"（看起来像没做这个功能）。

## 3. 三条纪律（在 `profile-derivation.mjs` 里，都有判据）

1. **身份是 `(provider, model)`，不是 `id`。**
   实测：库里三条 fjd 档案的 id 是 `fjd-ds-deepseek-v4-flash-openai`（连字符），
   而 `profileIdFor` 算出来的是 `fjd-ds.deepseek-v4-flash-openai`（点号）。
   按 id 认身份会让一次派生**多建三条重复档案**，而它们看起来完全正常。
2. **只建缺的，绝不改已有的。** 已存在的档案带着用户的真实选择（推理档位、限额、
   可能的偏离地址/另一把钥匙）。派生**连 `version` 都不动**。
3. **绝不自动删除。** 供应商清单里去掉的模型，对应档案只**报出来**（`orphaned`）。
   自动打墓碑是不可逆方向的动作，该由人决定；而且那条档案可能正被某个岗位绑定引用着。

## 4. 派生的档案天然就是"连接信息只存一份"的形态

派生的档案把 `endpoint` / `secretRef` 写成 **`null`**（留空 ⇒ 从供应商继承，
见 BUG-023 §6）。所以不会为新档案再造一份供应商连接信息的拷贝；
供应商改地址/换钥匙时这些档案自动跟着走。

## 5. 顺带修掉的两处"读出来写不回去"

### ① `get()` 的产物不能直接喂给 `update()`

实测踩到：`供应商不合法：未知字段：source, version, createdAtMs, updatedAtMs, deletedAtMs`。
`get()` 带着簿记字段，而 `normalizeProvider` 对未知字段是**拒绝**（密钥纪律，不能放松）。
新增并导出 `toProviderInput(provider)`：唯一一处"读出来的形状 → 能写回去的形状"的收窄。

> 一个"读出什么就能写回什么"的仓储，
> 与一个"读出来的形状比能写回去的形状多几个字段"的仓储，
> 在**只有手工构造输入**的那些路径上是同一个东西 —— 直到有人真的想读改写一次。

### ② 导入**不许**把 `runtimeType` 抹掉

DSH 的目录里没有这个概念（它的 provider 是 `api`/`baseURL`/`models`），所以快照对这一列
**没有意见**。直接用 NULL 覆盖的后果有两层：用户选的运行时没了，而且指纹判定会把它读成
"内容变了" ⇒ **每次导入都推进一版 version**（P2 影子对账每轮都报"刚改过"）。

同理 `update` 不给 `runtimeType` 时**保留原值**而不是清空：
"没给"读起来是"我对它没意见"，不是"我要把它清掉"。

## 6. 验收

- **纯函数** `resolveRuntimeType` 7 例（唯一候选 / 供应商优先 / 请求次之 / 多候选必拒 /
  空白串 / 去重 / 缺参数拒绝）；`planProfileDerivation` 18 例。
- **路由级** `model-providers-routes.test.mjs` ⑱–㉘（11 例）：保存即生成 / 改供应商只补新增的 /
  缺 `runtimeType` 也照样生成 / 导入也生成 / 老供应商走"补齐"且先给计划 / `dryRun` 一条不写 /
  冲突不覆盖别人的档案 / 孤儿不自动删 / 路由顺序 / `runtimeTypes` 列表。
- **仓储级** `provider-store.test.mjs` 8 例：往返 / NULL 的语义 / 导入不抹掉 / 非法值不落库 /
  收窄函数 / 老库幂等补列。
- 受影响 16 个套件 **328/328 绿**；四道门禁全绿。
- **真机**（那台机器，10 条档案 / 4 个供应商）：
  - 新建供应商一次请求 ⇒ `新增 3`，档案页立刻查得到，`endpoint=null`（继承）、`runtimeType=dsh`；
  - 改供应商加一个模型 ⇒ `新增 1 / 已存在 3`，老档案连 `version` 都不动；
  - 4 个历史供应商全部补齐（运行时写回行上），档案数 6 → 10。

## 7. 仍未做的（诚实登记）

- 面板的「编辑档案」仍然允许改 `provider` / `model`（那会让它偏离自动生成的身份）。
  没有拦，因为**拦**需要决定"改了之后原来那条岗位绑定怎么办"——那是一次产品决定。
- 孤儿档案（供应商清单里已没有的模型）仍然**只能手工删**，面板只提示。
- `model_profiles.provider` 仍然**没有外键约束**。
- `runtime_type` 这一列在老行上是 NULL，直到跑过一次"补齐"才回填；
  读取路径对 NULL 的处理是"用唯一能跑的那个"（有判据），所以功能上不缺，
  但**报表里会看到 NULL**。

## 8. 判断句

> 一份"要用户手打 8 个字段"的登记表，
> 与一台"这些字段全都已经知道"的机器，在**只有一个模型**的时候，差别只是麻烦；
> 在**供应商有 20 个模型**的时候，差别是这件事根本不会被做对。
