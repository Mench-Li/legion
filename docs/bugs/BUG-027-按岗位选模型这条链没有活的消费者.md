## 0. 一句话

系统里有**两个派工引擎**，只有一个在跑；而**在跑的那个从不问"这个岗位用哪个模型"**。

| | 谁在跑 | 它从哪取模型 |
| --- | --- | --- |
| **DSH 插件守护** `@dsh-external/dsh-scrum-worker` | **在跑** | `ctx.agentDefaultModel.currentSelection()` ⇒ DSH 的 `agent-default-model` |
| **Legion orchestrator worker** `product/orchestrator/worker.mjs` | **没在跑** | `employee_model_bindings`（经 `modelProfileRefFor`） |

## 2. 缺口的确切形状

派工那条路**已经为"按岗位覆盖模型"留好了位置**，只是填位置的输入从来是空的：

```ts
// plugins/src/index.ts
const modelRef        = t.agentSelectionSnapshot?.modelConfig ?? null          // :2332
const resolvedModel   = t.agentSelectionSnapshot?.resolvedModelConfig ?? null  // :2333
if (modelRef === null && resolvedModel !== null) throw new Error('任务包含未绑定引用的模型快照；拒绝使用未追溯的模型')
…
modelAgentOptions = agentOptionsForFrozenModel({ modelRef, resolvedModel, … })  // :2436
started = await ctx.subagents.start(selectedProvider, { …, ...(modelAgentOptions === null ? {} : { agentOptions: modelAgentOptions }) })  // :2444
```

即：**任务上没有冻结快照时，`modelAgentOptions` 是 `null`，于是走 provider 的默认模型**
（`agent-default-model` = `fjd-ds / deepseek-v4-flash-openai`）。
分支本身是对的（"没快照 ⇒ 用默认"），缺的是**让快照有值**的那一半。

快照列在 `run_attempts.agent_selection_snapshot`，而 `run_attempts` 是 **0 行** ——
所以这条"按岗位/按任务冻结模型"的路**一次都没被走过**。

## 3. 为什么这不是"迁移一下就好了"

将军最初的直觉是对的：**按岗位分工确实还没生效**。但缺的不是"把数据搬个地方"：

- 迁移把 `agent_models` 的 17 行搬成 `employee_model_bindings` ——
  而那张表**没有任何活的消费者**（见 §1）。搬完 17 行，派工照旧用默认模型。
- 真要让分工生效，要**接线**：在派工前按 `(空间, 岗位)` 解析绑定，把主档案的模型
  （以及备选链、单次预算）装进这次派工的模型选项。

  > 把配置搬到一张没人读的表里，与把配置放到它该在的地方，
  > 在**只做前者**的时候，是同一件事：什么都没变。

## 4. 绑定缺失时怎么办 —— **将军裁决：回落默认模型**（落地时加了一条"不静默"）

两个方向都有真实代价：

| | 表现 | 代价 |
| --- | --- | --- |
| **回落默认模型** | 岗位没绑定也能跑 | 用一个**没人选过**的模型跑完 —— 若不留痕，账面上只表现为"这个月花多了" |
| **拒绝派工** | 缺绑定 ⇒ 任务卡住并说清"去建绑定" | 已有任务会在接线的那一刻**全部停住**，直到 17 条绑定被建好 |

仓库别处的judgment偏向后者（`orchestrator/worker/run-inputs.mjs` 拒绝把"主档案配错"
降级成"备用顶班"：*"备用是为'运行时连不上'准备的，不是为'配置写错了'准备的"*）。

**2026-10-12 将军裁决：回落默认模型**（不拒跑）。落地时因此加了一条自己的纪律：

> 那句话反对的不是"回落"，是"**不报错**"。
> 一个"用了默认模型并且说了出来"的回落，与一个"用了默认模型而没人知道"的回落，
> 在账单上是同一件事，在排障时是两件完全不同的事。

所以 `decideDispatchModel()` 的返回值里 **`note` 是必填的一部分**，守护把它写进
两处：**日志一行**（`<taskId> 派工模型（空间/岗位）：…`）与**派工活动一条**
（`activity('dispatch', …)` ⇒ 工作台的动态流里看得见）。回落时 `note` 一定带 `⚠`，
并**分开报四种原因**（没绑定 / 绑定坏了 / 问不到中枢 / 没配 hubUrl）——四者修法不同。

## 4.1 判定顺序（冻结优先）

1. **任务上有冻结快照 ⇒ 用它。** 冻结的意义就是"这次不许被后改的配置影响"；
   拿实时绑定去覆盖它是**倒退**：同一份审批过的任务会在两次重试里用不同的模型。
2. 没有冻结 ⇒ 按 `(空间, 岗位)` 读 `GET /api/model-bindings/resolve`，命中主档案 ⇒ 用它的 provider/model。
3. 其余情况 ⇒ 回落平台默认模型 + 说清是哪一种（见 §4）。

另外一条：**provider 不支持 `agentOptions` 时也回落，但要说"本来该用哪个"**，
否则"绑定了却没生效"看起来与"没建绑定"一模一样（判据 ⑩ 守着）。

判据：`plugins/tests/dispatch-model.test.mjs` **14 例**（冻结优先 / 绑定命中 / 四种失败分开报 /
链首不是主档案算 broken / provider 能力 / 每次判定都有 note / 回落必带 ⚠ / 坏输入不抛）。

真机判定（2026-10-12，用真实 hub 与真实库、不重启宿主也能做的那一半）：

```
现在（绑定表为空）：
  software/coder        reading=no-binding  source=default-fallback  agentOptions=null
      note: ⚠ 岗位 software/coder 没有模型绑定 ⇒ 这次用了**平台默认模型**（岗位 software/coder 没有被指定的模型）
  software/requirement  同上
  gf001/reviewer        同上
冻结快照在时：source=frozen  agentOptions={"provider":"fjd-ds","model":"deepseek-v4-pro-openai"}
```

## 5. 接线时还要注意（已按这些做）

- **两个空间各有一份 17 行**（`software` / `gf001`），且同一个岗位在两个空间可以要不同模型
  （`gf001/reviewer` = pro，`software/reviewer` = flash）。所以解析按 `(scope, role)` 二元查。
- **守护与 Legion worker 是两套派工**。接的是**在跑的那个**（守护）。
- **聊天回帖那条链**读的是 `agent_models role=assistant`，与派工无关；没有动它。
- `agent_selection_snapshot` 在 `run_attempts` 上（不是 `tasks`）；`tasks` 表里那一列
  是看错列名造成的误判，实测 `non-null = 0/199`，3 条命中只是 `patches` 正文里提到过这个词。

## 7. 同一条链的另一半：**已做完**（2026-10-12）

顺序是按"先接线、再搬、最后拆桥"走的：

1. **接线**（本文件 §4–§5）：守护派工前按 `(空间, 岗位)` 读绑定；
2. **搬一次**：用「配置迁移」把 `agent_models` 的 17 行意图搬进 `employee_model_bindings`。
   真机实测：预演「将新建 0 个模型档案，建立 17 个岗位绑定，17 项按原样保留」→
   执行后绑定表 17 条，判定随之全线翻成 `binding`：

   ```
   software/coder        → fjd-ds/deepseek-v4-flash-openai（主档案 fjd-ds-deepseek-v4-flash-openai）
   software/requirement  → fjd-ds/deepseek-v4-pro-openai
   software/reviewer     → fjd-ds/deepseek-v4-flash-openai
   gf001/reviewer        → fjd-ds/deepseek-v4-pro-openai   ← 同一个岗位在不同空间给不同模型
   不存在的岗位           → default-fallback（⚠ 说明"没有模型绑定"）
   ```

3. **拆桥**：那 17 行搬完之后，「配置迁移」整个功能被删掉
   （模块 / 两条路由 / 面板页签 ① / 两套判据；`/api/model-migration` 命名空间不再存在，
   真机复验 HTTP 404）。它存在的**唯一**价值就是那一刻，用过即拆 ——
   一个"通往已经搬完的房间"的迁移功能，留着只会让人以为那份数据还在两张表之间同步。

> 一座通往还没建好的房间的桥，
> 在房间建好、并且已经走过一次之后，就是**脚手架**。
