# BUG-027｜「按岗位选模型」这条链没有活的消费者 —— 派工永远用同一个默认模型

> 状态：**仅登记**（未修）。修它**会改变派工行为**，所以要先把"哪些岗位会换成哪个模型"看清楚。
> 发现：2026-10-12，将军问「我现在还需要迁移嘛？我不是已经反向写入DSH了嘛」时查出来的
> 影响面（修的时候要动）：`plugins/src/index.ts`（守护的派工路径）、
> `orchestrator/worker/run-inputs.mjs`（Legion worker 那条路）、
> `team-hub/binding-store.mjs`（解析权威）、`employee_model_bindings`（数据）

## 0. 一句话

系统里有**两个派工引擎**，只有一个在跑；而**在跑的那个从不问"这个岗位用哪个模型"**。

| | 谁在跑 | 它从哪取模型 |
| --- | --- | --- |
| **DSH 插件守护** `@dsh-external/dsh-scrum-worker` | **在跑** | `ctx.agentDefaultModel.currentSelection()` ⇒ DSH 的 `agent-default-model` |
| **Legion orchestrator worker** `product/orchestrator/worker.mjs` | **没在跑** | `employee_model_bindings`（经 `modelProfileRefFor`） |

## 1. 现场读数（2026-10-12）

```
守护活着：scrum/daemon-software.json  lastSweepAt=2026-10-12T03:24:10Z  paused=false
                                   model={"provider":"fjd-ds","model":"deepseek-v4-flash-openai"}
           scrum/daemon-ozon.json      lastSweepAt=2026-10-12T03:24:07Z（同样在跑）

Legion 运行面从没被用过：run_attempts 行数 = 0（其中带冻结模型快照 = 0）
                         processes 里没有 product/orchestrator/worker.mjs

守护的源码里**一次都没问过** hub 的"岗位→模型"：
  plugins/src/**  里匹配 model-bindings / employee_model_bindings / primaryProfile = **0 处**

绑定的读点（全仓）只有三个，全都不在派工路径上：
  · GET /api/model-bindings（给界面看）
  · 配置包导出 / 导入
  · 迁移自己（写）
```

而**意图是存在的**，就在老表里：

```
agent_models（17 行，2 个空间）
  software/coder        → fjd-ds / deepseek-v4-flash-openai
  software/requirement  → fjd-ds / deepseek-v4-pro-openai
  software/reviewer     → fjd-ds / deepseek-v4-flash-openai
  gf001/reviewer        → fjd-ds / deepseek-v4-pro-openai     ← 同一个岗位在两个空间要不同的模型
```

**这 17 行现在只被一条链读**：聊天回帖的模型解析
（`team-hub/server.mjs` 的 `settings.model → agent_models role=assistant → 守护心跳`），
而且它只读 `role=assistant`（全库 2 行）。**派工不读它。**

## 2. 缺口的确切形状

派工那条路**已经为"按岗位覆盖模型"留好了位置**，只是填位置的输入从来是空的：

```ts
// plugins/src/index.ts
const modelRef        = t.agentSelectionSnapshot?.modelConfig ?? null          // :2332
const resolvedModel   = t.agentSelectionSnapshot?.resolvedModelConfig ?? null  // :2333
if (modelRef === null && resolvedModel !== null) throw new Error('任务包含未绑定引用的模型快照；拒绝使用未追溯的模型')
…
modelAgentOptions = agentOptionsForFrozenModel({ modelRef, resolvedModel, … })  // :2436
started = await ctx.subagents.start(selectedProvider, { …, ...(modelAgentOptions === null ? {} : { agentOptions: modelAgentOptions }) })  // :2444
```

即：**任务上没有冻结快照时，`modelAgentOptions` 是 `null`，于是走 provider 的默认模型**
（`agent-default-model` = `fjd-ds / deepseek-v4-flash-openai`）。
分支本身是对的（"没快照 ⇒ 用默认"），缺的是**让快照有值**的那一半。

快照列在 `run_attempts.agent_selection_snapshot`，而 `run_attempts` 是 **0 行** ——
所以这条"按岗位/按任务冻结模型"的路**一次都没被走过**。

## 3. 为什么这不是"迁移一下就好了"

将军最初的直觉是对的：**按岗位分工确实还没生效**。但缺的不是"把数据搬个地方"：

- 迁移把 `agent_models` 的 17 行搬成 `employee_model_bindings` ——
  而那张表**没有任何活的消费者**（见 §1）。搬完 17 行，派工照旧用默认模型。
- 真要让分工生效，要**接线**：在派工前按 `(空间, 岗位)` 解析绑定，把主档案的模型
  （以及备选链、单次预算）装进这次派工的模型选项。

  > 把配置搬到一张没人读的表里，与把配置放到它该在的地方，
  > 在**只做前者**的时候，是同一件事：什么都没变。

## 4. 接线时必须先回答的一个问题：绑定缺失时怎么办

这是修这个 bug 最容易做错的一处，两个方向都有真实代价：

| | 表现 | 代价 |
| --- | --- | --- |
| **回落默认模型**（今天的实际行为） | 岗位没绑定也能跑 | 用一个**没人选过**的模型静默跑完，而且不报错。同一件事在账单上只表现为"这个月花多了" |
| **拒绝派工**（仓库既有纪律） | 缺绑定 ⇒ 任务卡住并说清"去建绑定" | 已有任务会在接线的那一刻**全部停住**，直到 17 条绑定被建好 |

仓库既有的judgment在别处是同一条（`orchestrator/worker/run-inputs.mjs` 拒绝把"主档案配错"
降级成"备用顶班"：*"备用是为'运行时连不上'准备的，不是为'配置写错了'准备的"*；
`defaultRequestFor()` 也不猜 workspace/模型/目录）。所以**接线的方向应当是"拒绝 + 说清"**，
但那意味着**接线与建绑定必须同一次做完**，否则任务当场停摆。

## 5. 修的时候还要注意

- **两个空间各有一份 17 行**（`software` / `gf001`），且同一个岗位在两个空间可以要不同模型
  （`gf001/reviewer` = pro，`software/reviewer` = flash）。按 `(scope, role)` 查是必需的。
- **守护与 Legion worker 是两套派工**。要接线的是**在跑的那个**（守护）。
- **聊天回帖那条链**读的是 `agent_models role=assistant`，与派工无关；
  接线时不要顺手把它一起改掉（那会让"回帖用什么模型"与"士兵用什么模型"互相影响）。
- `agent_selection_snapshot` 在 `run_attempts` 上（不是 `tasks`）；`tasks` 表里那一列
  是我看错列名造成的误判，实测 `non-null = 0/199`，3 条命中只是 `patches` 正文里提到过这个词。

## 6. 判断句

> 一条"已经留好了位置、但输入永远是空"的分支，
> 与一条"根本没写"的分支，在**没人往那个位置放东西**的时候，跑的是同一段代码。
