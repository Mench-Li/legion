# BUG-028｜供应商列表把**引用名**发给了客户端（档案那边已经不发）

> 状态：**已修（2026-10-12）**。修法与验收见 §4–§5，另有 4 处变异验证。
> 发现：2026-10-12，拆「配置迁移」时把一条既有判据
> （`config-bundle-routes.test.mjs` 用例 ④「整条链路上任何响应体都不含密钥字面量」）
> **扩容**到 `/api/model-providers`，当场报出两条：
> 一条是**那次改出来的**（档案列表的 `credential.ref`，同批修掉）、一条是**既有的**（本文件）。
> 修的时候动了：`team-hub/routes/model-providers.mjs`、`team-hub/provider-store.mjs`、
> `team-hub/server.mjs`、`services-plugin/materializer.mjs`、
> `workbench/src/components/DshProvidersPanel.tsx` 与四套判据。

## 0. 一句话

`GET /api/model-providers` 的每一行都带 `secretRef` 原文，而档案那一族（`/api/model-profiles`）
只发 `credential.hasRef` —— 同一个密钥库、同一套引用名，两个端点两种口径。

## 1. 现场证据

判据 ④ 的前置自检（`hasRef: true` 证明库里这一行确实有引用名）之后：

```
AssertionError: ★ 供应商那一行本身也不该把引用名带出去：
  `secretRef` 与 `credential.hasRef` 说的是同一件事，前者多给了名字
```

## 2. 为什么值得修（而不是"反正要登录"）

本仓的纪律写在 `team-hub/model-store.mjs` 的文件头 ②，逐字是：

> `get(id)` 返回**抹掉 `secretRef`** 的 descriptor；`internalGet(id)` 才带它。
> 引用名也是**可枚举的攻击面**。

引用名不是密钥，所以这不是"泄漏了一把钥匙"。它泄漏的是**密钥库的槽位名**
（`FJD_DS_API_KEY`、`SVEA_DS_API_KEY`…）。两个真实后果：

1. **可枚举**：任何能读这一页的人可以列出这台机器上配了哪些凭证槽位；
2. **两份口径**：同一个库里同一种东西，档案端点抹掉、供应商端点不抹掉 ——
   而"按端点分别决定"正是纪律被忘掉的方式：

   > 一条"这个端点不吐引用名"的规矩，
   > 与一条"那个端点也吐了但它不是同一个端点"的解释，
   > 在下一个新增读端点的人看来是一样的。

## 3. 为什么不是一行删掉就完

面板**依赖**它保留编辑态（旧写法）：

```tsx
const keyRef = editing?.secretRef ?? defaultKeyRef(id)                       // 旧 :250
baseURL: ..., secretRef: form.key || editing?.secretRef ? keyRef : null,     // 旧 :262
```

即：用户只改显示名、没重新填密钥时，面板靠 `editing.secretRef` 把原名回传；
**不回传就等于把这条供应商的凭证清掉**。而第三处（面板）还牵出一条**内部消费者**：

**物化 / 影子对账**（`services-plugin/materialize-plan.mjs`）要把 Legion 的 `secretRef`
与 DSH 的 `apiKeyEnv` 归一化成同一个东西来比。名字一没了，Legion 侧会读成
"没有引用名"，**每一轮对账都报差异** —— 而"每轮都报差异"会让人把这道读数关掉，
那才是真正丢掉的东西（P1/P2 的可观测性就是它）。

## 4. 修法（四件事）

### ① 出站只有一个出口

`routes/model-providers.mjs` 的 `publicProvider(p)`：抹掉 `secretRef`，留
`credentialRequired`（"这条引用了一个凭证"）。**列表 / 创建 / 更新 / 导入**四个响应全过它 ——
"每个端点各自记得抹掉"与"有一个统一的出口"不是同一件事：前者在**新加一个端点**的那天就失效。

### ② "没给"与"给 null"分开（`provider-store.mjs` 的 `update`）

```js
const secretRef = Object.prototype.hasOwnProperty.call(input, 'secretRef')
  ? p.secretRef            // 显式给了（含 null）⇒ 按它来，null 就是"清掉"
  : existing.secretRef     // 没给 ⇒ 保留原值
```

这一条是 ① 的**前提**：读侧不给名字之后，"只改显示名"那次保存**必然不带** `secretRef`。
若那被当成"清掉"，用户会在毫无提示的情况下丢凭证引用。

### ③ 槽位名由**服务端**决定（面板零引用名）

客户端要写新钥匙，但它没有名字（也不该有）。于是请求带 `credentialValue`（明文值），
服务端用**那一行已有的**名字（可能是 DSH 导进来的 `apiKeyEnv`，两侧靠它对齐），
没有才用 `defaultSecretRefFor(id)`。判定下沉为纯函数
`resolveCredentialRef({ existingRef, id })`。

- "清掉"是显式的：`clearCredential: true`；
- 没接密钥库的部署**具名拒绝**（`SECRET_STORE_NOT_WIRED`），不静默忽略 ——
  静默忽略的表现正是"面板说保存成功、钥匙其实没进去"。

### ④ 内部消费者走**带鉴权**的第二读法（两读口径）

`GET /api/model-providers?includeSecretRefs=1`：默认那一份**没有名字**；
要名字必须过 `authorized`（那个部署的机器令牌）。判定是模块级导出的纯函数
`mayReadSecretRefs({ wantRefs, authorized, req })`，**没注入 authorized 就拒绝**。

这正是 `model-store.mjs` 的 `get` / `internalGet` 在 HTTP 层的对应物。物化那条路本来
就带令牌，所以只多一个参数；而没带令牌的读法拿不到名字。

> 一个"谁都能读、顺手也能读到槽位名"的读端点，
> 与一个"谁都能读、但槽位名要令牌"的读端点，在**没设令牌的部署**上是同一个东西
> —— 而那种部署本来就把整个中枢开放着，所以这不是新的泄漏面。

## 5. 判据与验收

- `provider-store.test.mjs` ⑨（4 条）：没给 ⇒ 保留 / 显式 null ⇒ 清掉 / 给了新的 ⇒ 换 / 新建 ⇒ null；
  ⑩（5 条）：已有名字优先、派生名、派生规则形状、id 空 ⇒ 具名报错、空白不算已有；
- `model-providers-routes.test.mjs` ⑮⑯⑱：默认读**没有** `secretRef` 键、带参数（已过令牌）能拿到、
  `mayReadSecretRefs` 三种输入逐一验、只改显示名不丢凭证、显式 `clearCredential` 真的清掉；
- `config-bundle-routes.test.mjs` ④（**翻转**）+ ④b（2 条）：所有响应都不含引用名（不再有豁免）、
  值不回显、失败必须具名；
- `materializer.test.mjs` ⑲（2 条）：物化读 Legion 目录**必须**带 `includeSecretRefs=1`
  （否则对账永远报差异）+ 反向锚（引用名真的进了归一化结果）。

**变异验证**（把错误写法放回去，确认判据会红）：

| 变异 | 结果 |
| --- | --- |
| 列表整行原样返回（回到修之前） | ✔ 红 |
| `update` 回到"没给 secretRef 就清掉" | ✔ 红 |
| `includeSecretRefs` 不再校验令牌 | ✔ 红 |
| 物化带令牌那一支丢掉 `includeSecretRefs=1` | ✔ 红（★ 第一版判据漏掉了它 —— 见 §6 第 3 条） |

## 6. 修的过程中踩到的三件事（都值得记）

1. **判据扩容前它是瞎的**：用例 ④ 原先只列 4 个端点，"新加了会泄漏的端点"与
   "没有任何端点泄漏"在它的读数里是同一个东西。**端点靠手列**是这条判据的结构缺陷
   （彻底的解法是按键名遍历所有读路由，那是另一件事）。
2. **"改了读侧"会打到谁，只有查过才知道**：物化那条链靠 `secretRef ↔ apiKeyEnv` 对齐。
   只删字段不补第二读法，症状会是"每轮对账都报差异"——
   一个**看起来像**"配置真的不一致"的假读数。
3. **夹具的盲点会伪装成判据的通过**：⑲ 第一版用 `enabled: false` ⇒ 门关着时根本不读目录，
   "没请求"被误读成"没带参数"；第二版没传 `teamHubToken` ⇒ 变异打不中。
   两次都是夹具的问题，不是被测代码的问题 —— 而两次都只有**变异验证**才暴露出来。

## 7. 判断句

> 一个"要登录才能看"的字段，
> 与一个"登录之后就不必再管"的字段，
> 在**谁来读这一页**这件事上是两回事；
> 而在**纪律是否还成立**这件事上是同一回事。
