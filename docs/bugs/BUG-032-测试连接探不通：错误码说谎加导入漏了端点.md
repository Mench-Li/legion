# BUG-032｜"测试连接"探不通一部供应商：错误码说谎 + 导入漏了端点

> 状态：**仅登记（未修）**
> 发现：2026-10-12，将军问「轮换有什么意义」时，实测「测试连接」在不同档案上给出不同结果，
> 于是逐条追下去。影响面：`team-hub/probe-service.mjs`、
> `services-plugin/dsh-snapshot.mjs`（导入）＋ `model_profiles.endpoint`。

## 0. 现场

同一次会话里，同一个中枢、四个供应商，两个能测、两个不能：

```
POST /api/model-profiles/fjd-ds-deepseek-v4-flash-openai/probe      → 200  ok=true  "连通且具备所需能力"
POST /api/model-profiles/svea-ds.deepseek-v4-pro-openai/probe       → 200  ok=true  "连通且具备所需能力"
POST /api/model-profiles/deepseek-official.deepseek-v4-pro/probe    → 503  code=PROBE_LAYOUT_BLOCKED
POST /api/model-profiles/deepseek-official.deepseek-flash/probe     → 503  code=PROBE_LAYOUT_BLOCKED
```

那 503 的正文是：

```
{"error":"无法测试连接：这个档案没有填 endpoint。**这次没有探测过**。","code":"PROBE_LAYOUT_BLOCKED"}
```

**码说的是"布局"，话说的却是"没填 endpoint"。** 两者不可能同时为真。

## 1. 缺陷 ①：错误码说谎（`probe-service.mjs:192`）

那个码的定义写在同一个文件里（`:46-53`）：

```js
export const PROBE_UNAVAILABLE_CODES = Object.freeze({
  /** 布局不合法（密钥库位置本身是错的） */
  LAYOUT_BLOCKED: 'PROBE_LAYOUT_BLOCKED',
  ...
})
```

而用它的地方（`:190-195`）是：

```js
// 没有 endpoint 就没法探。这是**配置缺失**，不是供应商故障。
const endpoint = typeof profile.endpoint === 'string' ? profile.endpoint.trim() : ''
if (endpoint === '') {
  return unavailableResult(PROBE_UNAVAILABLE_CODES.LAYOUT_BLOCKED, '无法测试连接：这个档案没有填 endpoint。…')
}
```

**注释自己都写着"这是配置缺失"**，而码给的是"密钥库位置本身是错的"。

### 为什么这不只是措辞问题

`code` 是给机器读的那一半：客户端按它分支（"密钥库打不开" vs "这条配置不全"），
而两者**下一步动作完全相反** —— 一个是去修布局/权限，一个是去补一个地址。

> 一个"我这次没法探"的拒绝，与一个"你的库位置不对"的拒绝，
> 在状态码与正文上都可以是正确的，而在**码**上是两件事 ——
> 只要有人按码分支，他就会去修错的那一件。

★ 今天**还没有**客户端按这个码分支（`PROBE_LAYOUT_BLOCKED` 在全仓只有这一个生产者），
所以它是**潜伏**的：面板显示的是正文（所以用户看到的是对的），
而任何一个按码做的自动化/新客户端会走错路。

⚠ 也**不要**顺手把它改成 `NO_CREDENTIAL_REF` —— 那是"档案没有 secretRef"，
与"没有 endpoint"是两件不同的配置缺失。要么新增一个具名的码，
要么让 `unavailableResult` 的 `detail` 承担这个区分（现在是 `{ detail: 'endpoint' }`，
但它不进制）。

## 2. 缺陷 ②：导入没捕获"内置默认端点"（更严重）

为什么 `deepseek-official` 的档案没有 endpoint？因为它的**供应商行**没有 baseURL：

| 供应商 | Legion 里的 baseURL | 它在 DSH 那边怎么来的 |
| --- | --- | --- |
| `fjd-ds` | `https://fjbigmodel.fjdac.cn/v1` | 用户写在 `cordis.patch.yml` 的 `llm-pi-ai` 里（显式 `baseURL`） |
| `svea-ds` | `https://fjbigmodel.fjdac.cn/v1` | 同上 |
| `deepseek-official` | **null** | DSH **内置插件**（`llm-deepseek`），端点来自插件自己的默认值 |
| `deepseek-account` | **null** | DSH **内置插件**（`deepseek-account-platform`），同上 |

也就是说：**凡是"端点由 DSH 插件内置、没有写进 patch"的供应商，导入进来就没有地址。**

两个后果：
1. **它的所有档案永远探不通** —— 而且报的是上面那个错的码（缺陷 ① 把真因盖住了）；
2. **物化开着时**（`LEGION_APPLY_MODEL_CONFIG=1`）可能会写出一份**没有地址**的供应商配置
   —— 而那会把一个本来能用的供应商写坏。处置物化那一批之前**必须先修这一条**。

### 修法的两个方向（要裁决哪一个）

- **甲：导入时读 DSH 的"实际生效值"**。`ctx.llm` / `settings.describe` 给的是**声明**，
  内置插件的默认值不在里面 ⇒ 要么从宿主 API（`llm/discoverModels` 那条）反推，
  要么让"没有地址"保持为空但**在档案上显式标注"端点来自引擎内置默认"**；
- **乙：不要为"地址来自引擎内置"的供应商派生档案**（它们在 Legion 里没有可用的坐标，
  派生出来的档案只会误导）。

★ 无论选哪条，都有一条**共同的底线**：**不能把"我不知道地址"当成"这条没有地址"**
（与 `credential-status.mjs` 纪律 ① 同族）。今天 `endpoint: null` 同时意味着
"确实没配"与"端点由引擎内置、我没读出来" —— 这两件事在库里长得一模一样。

## 3. 判断句

> 一个"我这次没法探"的拒绝，
> 与一个"你的库位置不对"的拒绝，在码上必须是两件事；
> 而一个"确实没配地址"的档案，
> 与一个"地址在引擎里、我没读到"的档案，在库里也必须是两件事 ——
> 否则修的人会朝着错的那一件去。
