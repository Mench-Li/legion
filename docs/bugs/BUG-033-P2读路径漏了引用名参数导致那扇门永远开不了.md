# BUG-033｜那扇门永远开不了：P2 读路径漏了一个查询参数

> 状态：**已修**（2026-10-12）
> 影响面：`services-plugin/shadow-materialize.mjs`（读 Legion 目录那一次请求）
> 判据：`services-plugin/shadow-materialize.test.mjs` ⑪b（+ 既有 `materializer.test.mjs` ⑲）

## 0. 一句话

影子对账读 Legion 目录时**只带了令牌、漏了 `includeSecretRefs=1`**，
于是 Legion 侧的每一行都"没有引用名"⇒ 与 DSH 侧的真名字比**永远不等**
⇒ **决策文档 P2→P3 的放行条件（"连续几轮 diff 为空"）永远不可能满足**。

## 1. 怎么抓到的（一次"把差异做成看得见的"立刻回本）

在此之前，这份差异**只活在一行日志里**，而且只有计数：

```
[2026-10-12T09:15:01Z] 供应商影子对账：新增 0 / 修改 3 / 删除 0 / 未变 1（clean=false）
```

那一天我先把它做成**读数**（`GET /api/model-materialization`），重启后第一次读到的就是：

```
修改 3
update = [
  { deepseek-official, fields: [apiKeyEnv] },
  { fjd-ds,            fields: [apiKeyEnv] },
  { svea-ds,           fields: [apiKeyEnv, models] }
]
```

**两个立刻可用的结论**：
1. 差异字段**全是 `apiKeyEnv`** —— 而 `fjd-ds` 两侧明明都是 `FJD_DS_API_KEY`
   ⇒ 这不是"它真的不一样"，而是"**Legion 侧那一份读不到引用名**"；
2. `svea-ds` 多一处 `models` —— 那是我自己改协议时回传模型只带了 `id`（同批已修）。

  > 把差异从"一行计数"变成"改哪几个字段"，
  > 是这一整条链上**第一次**让人能看着数据判断"该不该开门"。

## 2. 根因与为什么一直没被发现

hub 的默认读法**不含引用名**（那是密钥库的槽位清单，不该跟着读路径公开，见 `BUG-028`）；
要拿它必须显式带 `includeSecretRefs=1` 并且过令牌。**同一个参数在 P3 写路径
（`materializer.mjs`）里早就加了，还配了判据 ⑲；P2 读路径漏了**：

```
materializer.mjs       : '?token=…&includeSecretRefs=1'   ✅ 有判据 ⑲
shadow-materialize.mjs : '?token=…'                        ❌ 漏了 —— 而它才是喂给门禁的那一份
```

  > 一处"我读了另一份"的缺口，与一处"它真的不一样"的差异，
  > 在同一行 `修改 N` 里长得一模一样 ——
  > 只不过前者**永远不会消失**，而门禁的放行条件正是"它消失"。

而它之所以长期没被发现，还有第二层原因：**这条读路径的差异没有消费者**。
`materializer` 那一侧的异常会导致"写坏"，所以有人盯着；而 P2 只报告、不写，
于是"报错了"看起来无害 —— 直到有人真的要按它开门。

## 3. 修法（两处，缺一不可）

1. `shadow-materialize.mjs` 的 URL 带上 `&includeSecretRefs=1`（带/不带令牌两支都带）；
2. **两条路径各钉一条判据**：`materializer.test.mjs` 的 ⑲ 与新增的
   `shadow-materialize.test.mjs` ⑪b。只钉一处的话，**下一次还是会漏另一侧**。

⑪b 里还带一条**反向锚**：用同一份夹具，**不带**参数时恰好只报
`[{ id: 'fjd-ds', fields: ['apiKeyEnv'] }]`（与真机读数逐字一致）、**带上立刻 clean**
—— 把"一处参数 = 门能不能开"的因果钉完整，而不是只断言字符串里有那个参数。

## 4. 判断句

> 一个"永远报差异"的对账，与一个"真的总有差异"的对账，
> 在读数上是同一行；
> 而前者会让门永远关着 —— 关着的那扇门不报错，它只是**什么都不发生**。
