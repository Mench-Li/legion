# BUG-035｜热重载之后，插件的写入会**永久**失败（而且日志把没写说成"写坏了"）

> 状态：**未修**（已确证无害，但机制与文案都要修）
> 影响面：`services-plugin/index.js`（启动即建调度器）＋ `services-plugin/materializer.mjs` 的错误文案
> 实测：2026-10-12 18:00 / 18:06 两轮，`LEGION_APPLY_MODEL_CONFIG` 打开后
> （把它记下来是因为它**恰好发生在"开门"的那一刻**，任何人照这个流程做都会撞上）

## 0. 现象

改了 `cordis.patch.yml`（加 `applyModelConfig: true`）**而没有立刻重启** ⇒ 宿主热重载配置
⇒ 之后每 5 分钟一轮，全部长这样：

```
[09:55:59Z] 供应商影子对账：新增 0 / 修改 1 / 删除 0 / 未变 3（clean=false）
[09:55:59Z] 模型配置物化：写入失败（HMR transactions cannot be nested）→ 尝试回滚
[09:55:59Z] 模型配置物化：**回滚也失败了**（HMR transactions cannot be nested）
            —— DSH 的配置现在既不等于 Legion 的、也不等于改动前的，需要人工看一次
[10:00:59Z] …（同上）
[10:06:00Z] …（同上）
```

## 1. 机制（读 DSH 源码得出）

```ts
// packages/boot/config-editor/src/index.ts:153 —— 每一次配置编辑都包在这一层
await (hmr === undefined ? run() : hmr.runExclusive(run))

// packages/boot/hmr/src/index.ts:262-263 —— **已在事务里就立刻拒绝**
runExclusive(operation) {
  if (this.executing.getStore()) return Promise.reject(new Error('HMR transactions cannot be nested'))
  …
}
```

`executing` 是 `AsyncLocalStorage<boolean>`。配置热重载走 `runReload → runExclusive`，
于是**刷新过程中被重新初始化的插件是"在事务里"跑的**；而
`services-plugin/index.js` 在启动路径上就建好那个每 5 分钟一轮的调度器 ——
`AsyncLocalStorage` 的上下文**会被它创建的定时器回调继承**（这是 ALS 的定义行为，
不是实现细节）。⇒ **之后每一轮都仍然"在事务里"** ⇒ 每一次写入都被立刻拒绝。

**⇒ 它不是一次抖动，而是"到这个进程死掉为止"。** 唯一的解法是重启宿主。

## 2. 为什么"没有写坏"是可证的（而不是靠那句日志）

两件事叠起来：

1. `runExclusive` 在**已有的那一支**上是 `return Promise.reject(...)` —— **在任何工作开始之前**
   就拒绝了。所以 `settings.mutate` 的那次编辑从未开始；
2. 落盘目标是 `<profile.home>/settings.yaml`（`packages/settings/settings/src/index.ts:243`），
   而实测两个候选位置**都不存在**：
   `~/.dsh/settings.yaml` ❌ ｜ `~/.dsh/profiles/desktop/settings.yaml` ❌
   —— **一次成功的写入必然创建它**（这份部署里它从来不存在，因为 llm-pi-ai 的声明在 patch 里）。

⇒ 那句"既不等于 Legion 的、也不等于改动前的"是**误报**：它把
"被拒之前什么都没做"与"改了一半"看成了同一种。fail-safe 的方向没错，但**话是错的**，
而"需要人工看一次"这种指令会让人去做一件没有必要的事。

## 3. 该修的两处（这一轮**没有**修，先记账）

1. **机制**：插件**不该在启动路径（可能在 HMR 事务里）上就跑写入**。
   可选方向：把首轮物化推迟到事务结束之后（例如等一次 `setTimeout(0)` 之外的、由宿主确认 ready 的信号），
   或者干脆"热重载之后只报告、不写，直到下一次真正的冷启动"——后者更保守，也更符合
   "写入永远不该从一次重载里冒出来"这条直觉。

   > 一次"配置刚变"的重载，与一次"用户要求接管"的启动，
   > 在插件看来是同一个回调 —— 而**只有后者**该允许写。

2. **文案**：`materializer.mjs` 的失败/回滚文案要能区分
   "写入从未开始（可证没写）"与"写了一半、回滚也失败（真的要看）"。
   今天两者是同一句话，于是**真的需要看**的那一刻会被淹在假警报里。

## 4. 与 `applyModelConfig` 的关系（给操作者的结论）

**改 `cordis.patch.yml` 之后必须重启宿主**，不能指望热重载让写入生效 ——
热重载会让这个进程的写入路径**永久失效**（虽然方向是安全的：什么都没写）。
