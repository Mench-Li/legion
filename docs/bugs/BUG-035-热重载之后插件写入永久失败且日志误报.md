# BUG-035｜插件的写入**从来没成功过**：热重载把 HMR 事务上下文留在了调度器里

> 状态：**未修**（已确证无害，但"配置写进 DSH"这条能力**今天不工作**）
> 影响面：`services-plugin/index.js`（启动即建周期调度器）
> ＋ `services-plugin/materializer.mjs`（失败文案把"没写"说成"写坏了"）
> 实测：2026-10-12，宿主 18:12:09 冷启动之后（端到端验证时抓到）

## 0. 结论先说

**`LEGION_APPLY_MODEL_CONFIG` 打开也没用** —— 每一次写入都会在**开始之前**被 DSH 拒绝：

```
模型配置物化：写入失败（HMR transactions cannot be nested）→ 尝试回滚
模型配置物化：**回滚也失败了**（HMR transactions cannot be nested）
              —— DSH 的配置现在既不等于 Legion 的、也不等于改动前的，需要人工看一次
```

**最后那句是误报**：在**任何工作开始之前**就拒绝了，所以一个字节都没写（§3 有可证证据）。

## 1. 为什么是"从来没成功过"，而不是"偶尔抖动"

原本我以为它只在**手工改配置触发热重载**之后出现。端到端验证把这句话推翻了一半 ——
看 `~/.dsh` 插件日志里那次冷启动的完整序列：

```
[10:12:13.009] legion-services 挂载            ← 第一次挂载
[10:12:15.362] 供应商影子对账：…（clean=true）
[10:12:15.421] 模型配置物化：已启用，但本轮无差异
[10:12:15.422] 模型配置收敛：周期已启用，每 300 秒一轮
[10:12:16.228] legion-services 已随宿主停止（…周期收敛已停）   ← ★ 1.8 秒后就被回收
[10:12:16.242] legion-services 挂载            ← ★ 又挂了一次（热重载）
[10:12:18.541] 模型配置收敛：周期已启用，每 300 秒一轮          ← 活下来的是这一次的调度器
[10:17:18.719] 供应商影子对账：修改 1
[10:17:19.187] 模型配置物化：写入失败（HMR transactions cannot be nested）
```

也就是说：**每次启动都会紧跟着发生一次重载**（第一次挂载被立刻回收、第二次才是活的）。
于是"热重载之后写入失效"实际上等价于"**写入永远失效**"。

## 2. 机制（读 DSH 源码得出）

```ts
// packages/boot/config-editor/src/index.ts:153 —— 每一次配置编辑都包在这一层
await (hmr === undefined ? run() : hmr.runExclusive(run))

// packages/boot/hmr/src/index.ts:262-263 —— **已在事务里就立刻拒绝**
runExclusive(operation) {
  if (this.executing.getStore()) return Promise.reject(new Error('HMR transactions cannot be nested'))
  …
}
```

`executing` 是 `AsyncLocalStorage<boolean>`。重载走 `runReload → runExclusive`，
于是**在重载事务里被重新初始化的插件是"在事务里"跑的**；
而 `services-plugin/index.js` 在启动路径上就建好那个每 5 分钟一轮的调度器 ——
`AsyncLocalStorage` 的上下文**会被它创建的定时器回调继承**（这是 ALS 的定义行为），
而调度器是递归 `setTimeout`，于是**每一次后续唤醒都仍然在事务里**。

  > 一个"我在事务里"的标记，与一个"我是在那次重载里被建出来的"事实，
  > 在被建出来的那一刻是同一个读数；
  > 而它们分叉的地方是**那个标记永远跟着这个进程** ——
  > 于是这个进程此后**一次也写不进去**。

## 3. 为什么"没有写坏"是可证的（而不是靠那句日志）

两件事叠起来：

1. `runExclusive` 在**已有的那一支**上是 `return Promise.reject(...)` —— **在任何工作开始之前**
   就拒绝了，所以 `settings.mutate` 的那次编辑从未开始；
2. 落盘目标是 `<profile.home>/settings.yaml`（`packages/settings/settings/src/index.ts:243`），
   而实测两个候选位置**都不存在**（写入前、写入失败后各查一次）：

```
~/.dsh/settings.yaml                   不存在
~/.dsh/profiles/desktop/settings.yaml  不存在
```

   一次**成功**的写入必然创建它（这份部署里它从未存在，因为 llm-pi-ai 的声明在 patch 里）。

⇒ 那句"既不等于 Legion 的、也不等于改动前的，需要人工看一次"**是错的**，
而它错的方向有害：它把"被拒之前什么都没做"说成"改了一半"，
让操作者去做一件没有必要的事 —— 而**真的**需要人工看的那一刻，会被淹在假警报里。

## 4. 该修的两处

1. **机制（必须先修）**：写入**不能**从"在重载事务里建出来的调度器"上发起。
   可选方向：
   - **甲**：把发起写入的时点挪到事务之外（例如由一次**外部触发**驱动：
     面板上的"立即同步"按钮 → 经宿主的请求路径调进来，那条路径的异步上下文来自 HTTP 服务、
     不在 HMR 事务里）；
   - **乙**：插件在写入前**先探一次**自己是否在事务里（能探到就推迟到下一次冷启动之后），
     探不到就**只报告、不写** —— 保守，且与"写入永远不该从一次重载里冒出来"这条直觉一致；
   - **丙**：改走宿主已有的 HTTP 通道（`settings/mutate` / `credentials/set`，见
     `workbench/scripts/dsh-models-bridge.mjs`）—— ⚠ 这与 `DECISION-legion-owns-model-config.md`
     记下的"走进程内、不经 HTTP/登录"那条**相反**，所以要修的是决策，不是偷偷换路。
2. **文案**：失败与回滚的文案要能区分
   "写入从未开始（**可证没写**）"与"写了一半、回滚也失败（**真的要看**）"。
   今天两者同一句话。

## 5. 给操作者的结论

- 现在打开 `applyModelConfig` **不会**让配置写进 DSH，只会每 5 分钟产出一条假警报；
- **改 `cordis.patch.yml` 之后必须重启宿主**（热重载会让这个进程的写入路径永久失效）；
- 但**重启也救不了** —— 重启之后紧跟的那次重载同样会让新的调度器落在事务里。

## 6. 端到端验证的账（这一次是怎么确认的）

1. 记下写入前基线：`settings.yaml` 两处均不存在；patch 与 `~/.dsh/.credentials.yaml` 的哈希；
2. 在 Legion 改一处（`svea-ds` 的 `displayName` → `SVEA-DS（接管验证）`，经 API、带 version、
   进审计），先**预演**：`update=[{svea-ds,[displayName]}]`、`delete=[]` —— 只一处；
3. 等下一轮（10:17:18）：对账报 `修改 1`，物化**写入被拒**（本 bug）；
4. 收尾：把 `displayName` 改回原值（`version 9`），再查一次 —— `settings.yaml` 仍不存在、
   patch 与凭证文件哈希未变。**测试没有留下任何痕迹。**

## 7. 判断句

> 一次"配置刚变"的重载，与一次"用户要求接管"的启动，
> 在插件看来是同一个回调；
> 而**只有后者**该允许写。
> 把这两件事分开之前，那道开着的门只是一个读数 —— 不是一个能力。
