# BUG-040：审查阶段按 main 的新基线导入旧冻结提交，必冲突且整条阶段停摆

## 现象

T-219（代码审查·返工第 3 轮）在依赖解除后被守护认领，7 秒后自己转 `in_review` 并留评论：

```
⛔ 工作流上游版本核验失败，已停止自动派工：
Error: 导入上游阶段 implement 的冻结提交失败（合并已回滚）：
CONFLICT (content): Merge conflict in workbench/mobile/app.mjs
```

此后每 30 秒认领一次、每次都停在同一处 —— 不是偶发，是必现。

## 根因

两个事实叠在一起：

1. 审查阶段的工作区由 `prepareWorktree` **从 main 的 HEAD** 建分支（`git worktree add -b w/T-219 … HEAD`）；
2. 建完分支后才调 `materializeWorkflowCheckpoints` 把上游冻结提交 merge 进来。

上游冻结提交 `073ba1c6` 基于 `46821a46`（T-216 的旧提交）；而 main 在两轮之间
推进到了 `26f48561`，**改的正是 `workbench/mobile/app.mjs` 的同一段**。
于是「从 HEAD 建的分支」与「旧基线的冻结提交」做三方合并时，同段代码双方都改过
⇒ 冲突 ⇒ 自动回滚 ⇒ 抛错 ⇒ 派工中止。

冻结提交本身没有问题（它是 T-218 那一轮的真实产物）；错的是**给它挑了一个
main 已经走远了的基线去合并**。

## 修复

审查阶段新建分支时，基线取**上游冻结提交本身**，而不是 main 的 HEAD：

- `runtime/contracts/agent-workflow-checkpoints.mjs` 新增 `latestUpstreamCheckpoint()`：
  从 `upstreamStages`（由新到旧）里取第一个有效 checkpoint 的 `sourceCommit`。
- `plugins/src/workspace.ts`：`prepareWorktree(taskId, { baseRef })`，新分支的起点用 `baseRef`，
  缺省仍是 `HEAD`；**复用既有分支/目录时忽略** `baseRef`（续做不换基线）。
- `plugins/src/index.ts`：只在**审查阶段**计算并传入 `baseRef`。实现/设计阶段仍从 HEAD 建
  —— 它们要基于最新主分支写代码。

这样上游导入是空操作，审查看到的就是交来的那份代码；真正的冲突被留给**合回 main
的那一刻**（promote / 调解），那才是人能看见并裁决的地方。

## 验证

- `node --test runtime/contracts/agent-workflow-checkpoints.test.mjs`：7/7 通过。新增判据包括
  「以冻结提交为基线建的审查分支：导入是空操作」——main 改同一文件也不再冲突，
  且审查工作区里读到的仍是上游那份内容。
- `node --test plugins/tests/workspace.test.mjs`：36/36 通过。新增 3 条 argv 级判据：
  `baseRef` 逐字进 `worktree add`、缺省回落 `HEAD`、复用既有分支时忽略 `baseRef`。
- `node scripts/ci/build-external-package.mjs plugins`：通过（含 `tsc`，接口与 `.d.mts` 同步）。

## 遗留（没有在这次修的部分）

审查阶段的「基线取上游冻结提交」要求上游那条提交在本机对象库里。
跨机器交接（上游在另一台机器上跑的）仍然需要先 fetch 到本地，这条没做，
失败时的报错是既有的「冻结提交不在当前本机 Git 对象库中」。
