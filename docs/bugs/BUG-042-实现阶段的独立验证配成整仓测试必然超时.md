# BUG-042：实现阶段的「独立验证」配成整仓 `node --test`，必然超时 ⇒ 每个编码任务都卡在审查前

## 现象

2026-10-30，T-224（编码实现，`gate=0`，本该自动交接给审查）停在 `in_review`，评论说：

> ⚠ 实现阶段未提供可验证的隔离提交或明确通过的测试报告，未推进到审查阶段。

把它按非闸门阶段放行之后，T-225（代码审查 / Codex）仍然领不走，中枢每 30 秒拒一次：

```
T-225 认领失败：审查阶段缺少冻结设计版本或实现提交/测试证据，拒绝进入 review：实现报告字段或独立测试回执无效
```

而实现是真的：`w/T-224` HEAD `717607bf`、19 文件 +4514、工作区干净；定向复跑 117 pass / 0 fail。

## 根因

冻结的工作流定义把 implement 阶段的独立验证配成**整仓** `node --test`：

```json
"testRunner": { "executable": "node", "args": ["--test"], "timeoutMs": 900000 }
```

这个仓库跑不完 15 分钟。于是：

1. runner 在 900 秒到点被掐，回执 `exitCode=null` ⇒ `state: "unknown"`；
2. 实现阶段的自动交接要求 `testReport.passed` + `testVerification.state === 'passed'`，`unknown` ⇒ 停 `in_review`；
3. 审查阶段认领时中枢还要再核对一次（`server.mjs` 里两处 `=== 'passed'`）⇒ 永远 409。

> 一个"永远跑不完"的验证命令，
> 与一个"永远不通过"的验证命令，在流水线眼里是同一个东西。

## 修复

**① 定向验证脚本** `scripts/ci/verify-changed.mjs`（新）：
以 `git merge-base HEAD main` 为基准取本次改动，映射到该跑的套件，逐套**单独进程**跑
（`node --test --experimental-test-isolation=none <suite>`，`stdio: inherit`——
Windows 沙箱不允许 child_process 管道 spawn，但继承 stdio 可以）。
映射五类：同名套件、源码目录→测试目录、驼峰→短横线、import 引用者、源码断言型"提到者"（按仓库全路径）。

**② 工作流定义 v4**：implement 阶段改为

```json
"testRunner": { "executable": "node", "args": ["scripts/ci/verify-changed.mjs"], "timeoutMs": 3600000 }
```

（`timeoutMs` 同时抬到 runner 允许的上限 60 分钟，作为兜底；日常只会跑几分钟。）

## 验证

- `node --test scripts/ci/verify-changed.test.mjs`：**9/9**。
- 在 T-224 的真实 worktree 上跑：`changed=19 suites=9`，**退出码 0**，180 条断言全绿
  （identity-profile-store / identity-profile / identity-registration / user-store /
  mobile-api-contract / account-page / account-profile / identity-gate / mobile-board-parity）。
- 对照：同一提交的整仓 `node --test` 在 900 秒到点仍未结束（原来的回执就是这条）。

## 取舍（写在这里，免得以后当成 bug 再报一遍）

- 没有映射到任何套件时**判过**：文档/配置类改动本来就跑不出东西，判失败会把它们堵死。
  真正的质量闸门是紧随其后的审查阶段（Codex 看 diff）。要收紧就改 `verify-changed.mjs` 一处。
- 映射是启发式的：新增目录约定时要同步这里，否则会漏跑（不会误报失败）。
- 同一进程里连跑多套会串模块级状态（`TEAM_HUB_TOKEN` / `TEAM_HUB_DB` + `import server.mjs`）——
  这是为什么脚本坚持**每套一个进程**，而不是一次 `node --test` 多文件。
