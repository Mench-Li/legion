# BUG-047：事件投递表被持续灌爆（约 5 万行/分钟），30 个订阅者扇出把 hub CPU 拖在 40–70%

## 现象

BUG-046 修好 `advanceCursor` 之后（该函数自耗时 36.6% → 0.4%），CPU 仍常驻 40–70%，且：

```
2026-11-07 15:00  清库后剩余  222,845 行 event_deliveries
2026-11-07 15:02  实测         440,447 行   （15 秒内 +12,548 行 ≈ 5 万行/分钟）
2026-11-07 15:0x  再测         504,188 行
```

新火焰图（同一 3 秒采样）：

```
55.2%  exec          @ :0                        ← SQLite
12.9%  prepare       @ :0                        ← 语句重复准备
12.4%  auditEvent    @ team-hub/server.mjs:7988
 9.8%  garbage collector
 0.9%  subscriberOf  @ team-hub/event-delivery.mjs:342
 0.4%  advanceCursor ← 已修好
```

## 已测事实

- 订阅者 **30 个**，全部是 `anonymous:{workbench|mobile}:N`；
- 平均每订阅者约 1.5 万行；
- **`anonymous:mobile:3` 与 `:5` 的游标卡在 66** —— 前面有个洞，按"洞不许跳过"的规矩，它们的行会一直攒着；
- 事件来源**不是** `run_events`（仅 53 行）也**不是** `hub_event_tickets`（272 行），即不是运行事件或鉴权票据，而是别处持续广播的实时事件；
- 约 **28 事件/秒** 的稳定流入 × 30 个订阅者 = 每秒近千行写入。

## 与 BUG-046 的关系

BUG-046（`advanceCursor` 全量读）已修：单次 106ms → 1.25ms，`advanceCursor` 自耗时从 36.6% 降到 0.4%。
但**它是"放大器"，本条才是"水源"**：

> 修好放大器，让每次调用变快；
> 但水源还在灌，库里仍然每分钟多 5 万行 —— 下一轮放大器迟早还会被撑爆。

## 影响

- hub 的请求延迟被周期性拉高（实测 `/api/config` 12 秒超时、`/mobile/` 3 秒）；
- 库体积反复膨胀（刚 VACUUM 到 69MB，几分钟内又被灌回百 MB 量级）；
- 保留期（7 天）只能削峰、不能治本：行是**刚刚**产生的，不属于"过期"。

## 修复方向（待做）

1. **定位事件源**：找出每秒约 28 次广播的调用方，判断它是"正常实时事件"还是"重放/轮询风暴"；
   - 落点：`deliveryStore.plan()` 的所有调用方（广播入口），以及 `hub_event_tickets` 之外的 ticket/subscribe 路径；
2. **清理僵尸订阅者**：没有活 SSE 连接的 `anonymous:*` 订阅者，其投递行没有任何消费方；
   - 需要"订阅者活跃性"的判定依据（最后连接时间 / 连接计数），当前库里没有这个字段；
3. **把"洞"处理掉**：游标卡在 66 的两个订阅者，需要能判定那一段是**永久缺失**（永不补投）还是**待补投**；
   - 若永久缺失，应允许显式"封洞"（记审计），否则它们的行只能靠保留期慢慢清；
4. 短期止血：把保留期从 7 天降到 1–2 天，并降低批大小上限。

## 已完成的相关修复（供对照）

- BUG-046：`advanceCursor` 增量推进（106ms → 1.25ms，38/38 测试通过）；
- 投递行保留期：`pruneTerminal({ olderThanMs, limit })` + 每小时清理；已对真库执行删除 372,167 行、VACUUM 136MB → 69MB；
- 匿名订阅者**未**改为共享 id：测试 ⑤「不传 clientId 的连接是独立订阅者」明确禁止（共享会让后连者继承游标、漏事件）。
