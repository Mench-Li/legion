# BUG-048｜新建的工作空间**对创建者自己**是 403：创建那条链上没有"授予"

## 现象

桌面端点「＋ 新建工作空间」→ 勾起「🏠 本地/私有空间」→ 填名称（id=`personal-profile`，
名称「个人履历」）→ 建完界面立刻切到新空间，屏幕上是：

```
读取失败：403：无权访问空间「personal-profile」
（请确认 team-hub v2（:8787）已启动并选中有效工作空间）
```

2026-11-20 10:20 现场。**空间是建出来了的** —— 这一点让现场特别难判断：

| 看起来的结论 | 事实 |
| --- | --- |
| 「中枢没起来 / 没选中空间」 | 中枢在 8787 上正常响应，`POST /api/spaces` 回的是 **200** |
| 「新建没成功，再建一次」 | 再建也是 200（同名幂等 upsert），然后**还是** 403 |
| 「权限配置写错了」 | 那个空间的角色表里**一条行都没有** —— 不是配错，是没配 |

只读核对真库（`team-hub/team.db`）：

```
spaces:                software / default / ozon / nantai / personal-profile
hub_space_roles:       software(admin) / ozon(admin)     ← 只有这两个空间有角色
audit space:create:    member='general'（操作者名，**不是** userId）
```

也就是说：同一天 11-19 建的 `nantai`、更早的 `default` 与这次的 `personal-profile`
都是**孤儿空间**（一条角色行都没有）。

## 根因：缺陷不在判定，在**授予**

空间级授权（远程门禁 + `requireSpaceAccess`，设计文档 §13「一个项目的 Agent 无权读取
未授权项目」）要求"在这个空间里至少是 viewer"。`userStore.hasRoleAtLeast` 在**没有任何
角色行**时返回 `false` —— 这是**对的**，那条函数的注释写得很清楚：

> 一个"默认放行"的空缺会让"忘了授权"表现为"一切正常"，而这类漏配恰恰是
> 新空间开通时最常见的状态。

真正缺的是另一半：**新建空间这条链上没有任何地方会给创建者一个角色。**

- 工作台「＋ 新建工作空间」只是一个 `POST /api/spaces`（`workbench/src/components/NewSpaceModal.tsx` → `api.ts: createSpace`）；
- `POST /api/spaces` 只写 `spaces` 表（`routes/space-config.mjs`），**不碰 `hub_space_roles`**；
- 全仓唯一能写角色行的地方是身份族的 `POST /api/identity/roles/grant`（手动 API），
  而**工作台没有任何界面调用它**。

于是这条链必然断在这里：建完 → 立刻按新 scope 读任务（`fetchHubTasks` →
`/api/board?scope=<新 id>`）→ 403。**必然发生，不是偶发。**

`product/server/README.md` §④′(a) 里那条 `curl … /api/identity/roles/grant` 是给
**首次引导**用的（管那一个账号、那一个空间），它从来没有覆盖"事后新建的空间"。

## 修法（三半）

### ⓪ 界面：403 空间越权**不是**"中枢不可达"（这句提示把人指到了错的地方）

现场那句话的后半截是「（请确认 team-hub v2（:8787）已启动并选中有效工作空间）」——
而中枢明明在 8787 上好好响应。对着一个"你在这个空间里没有角色"的 403 说这句话，
人只会去重启中枢；重启一万次也还是 403。

这与 `hub-errors.ts` 里 `isAuthFailure` 那条现场**同形**（401 被当成"中枢不可达"，
于是重连了一整夜），修法也一样 —— 判据只认**具名码**，不做"403 就一定是越权"的外推：

- `workbench/src/hub-errors.ts` 新增 `isSpaceForbidden`：`code === 'SPACE_FORBIDDEN'`，
  或（老中枢 / 响应体不是 JSON 时）**403 + 那一句具名文案** `无权访问空间「…」`；
- `TaskCenterView` 的读取失败面板按它分岔：越权 ⇒ 说清"这个账号在这个空间里没有角色 +
  怎么办"，其余失败才说"请确认中枢已启动"；正文也改走 `hubErrorText`（带上后端的 `hint`）；
- 顺带把 `loadErr` 从**字符串**改成**错误对象**：压成 `${e.message}` 之后 `code` 就没了，
  而分岔正要靠它（正是 `hub-errors.ts` 文件头记的那条断链）。

### ① 未来：新建即把创建者登记成 owner（同一个事务）

`server.mjs` 新增 `grantSpaceCreator`（唯一判定处），由 `POST /api/spaces` 在
**空间行与授权行同一个 `withTx`** 里调用。分开做的后果就是上面那个现场：
中间断开一次，留下一个"建成了、但创建者自己进不去"的半成品空间。

四条闸，缺一条都会开出另一个洞：

| 闸 | 为什么 |
| --- | --- |
| **只有新建才授予**（`created === true`） | `POST /api/spaces` 是**幂等 upsert**："新建"与"改个名字"走同一个入口。更新既有空间时也授予 ⇒ 任何登录用户打一条 `{id:"别人的空间"}` 就能把所有权拿走 |
| 远程身份通道没开就不做 | 那时空间级授权整层不生效（没有 `__legionUser` 就放行），凭空写一行只会给未来留一条无法解释的授权 |
| 没有用户身份（机器令牌 / 本机无鉴权）就不授予 | 没有"谁"可授。这也让"机器令牌建出来的空间默认没有主人"成立，与「**系统管理员不自动能读所有空间**」那条口径不冲突 |
| `by: null`（系统授予） | 创建本身**就是**这次授权的依据（这是一个尚不存在的新 id，没有别人的东西可以被拿走）。不过 `requireRoleGranter`，否则第一个建空间的人永远建不成空间 |

授 `owner` 而不是 `viewer`：建空间的人要能把人拉进来、能删掉它；而按
`requireRoleGranter` 的口径，授 owner 需要"系统管理员或该空间的 owner"——
不给 owner 的话，创建者此后只能求管理员帮他配权。

留痕：`grantSpaceRole` 自己写一条 `identity:grant-role` 审计（`member`=`system`，
`detail.userId`=被授权人、`detail.role`=`owner`，`hub_space_roles.granted_by`=`system`），
与 `space:create` 同一个事务。

### ①b 同一个形状的**第二条入口**：装流程包也会建空间

`POST /api/workflow-packs/install` 在"这个包还没装过"时会顺手
`INSERT INTO spaces`（`product/workflow-packs/pack.mjs`），而工作台有「流程包」面板
（`WorkflowPacksPanel.tsx`）让登录用户装包 —— 于是漏掉这条入口的话，**装一个包也会得到
一个自己进不去的空间**，症状与这次的现场一模一样。

处理与 ① 同源，不写第二份判定：`installWorkflowPack` 增加一个 `onSpaceCreated(scopeId)`
钩子，在**它自己的事务里**、紧跟空间 `INSERT` 之后触发；路由把 `req` 与
`created: true` 交给同一个 `grantSpaceCreator`。既有空间走的是 `UPDATE`（`receipt` 已存在），
所以"只有新建才授予"那道闸天然还在（有用例钉着：升级**不**触发钩子）。

### ② 存量：孤儿空间补授权，**不猜创建者**

已经建出来的那些空间不会被 ① 碰到，而"谁该拿到 owner"没有可信依据 ——
审计里 `space:create` 的 `member` 是 `general` 这个**操作者名**，不是 userId：

```
{"member":"general","scope":"default","action":"space:create",
 "detail":{"space":"personal-profile","name":"个人履历",…}}
```

> 一个按"看起来像谁建的"去补授权的脚本，
> 与一个"把别人的空间送出去"的脚本，只差一次猜错。

所以 `team-hub/scripts/grant-orphan-spaces.mjs` 只做三件事：

```bash
node team-hub/scripts/grant-orphan-spaces.mjs                            # 只读：列出孤儿空间
node team-hub/scripts/grant-orphan-spaces.mjs --user general             # 只读：算出"会授给谁"
node team-hub/scripts/grant-orphan-spaces.mjs --user general --apply     # 真写：owner + 审计
```

- **默认不写**：`--apply` 是唯一会改库的开关（与 `BUG-004-apply-fix.mjs` 同一条纪律）；
- 判定只有一条：**一条角色行都没有** ⇒ 孤儿。已经有任何角色的空间一律不动；
- 审计与 ① 同源（`identity:grant-role`，外加 `detail.via='grant-orphan-spaces'` 以示区别）；
- 幂等：授完之后那些空间不再出现在计划里，第二次一行都不写。

## 已知边界（本次**没有**做，别当成已经安全）

1. **`scope` 写在 POST body 里的写路径仍不做空间级授权**（老台账，见
   `docs/superpowers/plans/2026-10-04-legion-server-pc-mobile-agent-implementation.md`
   里「顺带补上**空间级授权**」那一段的补充说明）：
   所以一个**不是**该空间成员的用户，仍然可以 `POST /api/spaces {id:"别人的空间", name:…}`
   把它改名。本次修法**没有**扩大这个面（它不授予任何角色），但也没有关上它 ——
   要关得在写路径上补空间级授权，那是另一件事。
2. **工作台没有角色管理界面**：给别人授权仍要走 `POST /api/identity/roles/grant`。
   所以"多用户 + 各自的空间"目前只有创建者自己开箱可用。
3. `GET /api/spaces` 不过滤角色：孤儿空间仍会出现在空间选择器里。
   本次不隐藏它 —— 藏起来只会让"我建的空间去哪了"变成第二个 bug。
4. 空间删除（`POST /api/spaces/delete`）与流水线写入（`POST /api/pipeline`）同样
   没有空间级授权判定，属同一条老台账。

## 与其它缺陷的关系

- **与 BUG-037 同形**：那一处是"合入主分支 ≠ 用户看到的东西变了"，这一处是
  "创建成功 ≠ 创建者能用"。两次都是**以为已经连上的那一段其实没连**。
- **与 BUG-027 同一族**：那条是"按岗位选模型这条链没有活的消费者"——配得出、没人读。
  这条是"建空间这条链没有授权的那一半"——建得出、进不去。
- **不是 BUG-017（多空间守护读错形状）**：那条是**读**的解析错，这条是**写**的授予缺。
