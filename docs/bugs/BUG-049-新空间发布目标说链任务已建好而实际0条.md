# BUG-049｜新空间发布目标：「一条链任务都没建出来」，而界面说「已建好，不必重发」

## 现象

2026-11-20，新建空间 `personal-profile`（「个人履历」，私有、未绑目录、编队为空、流水线为空）
里发布目标，得到：

```
⚠ 目标已发布，但**这个空间现在不会自动开工**：该空间未配置流水线——守护按角色过滤时会
跳过全部任务（或建链退回全编队造成死锁）（另有 1 项）→ 修复：POST /api/pipeline
（scope:"personal-profile", stages:[…]）（或 node team-hub/scripts/seed-pipeline.mjs
--scope personal-profile --file <roles.json>）（链任务已建好，开通执行 / 守护上线后会自动认领，
不必重发）
```

三句读数，三句都不准：

| 界面说的 | 真读数 |
| --- | --- |
| 「**链任务已建好**，…会自动认领」 | `tasks` 表 **0 行** —— 一条都没建 |
| 「…**不必重发**」 | 配好编队/流水线后**必须重发**：链是在发布那一刻建的，旧目标不会补建 |
| 「修复：（或 `node team-hub/scripts/seed-pipeline.mjs …`）」 | 这台中枢开着 `LEGION_REMOTE_AUTH=1`，而**该脚本一个 Authorization 头都不带** ⇒ 第一条 `GET /api/pipeline` 就 401（「读取现值失败：HTTP 401」） |

用户按提示做了两件事（等认领、跑修复命令），两件都没有结果，也都没有说清为什么。

## 根因（两个，同一族：**读数与事实两张皮**）

### ① 提示语的措辞绑在"发布成功"上，而不是"建出了几条链"

`workbench/src/App.tsx` 的那句提示无条件带一句「链任务已建好…不必重发」，
它只区分"预检有没有阻塞"，从不看**这一次到底建出几环**。

而建链 = **编队 ∩ 流水线启用岗位**（`server.mjs: createGoalChain` 的 `legacyRoute`/`build`）：

```js
// 编队本身为空属于既有合法态（如空空间先发目标后补编队）——保持 0 环建链，不改变既有行为。
if (build.length === 0 && roster.length > 0) { throw … }
```

空编队 + 空流水线 ⇒ `build.length === 0` 且 `roster.length === 0` ⇒ **0 环、不报错、发布 200**。
这是**有意**的合法态（先发目标后补编队），所以修法不是"发布时拦下来"，而是
**界面必须按真实建链数说话**。

### ② 修复命令跑不通：`seed-pipeline.mjs` 不带令牌

脚本走 HTTP（这个设计是对的：写入期校验/审计/SSE 都在服务端），但它从前既不读
`--token`、也不读环境变量，`fetch` 也不带 `authorization`。在**本机未开鉴权**的部署上
它能跑；一旦按 README 的建议给中枢设了令牌 + `remoteAuth='1'`（本机就是这套，隧道暴露
手机访问所必需），这条"修复命令"就必然 401。

> 一条跑不通的修复命令，比没有这条命令更贵：人会反复试它，
> 并最终以为是"我哪里抄错了"。

## 修法

### ① 措辞交给纯函数，按服务端回执的 `task.stages` 分岔

- `workbench/src/goalPublishNotice.ts`（新，纯函数）：`goalPublishNotice({ blocked, builtStages })`
  → `{ tone, text }`。三种情形分开说：
  - **0 环** → 明说「一条链任务都没建出来」，并指出「配好编队与流水线后**需要重新发布**」；
  - **N 环 + 有阻塞** → 保留原语义（链是真的、解锁即自动认领，不必重发）；
  - **回执没给数**（`stages` 缺失/NaN/负数）→ **两个断言都不下**，说「无法确认」，让人去看任务中心。
- `workbench/src/api.ts`：`publishGoal` 的返回从 `Promise<unknown>` 收敛成具名契约
  `GoalPublishResult`（含 `task.stages`）——回执的形状要能被类型读到，否则下一个人会
  `as any` 绕过去。
- `workbench/src/App.tsx`：接住回执 → `goalPublishNotice({ blocked, builtStages })` → `toast`，
  那句无条件的硬编码文案删除。

### ② `seed-pipeline.mjs` 支持令牌 + 失败可执行

- 新增 `team-hub/scripts/seed-pipeline-lib.mjs`（纯）：`argOf` / `hasFlag` /
  `resolveAuth`（`--token` > `LEGION_HUB_TOKEN` > `TEAM_HUB_TOKEN`）/ `authHeaders` /
  `explainFailure`。
- 脚本每次请求都带鉴权头（`headers: { ...HEADERS, ...(init.headers ?? {}) }`）；
  **空令牌不伪造** `Bearer `（那会得到一个 401，而"我明明给了令牌"会把排查带偏）。
- 401/403 的话术写明：这台中枢开了远程鉴权、加 `--token` 或 `export LEGION_HUB_TOKEN=…`、
  值去 DSH profile 的 `teamHubToken` 拿（**不打印值**）；服务端原话照旧附上
  （例如 `REMOTE_AUTH_MISSING`）。400/404 各自说各自的话，不冒充鉴权问题。

## 顺带被这条现场暴露的两件事（不影响本修法，单独立账）

1. **新建空间那条链不建流水线**（BUG-048 的邻居）：桌面端「＋ 新建工作空间」两步只做
   「建空间 + 选人入编」，**没有配流水线**这一步；而 `scopes:'auto'` 的守护只接管
   「已开通执行 + 流水线 ≥1 环」的空间。于是每个新空间都要人工补一次流水线
   （界面上也确实没有流水线编辑器，只有 `POST /api/pipeline` 与这个脚本）。
   本次按现场把 `personal-profile` 的四环流水线配上了，**但没有把这个缺口做进产品**。
2. **流程包不能装进已存在的空间**：`planWorkflowPackInstall` 在"该包没装过 + 空间已存在"
   时直接 `conflict / SCOPE_ALREADY_EXISTS`。所以"一键把空间配好"那条路只对新 id 有效，
   空间一旦建出来就只能手工补。

## 与其它缺陷的关系

- **与 BUG-048 同一条现场、同一族**：那条是"建了空间自己进不去（403）"，这条是
  "建了目标不知道有没有建链、以及给出的修复命令跑不通"。
- **与 BUG-016/A 一脉**：那一处补的是"发布之后要说清会不会自动开工"，
  本条补的是"**说清的话必须是真的**"——补了读数却没校验读数，等于换了一个地方说假话。
