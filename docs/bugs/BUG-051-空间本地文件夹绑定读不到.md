# BUG-051｜空间绑的「本地文件夹」从来没生效过：读 `/api/spaces` 时没带令牌

## 现象

空间 `personal-profile` 在指挥台里绑了本地文件夹 `D:\project\opc`（真 git 仓库，首次提交
`39cfb00`），中枢的 provision 面板也显示 `workspace-bound`。但第一个任务的 worktree 建在：

```
D:\project\DSH\legion\.legion-worktrees\T-312        ← 默认仓库
```

而不是：

```
D:\project\opc\.legion-worktrees\T-312
```

也就是说：**空间绑的文件夹一次都没生效**，而这台机器上没有任何一行错误或警告。

## 根因

`plugins/src/workspace.ts` 的 `refreshSpaceBinding()`：

```js
const res = await fetch(`${hubUrl()}/api/spaces`)   // ← 没带认证头
if (!res.ok) return                                 // ← 静默 no-op
```

本机 `cordis.patch.yml` 开了 `teamHubRemoteAuth: '1'`（团队中枢的远程鉴权），实测：

| 请求 | 结果 |
| --- | --- |
| `GET /api/spaces`（无令牌） | **401** `REMOTE_AUTH_MISSING` |
| `GET /api/spaces`（机器令牌） | 200，`{id:'personal-profile', localDir:'D:\\project\\opc', …}` |

于是每轮扫单都 401 → 静默返回 → `spaceBinding` 永远是 `null` → `repoRootFor()` 回落到
注入配置 `config.repoRoot = D:/project/DSH/legion` → 任务全在**默认仓库**里开 worktree。

> 一次没带令牌的读取，与一条"这个空间没绑文件夹"，
> 在 `if (!res.ok) return` 面前是同一件事 ——
> 区别只在任务落在哪个仓库里的那一次。

而中枢侧那张 provision 卡片读的是**库里的** `localDir`（它是有的），守护读的是**接口**
（它读不到）—— 两张皮，谁也不报错。这与 BUG-050 是同一个形状：**同一个事实有两个读数，
其中一个因为少带了一样东西而静默变成"没有"**。

## 修法

1. `WorkspaceDeps` 增 `hubHeaders: () => Record<string, string>`，`index.ts` 注入现成的
   `hubHeaders()`（与心跳、认领、派工用的是同一套头）。
2. `refreshSpaceBinding()` 带着它请求。
3. **非 200 不再静默**：记一行
   `空间仓库绑定刷新失败：HTTP 401（鉴权失败：守护没带中枢令牌 ⇒ 空间绑的本地文件夹不会生效，任务会落回默认仓库）`，
   且每 10 分钟最多一条（扫单很勤，别刷屏）。

## 验证

| 用例 | 守的是什么 | 读数 |
| --- | --- | --- |
| 假服务"没有 `authorization` 头就回 401" → 带令牌必须落绑定，且 `repoRoot` 取该目录所属仓库的 `toplevel` | 真能读到绑定 | 通过 |
| 反证：`hubHeaders` 返回空对象（模拟修复前）→ 401 ⇒ 绑定不动 | 证明这条用例真的在守那个洞，而不是恰好绿 | 通过 |
| `hub 返回非 200`：绑定不动，但**必须说一句**（HTTP 401 + 鉴权失败 + 连续失败不刷屏） | 静默才是 bug 的另一半 | 通过 |
| `plugins/tests/workspace.test.mjs` 全量 | 绑定/git/worktree 三段不回归 | **38/38** |
| `plugins tsc -p tsconfig.json --noEmit` | 类型面 | exit 0 |
| 实读 `/api/spaces` | 无令牌 401 / 带令牌返回 `localDir` | 见上表 |

## 已登记的边界

- 这只修了"读不到"；**绑定变更后已挂载的子守护**要等下一轮扫单才换仓库根（旧任务仍跑在旧仓库里）。
- `remoteUrl` 仍只作登记与提示（push 纪律不变：`w/*` 分支一律禁止 push）。
- 同一天还发现一个**内容层**的坑（未登记编号，待定）：岗位契约要求产出
  `docs/COMPANY.md`（worktree 根下的 `docs/`），而目标文档目录约定把同一份东西写在
  `docs/<goalId>/COMPANY.md` ⇒ 首轮必然"产出文档缺失"并停在 in_review。
  两处约定都合理，缺的是一句"产出路径以岗位契约为准"的说明（或让守卫两种路径都认）。
