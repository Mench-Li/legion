# PRT 阶段 0～1 实施计划（基线冻结 + Runtime Contract）

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** 在不与在途功能争用主干文件的前提下，冻结当前系统基线、立起 DSH 执行面边界棘轮，并交付可用内存 Fake Adapter 测试的 Runtime Contract。

**Architecture:** 阶段 0 以「只读采集 + 新增文档 + 新增脚本」为主，不触碰 `plugins/src/index.ts` 与 `team-hub/server.mjs`；阶段 1 全部落在新目录 `runtime/contracts/`，由契约测试与 Fake Adapter 驱动。两者共同构成后续大规模编排提取（阶段 3～4）的安全边界与比较基准。

**Tech Stack:** Node.js ESM、`node:test`、零第三方依赖（与仓库既有 CI 脚本一致）、`scripts/ci/run-ci.mjs` 阶段化 CI。

**Spec:** `docs/superpowers/specs/2026-09-11-legion-product-runtime-design.md`（位于分支 `codex/product-runtime-design`；本计划分支从 `main` 切出，合并该 spec 后方可直接引用）

## Global Constraints

- **不动主干文件**：本批次不修改 `plugins/src/index.ts`、`team-hub/server.mjs`。这两个文件近 60 个提交里分别被改 51 / 35 次，是与其他功能争用的唯一热点；阶段 3 之前不进入。
- **棘轮只紧不松**：`dsh-boundary` 基线只许在**真实迁移**后下移，且 `runtime/contracts/`、`orchestrator/`、`product/`、`security/` 永不允许基线例外。
- **契约不依赖 DSH**：`runtime/contracts/` 不得出现 Cordis/DSH 类型或 `ctx.*`（由 `dsh-boundary` 的 `must-be-zero` 判定强制）。
- **基线必须在系统还是当前形态时采集**：PRT-004/007/009 的数值会随在途功能持续漂移，越晚采集越无法证明新路径不是性能回退。
- **留痕按仓库纪律**：`docs/STATUS.md` 是「当前状态」唯一入口；`docs/**-evidence/` 是带 banner 的历史快照；CI 单入口 `node scripts/ci/run-ci.mjs`。
- **本批次结束即到闸门**：阶段 2.5（M1.5）未达标前不启动阶段 3。〔spec §13 Program 级停止条件〕

**结果（现场库实测；源库只读，全部实验在临时副本上做）：**

| 验证项 | 结果 |
| --- | --- |
| ① 只复制 `.db`（不含 `-wal`） | ❌ **丢 253 条 audit 记录，且无任何报错** |
| ② 三件套（DEPLOY.md §6 写法） | ✅ 完整恢复 |
| ③ `VACUUM INTO` 一致性快照 | ✅ 完整恢复，只需源库**读**权限 |
| ④ 从快照恢复到干净目录 | ✅ 单文件即可用 |
| ⑤ 恢复 `.db` 但残留陈旧 `-wal` | ❌ **陈旧 WAL 被重放，且 `integrity_check` 仍报 ok** |
| ⑥ 源库写入期间的文件复制 | ⚠️ 非同一时点视图（「恰好一致」不能证明原子性） |

**最危险的是 ⑤**：把 A 时点的 `.db` 与 B 时点的 `-wal` 放一起，SQLite 不拒绝、
库能正常打开、`integrity_check` 报 ok，只是内容混合了两个时点 →
**无法靠完整性校验发现**。而 DEPLOY.md 原回滚步骤正是「替换 .db（含 -wal/-shm 同批）」，
执行时漏掉一批就会落到这个状态。已把「恢复前必须先删 `-wal`/`-shm`」写进回滚表。

**一条被纠正的验收口径**：原计划写「校验 audit seq **连续性**」，但真实数据
**有 1 个缺口**（seq 4501–4502）。原因是分配器 `MAX(seq)+1`
（`team-hub/server.mjs:1196`）——回滚后作废号不回填，这是**有意设计**，不是缺陷。
口径改为「恢复前后**缺口集合**一致」。坚持「必须连续」会让 PRT-006 在真实数据上永远红，
而**永远红的验收项等于没有验收项**，还会训练人忽略它。

#### 评审闸门结论：**已降温，阶段 3 可以安排开工**

| 文件 | 最近 40 个提交触及 | 历史峰值 | 最近一次改动 |
| --- | --- | --- | --- |

| `team-hub/server.mjs` | **2/40** | 7/40（第 41–80 / 81–120） | 2026-09-10（37 个提交之前） |

判据：最近窗口内任一热点文件触及 ≤ 2 次。

**⚠️ 原计划里这个数字是错的，且错得刚好相反。** 原文写「近 60 个提交里分别被改
51 / 35 次」。实测：**51 / 35 量级是全history累计次数**（准确值 52 / 39），
不是近期频率。原因是 `git log -n 60 -- <file>` 会**先按路径过滤再截断**，
只要该文件被改过 ≥60 次就恒返回 60 ——「最近 60 个提交都在改它」。

正确写法是先取提交区间再做路径过滤：

```bash
oldest=$(git rev-list -n 40 HEAD | tail -1)
git log --format=%h "$oldest^..HEAD" -- plugins/src/index.ts | wc -l   # → 1
```

修正后（1/40、2/40）与原文（40/40 的观感）**结论正好相反**：
前者说「可以开工」，后者说「不能开工」。这个坑很容易重踩，因此做成了
`scripts/prt/hot-file-churn.mjs`（含单测直接锁定两种写法的差异，
防止有人把正确写法「简化」回去）。

**降温的直接证据**：09-11 一整天 16 个提交（P4-3/4/5/6 与本次 PRT）**没有一个**
碰过这两个文件——在途工作已经转移到 `whiteboard/**`。
