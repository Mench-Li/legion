# 阶段 D 真机验收运行手册（设计 §10 的九行验收表）

> 这份手册的对象是**拿到一台 Windows 机器的人**。它把设计 §10 那九行拆成
> "逐条怎么做、记录什么、什么算通过"，并明确标出**哪几行在这里做不完**。
>
> 依据：[自动更新设计](../specs/2026-10-02-legion-desktop-auto-update-design.md) §10、
> [实施记录](2026-10-04-auto-update-implementation.md) §5/§6/§7。

## 0. 先读这一节：这份手册**不能**替代什么

设计 §10 的原话是「每阶段记录实际证据；**测试替身通过不能替代 Windows 真机升级
验收**」。所以：

| 已经做完的（阶段 A/B/C） | 只剩真机能做的（阶段 D） |
|---|---|
| 协议、签名、序列高水位、缓存、调度、状态机 | 签名**真实**安装包并在真机安装 |
| 安装事务九步、维护屏障、日志、恢复入口 | 干净机器首次安装 |
| 托管部署（真机 nginx + 真签名清单已实测） | N−1 → N 的真实升级 |
| 撤回协议（真实托管上实测过） | 文件占用 / 断电故障注入 |
| 「装完之后核对」的命令行工具 | 生产 HTTPS 源、存储商、签名发布方、公钥、责任人 |

**本手册负责把后者变成"照做即可"**，但它自己**没有跑过**——那些行仍然需要一台
真机。写下来的价值是：真机到手时不需要重新设计验收步骤，以及**每一行要记录
什么**是事先定好的（而不是事后补一份好看的记录）。

## 1. 前置条件（开工前逐项打勾）

| # | 需要什么 | 怎么确认 |
|---|---|---|
| 1 | 一台**干净**的 Windows 目标机（10/11，与 `minWindowsBuild` 兼容） | `winver`；设计 §10 第 ③ 行要求"错误平台"被拒，所以要记下这台机器的 build |
| 2 | 一份**签过名**的发行（清单 + ZIP + 安装器） | `node scripts/update/publish.mjs …`（见实施记录 §6 的发布步骤） |
| 3 | Windows **代码签名证书** + 发布私钥 | 设计 §9 line 202：「签名私钥和 Windows 签名凭据保存在发布机或 CI 密钥存储」 |
| 4 | 随包的信任表里**有**那把发布公钥 | `product/release/update-trust.json`，用 `keygen.mjs` 生成 |
| 5 | 托管的 HTTPS 入口（或测试用的 HTTP + `allowInsecureHttp`） | `node scripts/update/verify-host.mjs --origin … --prefix … --channel …` |
| 6 | 本仓这一份代码（用于跑核对工具） | `git rev-parse HEAD` 记进验收记录 |

★ 第 5 项若是 HTTP，**只能**配 `internal` 通道——`canary`/`stable` 用 `http://`
会被客户端判 `host-insecure-origin`（这是设计 §4 line 81 的隔离要求，不是障碍）。

## 2. 逐行怎么跑

### ① 无更新、离线、超时、CDN 返回旧清单

| 步骤 | 命令 / 操作 | 记录什么 |
|---|---|---|
| 起一个"没有新版"的托管 | 发一份与当前版本相同的清单 | — |
| 点检查更新 | 桌面 → 设置 → 检查更新 | 界面显示"已是最新"，**不是**错误 |
| 拔网线后再点 | — | 用户手动检查显示错误 + 重试按钮；**自动**检查只留脱敏日志（设计 §6 line 134） |
| 把清单换成**更小** sequence 的那份 | `scp` 旧的 `feeds/<channel>/win-x64.json` | 客户端拒绝（`feed-sequence-regression`），**不**降级、**不**提示有新版本 |
| 恢复 | 传回正确清单 | — |

> 这一行的"CDN 返回旧清单"在真机上用**手工回滚托管上的清单**模拟；
> 真正操纵 CDN 的那一半需要能控制 CDN 的部署（本手册不做）。

### ② 清单伪造、未知 keyId、过期、sequence 回退

| 步骤 | 操作 | 记录什么 |
|---|---|---|
| 改清单一个字节 | 直接编辑托管上的 `manifest.json` | 拒绝；理由提到签名（`envelope-bad-signature`） |
| 用**别的**钥匙签一份合法清单 | `keygen.mjs` 另生成一把，重新签 | 拒绝（`envelope-unknown-key`）——**不退化成放行** |
| 把清单有效期改到过去并重签（用**真**私钥） | 改 `issuedAt`/`expiresAt` 后重签 | 拒绝（`envelope-expired`） |
| 换回正确清单 | — | 恢复正常 |

★ 第 1、2、3 条**已经在真实托管上做过一次**（证据见实施记录 §7.3），
这里记的是"在真机上当着验收人再做一次"。

### ③ 包被替换、错误签名、错误平台、磁盘不足、ZIP 越界

| 步骤 | 操作 | 记录什么 |
|---|---|---|
| 替换包内容 | 改 ZIP 里的一个文件（**不改**清单） | 下载后摘要不符 → 停止且**不**安装 |
| 换掉清单里的包摘要 | 改清单并重签 | 同上（这是发布端事故的形态） |
| 在 x64 机器上给一份 arm64 清单 | — | 拒绝（`release-unsupported-platform`） |
| 把磁盘填到只剩几百 MB | — | 预检判空间不足，**在动任何东西之前**停下 |
| 造一个含 `../` 的 ZIP | — | 拒绝（`extract-path-escape`） |

### ④ 重复点击、多个窗口、下载中发现新版

| 步骤 | 操作 | 记录什么 |
|---|---|---|
| 连点 5 次"检查更新" | — | 托管日志里**只有一次**通道清单请求 |
| 下载中点"检查更新" | 同时把清单换成新版本 | 下载被丢弃（`update-identity-mismatch`），提示重新确认；**不**静默装另一个版本 |
| 试着开第二个更新面板 | — | 复用同一个窗口（面板是单例） |

★ 第 2、3 条本轮有了机械判据（`client.test.mjs` 的"下载期间候选变了"、
`desktop/update-service.test.mjs` 的"面板是单例"），这里要的是**真机上的同一次**。

### ⑤ 有任务运行、不能安全取消、服务拒绝退出

| 步骤 | 操作 | 记录什么 |
|---|---|---|
| 让 team-hub 跑一个长任务，然后点安装 | — | 结论是"稍后"（`install-busy` / 在途任务），**不**强杀 |
| 超时之后 | — | 回到**可选**界面（设计 §7 line 150：超时**不是**强杀） |
| 用任务管理器让服务拒绝退出 | — | 落在维护态，且**不**继续装 |

### ⑥ SQLite WAL、附件写入、迁移失败、补丁失效

| 步骤 | 操作 | 记录什么 |
|---|---|---|
| 升级前后比 `team.db*` | 见 `docs/DEPLOY.md` §6.1 | `-wal`/`-shm` 的处理纪律（PRT-006） |
| 让一条迁移失败 | — | 回退被拒 → 维护态；向前修复入口 |
| 补丁层不成对 | 发布一份 `dshPatchBindings` 与目标不匹配的清单 | 预检判 `unverified` 并**在装之前**停下 |

### ⑦ 切换或迁移期间断电、helper 崩溃、指针损坏

| 步骤 | 操作 | 记录什么 |
|---|---|---|
| **断电注入**：在"停服务 / 切换 / 迁移"三个时点各拔一次电 | 每点至少一次 | 重启后的处置（自动恢复 / 要确认 / 拒绝）与日志终态 |
| 杀 helper | 切换中途 `taskkill` helper | 同上 |
| 损坏活动事务文件 | 手动截断 `active-transaction.json` | **必须**落在维护态（`journal-torn-active`） |

★★ 这一行是九行里**最硬**的一条，也最容易写成"看起来跑了"。
记录必须包含：**断电发生在哪一步**（从日志里的阶段读数取）、重启后的**实际**
处置、以及**数据**是否与升级前一致。

### ⑧ 错误发布撤回、清单续签、公钥轮换

| 步骤 | 操作 | 记录什么 |
|---|---|---|
| 撤回 | 发一份更高 sequence 指向当前安全版本的清单 | 新安装被停止；**已升级用户不自动降级** |
| 已下载但未安装的目标被撤回 | 在"就绪但未装"时撤回 | 安装被拒（`update-target-recalled`） |
| 续签 | 只改 `issuedAt`/`expiresAt` 重签，sequence +1 | **接受**（不能报"被撤回"） |
| 公钥轮换 | `keygen.mjs rotate` → 进随包信任表 → 新钥匙签清单 | 新钥匙签的清单被接受 |

★ 撤回**已经在真实托管上实测过**（实施记录 §7.3）。剩下的真机部分：
"真装一个坏版本 → 真撤回 → 真验证已升级用户的处置"。

### ⑨ 干净机器首次安装及 N−1 → N

| 步骤 | 操作 | 记录什么 |
|---|---|---|
| 干净机器跑签名安装器 | 双击 `Legion-Setup-win-x64.exe` | ① **签名有效**（见下）；② 装完之后能起来 |
| 装完之后核对 | `node scripts/update/verify-install.mjs --install-root <已装目录> --manifest <清单> --package <ZIP> --trust <信任表> [--expect-version 1.1.0]` | 报告里的"结论：**一致**"那一行，原样抄进记录 |
| 装 N−1 | 用上一版安装器 | 版本读数 = N−1 |
| 升到 N | 点更新 → 安装并重启 | 版本读数 = N；数据未丢；`--expect-version N` 的核对通过 |

**安装器签名怎么验**（PowerShell，在目标机上）：

```powershell
Get-AuthenticodeSignature .\Legion-Setup-win-x64.exe |
  Select-Object Status, SignerCertificate, @{n='Thumbprint';e={$_.SignerCertificate.Thumbprint}} | Format-List
```

判据：`Status` 是 `Valid`，且 `Thumbprint` **等于**发布记录里登记的那一个。
★ "签名有效"**不是**"这软件可信"——它只说明签名之后没人改过这个文件。
所以指纹必须与发布记录逐字比对，不能只看 `Status`。

## 3. 每一行的证据格式

一次真机验收的产物应当是**一份可以独立复核的记录**。建议每行记四项：

```
### 第 <n> 行 <标题>
- 时间 / 操作者：
- 这台机器：Windows <build>、<arch>；本次被测 HEAD：<sha>
- 发行：releaseId=<…>、productVersion=<…>、通道=<…>
       清单 sha256=<…>、包 sha256=<…>（从 verify-host 或 publish 的 summary 取）
- 做了什么（命令原文 / 截图路径）：
- 观察到的读数（**原文**，不要转述）：
- 结论：通过 / 不通过 / 未执行（未执行要写为什么）
```

★ **"未执行"必须写，且要写为什么。** 一份把没跑的几行留白的记录，
与一份写着"未执行：本机无法注入断电"的记录，对下一个读它的人价值完全不同
——前者看起来像"都跑了"，而后者告诉他**还差哪一步**。

## 4. 在哪里做不完（如实列）

| 行 | 为什么这里做不完 |
|---|---|
| ① | "CDN 真的返回旧清单"需要能操纵 CDN 的部署 |

★ 这些不是"缺陷"，而是**必须由人带着真机与凭据做的事**。
