# PRT-004 黄金流程定义（GF-001）

**对应**：`PRT-004`
**状态**：定义已冻结；实测基线见 [PRT-009 证据](../PRT-009-evidence/verify-evidence.md)
**可执行定义**：`scripts/prt/golden-flow.mjs`（本文件是它的人读副本；两者冲突时以代码为准）

---

## 1. 为什么需要「黄金流程」

阶段 3 要把执行编排从 `plugins/src/index.ts` 抽到 Orchestrator，新路径必须证明自己
与旧路径**行为等价**（spec §14.2）。「等价」不能靠人肉比较两次运行，必须有一份
**固定到字节**的输入与一份**机器可判定**的验收契约，让新旧两条路径跑同一件事、
产出可逐项对照的结果。

因此黄金流程要同时满足三条：

1. **输入固定**：夹具由代码生成，内容哈希被冻结（见 §3）。任何人、任何机器、
   任何时间重放，输入都逐字节相同。
2. **验收可机器判定**：全部验收项要么是命令退出码，要么是 JSON 字段，不存在
   「看起来做完了」。
3. **足够小但真的需要分工**：小到能完整读出，又要天然产生多段岗位交接。

## 2. 流程定义

| 项 | 值 |
| --- | --- |
| 标识 | `GF-001` |
| 任务 | `GF-001-T1`：为 `gf001-cli` 新增 `greet <name>` 子命令 |
| 目标 | 输出 `Hello, <name>!`；补充单元测试与 README |
| 岗位 | `planner` → `implementer` → `reviewer` |
| 交接 | 3 段（满足「至少两岗位交接」） |

### 交接契约

| 从 | 到 | 交付物 |
| --- | --- | --- |
| planner | implementer | 实施计划（改动文件清单 + 验收步骤） |
| implementer | reviewer | 代码改动 + 自测输出 |
| reviewer | planner | 评审结论（通过 / 打回理由） |

**为什么选这个任务**：它天然需要「先想清楚改哪几个文件」再动手，动手后需要有人
核对，且核对结论可被测试输出证实或证伪。换成「重命名一个变量」就不需要交接，
换成「重构一个模块」就无法机器判定。

## 3. 固定输入夹具

夹具是一个最小 Node CLI 项目，由 `FIXTURE_FILES` 生成：

| 文件 | 作用 |
| --- | --- |
| `package.json` | ESM 项目骨架，`npm test` → `node --test test/` |
| `src/cli.mjs` | 已有 `--version` / `help` / 未知命令三条分支；**不含任何 greet 线索** |
| `test/cli.test.mjs` | 3 个既有用例，覆盖上述三条分支 |
| `README.md` | 已记录 `--version` / `help` 用法；缺 `greet` |

**冻结哈希**：`2ad47fc49233d62a1ee586ea5da0a2fb422883606c8cd2e9f6cf5335251d38ea`

> **哈希变更记录（首版 → 现值）**：`package.json` 的 test 脚本由 `node --test test/`
> 改为 `node --test`。Node 24 把 `--test` 的位置参数当作**模块路径**解析、不展开目录，
> 于是 `node --test test/` 报 `Cannot find module '...\test'` 并以退出码 1 结束——
> **夹具自带的 `npm test` 从来没有通过过**。夹具内 3 条用例本身正确
> （`node --test` 自动发现时 3/3 通过），坏的是那条脚本。
>
> 缺陷之所以能在冻结时漏过去：当时所有用例都只读**字符串**（哈希、编码、缺 greet），
> 没有任何一条真的执行过夹具的 test 脚本。现已补上真实落盘 + 真实执行 `npm test`
> 的用例（`golden-flow.test.mjs`「夹具真实可执行」一节），并由 CI 常驻守着。
>
> 若未发现，黄金任务会带着一个「基线就是红的」测试命令开跑：implementer 被要求
> 「让测试通过」，而它面对的失败与 `greet` 毫无关系——这次执行作为阶段 0 的证据就不成立。

`assertFixtureHash()` 会在夹具漂移时报错。**改动夹具必须同步更新该哈希并在提交信息
中说明原因**——否则阶段 3 的对拍会退化成「两次输入不同却以为行为不同」。

### 夹具不得预告答案

夹具里**不能出现 `greet` 字样**（由单测强制）。任务要求由 `GOLDEN_TASK` 给出，
不能由仓库自己说「这里需要加一个 greet 子命令」——那会把「planner 需要自己判断
改哪几个文件」这一步抹掉，而这一步正是黄金流程要检验的东西。

### 夹具规范（由 `checkFixtureHygiene()` 强制）

- 统一 LF，不得含 CR
- 不得含制表符
- 必须以下一个 LF 结尾
- **全 ASCII**：夹具与「任务用什么语言描述」无关，但全 ASCII 直接消灭 BOM、
  编辑器编码、全角标点归一化这三类跨平台漂移
- 路径必须是安全的相对路径

> 这条规范在写夹具时当场抓到一次真实问题：初版夹具把中文写进了
> `src/cli.mjs` 的 usage 文本与测试名。中文本身没错，但它让夹具的字节取决于
> 文件编码约定，属于**可以整类消除的风险**，于是改成全 ASCII。

## 4. 验收契约

`GOLDEN_TASK.acceptance`，四项缺一不可：

| 字段 | 判据 |
| --- | --- |
| `filesChanged` | 改动文件清单（数组，供与预期清单对照） |
| `testCommand` | 实际执行的测试命令 |
| `testPassed` | 该命令是否通过（布尔） |
| `readmeUpdated` | README 是否补充了 `greet` 用法（布尔） |

验收提示：**greet 子命令可用、单元测试通过、README 已补充用法；四项缺一不可。**

对应 spec §4.4「每次员工执行都有确定的输入快照、输出产物、工具记录」——黄金流程的
验收契约本身就是这条要求的最小实例。

## 7. 不做的事

- **不伪造 token / 费用 / 端到端耗时**。这三个量必须有一次真实模型执行才能得到。
  编造一个数值比留空更糟：阶段 3 会拿它当性能回退的判据。
- **不把本流程做成 CI 门禁**。黄金流程需要真实模型执行与凭证，跑在 CI 里会让
  所有离线环境红；它是**对拍工具**，在阶段 3 与每次 DSH 升级前手动执行。
- **不追求覆盖率**。黄金流程的价值在于「固定」，不在于「多」。增加第二条流程前，
  先确认它回答的是第一条回答不了的问题。
