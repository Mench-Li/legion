# PRT-252：Workbench 模型配置的产品化校验与用户可见错误

> 结论：`runtime/contracts/model-config.mjs`（纯函数，**18 例**）+
> `POST /api/models` 的配置期校验 + `handleWrite` 的结构化错误透出。
> 在此之前，那个接口**什么都不校验**——`provider`/`model` 非空就写库并回 200。

---

## 1. 缺口的具体形态（读代码读出来的，不是推演的）

前端 `workbench/src/api.ts` 里那份候选表的注释写着：

```
DSH 部署可用模型候选（来源：~/.dsh/settings.yaml 各 provider.models）
```

**那是某台机器上某个 DSH 部署的快照**，硬编码在界面里。而服务端
`POST /api/models` 只做两个非空判断，然后 `INSERT ... ON CONFLICT DO UPDATE`，
回一个 200。

于是三件**完全不同**的事被同一个"成功"盖住：

| # | 真实情况 | 用户看到的 |
| --- | --- | --- |
| ① | 照着那份旧表配了**这台机器上没有**的模型 | 保存成功 |
| ② | 在 A 机器配好，换到 B 机器 | 保存成功（配置还在，模型没了） |
| ③ | 模型对，但那个档案**没有凭证** | 保存成功 |

三种情况的失败都出现在**很久之后、另一个地方**，而且
**与"当初配置时点错了"之间没有任何连接**——用户看到的是一次莫名其妙的运行失败。

---

## 2. 本模块的判断

> **「能存下来」不等于「能跑」。**
> 配置错误必须在**配置的那一刻**、用**用户能看懂的话**说出来，并带上"下一步做什么"。

但这句话有三个很容易踩空的地方，本模块刻意把它们分开——**每一条被合并掉，
都会产生一种用户看得见的坏结果**。

### ① 「校验不了」≠「配置错了」

读不到模型档案仓储时，我们**不知道**用户配得对不对。这时报"未知供应商"是**撒谎**：
它会让人去查拼写，而真正的问题是我们根本没查成。

所以那是独立的 `CANNOT_VALIDATE`，并且 **fail closed**：

> 一个"查不了就放行"的校验，比没有校验更坏——它会让人相信一件没被验证过的事。

### ② 「一个档案都没有」≠「你选的那个供应商未知」

没有任何档案 → 用户**还没登记任何模型**。此时说"未知供应商"会把人引向
"我是不是拼错了"，而真正该做的是"先去登记一个"。

**错误的具体程度必须与实际的确定程度相称。**

### ③ 「合法」≠「能跑」

缺凭证是一个**警告**，不是拒绝："先登记模型、后补凭证"是合法操作顺序，
拒绝它会把正常路径堵死。但静默通过也不行——用户会以为配好了。
所以是 `ok: true` + 一条**必须显示出来**的 warning。

**不允许存在"看起来成功了但跑不了"的沉默状态。**

---

## 3. 不猜的两处

**型号不做模糊匹配。** 只有前后空白会被 trim，其余一律精确比较。
近似匹配会让一个拼错的型号被悄悄接受，然后在运行时以另一种面目失败。

**不知道就不说。** 档案有两种形态：仓储 descriptor 带 `hasCredential`（布尔），
完整档案带 `secretRef`。**两者都没有时不报缺凭证**——那时我们不知道，
而猜"没有"会制造一条**永远不对**的警告。按本项目已记过的那条：

> **一条永远不对的告警，和没有告警，是同一件事。**

---

## 4. 结果码

| 码 | 何时 | 文案要点 |
| --- | --- | --- |
| `MODEL_CONFIG_OK` | 通过 | 可带 warning |
| `MODEL_CONFIG_EMPTY_SELECTION` | 缺 provider/model | 点名缺哪一个 |
| `MODEL_CONFIG_CANNOT_VALIDATE` | 读不到仓储 | **"未被验证，不等于配置有错"** |
| `MODEL_CONFIG_NO_PROFILES` | 一个档案都没有 | 给出"先去登记" |
| `MODEL_CONFIG_UNKNOWN_PROVIDER` | 供应商不在集合里 | 列出**实际登记过**的供应商 |
| `MODEL_CONFIG_UNKNOWN_MODEL` | 型号不在该供应商下 | 只列该供应商下的型号 |

`UNKNOWN_MODEL` 的候选**不得**混入别的供应商的型号——那会让用户以为换一家供应商就行。

另有一条用例断言**每个码都可达**：不存在"定义了但永远不会出现的分支"。

## 5. 接线

`POST /api/models` 里，在两个非空判断之后：

```js
const verdict = validateAgentModelSelection({ provider, model, profiles: modelStore.list() })
if (verdict.ok !== true) throw modelConfigErrorFor(verdict)
```

`modelConfigErrorFor` 抛出带 `statusCode: 400` 与 `code`/`field`/`hint`/`candidates`
的错误；`handleWrite` 把这些字段**只在存在时**附加进响应体
（逐个字段判断，不展开 `e`，避免把 `stack` 或内部字段带出去），
于是前端可以把错误落到**具体的输入框**上。

### 为什么这里拒绝而不是只警告

写出一个跑不起来的绑定，代价是用户在一次**真实运行失败**之后才回头怀疑配置；
而拒绝的代价只是他改一下下拉框。**两者不对称，所以拒绝。**

### 端到端实测（真起 hub、真发请求）

```
① 无档案时: 400
   {"error":"还没有登记任何模型档案，因此无法把它指定给智能体。
             请先在「模型设置」里登记一个供应商与型号（并配置凭证），再回来指定。",
    "code":"MODEL_CONFIG_NO_PROFILES",
    "hint":"请先在「模型设置」里登记一个供应商与型号（并配置凭证），再回来指定。",
    "candidates":[]}
```

注意它是 `NO_PROFILES` 而**不是** `UNKNOWN_PROVIDER`——正是 §2 ② 那条判断。

## 6. 变红验证

```
基线 fail = 0
✔ 变红  fail=2  「校验不了」塌成「配置错了」（让人去查拼写，而问题是没查成）
✔ 变红  fail=2  「一个档案都没有」塌成「未知供应商」（该做的是先去登记）
✔ 变红  fail=2  「查不了就放行」（fail open）
✔ 变红  fail=4  缺凭证静默通过（保存成功但跑不起来，且失败在很久之后）
✔ 变红  fail=1  路由不再调用校验（退回"什么都存"）
✔ 变红  fail=1  调用了校验但**忽略结果**（最隐蔽的一种：看着像校验过）
✔ 变红  fail=1  field 不再进响应体（前端拿不到该落到哪个输入框）
```

### 变红验证自身出过一次错，值得记

第 ⑤ 条第一版写成 `if (false) throw modelConfigErrorFor(verdict)`，
于是源断言里的正则 `/throw modelConfigErrorFor\(verdict\)/` **仍然匹配**，
用例**照样全绿**。

> **一个没生效的变红验证，和一个通过的验证，在输出上完全一样。**

这正是本项目已经记过的那条，而它刚刚在这里又发生了一次。改成**真的把调用删掉**
之后才变红；并补了 ⑤b（调用了但忽略结果），因为那是更隐蔽的一种"看着像校验过"。

---

## 7. 这道闸门的**盲区**（必须说清）

接线那一条是**源码断言**，不是行为断言。它抓住的是"调用被删掉"，
**抓不住"语义被削弱"**：把

```js
if (verdict.ok !== true) throw modelConfigErrorFor(verdict)
```

改成

```js
if (verdict.code !== 'MODEL_CONFIG_CANNOT_VALIDATE' && verdict.ok !== true) throw ...
```

（即"校验不了时放行"）时，**文本仍在，用例仍全绿**——上面的变红清单里
那一条就是**没红**的。行为覆盖在端到端冒烟里，不在套件里。

> **一道看不见某类改动的闸门，比没有闸门更危险**——它给人"已经守住了"的错觉。

所以这里把盲区写明，而不是让它看起来像全覆盖。要真正堵住这一类，
需要把 hub 路由测试纳进套件（一个**真起进程**的用例），那是下一步。

## 8. 未交付

- **前端还没用上这些字段。** `ModelConfigModal.tsx` 目前仍从硬编码的
  `MODEL_OPTIONS` 渲染下拉框，`field`/`hint`/`candidates` 拿到手也还没渲染。
  PRT-507（Workbench 模型设置页）会重做这一块；在那之前，
  **服务端已经不再接受非法配置**，只是错误在 toast 里以整句文案出现。
- **前端的 `MODEL_OPTIONS` 硬编码仍在**，与产品档案是两份来源。
  这是一个真实的漂移风险：界面可能提供一个产品里并不存在的型号，
  用户选了之后被服务端拒绝——比之前"静默存下来"好，但仍然绕了一圈。
  下一步应改为从 `/api/model-profiles` 拉取。
- **`MODEL_TIER_TEXT` / 档位（light/balanced/heavy/vision）不在产品档案里**，
  所以"按档位挑模型"这条体验暂时接不上。
- **hub 路由测试未纳入套件**（见 §7 的盲区）。
