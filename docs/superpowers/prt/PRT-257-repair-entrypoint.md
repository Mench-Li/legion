# PRT-257 修复入口的后半：让修复计划真的被行使

> 本文记录 `runtime/dsh-composition/repair.mjs`。它补的是
> `PRT-215-257-dsh-bootstrap.md` §5 里那句诚实边界：
> 「修复计划也**只到「给出动作名」，没有真的执行修复**」。

## 1. 落地前的事实

`repairPlanFor()`（`bootstrap.mjs`）把自检的失败项翻成
`{check, action, label, why, reasons}` —— 一份**计划**。而它此前唯一的消费者是
"打印给人看"：`git grep` 找不到任何执行其中动作的代码。

于是「修复入口」与「请重装产品」对用户是同一件事：**一句他早就知道的话**。

> 一个功能没有入口，与这个功能不存在，对用户来说是同一件事。

## 2. 哪些动作**不许**被自动执行（本节是全文最要紧的一节）

`reapply-composition-patch` 是唯一一个「我们明明有能力自动做」的动作——
`render.mjs` 能生成 `legion-host.patch.yml`。而它**必须**要求显式批准。

理由在 `index.mjs` 顶部：DSH 的用户 profile 是 `patchReload: 'live'`，
**组合改动热生效，不需要重启**。于是往运行中的 profile 写入这一层会
**立刻改变正在跑的 harness 的强制面，包括发起这次修复的那个进程自己**。

把它做成「自检没过就自动重写」的顺手行为，等于给一次误调用准备了
**把当前进程的沙箱降级**的能力。所以：

- 本模块**不含**任何写 profile 的代码，applier 一律**注入**；
- `reapply-composition-patch` 只有出现在 `approved` 里才会被执行；
- 没批准时它不是"跳过"，而是一条**具名的待办**（`needs-approval`），
  且说明里带 `patchReload` 这个理由——只说"没批准"等于没说。

| `action` | 处理方式 | 为什么 |
| --- | --- | --- |
| `reapply-composition-patch` | `applier` + **需要批准** | live reload：会改掉发起修复的进程自己的强制面 |
| `install-supported-runtime` | `manual` | 换的是 DSH 运行时本身，不在本产品范围内 |
| `fix-sandbox-backend` | `manual` | 沙箱后端是宿主的配置与运行环境 |
| `connect-composition-observer` | `manual` | 观察器是**注入**进装配调用的，接上它是改调用方的代码 |
| `inspect-manually` | `manual` | 没有预置修法 |

`manual` 是**如实说做不了**——好过给一个假装能做、实际什么也没改的按钮。

## 3. 判据是**重新自检**，不是 applier 的返回值

执行完动作后，本模块**重新跑一次自检**，并从**新结论**里读出每一项的判决。
applier 说自己成功了，只进 `applierSaid`（诊断用），**从不作为判据**。

修复是唯一一种「做错了反而更糟」的操作：其他任何动作做错，用户看到的是一个
**仍然坏着**的东西；修复做错，用户看到的是一个**看起来修好了**的东西，
而强制面依然不在。

> 一个**静默地什么都没修**的修复入口，比没有修复入口坏得多。

三条由此推出的规则：

1. 复核里**找不到**对应的检查项 → `unverified`，**不是** `fixed`。
   一项检查从报告里消失，比它报"没过"更值得警惕。
2. 复核自己失败（抛出 / 形状不对）→ 全部 `unverified`，**不是**全部 `fixed`。
3. applier **抛错**的项不参与复核改写：它没有成功执行过。
   「抛错但环境恰好自己好了」被记成"修复生效了"，下一次不会这么走运。

判决表是**总的**（`REPAIR_VERDICTS`，六条，没有第七条）：`fixed` /
`still-failing` / `unverified` / `needs-approval` / `manual` / `applier-threw`。

## 4. 「本产品做不了」与「接线缺一截」是两个判决

动作登记为 `via: 'applier'`，但调用方**没有注入** applier 时，
结果带 `REPAIR_NO_APPLIER` 与一句说明：

> 「…」被登记为可执行，但没有注入对应的 applier：这是接线缺一截
> （不是"本产品做不了"）。手动做也可以，但请知道这条是**可以自动化**的。

混成 `manual` 的话，排查方向会从"去人工重装"开始，而真因是没人接 applier。

同理，**未登记的动作不许被丢掉**：丢掉它等于那一项失败不存在，
而它仍然在阻止执行。

## 5. 顶层码：区分「没判定」与「判定为没好」

```js
code = outstanding.length === 0
  ? null
  : (recheckError !== null ? REPAIR_CODES.RECHECK_FAILED : REPAIR_CODES.STILL_OUTSTANDING)
```

两件事的下一步动作完全不同：**再查一次** vs **去解决那一项**。
顶层不塞一个笼统的失败码，具体判决在 `outcomes` 里。

`needsHuman` 不计入 `unverified`——它要的是**再查一次**，不是人工去修。

## 6. 变红验证：14 处，14 处红（第一轮 12 处）

第一轮两条没咬，**两条都是瞄错层**，且第二条暴露了一处真实的死代码：

| 探针 | 第一版瞄了什么 | 为什么没红 | 处置 |
| --- | --- | --- | --- |
| ⑰① | 阶段一的**占位判决**（`verdict: threw === null ? …`） | 阶段二**总会**用复核结果改写它——占位值在任何跑得通复核的路径上都不可观测 | 改瞄 `unverified` 的**文案**（被 applier 自述覆盖 → 用户读到"已修复"） |
| ⑰④ | 阶段二循环里的 `applier-threw` 守卫 | `final` 映射里**还有一道**同样的守卫，判决由后者决定；循环里那道只影响一个永不被读到的 `verdictOf` 条目 | 改瞄 `final`；**并删掉循环里那道死守卫** |

> 一道守着另一个守卫的守卫，在观测上与不存在同形。

删掉死守卫不是"顺手清理"：一段看起来像防线、实际不改变任何输出的代码，
会让下一个人以为那里有保护，从而不再在真正决定判决的地方加判断。

## 7. 本模块**没有**解决的事

- **真实部署里仍然没有调用方**。`repairRuntime` 从 `index.mjs` 导出、
  有 18 例套件、14 条破验证，但把它接进 Launcher 的"一键启动/修复"流程
  是 PRT-257 的另一半，**本批未交付**。
  出口被调用 ≠ 在真实部署里被调用。
- **`BOOTSTRAP_ALREADY_BOUND` 仍然是定义了但没有产生它的代码**。
  它不在本模块范围内，单独记录在 `PRT-215-257-dsh-bootstrap.md` §188。
- **`composition-patch-layer` 的真正修复仍然只能人工做**。本模块让它
  「可以被显式批准地执行」，但**没有**提供默认 applier——那正是
  §2 的取舍，不是遗漏。
