# PRT-304 任务扫描与认领策略

> spec 阶段 3：「`PRT-304`：提取任务扫描和认领逻辑。」
>
> `team-hub/claim-policy.mjs`（新增）+ `team-hub/run-store.mjs`（改为由它生成 SQL），
> 套件 `claim-policy`（35 例）。

## 1. 认领有两条路径，它们的差别只在「从哪一侧找」

| 路径 | 何时命中 |
| --- | --- |
| A. **从等着的尝试里挑** | 已经有第 N 次尝试排在队列里，直接把它租出去 |
| B. **从可入队的看板任务里挑** | 还没有任何尝试，把这条看板任务变成第 1 次尝试 |

## 2. 唯一真正要紧的那条纪律

**两条路径必须共用同一组「任务级资格」。**

这件事看起来是显然的，但它有一个很坏的失效模式：两条 SQL 各写一遍资格条件，
有人给其中一条加了个条件（或改了个状态名），另一条没跟着改。于是**同一个任务
从一条路径领不到、从另一条领得到**。

而「领得到」的后果是具体的：一条被将军拦下的任务（`hold = 1`）会在操作员以为
它停着的时候被执行——连带它的外部写操作。

> 一个「从等着的尝试里挑」与一个「从可入队的任务里挑」各写一遍资格条件的
> 认领逻辑，与一个「被将军拦下的任务照样会被领走」的认领逻辑，
> 是同一个东西——只是前者只在某一条路径上发生，平时看不出来。

所以资格规则提取成了独立模块：**`TASK_GATES` 只写一份，两条 SQL 都由它生成。**
想改资格条件，只有一处可改。

任务级资格现在有两条：`status = 'todo'` 与 `COALESCE(hold, 0) = 0`。

## 3. 三条「单源化」的东西

除了任务级资格，还有两处也只有一个来源：

| 单一来源 | 若各写一遍会怎样 |
| --- | --- |
| `TERMINAL_ATTEMPT_STATES` | 少列一个终态 → 那条任务**永远领不到**；多列一个 → 同一条任务被两个 worker 同时执行 |
| `QUEUED_ATTEMPT_GATES` | 尝试级资格只在一条路径上生效 |
| `PRIORITY_ORDER_SQL` | 高优先级任务排在后面，而没人会想到去查排序 |

`TERMINAL_ATTEMPT_STATES` 这一条值得单独说：**单一来源在这里反而让错误更隐蔽**
——名单漏掉一个成员时，SQL 会*忠实地跟着漏*，一致性检查全绿。
所以有一条用例把确切名单**钉死成字面量**，另有一条把三种终态之外的状态
逐个断言为「活跃」。

## 4. 加载时自检，且它必须是**可观测**的

`run-store.mjs` 在加载时就检查两条 SQL 确实共用了每一个任务级资格、
且都留了 `{scope}`。**为什么加载时抛而不是等到认领时**：这两条断言拦的都是
「静默失效」——它们不会报错，只会让某个 worker 在某个时刻多干了一件不该干的事。
一次启动就崩，远好过在生产里靠人去发现。

### 这里踩了两次坑，都是同一类

**第一次**：最初的自检只对**当前恰好正确的那份输入**作答——
`assertTaskGatesShared()` 读模块级的表，而那张表当时是完整的，
所以把校验逻辑削弱照样得到「没问题」。

> 一个只能对「当前恰好正确的那份输入」作答的校验，
> 与一个恒真的校验，在「它能不能发现错误」上同形。

处置：把两条 SQL 做成**参数**，用例喂一对故意分家的 SQL 进去。

**第二次**：参数化之后，用例能验「这个函数会抛」了，但**把 run-store 里那一行
调用删掉，用例照样绿**。于是导出 `CLAIM_SQL_INVARIANTS_CHECKED` 作为证据。

第一版导出的是一个**布尔**标记。结果那条"自检不跑却报成功"的探针
（把它改成 `= true`）**没咬**——因为能把它写成 `true` 的，恰恰就是那个把自检
删掉的改动。

> 一个可以被人随手写成 `true` 的「自检通过」标记，
> 与一个恒真的校验，在「它到底拦不拦得住」上是同一个东西。

处置：导出的是**证据的内容**——它校过的那两条 SQL 文本
（`{ ok, sqlA, sqlB }`）。想让证据成立，就得真的把它们生成出来。

## 5. 纯函数参考实现必须与 SQL 一致

`isTaskEligible` / `isAttemptClaimable` / `explainClaim` 是同一套资格的可读版本，
供 dry-run 与诊断使用。它们的价值取决于**与 SQL 一致**：

> 一个说法与做法不一样的说明书，与一本印错的说明书，
> 在「照它做会不会出事」上是同一个东西。

所以有一条用例把**每一个 gate 的 SQL 片段交给真的 SQLite 执行**，
再把结果与 `holds()` 在**同一批任务**上比对——不是"两段我手写的逻辑是否一致"，
而是"参考实现与真正跑的那条 SQL 是否一致"。

### 拒绝理由必须分开

`hold`、`非 todo`、`空间不匹配`、`退避未到点`、`被更新的尝试取代`
各有**自己的**理由码。把空间不匹配混进「资格不够」里，会让一次跨空间访问
看起来像一次正常的「这任务还不该领」。

## 6. 端到端：用真的库验证缺陷确实被拦住

除了比对 SQL 文本，还有一组用真 `DatabaseSync` 的用例：

- 被 `hold` 的任务：**两条路径都领不走**——包括**手工塞一条 `Queued` 尝试**
  进去（模拟「先排了队，然后才被拦截」），这正是漏掉任务级条件时会失守的地方；
- 被标成 `done` 的任务同样两条路径都领不走；
- 正常任务仍然领得到（改动没有把整条路堵死）；
- 退避没到点领不走，**时间推过去之后必须能领到**（否则「闸门」变成了「永久堵死」）；
- 只有最新那一次尝试会被领走（老的不该被重放）；
- 分空间领取：另一个空间的任务领不走。

## 7. 变红验证：22 处，22 处红

重点：★★ 两条路径各自漏掉 `hold` / ★ 共用自检恒返回 ok /
★★ **加载时自检不跑却报成功** / ★ 两条 SQL 少了 `{scope}` /
★★ 终态名单漏一个 / ★ 参考实现不看 `hold` / ★ 空间不匹配被混掉 /
★ 退避闸门失效 / ★★ 不判「是不是最新那一次」/ ★ `hasActiveAttempt` 恒 false /
★ 优先级排序消失 / ★ 拒绝码去重。

## 8. 本批**没有**解决的事

- **没有改动的行为语义**：这是一次**提取**，认领的实际行为与提取前一致。
  两条 SQL 的 `AND` 顺序变了（资格片段统一排在前面），对 SQL 语义无影响，
  但**参数顺序**保持原样（退避闸门仍是第一个 `?`）。
- **`isTaskEligible` 等纯函数目前没有生产调用方**：它们是诊断/dry-run 的
  参考实现，`--json` 策略快照 `claimPolicySnapshot()` 也还没有 CLI 用它。
  **不要读成「产品已经能在认领前预演判定了」。**
- **`CLAIM_REJECTIONS.ATTEMPT_ACTIVE` 只在 `explainClaim` 里产生**：
  path A 的「没有活跃尝试」条件仍然只存在于 SQL 的 `NOT EXISTS` 里，
  没有对应的纯函数 gate（因为它是子查询而非单行谓词）。
- **`claimPolicySnapshot()` 没有接进任何 `--json` 出口**。
- **`team-hub/server.mjs` 里的路由没有变**（路由仍是 136 条），
  这次提取**没有新增任何 HTTP 面**。
- **PRT-315/316（拆分 `plugins/src/index.ts`、team-hub 模块提取）没有做**。
