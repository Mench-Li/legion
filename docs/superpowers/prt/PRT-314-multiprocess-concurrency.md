# PRT-314：WAL、`busy_timeout` 与原子领取事务的多 worker 并发语义

**对应 spec**：§6.4 运行状态机、§6.10 进程顺序、§12 的 PRT-314
**阶段 3 完成标准**（spec 第 885 行）：强制终止 worker 或 DSH 后，重启不会丢任务、伪装成功或重复执行已确认的外部写操作。
**交付物**：`team-hub/scripts/claim-probe.mjs`（真子进程探针）、`team-hub/run-concurrency.test.mjs`（5 例）、
`team-hub/schema-util.mjs`（原子迁移原语，从 `server.mjs` 与 `run-store.mjs` 各一份收敛为一份）

---

## 1. 为什么必须是真的操作系统进程

同一进程内的两条连接共享的比不同进程多得多：同一份 `node:sqlite` 模块实例、
同一次 `PRAGMA` 设置、同一个事件循环——而且**两条 `BEGIN IMMEDIATE` 不可能真的同时发出**
（JS 是单线程）。

因此「并发领取只有一个赢家」在那种测法下几乎必然成立。它证明的是
"我把条件更新写对了"，而不是"两个进程抢的时候不会都赢"。而后者才是
「不重复执行已确认的外部写操作」在数据面上的真正含义：
两个 worker 各执行一遍 = 对已发生的付费/推送就是重复副作用。

多进程这一层要验的是另外三件事：

| 判据 | 为什么单进程测不出来 |
| --- | --- |
| WAL 的**跨进程**可见性 | 同一连接永远看得到自己的写入；跨进程才依赖 WAL 的共享内存索引与 `-wal`/`-shm` 文件 |
| `busy_timeout` 真的在等 | 同一进程的锁争用会先被 JS 事件循环串行化掉，根本到不了 SQLite 的锁等待 |
| 条件更新在**真并发**下的胜负 | 见上：两条 `BEGIN IMMEDIATE` 不是同时发出的 |

## 2. 探针（`team-hub/scripts/claim-probe.mjs`）

一个**测试夹具**，不是产品代码：它以独立进程运行、自建连接、把结果打成一行 JSON
（产品里的 worker 走 HTTP，数据面单源）。

- 连接设置与 `server.mjs` 一致：`busy_timeout = 5000` 先设，再确保 WAL。
  少了 `busy_timeout`，多进程争用会直接抛 `SQLITE_BUSY` 而不是按预算等待——
  那是"偶发失败"而不是"明确拒绝"，会把并发问题伪装成随机故障，而随机故障最难查。
- 用 `Atomics.wait` 忙等到指定**绝对时刻**才动手。不用 `setTimeout`：
  定时器精度受事件循环影响，N 个进程会在几十毫秒的窗口里散开，
  于是「真的同时争用」变成了「先后到达」——用例照样通过，但它验证的东西已经不是并发。
- 只输出 JSON 能安全承载的叶子字段。

## 3. 五条判据

### ① WAL 跨进程可见 + 读不被写阻塞

父进程领走任务后，子进程必须看到**同一个真相**（`code 0` + `queue-empty`）。
判据是 `code === 0` 而不是 `claimed !== null`：表或库不可见时探针会**报错退出**，
因此"队列空"恰好证明了跨进程可见。

同时断言 `pragma_journal_mode` 是 `wal`：回滚日志模式下读写互斥，多 worker 会互相饿死。

### ② `busy_timeout` 真的在等

父进程用 `BEGIN IMMEDIATE` 持住写锁，子进程在锁被持有时写入。
没有 `busy_timeout` 时它会立刻拿到 `SQLITE_BUSY`（"database is locked"）。

**这里踩到一个脚手架死锁**：写成 `env.db.exec('BEGIN IMMEDIATE')` →
`await runProbe(...)` → `COMMIT` 时，父进程在等子进程、子进程在等父进程的锁，
两个一起等到超时。那不是"写锁生效"，那是测试自己锁死了自己，
并且会把结论误导成"连接失败"。改为用**定时器异步放锁**。

### ③ 6 个进程同时抢同一条任务，恰好一个赢

所有进程等到同一个绝对时刻再动手，前后留 250ms 让它们都启动完。
断言：赢家恰好 1 个；输家必须给出**明确原因**（`lost-race` 或 `queue-empty`，
两者分开是因为前者该立刻再试、后者该退避等待）；库里恰好一条尝试且属于赢家。

### ④ 并发补列不崩（**这条抓到了真实缺陷**）

造一个"真的老库"——只有 PRT-302/303/313 那批的列，没有 PRT-309/310/311 新增的列。
这正是线上可能出现的样子（上一批已经推送到远程）。然后两个**进程**同时启动各跑一遍迁移。

### ⑤ 领取用的是 `BEGIN IMMEDIATE`

父进程持锁期间子进程只能等；锁放开后它领到那条尝试，且实测等待时长接近持锁时长。
若领取是"读→改→写"（没有写锁语义），子进程会在锁放开前就读到 `Queued` 并成功——
那样两个持有者可以同时认为自己领到了同一行。

## 4. 抓到的真实缺陷：非原子的 `ensureColumn`

`ensureColumn` 是启动期迁移的唯一入口。我把它从 `server.mjs` 提取成共享模块时，
顺手写成了最自然的形状：

```js
// ✗ 错的
if (columnExists(db, table, column)) return false
db.exec(`ALTER TABLE ${table} ADD COLUMN ${column} ${ddl}`)
```

`server.mjs` 里原有的实现是**原子**的（`BEGIN IMMEDIATE` 内重读列名再 ALTER），
而且注释里写明了原因。我重写时丢掉了这一点。

后果：两个并发启动的进程都读到「列不存在」，于是都执行 ALTER，
后者拿到 `duplicate column name: idempotency_key` 并在**模块加载期**崩溃。
真实形态是 8787 独立进程与 3080 宿主外壳同时启动时其中一个起不来，
表现为 `/team-hub` 路由缺失 + 一条加载失败日志，**看起来与数据库迁移毫无关系**。

### 为什么这条用例值得单独说

我把实现改回非原子版本跑了一遍，确认用例会红：

```
✖ ④ 并发补列：两个进程同时迁移一个「老库」，都成功且只补一次
  Error: duplicate column name: idempotency_key
```

再恢复原子实现确认变绿。**一个无论实现对不对都通过的用例没有价值**——
并发用例尤其容易被写成那样（时序不对时它"碰巧"不触发竞争，于是永远绿）。
因此这条例用是被验证过"能红"的。

修复方式不是再写一遍，而是让实现**只有一份**：`team-hub/schema-util.mjs`
导出 `columnExists(db, table, column)` 与 `ensureColumn(db, table, column, ddl)`，
`server.mjs` 的 30 多处调用点改为补 `db` 参数的薄包装，`run-store.mjs` 直接调用。

一份微妙的并发原语存在两份实现时，其中一份迟早会腐烂——
这次腐烂的是我新写的那份，而被它影响的却是一个与运行面无关的启动路径。

## 5. 顺带修掉的两处测试脚手架缺陷

两者都不是产品问题，但都会把结论带偏：

**① 脚手架死锁（见 §3②）**：父进程同步等子进程拿它自己持有的锁。

**② 一处断言与注释正好相反**：写在
`// 另一个进程读到同一状态` 下面的是 `assert.notEqual(probe.result.claimed, null)`。
但任务已被父进程领走，子进程**应该**领不到。改成断言 `code === 0` +
`claimed === null` + `reason === 'queue-empty'`，并写清为什么
（表不可见时探针会报错退出，而不是优雅返回"队列空"）。

## 6. 未交付

- **多进程压测的规模与锁等待预算**：目前是 6 个进程、`busy_timeout = 5000`。
  真实部署的 worker 数量、以及**争用激烈时 `busy_timeout` 是否够**没有实测曲线。
  当前判据只回答了"能正确串行化"，没有回答"多忙会开始超时失败"。
- **跨进程的优雅停止**：本批验证的是数据面并发语义，
  没有覆盖"一个进程在被强杀时另一个进程正在写"这一时序（属 PRT-312 的强杀演练）。
- **PRT-312 的真实强杀整链路演练**：Windows 上强制终止不走信号处理器，
  因此"进程被杀 → 租约过期 → 回收 → 另一 worker 接手"仍是分两段验证的。
