| `team-hub/server.mjs` | 2 | 7 |

在那之前动它，会和别人每天的功能提交搅在同一片 diff 里。

★★★ **上表在 2026-09-17 被复核过，结论不变但数字要改口径。**
当时那个探针的窗口计数写法（`<oldest>^..<newest> -- <file>`）在带合并的历史上
**两个方向都会错**——`A^..B` 会沿合并的第二个父亲捞进一大堆不在窗口里的提交
（详见 `docs/MULTI-AGENT-FEATURE-STATUS.md` §6.1）。
在**当年那次判定所在的那个提交**（`9bec1e5`）上复算，最近窗口的两种写法**给出同一个数**：

```text
9bec1e5（2026-09-11，门禁通过那次）
  plugins/src/index.ts   w1: 精确 1 / 区间 1     峰值 精确 9
  team-hub/server.mjs    w1: 精确 0 / 区间 0     峰值 精确 10
```

于是**"已降温"这条判定本身没有被这处缺陷污染**（最近窗口一致，都 ≤2）。
但上表里 `team-hub/server.mjs` 那一行的「2」和「7」**我复算不出来**（精确值是 0 和 10）——
它们可能来自另一个提交或更早的窗口口径。这一条如实记下，不改历史表格。
⚠️ 而 2026-09-17 当天的读数**已经不是**"已降温"：精确值 `team-hub/server.mjs` **9/40**，
超过阈值 2 ⇒ **未降温**。那个变化与"当年那次判定"无关，是**这期间真的有人一直在改它**。

> > 与一个"根本没有兜底逻辑"，在没有事故的时候是同一个东西——

而这段代码做的事一点都不轻：它会对**有未提交产出的 worktree** 执行

登记了产物、但从未进过任何 commit，被连文件带目录删掉。

## 2. 依赖分三类，各自有各自的理由

拆分的唯一技术难点是：**把原来隐式捕获的东西显式化**。

① **纯函数/工具**（`log` / `runGit` / fs 原语）：直接注入。
② **可变状态**（`hubUrl` / `useHub` / `stageByRole`）：**传取值函数，不传值**。

这三个在原文件里都是 `let` 且运行期会被**重新赋值**——
`detectHub()` 探测成功后写 `hubUrl` 与 `useHub`；换流水线来源时
`stageByRole = new Map(...)` 整个换掉。

> 一个"构造时快照了可变配置"的模块，
> 与一个"每次用之前重新取值"的模块，在只跑一次的场景里是同一个东西——
> 只不过前者会在配置变化之后，安静地继续按旧的来。

失效症状具体是：探测到 hub 了、调解员还是不走 hub（**多空间任务没人调解**），
或者换流水线之后判定永远说"这个角色不在流水线里"，而**一行错都没有**。

③ **兄弟能力**（`safeComment` / `advanceTo` / `activity` / `getTask` /
`listTasks` / `startOneShot`）：这些要写 hub、要跑 subagent，仍属于 worker 的
上下文，**故意留在 `index.ts`**，由构造点注入。调解模块只声明
"我需要一个能安全发评论的东西"，不关心它怎么实现——这也让它能只用替身测。

`mediateAttempts` / `mediateRetryAt` / `mediating` 同理留在外面：worker 内嵌调解
与公共调解员两条路径**共用同一份**重试计数，搬进去会变成两份。

## 3. ★ 两处刻意的取舍

### 3.1 `config` 用结构性类型，不 import `Config`

`Config` 是 `index.ts` 里 zod schema 推出来的值，import 它会形成**真的**运行时循环依赖。
所以 `mediation.ts` 只声明本切片真正读的四个字段。

这不造成漂移：调用点传的是**真的** `Config`，TypeScript 在赋值处校验可赋值性——
`config.intervalMs` 被改名的那天，**编译会红在调用点**，而不是让模块安静地读到 `undefined`。

### 3.2 ★ `MediatorSchema` 自述形状，不 import `ObjectJsonSchema`

PRT-108 的棘轮门禁把 `@deepseek-ai/dsh-tools` 算作「DSH 执行面记号」，
基线只允许**既有**文件持有；新增文件出现执行面记号**直接红**。

我第一版直接 `import type { ObjectJsonSchema }`，门禁红了。摆在面前两条路：

- `--update-baseline` 把它加进基线 —— 但那正是门禁设计上要防住的「洗白」；
- 让这个模块**真的**不依赖 DSH。

选了后者。`mediation.ts` 只声明自己产出的两种节点
（带枚举的字符串、字符串数组），并**不复述** DSH 的完整子集：

```ts
export interface MediatorSchema {
  type: 'object'
  properties: Record<string, MediatorNode>
  required: string[]
  additionalProperties: boolean
}
export type MediatorNode =
  | { type: 'string'; enum?: string[] }
  | { type: 'array'; items: MediatorNode }
```

**这不比 import 弱**：接线点（`index.ts` 传真实的 `startOneShot`）会做可赋值性检查，
`MediatorSchema` 必须是 `ObjectJsonSchema` 的子类型才编译得过。DSH 收窄子集时，
报错发生在**编译期的构造点**。

> 一个"从 DSH import 类型"的模块，
> 与一个"自述形状、由接线点证明兼容"的模块，在编译通过时是同一个东西——
> 只不过前者把耦合藏在一行 import 里，后者把它摆在构造点上。

> 一个"新增文件里多一行 `import type`"的改动，
> 与一个"插件层开始自己长 DSH 执行面依赖"的改动，在棘轮门禁眼里是同一个东西——
> 只不过前者根本不影响运行时（类型会被完全抹掉）。

**门禁最终零例外通过**：`dsh-boundary: PASS（执行面依赖未增长：3 个文件 / 26 处，均在基线内）`。

> 顺带：门禁的扫描口径是**词法**的，注释里的记号同样计数。它自己的文件头解释了
> 为什么不去剥注释（`stripComments` 认不出正则字面量里的 `//`，
> 会把**假阳性换成假阴性**，而边界门禁里漏算远比多算严重）。实测确认
> 注释里写包名**不会**触发（`PACKAGE_RE` 需要 import 上下文），所以正文里保留了讨论。

## 4. 验证一：搬得对不对（逐字对拍）

重构最容易出的错不是"编译不过"，是"**编译过了但某一行悄悄变了**"。

做法：把旧版 `index.ts` 临时还原、构建一次，取回 `lib/index.js`；
再构建新版，取回 `lib/mediation.js`；然后按大括号配平**抽出每个被搬走的声明**逐字比较。

只放行一份**穷尽的改写白名单**（可变状态与时钟从隐式捕获变成显式注入）：

```
stageByRole.  →  stageByRole().
useHub        →  useHub()
${hubUrl}     →  ${hubUrl()}
Date.now()    →  now()
```

白名单写成**改写规则**而不是"允许出现的字符串清单"：

> 一个"我事先列了几条允许的差异"的检查，
> 与一个"真的验证了除这几条外什么都没变"的检查，在绿的时候长得一样——
> 只不过前者会在下一次改写时，把新的差异也一起放过。

结果：

| 被搬走的声明 | 结果 |
| --- | --- |
| `mediateReview`（127 行） | ✅ **逐字相同** |
| `dispatchMediator`（29 行） | ✅ 逐字相同 |
| `mediatorRecoverWorker`（36 行） | ✅ 逐字相同 |
| `mediationCtxFor`（6 行） | ✅ 逐字相同 |
| `MEDIATOR_SCHEMA`（11 行） | ✅ 逐字相同 |
| `isMediatableMergeFail` / `preserveWorktreeLoose` / `refreshSpaceRepos` / `sweepMediation` | ✅ 差异**仅在已声明的注入改写内** |

并断言新版 `index.js` 里**不再含**这些函数体。

## 5. 验证二：新用例真的咬得住（断验证 9/9）

判据是 `fail > 0 && !importErr`，且每个探针还要断言**红的条数**与**红的用例名**——
避免"红了 5 条别的"被当成通过。

| # | 弄坏什么 | 结果 |
| --- | --- | --- |
| ① | 拆掉完整性闸门（合入后不再核对 `HEAD` 与 `w/<id>`） | ✅ 红 1 条（正是那条） |
| ② | `stageByRole` 改回构造时快照 | ✅ 红 1 条 |
| ③ | `now` 改回 `Date.now()`（旁路掉注入的时钟） | ✅ 红 1 条 |
| ④ | 去掉 🛑 放弃标记排除（重启后会无限重调解） | ✅ 红 1 条 |
| ⑤ | `publicMode` 下把"任何人"都算人工介入 | ✅ 红 1 条 |
| ⑥ | `sweepMediation` 去掉 `break`（一轮调解多个） | ✅ 红 1 条 |
| ⑦ | 刷新失败时清空空间缓存 | ✅ 红 1 条 |
| ⑧ | 去掉 24h 哨兵（每轮刷一条 🛑 评论） | ✅ 红 1 条 |
| ⑨ | 调解异常时不回退合并态 | ✅ 红 1 条 |

源码**逐字节还原**（哈希校验，`finally` 里兜底，被 kill 也不会留下变异版本）。

探针 ② 第一版**没咬住**（`fail=0`），查下来是**我的夹具错了**：
我写的是 `mutable.set('archive', ...)`——在同一个 Map 上增删键。
而真实的改写是 `stageByRole = new Map(...)`，**换掉整个 Map**。
在"同一个 Map 上增删"的夹具里，"取值函数"与"快照"拿到的是**同一个对象**，
两种实现都通过。

> 一个"在同一个 Map 上增删元素"的替身，
> 与一个"换掉整个 Map"的替身，在"取值函数 vs 快照"这件事上是同一个东西——
> 只不过前者会让快照实现看起来也是对的。

改成 `stages = new Map([['archive', ...]])` 后探针立刻咬住。同一批还补了一条
`hubUrl` / `useHub` 的活性用例。

## 6. 两个在写用例时发现的真东西

### 6.1 完整性闸门只在冲突解决路径上

我第一版把夹具写成"干净合入 + `HEAD` 与 `w/<id>` 有差异"，结果**没触发**闸门。

看代码才确认：这道闸门在**冲突解决路径**（3c→4），干净合入路径（3a）没有它——
而且**不需要**：那条路上的 `git merge --no-ff` 由 git 自己保证产出**双亲**提交，
不存在"树丢了"的形态。

> 一个"在不需要它的路径上也有"的检查，
> 与一个"只在需要它的路径上"的检查，在用例全绿的时候长得一样——
> 只不过前者会让你以为干净合入也被保护着。

### 6.2 `some(...)` 形式的断言在"已经发生过一次"时等于没测

「调解异常要回退合并态」那条，我原本断言
`runGit.calls.some(c => c.args.join(' ') === 'merge --abort')`。
但 `mediateReview` 的**步骤 0** 本来就会 abort 一次——所以异常路径完全没回退时，
`some` **也是绿的**。

改成数次数（`=== 2`）。

> 一个 `some(...)` 形式的断言，与一个"真的数了次数"的断言，
> 在被测调用恰好已经发生过一次时，读数是同一个东西。

### 6.3 替身按"书写顺序命中第一条"是个陷阱

`diff --name-only HEAD` 与 `diff --name-only HEAD w/T-1` 都是真实调用，前者是后者的**前缀**。
按书写顺序命中时，先写的那条会把后写的那条**整条吃掉**，于是完整性闸门那类用例
会因为一个空输出而**看起来通过**。改成**最长前缀优先**。

> 一个"按书写顺序命中第一条"的替身，
> 与一个"命中最长匹配"的替身，在规则恰好从窄到宽书写时是同一个东西——
> 只不过前者会在下一个人插入一条更宽的规则时，悄悄改掉已有用例的含义。

## 9. ⚠️ 诚实边界

1. **只完成 1 个切片。** spec 要求按**五类边界**（仓储、状态机、workspace、验收、交接）
   拆分，本批只做了「交接」这一类，而且只做了其中的合入调解一块。
   `spaceWorker()` 仍是约 2600 行。
2. **`plugins/src/types.ts` 目前只搬了 `Task` 与 `StageDef`。** `GoalCtx` / `PipelineDef` /
   `DiscussionDef` / `Config` 仍在 `index.ts`——按"每次只迁移一个切片"的纪律，
   本次改动的全部意义是「行为零变化」，多搬的每个类型都会扩大面积、削弱能证明的东西。
3. **逐字对拍证明的是"搬对了"，不是"这段代码是对的"。** 它只能证明新旧一致；
   里面原有的问题（如果有）会**一起**搬过来。
4. **断验证的 9 个探针只覆盖新用例断言到的东西。** 没断言到的分支（例如
   `preserveWorktreeLoose` 里 `add` 成功但 `commit` 失败那条路径）本轮没被覆盖，
   也就没被探针检验。
5. **`worker-regression.test.mjs` 等端到端用例确实走了调解路径**（它们跑真实守护），
   所以这次重构有端到端证据；但那些用例是**本批之前**就有的，
   它们覆盖的是调解的**主路径**，不覆盖 §7 里的边界分支。
6. **本批没有触碰 `team-hub/server.mjs`。** PRT-316（先提取 team-hub 数据库初始化、
   运行仓储、审计投影与路由模块）是同一阶段的另一件事，仍未启动。
