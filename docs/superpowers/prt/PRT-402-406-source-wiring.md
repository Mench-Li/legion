# PRT-402~406：来源装配的生产数据面

> spec §6.5。`runtime/context/sources.mjs` 把九类来源的归一、信任与截断都做全了
> （`collectCandidates` 一个入口），`createHubContextStage` 也早就留好了
> `loadSources(lease)` 注入点——而它的**默认值是 `async () => ({})`**。

## §1 这一批要解决的问题

关心智装配的三行（PRT-402/405/406）在进度表上都写着同一句诚实边界：
**"没有任何生产代码调用它"**。而"没有调用方"这件事的后果不是"少一个功能"：

> 一个"零来源"的运行会冻结出一份**完全合法**的空快照。
> 于是"这次运行看了 0 个来源"与"我们忘了接线"在下游是同一种记录，
> 而模型会照着一份空上下文继续跑完，并把结论写进回执。

kill-drill 走的正是这条路（发零来源 → 合法空快照），
所以这个缺口在演练里**看起来完全正常**。

## §2 ★ 本模块唯一要紧的纪律：读失败 ≠ 没有

hub 上**根本没有**的东西，与**有但这次读失败了**，在快照里都表现为
"这条来源不在"。两者必须走不同的路：

| 处境 | 含义 | 处置 |
| --- | --- | --- |
| **没有这条路** | 世界的形状（hub 至今没有 teamPlan 读端点） | 如实声明不可用，快照记 `missing` 并带原因 |
| **404** | 问过了，它说没有 | 返回 `null`，由调用方决定是否致命 |
| **500 / 超时 / 连接断** | **我们没问到** | **抛错**（`SOURCES_READ_FAILED`） |

> 一次"读失败"被当成"没有"，与一次"真的没有"，
> 在快照里长得一模一样——只不过前者会让模型基于一份不完整的世界观
> 得出结论，而快照上写着"来源已完整清点"。

这条区分是本模块存在的全部理由。把三种都归成"读不到就算了"的实现，
会让每一次网络抖动**静默地**变成一次"上下文更少的运行"。

## §3 hub 读面的真实覆盖（量出来的，不是推断的）

逐个在 `team-hub/server.mjs` 里找过 `GET` 路由声明：

| 来源族 | 读端点 | 本装配器的处理 |
| --- | --- | --- |
| `goal` | `GET /api/goal?scope=` | ✅ 按任务的 `goalId` 精确取 |
| `task` | `GET /api/task?id=` | ✅ 且评论与产物引用都在这一个响应里（`rowToTask`） |
| `comments` | 随任务详情返回 | ✅ 补上内容派生的稳定 id |
| `artifacts` | 引用随任务详情返回 | ✅ **只给引用**（PRT-405） |
| `skills` | `GET /api/skills?scope=` | ✅ 有上限 |
| `teamPlan` | **无** | ⛔ 显式 `null` + 点名 |
| `employeeManifest` | **无** | ⛔ 显式 `null` + 点名 |
| `userFeedback` | **无** | ⛔ 显式 `null` + 点名 |
| `upstreamDeliveries` | **无** | ⛔ 显式 `null` + 点名 |
| `workspaceState` | **无** | ⛔ 显式 `null` + 点名 |

**刻意不消费**的两个端点（连同理由，由 `availability().unconsumed` 给出）：

- `GET /api/artifact/content` —— 产物正文通常很大，"要不要读进来"是一个**预算决定**，
  该由调用方显式做（PRT-405）。
- `GET /api/skill-source` —— 同一类体积决定；`/api/skills` 的条目已足以让模型
  知道自己有哪些技能可用。

### 3.1 为什么缺失要**列出来**而不是不提

"这条来源不在快照里"与"这一类来源我们根本取不到"在账本上长得一样。
列出来之后，运维能一眼看出缺的是**产品的**这一块，而不是自己的配置。
形状与 `product/metrics-source.mjs` 的 `missing` 一致：
两种缺失在界面上都表现为「—」，但只有一种是**还没做**。

### 3.2 `upstreamDeliveries` 为什么不拿 `/api/runtime/handoffs` 顶

那个端点是 **worker 的移交状态**，不是上游员工的交付物。
拿它顶会把"某个 worker 交出了租约"读成"上游交付了一份成果"——
而 `upstreamDeliverySources` 给这一类来源的 `type` 是 `upstream-delivery`，
下游按它做"污染传递性"的判断。填错类型比填 null 更坏。

## §4 ★ 评论 id 必须内容派生

hub 的评论是 `{ by, at, text }`——**没有 id**。而 `commentSources` 要求非空 id，
且 PRT-404 明确规定评论按 `(createdAtMs, id)` 排序：

> "数据库查询顺序不是数据的一部分，它变了不该让快照哈希变"

所以**不能**用数组下标当 id：下标把"查询顺序"偷偷变回了数据的一部分，
一条评论被重新排序就会让同一个世界算出两个快照哈希——
而快照哈希正是回放与篡改检测的凭据。

用 `sha256(by \0 at \0 text)` 的前 16 位：同一条评论**永远**得到同一个 id，
与它排第几无关。作者也进 id——两个不同的人说同一句话是两条评论。

同一件事的另一半：hub 的 `at` 是 **ISO 字符串**，而 `sources.mjs` 的
`acquiredAt` 要 epoch 数字。`epochMsOf` 负责换算，且**取不到时返回 `undefined`
而不是 `0`**——`0` 会被读成 1970 年。

## §5 构造期就拒绝的三种接线错误

| 情形 | 码 | 为什么不能推迟 |
| --- | --- | --- |
| 没给 `read` 能力 | `SOURCES_LOADER_BAD_WIRING` | 没有它只能返回零来源，而零来源会冻结出一份**完全合法**的空快照 |
| lease 上没有 `scope` | `SOURCES_LOADER_NO_SCOPE` | 来源该放进哪个空间无从判断，而**放错空间就是一次越权** |
| lease 上没有 `taskId` | `SOURCES_LOADER_NO_TASK_ID` | 上下文里没有"这次要做什么"，模型会照样跑完并给出结论 |
| 任务读回来是空的 | `SOURCES_LOADER_TASK_NOT_FOUND` | 这个 Attempt 是为一个不存在的任务领的；**与"读不到"修复动作完全不同** |

`requireTask: false` 供演练/空跑使用——但那时来源里仍然如实为空，
而不是编一个占位任务。

## §6 验证

### 6.1 套件（22 例）：起**真的 hub**

本模块的全部工作就是在读面上取数：端点路径、查询参数名、响应形状
（`/api/goal` 回的是 `{goals:[…]}` 还是裸数组、任务详情里评论叫什么字段）。
这些**只能**由真的 hub 回答。

> 一个用假 hub 喂出来的"装配器已验证"，
> 与一个从没发过那次请求的"装配器已验证"，是同一个东西——
> 只不过前者的用例数是完整的。

### 6.2 破坏性验证：63①–63⑫

见 `docs/STATUS.md` 的本轮条目与探针输出。

### 6.3 写这一组时踩到的两处（如实记录）

**① `/api/create` 不采用调用方给的 `id`**，它自己发号（`T-001`…）。
夹具用了自己编的 id，于是后面 `/api/task?id=<编的>` 全是 404——
表现成"装配器读不到任务"，**看起来像本模块的缺陷**。

> 一个"夹具用错了 id"的 404，
> 与一个"装配器端点写错了"的 404，在测试输出里长得一模一样。

**② 探针指向了它补丁没碰的文件。** 初版 63⑫ 补丁打在 `run.mjs` 上，
却让探针去跑 `sources-loader.test.mjs`——那套用例自建 hub 客户端，
根本不经过 `run.mjs`。`fail=0` 会被读成"这条判据测不出来"。

这与 PRT-711 的"锚点没命中"、PRT-712 的"跑错测试文件"是同一类：
**探针自身的错误伪装成判据的缺陷**。故探针的 `files` 必须与补丁所在模块对应。

## §7 诚实边界

- `createHubContextStage` 的默认 `loadSources` **仍然是** `async () => ({})`。
  本批交付的是**可用的**装配器，不是"已经自动接上"——
  默认值改为本装配器是另一个决定（它要求进程里已经有一个 hub 客户端）。
- 生产 CLI 入口的 `executor` 仍为 `null`（RuntimeAdapter 是 PRT-253/311），
  所以**今天没有真实部署走过这条路**。本接线目前只在用例与真实 hub 上验证过。
- `teamPlan` / `employeeManifest` / 用户反馈 / 上游交付 / 工作区状态
  **取不到**，因为 hub 没有这些读端点。这是**产品侧的缺口**，
  不是本模块配置错了。补齐它们要新增读端点（会动路由基线）。
- 兄弟任务（`tasks`）刻意不取：它们属于"当前任务之外的东西"，
  该由调用方显式决定要不要，而不是由装配器顺手全带上。
- 产物的**正文**不取，只给引用；`includeContent` 的通路留在
  `artifactSources` 里，由调用方按预算决定。
