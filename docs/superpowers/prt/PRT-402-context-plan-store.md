# PRT-402（数据面批）：TeamPlan 与 EmployeeManifest 真的存在了

> 那两条来源函数（`teamPlanSource` / `employeeManifestSource`）**早就做全了**，
> 而且两条都是 `required: true`。但 hub 上没有它们的读端点，于是
> `sources-loader.mjs` 只能传 `null`，装配器**每次运行**都产出两条 `missing` 候选。
>
> > 一个"每次运行都缺两条必需来源"的产品，
> > 与一个"这次运行确实没有团队计划"的运行，在快照上长得一模一样——
> > 只不过前者的那两条缺失**永远**不会消失，于是没有人会去看它们。

本批把这两条从"还没做"变成"有了"：新增 `team-hub/context-plan-store.mjs`
（两张表 + 冻结/递增/明文检查）、6 条 hub 路由、装载器真的去读。

---

## 1. ★ 先量了一下"缺"到底长什么样

动手之前跑了一遍真 hub + 真装载器 + 真装配器，把**改动前**的账本打出来：

```
对照（teamPlan=null）included: task:T-001
对照 excluded: team-plan:missing:missing | employee-manifest:missing:missing
```

两条 `required: true` 的来源进了 `excluded`，理由是 `missing`，**每一次运行都是**。
改动之后：

```
included: employee-manifest:e-e2e | task:T-001 | team-plan:tp-e2e
excluded: (无)
```

这就是整批的完成判据，而它是**跑出来的**，不是推断的。

---

## 2. ★ 冻结：TeamPlan 按 `(scope, id, version)` 追加

spec 第 7 行把 TeamPlan 定义为「目标创建时**冻结**的团队、岗位、流水线和能力包组合快照」。
"冻结"不是"我们打算不改"，是**结构上改不了**：复合主键里有 `version`。

- 同一 `(scope, id, version)` 内容逐字相同 → **幂等**成功（`idempotent: true`）；
- 内容不同 → `TEAM_PLAN_FROZEN` **409**，要改就发新版本。

> 一个"按版本追加"的 TeamPlan，
> 与一个"原地可改写"的 TeamPlan，在没人改过它的时候是同一个东西——
> 只不过后者会让三个月前那次运行指向**今天的**计划，而它看起来完全正常。

**幂等而不是冲突**这一条是刻意的：重跑一次同样的写入是正常路径（脚本重试、
两个进程同时启动）。把它判成冲突会让调用方无法安全重试，而它本来没有副作用。

### 2.1 状态码分档：409 不是"随便挑的"

| 码 | 状态 | 调用方该做什么 |
| --- | --- | --- |
| `TEAM_PLAN_FROZEN` | 409 | 请求合法，是**状态**不允许 → 发一个新版本 |
| `TEAM_PLAN_NOT_FOUND` | 404 | 建一份计划，或把目标接上计划 |
| `TEAM_PLAN_INVALID` / `BAD_VERSION` | 400 | 改请求 |
| `MISSING_PARAM` | 400 | 把 scope / role 填上 |

> 一个"所有错误都回 400"的接口，与一个"按修复动作分档"的接口，
> 在调用方只有一种修法的时候是同一个东西——只不过前者会让
> "发一个新版本"与"把 scope 填上"看起来是同一种失败。

## 3. ★ EmployeeManifest 是活的，但 `version` **由服务端递增**

岗位边界会变（新工具、新审批策略），所以它不做追加冻结，更新原地生效。
但 `version` **不接受调用方指定**：

`sources.mjs` 用 `manifest.version ?? manifest.updatedAtMs` 当来源版本，
于是"边界变过没有"**直接决定快照哈希**。让调用方随便填 version 的后果是
一次边界变更**不改变**快照哈希——两份内容不同的上下文被认成同一份。

> 一个"version 由调用方给"的写入路径，
> 与一个"version 由服务端递增"的写入路径，在调用方每次都老实递增时是同一个东西——
> 只不过前者会在某一次忘记递增时，把一次边界变更变成一次**静默的无变化**。

---

## 4. ★ 不猜：缺 `goalId` / `role` 就**不发那次请求**

装载器读计划要 `goalId`，读清单要 `role`（或 `employeeId`）。两者缺一时
**不发请求**，由 `sources.mjs` 产出一条 `missing` 候选。

理由不是省一次往返：**随便给一份岗位清单**会让模型照着一个**不是它的**边界干活，
而它看起来完全正常（清单是合法的、有内容的、有版本的）。

路由那一层同样"不猜"：清单端点两个参数都不给 → **400 `MISSING_PARAM`**，
而不是"返回任意一份"。

> 一个"取不到就返回第一份清单"的端点，
> 与一个"缺身份就拒绝"的端点，在只有一个岗位的空间里是同一个东西——
> 只不过前者会在第二个岗位出现的那一天，开始**静默地**把别人的边界递出去。

---

## 5. ★ 缺席一律 404，不返回 `200 + null`

装配器把 404 翻成 `null`，再由 `sources.mjs` 产出**带原因**的 `missing` 候选。
若路由回 `200 {plan: null}`，"读到了、它是空的"与"读不到"就分不开了——
而那正是整个装载器要防的事。同理，`{}` 也不行：

`teamPlanSource({})` 里 `plan.id` 是 `undefined` → 抛 `TeamPlan 必须有 id`；
更坏的是它**不抛**的那条路——一个空对象会让 `sources.mjs` 走进"有来源"分支，
产出一条**内容为空**的 TeamPlan，于是它不再出现在 `excluded[]` 里，
而快照会声称模型看过团队计划。

> 一个"读不到就给个空对象"的兜底，
> 与一个"这份来源确实存在、只是内容为空"的记录，在账本上是同一个东西——
> 只不过前者会让一条**缺失**从"被排除"那一栏里消失。

## 6. ★ 明文密钥 fail closed —— 而这条检查比它看起来的**窄**

两张表的内容会**逐字进模型上下文**（`sources.mjs` 把记录 `stableRecord` 成文本
塞进 `content`），所以一个写进清单的明文密钥不是"存在本地库里"，而是
**被发给供应商**——比日志里出现密钥严重一级（日志在本机、能删能轮换；发出去撤不回来）。

用与 `model-store.mjs` **同一个** `findPlaintextSecrets`，命中就**拒收**
（不是脱敏：脱敏是过滤器，只能拦下它认得的形态，而模式表是有限的）。

### 6.1 ★ 检查必须在**归一化之前**跑

写测试时量出来的：`normalizeTeamPlan` 会**丢掉未知字段**，于是一个被塞进
`plan.apiKey` 的明文密钥在归一化后就不见了——检查什么都看不到。

丢掉当然比存下来安全，但**静默丢掉**是最坏的处置：调用方提交了一个密钥、
收到 200、以为它存下了。而它该收到的是"你在往计划里塞密钥"。

> 一个"归一化后再查明文密钥"的检查，与一个"归一化前也查"的检查，
> 在用户规规矩矩填 `note` 时是同一个东西——只不过前者会把
> "往 payload 里塞了一个密钥"**静默地做成一次无害的丢弃**。

### 6.2 ⚠️ 诚实边界：它不是子串扫描

判据只有两条：① 键名像密钥载体且值是字符串；② **整个**字符串匹配一个
密钥前缀形态（`^sk-…$` 这类，带锚点）。所以下面这段**会通过**：

```js
note: '把 key: sk-live-abc… 记在这里'
```

也就是说：**把一个密钥粘进自由文本字段，这条检查拦不住。**
不做子串扫描是有意的取舍（误报会让正常文本写不进去），但那条取舍的代价
被钉成了一条会执行的用例（`⚠️ 边界：明文检查抓的是键名与整个值，不是子串扫描`），
而不是等它发生。

判据 `fail > 0 && !importErr`；每个探针还要断言**红了哪几条**；

### 7.1 ⑦/⑨ → 一行**永远不会改变结果**的死代码

第一版 `putTeamPlan` 里我写了两行：

```js
assertNoPlaintextSecrets(input, null, 'TeamPlan')      // ← 第一个参数是 raw
const plan = normalizeTeamPlan(input)
assertNoPlaintextSecrets(input, plan, 'TeamPlan')      // ← 第一个参数**也是** raw
```

第二行已经把 raw 查了，所以第一行**永远不改变任何结果**。它的害处不是浪费一次
遍历，而是让"把 raw 那一遍拿掉"的探针**咬不住**——那条性质看起来受到了保护。

> 一行"查了原始输入"的调用，与一行"查了原始输入、但紧接着又查了一次
> 同样的东西"的调用，在行为上是同一个东西——只不过后者会让那条性质的
> 断验证探针失效，于是**它看起来被守住了**。

已删掉重复行，`(raw, normalized)` 由**一次**调用完成。

### 7.2 ⑭ → 三条路由分支**零覆盖**

探针⑭把「清单端点必须要求 role/employeeId」改坏成 `if (false)`，
**一条用例都没红**。也就是说那几行校验**没有任何用例覆盖**。

> 一段"写了但没被任何用例打过"的参数校验，
> 与一段"根本没写"的参数校验，在有人真的漏传参数的时候是同一个东西——
> 只不过前者在代码审查里看起来是完成的。

补了 5 条路由级用例（缺 role → 400、缺 scope → 400、非法 version → 400、
两条列表路由 + 空间过滤、冻结冲突经 HTTP 是 409 且带 id/version）。

### 7.3 ④ → 探针改在了**相邻分支**上

隔离用例走的是"不带 version"那一条分支，而我的探针改的是"带 version"那条。
`fail=0`，看起来像用例没守住隔离，实际是探针改错了地方。

> 一个"改在相邻分支上"的探针，与一个"真的没咬住"的探针，
> 在 `fail=0` 这个读数上是同一个东西——只不过前者什么也没证明。

### 7.4 探针锚点的换行符

`server.mjs` 是 CRLF（7000+ 行），store 与 loader 是 LF。第一版所有锚点都用
`\n` 写，于是改在 `server.mjs` 上的两个探针报"锚点未找到"——而那个报错
看起来像"探针找错了地方"，实际是"探针写对了地方，换行符不匹配"。
`mutate()` 现在会按目标文件回退到 CRLF。

## 8. ★ `UNSERVED_SOURCE_FAMILIES` 里那两条**不删**，搬进 `formerlyUnserved`

删掉的后果是：下一次有人看到一份带 `missing` 候选的快照时，没有任何地方
告诉他这两条**曾经每次运行都缺**——而那正是它们最危险的地方：
一个恒久不变的缺口看起来像一条正常的账本条目，于是没有人会去看它。

> 一个"把修好的缺口从清单里删掉"的账本，
> 与一个"记着它曾经永远缺"的账本，在今天的快照上是同一个东西——
> 只不过前者会让同一个缺口再犯一次，而没人记得它犯过。

`availability()` 现在同时给出 `unserved`（还缺的 3 条）、
`formerlyUnserved`（补上的 2 条，带 `fixedBy` / `servedBy` / `was`）、
以及 `consumed`（真的会去读的 5 条端点）。

## 11. ⚠️ 诚实边界

1. **`TeamPlan` 的写入路径还没有生产调用方。** `POST /api/team-plans` 有了
   （测试在用），但没有任何地方在**目标创建时**自动冻结一份计划——
   spec 说的是"目标创建时冻结"，而那个时机点还没接。
   *这与 PRT-505 的 `store.put` 零调用方同源：读写两端都在，中间的触发点没有。*
2. **`employeeManifests` 同理**：没有"岗位被创建/修改时同步写一份清单"的接线。
   现在要人工 `POST`。
3. **`teamPlan.goalId` 是自由字符串。** 我没做"goalId 必须指向一个存在的目标"
   的校验——hub 上目标存在 `goals` 表里，但加这条校验要跨存储依赖。
   代价：一个拼错的 goalId 会让装载器**读不到**计划（404 → `missing`），
   而那是安全的失败方向。
4. **清单按 `(scope, role)` 唯一**，所以一个岗位在一个空间里只有**一份**清单，
   不保留历史版本。`version` 只递增不存档——"上个月的边界是什么"答不出来。
   若将来需要，得改成追加表（像 `team_plans` 那样）。
5. **端口面没有做权限判定。** 新路由只走 `authorized(req)`（Bearer token），
   没走 `checkPermission`。写路径（POST）也没有 `requireMember`——
   也就是说 `actor` 是**可选**的，审计里可能是 `null`。
   这与 `POST /api/context-snapshots/assemble` 的现状一致，但**不是**一个可以
   长期保持的状态：能改岗位清单的人，等于能改"模型被允许做什么"。
6. **明文密钥检查不做子串扫描**（见 §6.2）。
7. **`listTeamPlans` / `listEmployeeManifests` 的 `limit` 上限 500**，
   没有分页游标。超过 500 个计划的空间列不全，而响应里没有"还有更多"的标志。
8. **`counts()` 里 `teamPlans` 与 `teamPlanVersions` 是同一张表的两个数**，
   现在相等（一个是 `COUNT(*)`，另一个也是），留着是因为它们的**含义**不同——
   一旦加了保留/清理策略就会分叉。现在它是个没有区别的字段。
9. **断验证的 18 个探针只覆盖用例断言到的东西。** 例如
   `listTeamPlans` 在 `scope === null` 时的那条分支（列全部空间）没有被探针检验。
