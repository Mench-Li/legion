# PRT-402（触发点批）：TeamPlan 在**目标创建时**冻结，EmployeeManifest 在**编队变更时**写

> 上一批把读写两端都做齐了：表、路由、装载器。但**没有任何地方写它们**。
>
> > 一个"读写两端都齐、只是没人写"的数据面，
> > 与一个"根本没有这张表"的数据面，在**第一次运行**的时候是同一个东西——
> > 只不过前者的用例是绿的。
>
> 这一批补的是那个**时点**。spec 第 7 行把 TeamPlan 定义为
> 「目标创建时**冻结**的团队、岗位、流水线和能力包组合快照」——
> "目标创建时"是时间点，而它在此之前不存在。

---

## 1. ★ 触发点 A：`publishGoalRecord` 冻结计划

`POST /api/goal` 的落点是 `publishGoalRecord`，它在**同一个事务**里：

1. `INSERT INTO goal` 建目标；
2. `createGoalChain` 建链，返回 `{count, tasks:[{id, role, label}], mode}`；
3. **`putTeamPlan({ id: goalId, version: 1, goalId, stages: chain.tasks.map(role+label) })`**。

`id = goalId` 而不是另起一个 `TP-xxx`：计划是**这个目标**的计划，
两者同生共死；一个独立的 id 会让"这份计划属于哪个目标"变成又一个要维护的引用。

`version: 1`，之后只增不改（冻结语义由复合主键保证，见上一批的文档）。

`contextPlanStore()` 里的 store **自己不开事务**（模块里没有一处
`BEGIN`/`COMMIT`/`SAVEPOINT`）——所以它的写入**加入调用方那个事务**。
这不是巧合，是这一批能成立的前提：目标与它的计划必须一起成或一起不成。

---

## 2. ★ 刻意**不把目标正文抄进**计划

计划里有 `title` 与 `objective` 两个字段（`sources.mjs` 会序列化它们）。
我**没有**填 `objective`。

理由是这一批里最要紧的一个取舍：若把正文抄进去，正文就是**用户散文**，
而计划要过 `findPlaintextSecrets`。于是：

```
objective: '把 key: sk-live-… 记进笔记里'
```

会让**发布目标**失败——而真正把这句话发给供应商的那条路（目标上下文，
PRT-403）**一点没变**。也就是说：新加的那道门拦住的是一次本地写库，
漏掉的是那次真正的外出。

> 一个"把目标正文抄进团队计划"的冻结，
> 与一个"只冻结团队、岗位与流水线"的冻结，在正文不含密钥时是同一个东西——
> 只不过前者会让一次**发布目标**因为一句像密钥的正文而失败，
> 而那条真正的泄漏路径一点没变。

正文仍然进上下文——走**目标来源**，那是它唯一该走的地方。
计划只说自己该说的话：这次运行时，团队与流水线是什么样。

这条取舍被钉成了一条会执行的用例：正文里带 `sk-live-…` 的**发布目标是成功的**，
且计划里搜不到那段散文。

## 3. ★ 空编队也照样冻结（`stages: []` 是**事实**，不是缺口）

`createGoalChain` 在编队为空时建 0 环链（既有合法态）。此时计划仍然写出来，
`stages` 是空数组。

> 一个"空编队就不写计划"的实现，
> 与一个"写一份 `stages: []`"的实现，在跑起来之后是同一个东西（都没有阶段）——
> 只不过前者产出的是 `missing`（"我们没去看"），
> 后者产出的是一句**真话**："创建这一刻，流水线是空的"。

两者在账本上完全不同：`missing` 会被排除并附原因，空计划是**已读到的内容**。

## 4. ★ 触发点 B：编队变更时写清单，但**只在真的给了边界内容时**

`POST /api/agents` 在写完 roster 之后，若调用方给了
`responsibilities` / `allowedTools` / `deniedTools` / `approvalPolicy` / `limits`
中的**任意一个**，就写一份 EmployeeManifest。

反过来——**什么都不给就不写**。这一条不是省事：编队记录本来只有
`role/name/kind/avatar`，替它写一份空清单会让 `allowedTools: []` 被模型读成
"这个岗位不允许使用任何工具"。那不是"没有配置"，那是一条**假规则**，
而它会改变模型的行为。

> 一个"没配置就写一份空清单"的实现，与一个"没配置就不写"的实现，
> 在界面上都显示"没有"——只不过前者会让模型读到一条它自己编出来的岗位规则，
> 而那句话会**改变它的行为**。

不写，装载器就产出一条**带原因**的 `missing`（"这次运行没有关联任何员工清单"），
那才是实话。用例同时钉了两边：`employeeManifest` 为 `null`、读端点 404、
且装载器仍把它列为一条具名缺口。

### 4.1 `employeeId` 是**岗位的地址**，不是一个人

hub 的编队是 `roster(scope, role)` 的主键形状——**没有"某个员工"这个实体**。
所以默认 `employeeId = \`${scope}/${role}\``：一个可读、稳定、可寻址的岗位地址。

写一个凭空的个人 id 比这更坏（它看起来像"某个具体的人"，但库里没有这个人）。
调用方要给真身份就显式传 `employeeId`。

## 5. ★ 我自己的用例量出一个真缺陷：`POST /api/agents` 不是原子的

`★ 边界内容里带明文密钥 → 拒绝，且编队那一行也不该被写进去` 第一次跑就红了：

```
AssertionError: 编队里不该有 bad：["bad","coder","dev","reviewer","tester"]
```

清单写失败（明文密钥 fail closed）之后，**roster 那一行已经落库了**。
于是库里出现"编队里有这个人、但他的清单没有"——而那个状态**看起来一切正常**：
列表里有他、任务照样派给他，只是他的岗位边界永远是 `missing`，没人会去查。

修法是把 roster 写入与清单写入包进**同一个 `withTx`**：

> 一个"先写编队再写清单、失败就报错"的接口，
> 与一个"两件事在同一个事务里"的接口，在清单从不失败的时候是同一个东西——
> 只不过前者会在清单失败的那一次留下一个**半成品**，
> 而调用方从错误响应里看不出编队已经被改了。

这条用例现在也钉住了事务性：断验证探针㉑（把 `withTx` 换成裸 IIFE）红了 **6 条**。

## 6. 测试层的一个错：`handleWrite` 把结果包在 `task` 下

三个新用例第一次全红，报的是"发布目标没有返回 goal id"。
实际响应是 `{ok:true, task:{goal:{id}, stages, mode, teamPlan}}`，
而我在断言里写的是 `body.goal.id`——**找错了一层**。

> 一个"找错了一层"的断言，与一个"服务端真的没给"的断言，
> 在失败信息上是同一个东西——只不过前者会让人去读服务端的代码。

`/api/agents` 同理（`body.task.employeeManifest`）。

### 7.1 断验证工具本身的一处错

新增跨文件探针（⑬ 改 `server.mjs` 但套件是 `sources-loader.test.mjs`；
㉔ 改 `notify.ts` 但套件是 `notify-hub-smoke.test.mjs`）之后，
"恒等替换"检查（"改了等于没改"的探针是无效探针）拿的是
`ORIG.get(套件文件)` 去比 `被改文件`——两个不同的文件，**恒不相等**，
于是恒等检查在这两个探针上"永远通过"，等于没检查。

修法：让 `mutate()` 自己记下它改了哪个文件（`lastMutated`），检查按它比对。

> 一个"从探针的说明文字里推断它改了哪个文件"的检查，
> 与一个"让修改动作自己报告改了哪个文件"的检查，在探针只改一个文件时
> 是同一个东西——只不过前者会在跨文件探针上静默地**什么都不检查**。

## 8. ★ 全量 CI 抓出一个**真集成后果**（notify 套件变红）

`syntax/env/boundary/deps/build/smoke/stage/doc` 全过，`test` 红一套件：

```
✖ notify（P2-4 通知分类/优先级/批量已读/跳转/去重补齐） → tests=15 pass=14 fail=1
  AssertionError: 批量已读全覆盖 → 游标压实推进   3 !== 6
```

量出来的 seq 布局（把诊断打进那个套件跑了一遍，然后 `git checkout` 还原）：

```
raw:   1:create 2:transition 3:create 4:team-plan.freeze 5:goal:publish 6:skill:submit 7:chat:create 8:chat:message
items: 6:skill:submit 5:goal:publish 3:create 2:transition 1:create     （seq 4 不是通知项）
→ stBatch: { cursor: 3, ids: [5,6] }
```

根因：`seed()` 会 `POST /api/goal`，而本批之后**每次发布目标都会多写一行
`team-plan.freeze` 审计**。那一行不在 notify 白名单里（它是自动派生的写入，
通知它只会是噪声），于是它**永远不被标记已读**；而
`applyMarkRead` 的压实是在 **seq 全空间**上做的（`while (ids.has(cursor + 1))`），
所以游标只能停在它之前。

而那条断言 `cursor === maxSeq` **只在"可通知的 seq 从 1 到 maxSeq 稠密连续"时成立**——
本批之前之所以通过，只是因为当时唯一被排除的行（`chat:*`）恰好全在**顶部**，
不在 `maxSeq` 之下。也就是说它一直是**种子数据的巧合**，不是设计性质。

> 一个"游标必然推到最高 seq"的断言，
> 与一个"没有一条**通知项**仍未读"的断言，在审计序列恰好稠密时是同一个东西——
> 只不过前者会在出现一行"不值得通知的审计"时变红，
> 而那次变红与用户看得见的东西毫无关系。

**这不是把断言改宽来变绿**，两条理由：

1. **用户可见的性质没有变**：`countNotifyUnread` 按**通知项口径**计算，
   批量已读后仍然是 0。改后的断言直接钉这一条，并且**逐条**验证每个通知项
   都被判为已读（在游标之下或在显式集合里）。
2. **新边界被钉住了**，不是被绕开：用例现在显式算出"不可通知的 seq"，
   断言游标**不得越过**其中任何一个，并断言游标之上的通知项确实落进了显式集合。
   探针 ㉔ 把压实改成"越过空洞"（激进版本），这条断言当场变红——
   边界是**可执行的**，不是注释里的。

另外"全部已读"那条逃生路径（`markAllNotifyRead(scope, maxSeq)`）仍然把游标推到
`maxSeq`，用例紧跟着就验证它——所以"游标卡在中间"不会让用户永远清不掉红点。

## 10. ⚠️ 诚实边界（本批新增/更新）

1. **计划里没有"能力包"。** spec 的原文是「团队、岗位、流水线**和能力包**组合快照」，
   而现在冻结的是**链上的岗位与阶段标签**。能力包（capability packs，
   `runtime/packs/`）整条线还没有生产调用方，所以计划里没有它们的影子——
   计划是 spec 那句话的**三分之二**。
2. **计划里没有成员姓名。** `stages` 只记 `role` + `label`。姓名是可改的显示字段
   （`ON CONFLICT DO UPDATE SET name`），而角色才是链上可执行的那件事。
   代价：三个月后问"当时是谁在做"，计划答不出来（要去查审计）。
3. **本次改动之前发布的目标没有冻住的计划。** 没有回填：回填要么猜当时的编队
   （编队此后可能已改），要么写一份假的。那些目标会如实产出 `missing`。
4. **编队删除没有对应的清单失效。** `POST /api/agents` 只处理"新增/改名"。
   从编队里移除一个岗位不会删掉或作废它的清单——一个已离开编队的角色，
   它的清单还在库里、还读得到（若还有任务引用那个 role）。
5. **`POST /api/agents` 的清单写入没有独立权限。** 与上一批的 ⑤ 同源：
   能改编队的人现在等于能改"这个岗位被允许用什么工具"，而这条路径没有
   `checkPermission`、`actor` 是可选参数。
6. **`employeeId` 默认值是 `scope/role`**，所以"同一个人换了角色"在库里表现为
   **两个**清单（两个 employeeId），不相关。这不是 bug，是"编队按角色组织"
   这一事实的直接后果，但它意味着"一个人的边界"这个问题在这里**问不出来**。
7. **`slice` 模式下冻结的是切片后的链**（到 `test-designer` 为止），
   不是全流水线。那是本次运行**真的会用到**的那部分，但若有人以为计划是
   "整个空间的编队"，它会显得不完整。
8. **每次发布目标都会多写一行审计**（`team-plan.freeze`）。它是自动派生的事实记录，
   不在 notify 白名单里——于是它**挡住连续已读游标**（见 §8）。
   用户可见的未读数不受影响，但 `cursor` 不再等于最高 seq，
   依赖"游标 = 水位"的外部消费者（如果有）需要按显式集合一起判断。
9. **`team-plan.freeze` / `employee-manifest.*` 这三行审计没有专门的通知语义。**
   "某个岗位被允许的工具变了"其实是一件**值得让人知道**的事（它改变模型能做什么），
   但白名单没收录它，所以现在没人会被告知。这是本批留下的一个产品问题，
   不是实现问题。
