# PRT-404：用户反馈有了自己的读端点（而不是从评论里挑出来）

> 装载器里 `userFeedback: []` 是一行**硬编码的空数组**。它的注释说得很清楚：
> hub 没有用户反馈的读端点，而**不能拿任务评论去填**它——`sources.mjs` 里
> 用户反馈是另一个类型（`user-feedback`），因为"要不要按反馈调整"的处理
> 与评论不同，混成一个会让那件事无从下手。
>
> 于是每次运行，模型都读不到用户说过什么。

本批给用户反馈补上：hub 的第三个批注列、一条写入口、一条专用读端点，
以及装载器真的去读它。

---

## 1. ★ 反馈是一个**独立的列**，不是一个 `kind` 标记

最省事的做法是往现有的 `comments` 数组里塞 `{ by, at, text, kind: 'feedback' }`，
然后用的时候按 `kind` 过滤。我没有那么做：

> 一个"把反馈塞进 comments 数组、加个 kind 字段"的实现，
> 与一个"给它自己的列"的实现，在只看反馈的时候是同一个东西——
> 只不过前者要求**每一个**读 comments 的地方都记得过滤掉它，
> 而漏掉一处就会让同一条反馈同时以"同事的评论"和"用户的反馈"两种身份
> 进模型上下文。

那个"漏掉的地方"不是假设：装配器**正是**按 `task.comments` 读评论的
（`sources-loader.mjs` 的 `toComments`）。分成两列之后，"不混淆"这件事
**在结构上**成立，而不是靠每一处读点自觉。

代价是多一个列——而这张表本来就有这个先例（`evidence`、`review_notes`、
`artifacts` 都是并列的批注/登记列）。两个地方都加：`CREATE TABLE tasks`
（新库）与 `ensureColumn('tasks','feedback', …)`（老库迁移）。

### 1.1 ⚠️ 一个我自己踩的坑：SQL 模板字符串里不能写 `//`

第一版我把上面那段解释写进了 `CREATE TABLE` 的模板字符串里，`node --check` 当场报
`missing ) after argument list`——因为那段话里有一个反引号，把模板字符串截断了。

**那次报错是幸运的**：如果那段话里没有反引号，它会变成一段被 SQLite 拒绝的 DDL，
而失败会发生在**进程启动期**——排查方向会从"我改的这段话"变成"数据库怎么了"。

> 一个"在 SQL 模板字符串里写 `//` 注释"的改动，
> 与一个"把注释写在 `db.exec` 外面"的改动，在注释里恰好有反引号时是同一个东西——
> 只不过前者会在**恰好没有**反引号时，把一段说明文字变成一条启动期 SQL 错误。

## 2. ★ 三个批注列，一个写入口

`commentTask(id, by, text, isEvidence)` 改成
`appendTaskNote(id, by, text, field)`，`field ∈ {'comments','evidence','feedback'}`。

三条路径共用写入口是有意的：它们都是"往任务的某个批注列追加一条 `{by,at,text}`"，
分成三个路由只会把同一段校验抄三遍。`POST /api/comment` 接一个
`kind: 'feedback'`（缺省仍是评论；`isEvidence: true` 仍是证据）。

审计动作随之分成 `comment` / `evidence` / `feedback` 三个名字——
它们在排障时的排查方向不同（谁在什么时候改了什么性质的记录）。

★ 顺手删掉了 `commentTask`：路由改成直接调 `appendTaskNote` 之后，它就成了
**只有定义、没有调用**的死代码。

> 一个"留着给旧调用方用"的兼容包装，
> 与一个"已经没有任何调用方"的死函数，在现在这一刻是同一个东西——
> 只不过前者会让下一个人以为还有别的调用方，于是不敢改它的语义。

---

## 3. ★ 专用读端点 `/api/task-feedback`

为什么不复用 `/api/task`（它现在也带着 `feedback` 列）：

> 一个"从任务行里自己挑反馈"的读法，
> 与一个"问专门那个端点"的读法，在只有一种批注的时候是同一个东西——
> 只不过前者会在有人忘了挑、顺手把 `comments` 也当反馈时，
> 把"同事说了一句话"读成"用户要求调整"。

`GET /api/task-feedback?scope=&taskId=` 的三个失败面都被刻意区分：

| 情况 | 回答 | 为什么不是别的 |
| --- | --- | --- |
| 缺 `taskId` | **400** `MISSING_PARAM` | 我们不知道该问哪个任务，这不是"没有反馈" |
| 任务不存在 | **404** `TASK_NOT_FOUND` | "任务不存在"与"这个任务没有反馈"是两件事 |
| `scope` 对不上 | **404** `TASK_NOT_FOUND` | 任务 id 全库唯一，但拿别空间的 id 来问**仍是一次越权读取**（装配是按空间做的） |
| 有反馈 | 200 `{ok, taskId, count, feedback}` | —— |
| 没有反馈 | 200 `count: 0` | 这个才是"确实没有" |

## 4. 装载器：读它，映射它，如实登记它

- 新增 `toFeedback(body)`：与 `toComments` 同一套映射（`{id, author, body, createdAtMs}`），
  id 同样由 `commentIdOf({by,at,text})` 内容派生。
- **一条反馈在库里只存在于 `feedback` 一列**，所以两条列表的 id 不会撞——
  这一点由用例钉住（来源 id 必须唯一）。
- 没有 `taskId`（`requireTask: false` 时可能走到）就**不读**那次请求——不猜。
- `userFeedback` 从 `UNSERVED_SOURCE_FAMILIES` 搬到 `FORMERLY_UNSERVED_SOURCE_FAMILIES`
  （`fixedBy: 'PRT-404'`），`consumed` 从 5 条端点变 6 条，`unserved` 从 3 条变 2 条。

### 4.1 ★ 新登记的一处**形状决定的**边界：`listShapedAbsence`

`teamPlan` / `employeeManifest` 是**单值来源**：缺席传 `null`，装配器产出一条
带原因的 `missing` 候选——所以"这次没有"与"我们没去读"在快照里**分得开**。

而 `comments` / `userFeedback` / `upstreamDeliveries` 是**列表形**来源：缺席只能传 `[]`，
而空数组产出**零个**候选：

> 一个"列表形来源缺席时给空数组"的装配，
> 与一个"确实没有这一类内容"的装配，在账本上是同一个东西——
> 只不过前者会让一条**没去读**的来源彻底不留痕迹。

这条边界需要**新的位置**才能表达（"已读但为空"的候选，或快照级的来源清点），
那是 PRT-408 的来源清单该做的事。现在把它如实列进 `availability().listShapedAbsence`，
让它至少是**已知的**，而不是看起来不存在。

## 5. ★ 断验证 30/30（本批新增 6 个）

| # | 弄坏什么 | fail |
| --- | --- | --- |
| ㉕ | 反馈改从 `/api/task` 那一行里自己挑 | 1 |
| ㉖ | `kind: "feedback"` 被忽略，反馈写进 `comments` 列 | 2 |
| ㉗ | 反馈端点缺 `taskId` 时不拒绝（照答 200） | 1 |
| ㉘ | 反馈端点不做空间校验（跨空间也照答） | 1 |
| ㉙ | 反馈端点把"任务不存在"答成 200 + 空数组 | 1 |
| ㉚ | 没有 `taskId` 时照样去读反馈端点 | 1 |

合计 **30/30 咬住，0 无效，0 没咬住，源码逐字节还原**。

### 5.1 ★ 两个探针逼出来的两件事

**① 探针⑮ 的锚点漂移了。** PRT-404 把 `userFeedback` 从 `UNSERVED` 搬到
`FORMERLY` 之后，那个探针原来的锚点（`Object.freeze({ key: 'userFeedback'`）
**在文件里仍然存在**——只不过出现在**另一份清单**里。于是它把两条塞进了
`formerlyUnserved`，红的是"两份互为补充"那条，而"取不到的来源族"那条没红。

> 一个"按旧文本找锚点"的探针，与一个"按意图找锚点"的探针，
> 在被搬动的那段文本恰好还存在于文件别处时是同一个东西——
> 只不过前者会**改对文件、改错地方**，而它看起来照样"咬住了"。

现在锚在 `upstreamDeliveries` 上（`UNSERVED` 的第一条），意图唯一。

**② 探针㉕ 只咬住一条断言，而那本身是个事实。** 任务行**也**带着 `feedback` 列
（写入的响应要能回读到自己刚写的那一条），所以"从任务行里挑"在**数据层面**
与"问专门端点"结果相同——唯一能分辨两者的是**端点断言**。

> 一个"数据对得上就算接线正确"的验证，
> 与一个"数据对得上、而且只从一个地方取"的验证，在只有一种批注列时是同一个东西——
> 只不过前者会在有人把读点复制到每个消费者之后仍然全绿，
> 而"不混淆"这件事本来就是靠**单一取数点**保证的。

**③ 一个探针被**撤掉**了，因为它无法有效。** 我原本写了一个"把 `feedback` 从
`CREATE TABLE` 里拿掉"的探针，它咬不住——而这个"咬不住"是对的：
`ensureColumn` 每次启动都会跑，所以无论 `CREATE TABLE` 有没有那一行，新库老库都有这一列。
也就是说那一行**行为上是冗余的**（只对读代码的人有意义）。

> 一个"验证了某个没有可观测后果的性质"的探针，
> 与一个什么都没验证的空壳，在通过的时候是同一个东西。

所以我在脚本里留的是**那段说明**，而不是一个永远通过的空探针——
"咬住 N/M"这个读数不该被一个不可能咬住的探针稀释。

## 7. ⚠️ 诚实边界

1. **反馈的"处置"没有分类。** 一条反馈只是"某人在某个时刻说的一段话"。
   spec 说用户反馈与评论的**处理**不同（"要不要按反馈调整"），但**没有**定义
   反馈的档位（接受/拒绝/调整方向）。我没有发明这套词汇——如果产品以后需要
   "这条反馈要求我改什么"，那要加一个字段，而**现在它不存在**。
2. **反馈没有独立的权限。** 写反馈走的是 `POST /api/comment`，它的权限模型
   与评论完全一样。也就是说：**能评论的人就能写用户反馈**。而反馈在装配里
   进的是"用户要求"那一类来源——这个不对等值得一次专门的设计，不是本批能顺手解决的。
3. **反馈不会自动出现在任何界面上。** 没有 Workbench 页面写或看反馈，
   现在只有 HTTP 路由（与 PRT-402 的 `POST /api/team-plans` 同源的问题）。
4. **反馈只挂在任务上。** 目标级、空间级的反馈无处可放；
   `GET /api/task-feedback` 的键是 `taskId`。
5. **列表形来源的缺席仍不留痕迹**（见 §4.1）——要 PRT-408 的来源清单才能表达。
6. **`/api/task` 也返回 `feedback`**，所以一个"从任务行里挑"的实现数据上是对的
   （探针㉕量出来的）。防线是**端点断言**，不是数据断言。
7. **反馈没有条数上限。** `feedback` 列是一个无限增长的 JSON 数组，
   每次都整列读写（`comments` 也一样）。一个被反复反馈的任务会越来越慢。
8. **老库的迁移只加列、不回填。** 迁移之前写在别处（如 `comments`）的历史反馈
   不会被认出来——它们继续以评论的身份进上下文，而那是**当时**的真相。
