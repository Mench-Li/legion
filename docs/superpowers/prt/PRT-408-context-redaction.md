## 1. 与日志脱敏的区别不是程度，是**不可撤回性**

Legion 里有两个脱敏消费方，而它们的目的不同：

| | 目的 | 错了会怎样 |
| --- | --- | --- |
| 日志 / 异常 / 事件（PRT-208） | 别把密钥**写进日志** | 还在本机，能删、能轮换 |
| 上下文（PRT-408） | 别把密钥**发给模型** | **撤不回来**——进了对方的日志、缓存、训练管道 |

后者严格得多。但两者要认的"什么算密钥"**是同一件事**：供应商前缀、
`Bearer`、URL 内嵌凭证、私钥块、挂在敏感键名下的值。

两份表会漂移，而漂移的那一次就是漏掉一种新密钥形态的那一次。
所以本批把模式表**提取**到 `runtime/contracts/redact-patterns.mjs`，两侧共用同一份
——与 PRT-413 的 canonical JSON 是同一种做法：**提取共享基础库，而不是重写一份**。

`redact.mjs` 现在从共享表 re-export 原来的名字与形状，于是既有调用方一行都不用改。
一条用例断言两侧拿到的是**同一个冻结对象**，不是两份内容相同的拷贝。

### 两侧真正不同的一处（值得显式钉住）

日志是一条 `{ token: '...' }` 的**结构化记录**，所以按键名就能拦住。
上下文是一整块**自由文本**，`token: xxx` 只是文本里的几个字——只能按**值形态**认。

所以上下文侧**没有**按键名脱敏。一条用例刻意钉住这个局限：

```js
// 值形态没命中 → 不脱敏
assemble([src({ content: 'token: thisIsNotAMatchingSecretShape' })]).redactions  // []
```

这是**已知且刻意**的局限，不是遗漏：在不误伤正常文本的前提下，
无法从自由文本里认出"任意形状的密钥"。

## 2. 三条判断

### ① 脱敏是**内容变换**，不是排除

一个被脱敏的来源**仍然在 `sources[]` 里**。它还是这次运行的输入，
只是正文的一部分变成了标记。整条排除会丢掉「我看过这份文档」这个事实。

`describeAssembly` 因此说「其中 N 个已脱敏」，而**不说**「排除 N 个」——
说成排除会让用户以为那份文档根本没进去。

### ② 脱敏改变哈希，且这件事**可见**

`contentHash` 是**实际发出去那一版**的哈希（同名字段必须自洽，
否则读者拿它去校验 `content` 会得到一个说不清的失败），
而原文的哈希与长度另外留着（`preRedactionContentHash` / `preRedactionChars`）。
「它原本是什么」因此仍然可查，而不是消失。

`redactions[]` 与 `redactionSchema` **一起进哈希**：

> 脱敏规则变了之后，同一份输入就该是两个不同的快照。
> 否则回放会给出与当初不同的结果，而哈希说它们是同一份。

### ③ 脱敏**先于截断**，账本按"发生过"记

顺序不能反。先截断再脱敏的话，一次裁剪可能正好切在一个密钥中间，
剩下的片段不再匹配任何模式，于是**一段残缺的密钥被发了出去**。

这带来一个必须说清的后果：被裁掉的那部分里的密钥**也会进脱敏账本**。

**这一条我第一版写反了。** `redaction.mjs` 的注释与一条用例都断言
「没发出去就不该记脱敏」，然后用例红了。红的是**测试**，不是实现：

> 「这份来源含有一个密钥，我们把它脱敏了」是**真话**；
> 「那一部分有没有被发出去」由 `truncations[]` 单独回答。

两个方向的风险不对称：多记一条（安全侧）与漏记一条**真的发出去**的脱敏
（灾难侧）不能同日而语。而当前顺序**不可能**漏记——脱敏覆盖整份正文，
任何后来进入 `finalText` 的字符都已经过脱敏。

对比之下，**被权限排除**的来源确实不进脱敏账本：排除发生在 `pending` 之前，
它的正文从来没被读进来。那是真的"没脱敏过"，与上面那条不同。
两条用例分别钉住这两种情况，因为它们**看起来一样**（都是"没发出去"），
而原因完全不同。

## 3. 审计里只有路径与说明，**没有原值**

```js
redactions: [{ sourceId: 'document:doc1', at: 'content', why: 'OpenAI 风格密钥' }]
```

`at` 是稳定路径，`why` 是命中的模式说明。把原值写进快照的审计
等于把泄漏从正文搬家到审计，问题一点没少。

三条用例从三个角度断言这一点：`redactions[]` 里没有密钥、没有密钥片段、
**整份快照序列化之后**也没有。

`redactForModel()` 只返回 `{text, hits, changed}`——调用方**拿不到**原值，
就写不进审计、日志、快照。这不是"不方便"，这是这个函数存在的理由。

## 4. 接线（本仓库最常见的失败形态）

「模块写好了、用例绿了、没有任何人调用它」在 Legion 里已经出现过三次
（PRT-504、PRT-507、PRT-402~406）。所以脱敏的用例里有一条**读源码**断言：

```js
assert.match(t, /redactSource\(p\.source\)/, '必须真的在装配流程里被调用')
const iRed = t.indexOf('redactSource(p.source)')
const iTrim = t.indexOf('// ⑥ 预算裁剪')
assert.ok(iRed < iTrim, '脱敏必须在裁剪之前')
```

这不是"字符串出现过"式的假绿：它同时要求**调用点存在**与**调用点在前**。
PRT-401 上曾出现「字符串出现过就算接线」，这里不重复。

端到端也验了：真实 hub 进程上装配一份含三种密钥形态的文档，
`finalText` 里没有密钥、主机名保留、来源仍在 `sources[]`、哈希校验通过。

  但它意味着"用户把密钥放在 `content` 里，同时键名也是 `apiKey`"

  但那时没有产出路径；现在有了。`redactSource` 额外加的
  `preRedactionContentHash` / `preRedactionChars` / `redactionSchema`

  与 `truncated` / `fullChars` / `fullContentHash` 同样处理。
  这个"契约之后追加字段"的模式现在是三处，值得在 PRT-410 一并审视。

  本模块的天然消费方。
