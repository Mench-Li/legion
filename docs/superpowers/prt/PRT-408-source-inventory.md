# PRT-408 收尾：来源清单 —— 把"没去取"与"取了但没有"分开

> 装配器与装载器里，同一句话重复了**三次**：
>
>   > 一个"列表形来源缺席时给空数组"的装配，
>   > 与一个"确实没有这一类内容"的装配，在账本上是同一个东西——
>   > 只不过前者会让一条**没去读**的来源彻底不留痕迹。
>
> 三处后面都跟着同一句："这条边界需要**新的位置**才能表达……
> 那是 **PRT-408 的来源清单**该做的事。"
>
> 本批就是那个位置。

`PRT-408` 的三项里，**脱敏**（PRT-407/408 前批）与**内容哈希**（PRT-401 起）早已交付；
只有**来源清单**一直缺席。这份文档只讲这一项，以及它带出的三件事。

---

## 1. 语义：处置与排除理由是**正交**的

先别急着写代码——`EXCLUSION_REASONS` 已经有一栏"为什么它没进去"，
很容易就把清单塞进去当第二个理由。那是错的。

一个来源可以**去了、取到了、但因为越权没进去**；也可以**根本没去取**（没有任何排除理由）。
前者是策略问题，后者是接线问题，**责任人不同**：

```js
export const INVENTORY_OUTCOMES = Object.freeze({
  READ: 'read',                    // 去取了，取到了
  READ_EMPTY: 'read-empty',        // 去取了，这一类**确实是空的**
  READ_FAILED: 'read-failed',      // 去取了，**没取到**
  NOT_ATTEMPTED: 'not-attempted',  // **没去取**
  SKIPPED: 'skipped',              // 去取了，但这一条被跳过（前驱不是 done）
})
```

合并成一个字段之后，"没进去"这一个读数会同时覆盖两种完全不同的处置。

---

## 2. ★ 措辞收紧之一：`not-attempted` 不许带 `count`

```js
if (outcome === INVENTORY_OUTCOMES.NOT_ATTEMPTED && count !== null) {
  throw new Error('not-attempted 的来源不能有 count：没去取的东西没有条数可言'
    + '（0 会与"确实没有"重合）')
}
```

**没去取的东西没有条数。** 写成 `0` 会让它与"去了、确实是空的"在读数上重合，
而那正是这份清单要分开的两件事：

> 一个"没去取也记 0 条"的清单，
> 与一个"确实没有"的清单，在没人去数的时候是同一个东西——
> 只不过前者会让"接线漏了"读起来像"这次恰好没有"。

`READ_EMPTY` 的 `count` 则必须**真的是 0**（"空"不是一个可以随便填的说法）。

---

## 3. ★ 措辞收紧之二：清单排序是**数据的函数**

`createSourceInventory` 按 `family` 排序后冻结，且 `freezeContextSnapshot`
**归一化**（排序 + 逐条校验）而不是原样收下调用方给的数组：

> 一个"清单顺序碰巧固定"的哈希，
> 与一个"清单顺序是数据的函数"的哈希，在调用方从不改变组装顺序时是同一个东西——
> 只不过前者会在有人换了两条 push 的先后之后，
> 让**同一份取数路径**算出两个快照哈希。

这与对上游产物引用做投影（`toUpstreamArtifacts`，PRT-405）是同一个理由。
★ 这一条是**被自己写的用例当场撞出来的**：第一版只做了 `createSourceInventory`
的排序，`freezeContextSnapshot` 却原样收下数组，于是"顺序无关"那条断言红了。

---

## 4. ★★ 措辞收紧之三（**真缺陷**）："发过请求" ≠ "请求成功"

第一版的判定是：

```js
const didRead = (fragment) => reads.some((r) => r.ok && r.path.includes(fragment))
```

于是 `/api/skills` 回 **404** 时，清单申报 `not-attempted`——**"我们没去读"**，
而请求**确实发出去过**。

> 一个"只看成功请求"的清单，
> 与一个"根本没接线"的清单，在端点恰好报错的时候是同一个形状——
> 只不过前者会把"读失败了"记成"我们没打算读"，
> 而这两件事的修复动作完全不同（**查 hub** vs **改接线**）。

现在三态分开：

```js
const didAttempt = (fragment) => attemptsOf(fragment).length > 0   // 发过请求
const didSucceed = (fragment) => attemptsOf(fragment).some((r) => r.ok)  // 请求成功
```

这个缺陷**是被一条用例逼出来的**（不是我自己看出来的）：
"发过请求但没成功 ≠ 没去读"那条用例红了，才发现 `didRead` 的名字与它做的事不符。

---

## 5. ★ 消费方：谁申报、谁转交

清单由**取数方**申报，装配器不自己推断：

| 环节 | 文件 | 做什么 |
| --- | --- | --- |
| 申报 | `orchestrator/worker/sources-loader.mjs` | 按真实发出的 `reads` 逐族如实填 11 个族 |
| 转交 | `orchestrator/worker/context-stage.mjs` | `sourceInventory: inputs.sourceInventory` |
| 接收 | `runtime/context/assembler.mjs` | 校验形状、进快照、进哈希、进人读摘要 |

**装配器为什么不自己推断**：

> 一个"装配器自己猜取了哪些来源"的实现，
> 与一个"由取数方如实申报"的实现，在取数没漏的时候是同一个东西——
> 只不过前者会把**漏掉的那一次**写成"这一类确实没有"，
> 而清单的全部意义正是把这两件事分开。

申报依据是 `reads`（真实请求），**不是复述那段 `if`**：

> 一个"照着自己刚写下的 if 复述读了什么"的清单，
> 与一个"照着**真的发出的请求**申报"的清单，在没人动过那段 if 时是同一个东西——
> 只不过前者会在条件改掉之后继续申报旧事实，而它看起来是自洽的。

## 6. 人读摘要：缺了来源的快照不能读起来像完整

`describeAssembly` 新增四段：

```
…；**没去取** 2 类（documents、workspaceState）；取数失败 1 类（skills）；取了但没有 1 类（comments）…
```

> 一个"只报包含几个来源"的摘要，
> 与一个"还报了有几类压根没去取"的摘要，在接线全都接上的时候是同一个东西——
> 只不过前者会在接线漏掉一条时，让那份快照看起来**完整**。

## 7. 断验证：53/53，以及探针 ㊾ 的价值

新增 13 个探针（㊹~⑥④）：`not-attempted` 带 count / `read-empty` 不校验 / 不排序 /
不放进快照 / 放弃归一化 / **阶段不转交** / **只看成功请求** / 恒报 `read-empty` /
链头与链断了混为一谈 / 漏掉一个族 / 摘要不报"没去取"。
合计 **53/53 咬住，0 无效，0 没咬住，源码逐字节还原**。

### 7.1 ★★ 探针 ㊾ 的价值不是"咬住"，是**逼出一条真用例**

第一版把 ㊾ 指向 `sources-loader.test.mjs`（那里的用例**直接调** `assembleContext`，
根本不经过 `context-stage`），读数 `fail=0`。

而真正的问题是：**"那一行到底有没有被转交"当时没有任何用例守。**
清单在 loader 那侧被测得很细，而"它到底有没有进快照"没有人管。

> 一个"探针没咬住就改小期望"的处理，
> 与一个"先问清楚没咬住是因为代码对还是因为没人测"的处理，
> 在代码确实对的时候是同一个东西——只不过前者会把
> **一处无人守的接线**永久留成"已验证"。

于是补了 `context-stage.test.mjs` 的「⑦ 来源清单被转交进快照」（3 例），
㊾ 随即咬住两条（`fail=2`）。

### 7.2 ★ 同一个"指错套件"的错误，我犯了**两次**

㊸ 指错（应在 `redaction.test.mjs`，写了 `assembler.test.mjs`），
⑥④ 又指错（应在 `sources-loader.test.mjs`，写了 `assembler.test.mjs`）。

两次的教训是同一个：**`fail=0` 有两种成因**——"没人测"与"测在别处"——
而它们在读数上**分不开**。第二次之后我在探针定义处写明了这一点。

PRT-408 行里原文写着："装配仍未接进 worker 的 `buildContext`（PRT-411）"。

> 一句"这一环还没接上"的诚实边界，
> 与一句"这一环其实接好了、只是我上次没查"的边界，
> 在只读文档的人眼里是同一个东西——只不过前者会让人去做一件已经做完的事。

因为它没有用例守——功能错了会红，边界错了只会被相信。

## 11. ⚠️ 诚实边界

1. **逐族的手工申报仍是手写的。** `sources-loader` 里 11 个族各写一条 `inventory.push`，
   没有"族注册表 → 自动生成"的机制。新增一个来源族时**要记得同时加一条**——
   目前由用例「清单覆盖每一个来源族」兜住（漏了会红），但那是一份手工清单。
2. **申报的粒度是"族"，不是"次"。** 一族只报一条处置。若一次运行里同一个族
   一半成功一半失败（例如读前驱时某个前驱超时），清单记的是**整族**的处置，
   细致的差异只在 `upstreamSkipped` 里。
3. **`endpoint` 是示意而非精确契约。** 上游交付记的是 `/api/task?id=`（带占位），
   实际请求是逐个前驱的真实路径。清单记录的是"哪一类端点"，不是完整 URL 列表
   （完整列表在 `lastReads()` 里）。
4. **`read-failed` 只在"请求发出但没成功"时出现**，且**只有 404 会被
   `notFoundIsNull` 吃成 null**——别的失败（500/超时）会让 `readOrThrow` **抛错**，
   于是整个 `loadSources` 失败，**清单根本不会被产出**。也就是说：
   `read-failed` 覆盖的是"读了、404、被当成没有"这一类，不是"所有读失败"。
   这是刻意的（读失败必须让运行失败，见文件头），但值得说清。
5. **清单不改变"取数决策"。** 它只记录。没有任何一条逻辑因为清单而少读或多读一个端点。
6. **界面仍未读它**：`workbench/src/snapshotView.ts` 不认识 `sourceInventory`，
   所以清单目前只有 `describeAssembly` 的文本摘要与直接的字段访问两个出口
   （PRT-507/409 的视图问题）。
7. **上下文侧仍没有按键名脱敏**（自由文本里 `token: xxx` 只是几个字，只能按值形态认）——
   这是刻意保留的局限，本批未变。
8. **诊断包脱敏（PRT-710）/ 心跳脱敏（PRT-713）** 与本批无关；PRT-408 行里对它们的
   交叉引用已陈旧（那两条各自自报交付）。
