# PRT-409（收尾）：快照保留策略与墓碑

> spec line 897：「`PRT-409`：持久化快照并支持查看和导出。」
> spec line 748：「日志、事件和产物设置容量上限与保留策略。」

PRT-409 的原文缺口是三件：**导出**、**保留策略**、**快照查看的界面**。
导出已在上一批交付（`PRT-409-snapshot-export.md`）。本文记录**保留策略**。

---

## 1. 为什么快照不能沿用日志那一套

`product/lifecycle/retention.mjs`（PRT-904）管的是 log / event / artifact。
给快照挂上 `event` 类、于是 30 天上限顺手生效，会很方便。代价是：

> 一个"用日志的 30 天上限顺便清掉快照"的实现，
> 与一个"30 天之后再也回答不了那次运行看到了什么"的实现，
> 是同一个东西——只不过前者的配置看起来是统一的。

快照**不属于**那三类里的任何一类，因为它是**证据**：

> 一份快照存在的唯一理由是回答"模型当时看到了什么"。
> 删掉它，这个问题的答案就永久消失，而且**不可撤回**——
> 不像日志可以再打一遍，也不像产物可以重新生成。

所以新增 `team-hub/context-retention.mjs`，有**自己的**策略对象、类名与默认值。
`SNAPSHOT_CLASS_ID = 'context-snapshot'`，而用例钉住它**不在**
`['log','event','artifact']` 里。

**与 `planRetention` 的关系：判据照抄，实现分开。** 两者都有时间/容量两条规则、
都从最旧开始删。但没有复用它的实现——复用会把"删一条日志"与"删一份证据"
变成同一条代码路径，而这条路径上任何一次改动都会**同时**作用于两者，
于是一次为了日志调的参数会悄悄改变证据的去留。

## 2. ★ 默认不销毁任何证据

```js
export const DEFAULT_SNAPSHOT_RETENTION = Object.freeze({
  maxAgeDays: null,
  maxBytes: null,
})
```

两个 `null` 是**显式**写出来的，不是"忘了配"。在既有 doctrine 里这两个值不同：

| 值 | 含义 |
| --- | --- |
| `null` | 我**故意**不设上限 |
| `undefined` / 字段缺席 | 我忘了配 → 报 `POLICY_INCOMPLETE` |

> 一个有上限的默认值会成为一次**静默的数据丢失**——
> 它在用户没做任何决定的情况下，把"能还原"变成了"过期查不到"。

`assertSnapshotRetentionExplicit` 把这条性质**算出来**（`deletesNothingByDefault`），
而不是只写在注释里。

---

## 3. ★★ 清掉之后必须留下墓碑

这是本批**最重要**的一条。

`contextStore().get()` 对"库里没有这一行"返回 `null`，路由给 404。
如果清理由此**借用**同一个 404：

> 一份"被保留策略清掉"的快照，与一份"从来没有过"的快照，
> 在 `GET` 回来时是同一个 404——
> 只不过前者意味着"**这次的输入我们已经丢掉了**"，
> 而后者意味着"**你查错了 id**"。

对一个以"可还原"为卖点的产品，这两件事的差别就是全部意义所在。

### 3.1 清理是搬家，不是 delete

```
run_context_snapshots          run_context_snapshot_tombstones
  attempt_id   ──────────►       attempt_id
  final_text                     snapshot_hash   ← 内容哈希留住了
  payload_json                   bytes           ← 丢掉了多少
  ...                            purged_at_ms    ← 什么时候
                                 actor           ← 谁决定的
                                 reason          ← 为什么
```

墓碑里**没有正文**——那正是清掉它的理由。但它回答了"它是不是存在过"。

### 3.2 三态读面

新增 `store.locate(attemptId)` 返回 `live` / `purged` / `absent`。
路由据此给 **410 Gone**（它曾经在，现在不在了）而不是 404，
并把墓碑一并返回。

三条读路必须**一致**：

| 请求 | purged 时的响应 |
| --- | --- |
| `GET /api/context-snapshots/:id` | 410 + `CONTEXT_SNAPSHOT_PURGED` + 墓碑 |
| `GET /api/context-snapshots/:id?verify=1` | 410 + `CONTEXT_SNAPSHOT_PURGED` |
| `GET /api/context-snapshots/:id/export` | 404（**不导出**一份"空的但格式正确"的文档） |

第三行是一个**刻意的不一致**：导出的是一个**文件**，
而一份指着已清快照的"空导出"会作为证据被下游读走。
"导不出来"比"导出一份空的"好——后者是**盖过章的错证据**。

### 3.3 墓碑不可改写

已清的墓碑**不许**被后来的清理覆盖（理由、时间、操作人一字不变）。

> 一条"被后来某次清理顺手改写了理由"的墓碑，
> 与一条"从没记过理由"的墓碑，对审计是同一个东西——
> 只不过前者看起来是有记录的。

第二次 `purge` 同一 id 返回 `{purged:false, alreadyPurged:true}`，
幂等但不改任何字段。

### 3.4 墓碑记的是"实际丢了什么"，不是"调用方以为丢了什么"

`bytes` 与 `snapshotHash` 从**将被删的那一行**读出来，不是调用方给的。
调用方给的值描述的是它**以为**自己删了什么。

用例里直接**谎报** `bytes: 1, snapshotHash: 'sha256:lie'`，墓碑必须无视。

## 4. ★ 字节不是字符

`maxBytes` 比的是**字节**。快照正文里大量是中文——UTF-8 下一个汉字 3 字节。

> 一个"拿字符数当字节数去比容量上限"的保留策略，
> 与一个"上限比配置的宽三倍"的保留策略，是同一个东西——
> 只不过它在纯英文数据上恰好是对的。

所以 `utf8Bytes()` 一律走 `Buffer.byteLength(text, 'utf8')`，**不碰 `.length`**。

而且一条快照行的占用是 **`final_text` + `payload_json`** 两份：

```js
export function snapshotRowBytes({ finalText = '', payloadJson = '' } = {}) {
  return utf8Bytes(finalText) + utf8Bytes(payloadJson)
}
```

只算正文会低估——`payload_json` 里有全部来源、分段与账本，
在来源多的时候它比正文大得多，而**低估用量会让上限失去意义**。

## 5. 判据

### 5.1 最旧的先清

```js
const ordered = [...sized].sort((a, b) => (a.frozenAtMs - b.frozenAtMs)
  || (a.attemptId < b.attemptId ? -1 : (a.attemptId > b.attemptId ? 1 : 0)))
```

方向必须写死在这里：写反了不会报错，只会把**最有用的**证据删掉，
而报表看起来完全正常。同刻的按 `attemptId` 兜底排序，
让计划是**确定的**（否则同一批输入两次算出不同的清理集）。

### 5.2 被进行中 Run 引用的**两轮都不清**

`planRetention` 的第一版只在容量轮做了引用判断，漏了时间轮——
于是"超过 30 天的产物"照样被删掉，哪怕它正被一个进行中的 Run 用着。

本模块从一开始就让两轮共用同一个 `decide`：

```js
const decide = (entry, why) => {
  if (doomed.has(entry.attemptId)) return
  if (entry.runId !== null && active.has(entry.runId)) { /* PINNED，保留 */ }
  ...
}
```

被引用的会留下一条 `PINNED` finding，说明**为什么没清**。

★ 一个判断写两遍就会有一天只改一处——所以权威判断**各只有一处**，
容量循环里那句 `if (doomed.has(...)) continue` 只是一条**快路径**
（撤掉它什么都不变，已实测；见 §7 的 `68⑬`）。

### 5.3 清完仍超上限 → 如实报，而不是继续删

```
CAP_UNREACHABLE
```

> 一个"上限达到了"的报表与一个"上限其实没达到"的报表，
> 在只看有没有 finding 的人眼里是同一个东西。

### 5.4 形状不对的行不清

缺 `attemptId` / 缺 `frozenAtMs` 的行**算不出它多旧多大**，
所以**不清**并报 `ROW_MALFORMED`。宁可留着一份算不出大小的证据，
也不要删掉一份本来该留的。

### 5.5 没有 `nowMs` → 什么都不清

与 `planRetention` 同一条纪律：猜一个当前时间的后果是**删掉不该删的**，
而这个方向不可撤回。

## 6. 路由

### 6.1 `GET /api/context-snapshots/retention` — 只读预览

**什么都不删。** 把"看计划"与"执行"拆开，是因为清理证据不可撤回，
而一个"调用即删除"的接口没有让人反悔的地方。

`maxAgeDays` 与 `maxBytes` **必须显式给出**（不设上限写 `null`）：

> 一个默认值会让"我这次想不设上限"与"我忘了传"变成同一个请求。

`activeRunId` 可重复，由调用方给——hub 的 **Run 状态**是 run-store 的事，
快照账本不知道"谁还在跑"。这里**不猜、不高估**：猜错的方向是删掉活着的证据。

只回计划，**不回正文**。

### 6.2 `POST /api/context-snapshots/purge` — 执行

`dryRun` **没有默认值**：

> 默认 `true` 会让真的清理静默失效（调用方以为自己删了）；
> 默认 `false` 会让一次查询删掉审计证据。

必须给 `actor` 与 `reason`，两者分开报码。

**校验失败一律 `throw`（400），不是 `return {ok:false}`**——
`handleRun` 会把回调的返回值展开成 **HTTP 200**，
于是"缺 actor"会变成一次成功的响应，而调用方以为清理发生了。

一次一个 `attemptId`，各自一个事务。**不做一次大事务**：
中途失败时要能说清"已经清了哪几份"，而一个回滚掉的大事务
会把"清了一半"与"什么都没清"变成同一个结果。

### 6.3 `GET /api/context-snapshots/tombstones` — 丢过什么

返回 `counts: {live, purged, everRecorded}`，且

```
everRecorded = live + purged
```

> 一个"清理之后总数下降了"的报表，与一个"证据悄悄丢了"的报表，
> 在只看一个数字的人眼里是同一个东西。

## 7. 验证

- 新增套件 `context-retention`（**29 例**），起真 hub + 真 HTTP。
- 破坏性验证 **24/24 必须变红的都变红了**（`68①`–`68㉗`）。
- 另有 **3 处设计上冗余、无法被单独证明**，**明确写下来**而不是假装验过：

| 探针 | 为什么测不到 |
| --- | --- |
| `68⑬` 容量循环的 `doomed` 快路径 | 权威判断在 `decide()` 里各只有一处；撤掉快路径什么都不变 |
| `68㉖` purge 的事务 | 保护的是"两条语句之间进程死掉"这个窗口；用例只能断言**终态** |
| `68㉗` purge 之后的复读确认 | 防的是"我们以为删了"；正常路径上永远通过 |

> 一条"设计上冗余、因而无法被单独证明"的保险，
> 与一条"从来没被执行过"的死代码，在覆盖报告上看起来一模一样——
> 区别在于前者被**明确写下来**了，于是下一个人不会去删它。

- 既有套件 `context-store` 的"不可变"用例**被这批改动弄红了一次**——
  它在做自己该做的事。应对是把它**收紧**而不是放宽：原文钉的是
  "整个 store 里没有任何删除入口"，现在拆成三条更锋利的
  （读/写/删分类 + 没有就地改写 + 唯一的删除必须留墓碑）。
- 六道门禁全 PASS；全量 CI 见 `docs/STATUS.md`。

### ★ 本项目第三次踩到同一个形状

`assertSnapshotRetentionExplicit` 里有**两条**独立的拒绝：

1. `!Object.hasOwn(policy, key)` —— "这个字段整个缺席"
2. `!(Number.isInteger(...) && ... > 0)` —— "这个值不合法"

传 `{}` 时两条**都**会拒，于是撤掉①之后 `.ok` 仍然是 `false`、用例照样绿
（探针 `68⑲` 一开始 `fail=0`）。而调用方拿到的理由从
"你**忘了**写这个字段"变成了"这个值不合法，收到 undefined"。

> 一句"你忘了写 maxAgeDays"，与一句"maxAgeDays 只能是正整数或 null，
> 收到 undefined"，在只看 `ok` 布尔的人眼里是同一个东西——
> 只不过前者告诉调用方去**补一个字段**，
> 后者会让它去**改一个它根本没写的值**。

修法同前两次（PRT-412 的权威字段名单、PRT-409 导出的两层校验）：
**把理由单独钉住**，断言两条防线给的说明不同、且各自提到自己的事。

## 8. ⚠️ 诚实边界

**PRT-409 仍然不是 ✅**：原文缺口三件里，导出与保留策略已交付，
**「快照查看的界面」仍未做**——hub 侧已有三条读路由，
但 workbench 里没有任何视图读它。

其它真缺口：

- **本批没有自动清理的调用方。** `planSnapshotRetention` 与 `purge` 现在
  有生产调用方（两条路由），但**没有定时任务**去跑它——
  保留策略要生效需要有人（或某个调度）定期调 `purge`。
  「有策略但没人执行」与「没有策略」在磁盘用量上是同一个东西。
- **`purge` 不做权限检查**，与 hub 现有读路由一致的本机回环信任模型。
  但删除比读取更需要权限——这一点值得记下。
- **墓碑永不过期。** `run_context_snapshot_tombstones` 只增不减，
  一条墓碑 ≈ 200 字节。规模上不是问题，但它同样**没有保留策略**——
  这与"保留策略本身也需要保留策略"是同一类自指问题，本批不解决。
- **`maxBytes` 只算快照表**，不含 `-wal`/`-shm` 或索引开销，
  所以库文件会比账面上的数字略大。
- **清理不做内容审查**：被清的正文里有没有本该保留的东西，策略不知道。
- **PRT-413 的缺口仍在**（为具体 ModelProfile 接入真实词表）。
