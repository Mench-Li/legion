# PRT-409（右半部分）：快照导出——两个哈希的分工，与离线可验

> spec line 897：「`PRT-409`：持久化快照并支持查看和导出。」
>
> 左半部分（持久化 + 查看 + 三条路由 + 18 例）早已交付。
> 本批补的是**导出**，以及过程中发现的两处自身缺陷。

## §1 导出要解决的问题

`run_context_snapshots` 里那份快照是本机的一个 SQLite 行。而"导出"的用途
几乎总是**离开这台机器**：给审计的人、给支持的人、附在 bug 报告里。
一旦离开，它就要能自己回答一个问题：

> 我手上这份文件，和当初冻下来的那份，是不是同一份？

## §2 ★ 为什么是**两个**哈希，而不是一个

快照自带 `snapshotHash`，盖住冻结下来的正文。很自然地会想：既然如此，
导出里带着它不就能验证了吗？**不能**——因为导出文件还有一层**封皮**：
这份导出是从哪个 attempt 导的、谁导的、什么时候导的。

> 一个"正文哈希在导出里验得过、而封皮没有任何哈希"的导出，
> 与一个"谁都能把 attemptId 换成另一个 Attempt"的导出，是同一个东西——
> 只不过前者看起来是可验证的。

具体后果：把封皮里的 `attemptId` 从 `att:A:1` 改成 `att:B:1`，正文原样不动，
**单哈希验证会照样通过**。于是一份指着另一个 Attempt 的文件"验过了"。
对审计来说这比没有导出更坏——它是一份**盖过章的错证据**。

所以导出有**两个**独立的哈希，验证也**分开报**：

| 现象 | 结论 | 对审计意味着 |
| --- | --- | --- |
| `snapshotHash` 不对 | **正文**被改过 | 内容不可信 |
| 正文对、`exportHash` 不对 | **封皮**被改过 | 这份文件在说谎关于它从哪里来 |

两者错的东西完全不同，合成一个 `ok` 会让其中一件悄悄消失。

## §3 哈希覆盖范围写成"取余"，不是"列举"

第一版的 `computeExportHash` 写的是 `{ envelope, snapshot }`——于是顶层那个
冗余的 `snapshotHash` **不在覆盖范围内**。用例里把顶层 `snapshotHash` 改成
另一个值，验证结果仍然报 `ok: true`。

> 一份"报了问题却仍然说 ok"的验证结果，
> 与一份"没问题"的验证结果，对调用方是同一个东西——
> 只不过前者的 findings 里躺着一行没人看的字。

但"列举要哈希的字段"这个写法本身还有一个更慢的毛病：

> 一个"新加一个字段就必须记得把它加进哈希"的导出格式，
> 与一个"某天有人加了一个字段、而它不在哈希覆盖范围内"的导出格式，
> 是同一个东西——只不过前者的哈希覆盖范围**看起来**是完整的。

所以改成"**除了 `exportHash` 自己，全都盖住**"：新增字段自动被覆盖，忘不掉。

## §4 ★ 破坏性验证抓到的第一类：两条防线互相覆盖

修完之后跑破坏性验证，发现把覆盖范围**退回**"列举字段"时，**用例照样绿**。

原因：顶层 `snapshotHash` 不在覆盖范围内 → `exportOk` 仍为真；但那条
"两份 snapshotHash 不一致"的 finding 仍旧被产出来，而 `ok` 把 findings
也算进去了 → `ok` 依然为假 → 用例通过。

> 一个"两条防线互相覆盖、于是谁都可以不存在"的实现，
> 与一个"只有一条防线、而它是好的"实现，在用例上看起来一模一样。

**这是"防御纵深"的一个真实代价**：多一层防线会让单层失效变得不可见。
修法是不要只钉合成结论 `ok`，而要**分别钉住** `exportOk` 与 `snapshotOk`：

```js
assert.equal(v.exportOk, false)   // 直接钉住"这个字段在不在哈希覆盖范围内"
assert.equal(v.snapshotOk, true)  // 正文没被改——不该被牵连
```

改完之后同一个探针从 `fail=0` 变成 `fail=1`。

## §5 ★ 破坏性验证抓到的第二类：两层同码不同理由

路由先查 `by`/`atMs`，构建器再查 `exportedBy`/`exportedAtMs`。
把**路由那一层整层删掉**，构建器照样会拒绝，**状态码一字不变**（都是 400）——
只是理由换了一套。

> 同一个请求被两层校验都拒绝、而两层给的**理由**不同，
> 只看状态码分辨不出是哪一层拦下的——
> 于是"路由层的检查"可以整层不存在，而用例全绿。

修法是钉住**具名码**（`EXPORT_BY_REQUIRED` / `EXPORT_AT_REQUIRED`），
并顺带断言两种缺参给**不同**的码——同一个码会让调用方不知道该补哪一个。

**这是本项目里第二次踩到同一形状**：PRT-412 的 `AUTHORITY_BEARING_KEYS`
与 `SOURCE_ALLOWED_KEYS` 白名单也是"两层、同状态码、不同理由"。
两次的教训是同一条：**每一层防线的"理由"都必须单独钉住，不能只钉它拒绝了这个事实。**

## §6 拒绝导出验不过的记录

一次成功的导出会把"可验证"这三个字盖在这份文件上。把一份验不过的记录导出
出去，等于把一次篡改**洗白**成一份看起来带哈希的正规文件。所以导出前
**两道**校验：

1. 正文自洽（`verifySnapshotHash`）；
2. 正文哈希与**库里那一行**记的哈希一致。

只做 ① 会漏掉"有人把整行连同 payload 一起换成另一份**自洽**的快照"。

## §7 为什么离线验证要另起进程

> 一份"要连回那台服务器才能验证"的导出，不是导出，**是截图**。

在同一个进程里"不碰库"是个自我承诺。用例里另起一个 node 进程，
**不传** `TEAM_HUB_DB`、不传任何库路径，只给它一个 JSON 文件路径。
同一个子进程也要能识破**封皮篡改**——否则"离线可验"是空话，
它可能只是"永远说 ok"。

## §8 一条被钉住的边界：同一次导出的两次不同时间

`exportedAtMs` 是封皮的一部分，而封皮进了 `exportHash`。所以同一份快照导两次，
**导出哈希必然不同**，而**正文哈希必然相同**。

这条断言的方向很容易写反。写成"两次导出应当同哈希"会把一条正确的行为
报成缺陷；更糟的是，它可能诱使实现把 `exportedAtMs` 从哈希里拿掉——
于是"这份文件是什么时候导的"就变成了一句可以随便改的话。

用例的写法是：断言两者**不同**，再断言差异**只在封皮**
（正文的 canonical 文本逐字节相同），再断言**整份** canonical 文本确实不同
（证明封皮真的进了覆盖范围——少了这一条，"只哈希正文"的实现也能通过）。

## §9 验证

- 新增套件 `context-export`（**16 例**，起真 hub + 真子进程）。
- 破坏性验证 **11/11 必须变红的都变红了**，另有 1 处**设计上冗余**（见下）。
- 路由顺序也被单独钉住：`/export` 必须排在 `<attemptId>` 通配路由**之前**，
  否则通配那条会把含 `/` 的 id 判成 400 `MISSING_PARAM`，
  而导出路由看起来像"写好了"。

### 探针汇总（67①–67⑫）

| 探针 | 撤掉什么 | 结果 |
| --- | --- | --- |
| 67① | 覆盖范围退回"列举字段" | `fail=1` |
| 67② | `ok` 不再算 findings | **预期全绿**（设计上冗余，见下） |
| 67③ | 导出前不验正文哈希 | `fail=1` |
| 67④ | 不比对存储行哈希 | `fail=1` |
| 67⑤ | 顶层冗余 snapshotHash 不进文档 | `fail=2` |
| 67⑥ | 不检查两份 snapshotHash 是否一致 | `fail=1` |
| 67⑦ | `exportedAtMs` 整数校验 | `fail=1` |
| 67⑧ | 路由不要求 `by` | `fail=1` |
| 67⑨b | 路由不认 `/export` 后缀（等价于被通配路由抢走） | `fail=4` |
| 67⑩ | 不存在的 attempt 给空导出而非 404 | `fail=1` |
| 67⑪ | 封面版本不同时硬读 | `fail=1` |
| 67⑫ | 正文 tamper 判定被短路 | `fail=1` |

**67② 是坦白，不是漏测。** 在覆盖范围改成"取余"之后，每一条 finding
都同时会让某个布尔翻转，所以撤掉 `findings.length === 0` 这一项，
总判定照样是假。它在**今天**确实冗余，保留它是对**将来**新增 finding 的保险。
把它写成"预期全绿"而不是假装它能被孤立地验出来：

> 一条"设计上冗余、因而无法被单独证明"的保险，
> 与一条"从来没被执行过"的死代码，在覆盖报告上看起来一模一样——
> 区别在于前者被**明确写下来**了，于是下一个人不会去删它。

## §10 ⚠️ 诚实边界

- **本批只做了"导出"这一半。** PRT-409 的原文缺口是「导出、保留策略、
  快照查看的界面」三件——本批交付导出（含路由），
  保留策略与查看界面仍未做，PRT-409 保持 🟡。
- 导出**不加密、不签名**。它证明的是"内容与封皮都没被改过"，
  不是"这份文件来自一台可信的机器"——后者需要签名，而本项目零依赖。
  能做的只是把哈希带出去，让接收方**能**核对。
- `verifySnapshotExport` 只验哈希，**不做内容审查**。一份验得过的导出
  仍然可能包含不该外传的内容；内容的处置是"谁能导出"的问题（见下条）。
- 导出路由**不做权限检查**：任何能访问 hub 的调用方都能导出任何 attempt。
  这与 hub 现有的读路由一致（本机回环 + token 的信任模型），
  但值得记下来——导出正是"把内部数据变成一份可以带走的东西"的那个动作。
- 版本不同时**不猜**字段语义（报 `wellFormed: false`），代价是导入方
  必须先升级才能读新版本的导出。
