# PRT-410 / PRT-412：上下文的端到端契约（确定性、越权、超限、回放、不可信不扩权）

> spec §6.5、§11 验收（PRT-410 确定性/越权/超限/回放测试；PRT-412 标记不可信来源
> 并验证其不能扩大权限或改变审批策略）
>
> 交付物：`team-hub/context-e2e.test.mjs`（22 例）+ `team-hub/server.mjs` 的一处具名码修复

---

## 1. 这一批问的是**另一层**的问题

`runtime/context/` 下的装配器、来源、脱敏、tokenizer、仓储
**各自都有套件、且全绿**：

| 套件 | 验的是什么 |
| --- | --- |
| `context-assembler` | 裁剪三账本守恒、权限只拿元数据、必需来源放不下即失败 |
| `context-sources` | 归一、默认不可信、权威字段拒绝 |
| `context-redaction` | 脱敏先于截断、账本不记原值 |
| `context-tokenizer` | 保守估算必须是上界 |
| `context-store` | 快照不可变、落库前与读回时都验哈希 |

那五条全是**纯函数**：输入是内存里的对象，输出是内存里的对象。

而这一组问的是：

> 那四条性质**跨过 HTTP 与 SQLite 之后**还成立吗？

这不是"覆盖更多"，是**换了一层**。中间多了两样东西：

1. **JSON 序列化**——它会吃掉 `undefined`、把 `Date` 变成字符串、
   把所有数字变成 double、丢掉 `Map`/`Set` 的形状。
   而哈希是对**内容**算的：一次往返就可能让"确定"变成"不确定"。
2. **一条 HTTP 响应**——调用方（worker）对抗的是状态码与 `code`，
   不是那个抛出来的异常对象。

第 2 点在这一批里直接产出了一个真缺陷（第 5 节）。

## 2. 一条容易被写错的响应形状

`POST /api/context-snapshots/assemble` 返回的是：

```js
{ recorded, summary, snapshotHash }   // ← 没有完整快照
```

要看正文、分段与两个账本必须再
`GET /api/context-snapshots/<attemptId>`。

**这不是绕路，而是回放要问的问题本身**：写与读是两条独立的路，
而"读回来的是不是当初写下的"只有在读回来之后才能回答。
第一版用例写成 `assemble(...).body.snapshot.finalText`，
八条一起 `TypeError` ——那八条**一条都没在验它们声称的东西**。

## 3. 五组断言

### ① 确定性

- 同一份输入装配两次 → 同一个哈希；**正文也一致**
  （只比哈希会漏掉"哈希对了但正文换了"）
- **候选顺序反转 → 哈希不变**。这是最强的一条：装配器内部先排序再算哈希。
  若排序缺席，"同一份上下文"就取决于调用方拼数组的顺序
- 冻结时刻参与哈希（不同 `frozenAtMs` → 不同哈希）
- **换一个字节 → 冲突**（同 attempt 换内容必须 409，且不许静默覆盖）

后两条是配对的。一个**对变化不敏感**的哈希会让回放、去重、篡改检测
三件事同时静默失效——而它的表现在所有正向用例里都是"通过"。

### ② 越权

- 不可读的来源进 `excluded`，且它的内容**不在正文里**
  （只在账本里记一笔是不够的——那证明不了内容没泄漏）
- `canReadIds: []` → 一个都不进，正文为空
- **权限字段一个都不给 → 400**，不是默认放行

`canReadIds: []` 与"没给"是两件不同的事：前者是明确的"谁都不许"，
后者是调用方写错了请求。把它们合并处理，就是把一次明确的拒绝变成一次放行。

### ③ 超限

- 非必需来源放不下 → 裁掉、**快照照常落库**、裁剪留有账本
- **必需**来源放不下 → 400 `CONTEXT_TOO_LARGE`，且库里**没有**半份快照
- 没有精确 tokenizer 时**明说**是保守估算

第二组的两个后果都要验。只验状态码的话，一个"先落库再报错"的实现
会留下一条没有对应 Attempt 结论的快照——**它看起来像一次正常的装配**。

### ④ 回放

- 读回时重算哈希 → `verification.ok === true`
- **重放**：用同一份输入重新装配，得到的哈希与历史那一份相同
- 篡改库里的正文 → `ok === false`
- 篡改库里的哈希 → `ok === false`
- 读回的是**当初写下的正文**，不是重新装配出来的

最后一条最要紧：若读回时重新装配，历史就成了"用今天的政策解释过去"——
而权限、预算、来源都可能已经变了。

### ⑤ 不可信来源不能扩权（PRT-412）

- 权威字段**逐个**拒（`grants`/`policy`/`approvalPolicy`/`manifestPatch`/
  `manifest`/`toolScope`/`allowedTools`/`permissions`/`roleChange`/`budgetOverride`）
- 未知字段也拒（不许搭便车）
- **可信来源同样**不能携带权威字段
- `sources.scope` 不能把来源放进另一个空间
- 上游交付物即使自称 `trusted` 也仍是 `untrusted`

第一条**逐个字段**过一遍而不是挑一个代表：名单是一条可枚举的承诺，
漏掉其中任何一个都是一条提权路径；而"挑一个代表"的测法
对名单后半段的增删**完全不敏感**。

最后一条把 PRT-402~406 的核心判断钉住：**信任看的是"谁写的"，
不是"谁转发的"**。但它的内容照常进上下文——不可信 ≠ 不可见。
把不可信内容整段丢掉是另一种错：那会让模型看不到真实世界里的输入。

## 4. 变红验证：12 处，12 处红

| 探针 | 破坏的判断 |
| --- | --- |
| ⑥① | 权威字段的拒绝不带具名码 |
| ⑥② | 权威名单与未知字段白名单**两层一起**拆 |
| ⑥③ | 权威字段只对**不可信**来源拒绝 |
| ⑥④ | 未知字段被静默忽略 |
| ⑥⑤ | 权限字段缺失时默认放行 |
| ⑥⑥ | `canReadIds: []` 被当成"没给" |
| ⑥⑦ | `sources.scope` 真的进了快照的作用域 |
| ⑥⑧ | 超限失败后仍把快照落库 |
| ⑥⑨ | 候选不排序就算哈希 |
| ⑥〇 | 读回时重新装配而不是读存下的正文 |
| ⑦① | `verify` 恒为通过 |
| ⑦② | 同 attempt 换内容时静默覆盖 |

### 四个探针第一轮「没咬住」——每一个都教了一件事

**⑥②/⑥③「补丁应用了但用例没红」。** 只拆掉权威字段那一圈**不够**：
未知字段白名单独立地挡住了同样的键。这不是坏事——**纵深防御真的在起作用**——
但它意味着那两条探针问不出任何东西。改成**两层一起拆**，9 条与 7 条立刻红。

> 一条只拆掉一层防线的探针，与一条根本没打上的探针，
> 在"用例没红"这个读数上是分不出来的。

**⑥⑤「补丁没应用」。** 锚点写的是
`code: 'CONTEXT_PERMISSION_REQUIRED',`，而真实那一行是
`ok: false, code: 'CONTEXT_PERMISSION_REQUIRED',`。而且**即使打上了也没用**——
换个错误码名字只证明"码被断言了"，证明不了"缺失时不会放行"。
改成 `if (false) {`（真的放行）之后，3 条红。

**⑥⑦「补丁应用了但用例没红」——这条最有价值。**
探针对准的是路由里覆盖 `collectCandidates` 作用域的那一句。
它没红的原因是：**那条护栏当下观察不到**。实测三条收集路径
（评论 / 任务 / 目标）**都不给来源设 `scope`**，所以来源上的 `scope`
恒为 `undefined`，覆盖与否结果一样。

于是做了两件事，而不是把测试改到能红为止：

1. 把用例改成断言**不变量**（外来作用域不得出现在快照或它的来源上），
   并**在注释里写明**这条护栏当下观察不到、它是防"以后有人让来源带上
   scope"的护栏。一个不能被观察的护栏，不该假装有覆盖。
2. 把探针对准**真正承重的那一处**（`policy.scope`）——改了它，
   外来作用域真的进了快照，3 条红。

这正是本仓库反复出现的那个判据：
> 一个不能被违反的保证，与一个不存在的保证，在输出上完全一样。

## 5. 顺带修掉的真缺陷：最要紧的那次拒绝没有名字

写 ⑤ 那一组时发现：来源携带 `grants` **确实被拒了**（400），
但响应体里是 `code: null`。

原因是 `createContextSource` 抛的是**普通 `Error`**（没有 `code`），
而 `handleRun` 对没有码的异常一律发 `code: null` 的 400。

后果不是"能不能拦住"，而是**拦住之后调用方能不能程序化地知道原因**：

```
{ ok: false, code: null, error: "来源 evil 携带了会改变权限/策略的字段 grants：…" }
```

调用方要么去匹配错误文案（**文案会随措辞变更而碎**），
要么把它当成"某个 400"一并处理。而这条路由上**最要紧的一次拒绝**
就是这一个——"不可信内容想携带 `grants`"。

而这份代码在同一个路由里已经为别的事做过正确的处理：

```js
ok: false, code: 'CONTEXT_PERMISSION_REQUIRED',
```

注释里写着理由：「消息能读、但客户端**无从程序化判断**」。
**同一条路由上两种风格并存**，所以这不是设计取舍，是漏了一处。

修法：在路由里接住 `createContextSource` 的异常，包成带
`code: 'CONTEXT_BAD_SOURCE'` 的 400，并在消息里带上是哪个候选被拒。
复用已有的码而不是新造一个——让"来源本身不合法"在这条路由上
**只有一个名字**，不管它来自 `collectCandidates` 还是这一层。

探针 ⑥① 守的就是这一条：把码去掉，7 条红。

## 6. 未交付

- **`replay` 没有工具**。这一批验的是"同一份输入重新装配得到同一个哈希"，
  但没有交付"拿一份历史快照作为输入、跑完整条 Attempt 并断言结论相同"
  的重放工具。前者是后者的地基，不是它本身。
- **PRT-412 的端到端扩权验证只做到"拒绝"这一半**：
  "从真实 hub 读到一份恶意 repo 文件 → 走完整条链路 → 断言审批策略没变"
  里的"审批策略"那一半没有交付——因为审批策略本身（PRT-3xx）
  尚未接线，现在没有任何东西可以断言"没变"。
- **来源的 `scope` 在高层路径上恒为 `undefined`**（第 4 节 ⑥⑦）。
  这是一个**未定**的设计点：来源带上 scope 之后，权限判定要以谁为准，
  spec §6.5 只说了"权限过滤"没说这一层。现在的护栏是防它乱来，
  而不是在实现一个已定义的行为。
- **`final_text` 等扁平列与 `payload_json` 可以漂移**，而 `verify` 只看后者。
  权威副本是 `payload_json`；扁平列是给 SQL 查询用的投影。
  一个改了扁平列的篡改**验不出来**。这一条**如实记下**：
  它不影响回放（读回以 payload 为准），但影响任何直接查那些列的检索功能。
