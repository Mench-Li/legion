# PRT-411：冻结时点与「运行中更新进入下一次 Attempt」（spec §6.5、§6.4）

> 阶段 4 收口。交付 `orchestrator/worker/context-stage.mjs` + 套件 `context-stage`（27 例）、
> 把 `buildContext` 从**注入的桩**变成真实阶段、把 `requiresPersist: ['attempt','contextSnapshot']`
> 从**一段 JSON** 变成真闸门。
>
> spec §6.5：快照在 `BuildingContext` 完成、Attempt 进入 `Running` 之前冻结，
> 之后不可修改；运行中到达的新评论与目标更新**只进入下一次 Attempt**，首版不热注入。

---

## 1. 这一批修的是一句"说了但不成立"的话

状态机为 `BuildingContext → Running` 声明了：

```js
Running: Object.freeze({ requiresPersist: Object.freeze(['attempt', 'contextSnapshot']), … })
```

而在本批之前，`contextSnapshot` **没有出现在 `EVIDENCE_CHECKS` 里**。
`checkEvidence` 对未登记项的处理是：

```js
const probe = EVIDENCE_CHECKS[name]
if (probe === undefined) continue // 尚未实现核验的证据种类
```

于是这条声明**只是事件流里的一段 JSON**。更糟的是它同时具备了另外两个条件：

1. `orchestrator/worker/main.mjs` 的 `buildContext` 是一个注入的**桩**
   （`async () => ({ kind: 'minimal', note })`）；
2. 它的返回值被 `step()` 返回后**直接丢掉**。

三者合起来的效果是：Attempt 可以一路走到 `Running`，
**没有任何上下文快照**，而记录里看不出任何异常。

> 「声明了一件事」与「保证了一件事」在输出上完全一样，只要没人去违反它。

所以本批做了三件事，而不是一件：把声明变成闸门、把桩换成真阶段、把结果写进证据。

---

## 2. 「没接」与「没做」是两回事（§6.4 的边界）

`inPlaceStages()` 里原本并排放着两个降级阶段：

```js
prepareWorkspace: async () => ({ kind: 'in-place', note }),
buildContext:     async () => ({ kind: 'minimal',  note }),
```

它们看起来对称，其实处境**完全不同**：

| | 状态 | 正确的处理 |
| --- | --- | --- |
| 工作区隔离（PRT-306） | **真的没交付**——全仓库没有工作区表、没有 store | 只能如实声明降级 |
| 上下文快照（PRT-401~413） | **已全部交付**，装配器/来源/脱敏/tokenizer/仓储各有套件且全绿 | 只是**没接**——必须接上 |

「模块写好、用例绿、没有人调用」与「功能不存在」在用户看来完全一样。
所以现在 `buildContext` 只在调用方**明确给出** `contextStage` 时才降级，
并且降级与否是**可判定的**（`contextFrozen: false`），不靠 `kind` 的字符串去猜。

PRT-306 的降级声明一个字没动——那一半是真的没做，改了就是撒谎。

## 3. 两条判断

### ① 装配输入拿不到时**失败**，不降级成空上下文

一份空的快照会让 Attempt 走进 `Running` 而模型什么都没有——**比失败坏得多**：
失败会被重试或上报，空快照会被当成"正常运行"。

同理，**落库失败必须让整个阶段失败**。catch 之后继续会造出一个
"跑过了但无据可查"的 Attempt，而那正是 spec §6.5 要消灭的东西。

### ② 权限判定 fail closed，且**默认拒绝**是有痕迹的

`canRead` 不传时默认 `() => false`——拒绝一切。
一个"默认都能读"的默认值会让**一次接线遗漏**变成**一次静默越权**。

但仅仅拒绝还不够：那样"没人接线"与"权限判定结果是全都不可读"
在证据里长得**完全一样**。所以结果里带 `canReadDefaulted: true`，
审计里也带一份。

> 这条是变红探针 ㊽ 教出来的。它原本只改了**审计**那一行而用例仍然全绿
> ——说明审计里那个字段**没有任何断言在管**。我把它对准返回值并补上断言之后才红。
> 一个没人断言的字段和一个不存在的字段是同一回事。

另外 `canRead` 抛异常时**排除这一个来源**而不是让整次装配失败。
第一版我断言成"失败"，用例红了——**红的是测试**：无法判断不等于可以放行，
但"权限服务抖了一下"也不该让整个任务失败。排除它、在 `detail` 里带上真实错误，
运行继续。（排除原因里必须带真实错误，否则"权限服务挂了"与"这个人确实无权"
在记录里长得一样，排查会走错方向。）

## 5. 顺带发现的两件事

### `workspace` 是一条**没人实现的声明**

新加的「核验清单是**总**的」用例把状态机声明的所有 `requiresPersist`
名字收齐逐个归类，第一次跑就红了：

```
`workspace` 既没有核验实现，也不在"已知未实现"清单里
```

`PreparingWorkspace → BuildingContext` 声明了
`requiresPersist: ['attempt','workspace']`，而全仓库**没有任何工作区持久化**
（没有表、没有 store）——因为 PRT-306 本身还没交付。

所以它此刻**不可能**被核验。这条用例的价值不是"修好它"，而是**逼它显式存在**：
它现在列在 `KNOWN_UNIMPLEMENTED` 里，带理由，交付 PRT-306 时必须回来挪走。
一条"没人实现的声明"与一条"实现了的声明"在事件流里长得一模一样。

### 用例夹具在**走一条走不通的路**

闸门变严之后，`run-store.test.mjs` 里 5 条用例立刻红了。
红的是**用例**：它们此前都在"不落快照就进 `Running`"——
而那正是实现变严之后**不应该允许**的事。夹具现在走**真实的写入路径**
（`assembleContext` → `contextStore.record`），而不是手写一条 INSERT：
后者要把 20 个 `NOT NULL` 列名抄一遍，列一旦增删就会**静默地**与真实表结构脱节。

这一条在整轮 CI 上放大成了 8 个套件、约 60 条用例。处理方式是**分两类**：

| 夹具形态 | 怎么补 |
| --- | --- |
| 直接持有 store 的（acceptance / handoff / policy） | `team-hub/context-fixture.mjs` 的 `freezeFixtureContext()`，走真实写入路径 |
| 走 HTTP 的（run-routes / acceptance-routes / handoff-routes） | 调**真实的装配路由** `POST /api/context-snapshots/assemble` |
| 真实 worker 进程内跑的（run-plane-e2e） | `createHubContextStage()` |
| 真实 worker **子进程**（kill-drill） | 同上，在 `kill-drill-worker.mjs` 里 |

「走 HTTP 的」那一类刻意不绕过去（不直接写库）：于是"冻结在 `Running` 之前"
在测试里也是真的被走了一遍。三条路由套件的 44 条用例因此同时覆盖了
**路由 + 闸门 + 阶段**三者的接缝——而那个接缝此前没有任何东西在看。

## 6. 远程 worker 的 `buildContext`：装配在 hub 那一侧

给 `run-plane-e2e` 和 kill-drill 补夹具时暴露出一个**真实的设计缺口**：
装配需要的数据（目标、任务、团队计划、员工清单、评论、产物）都在 **hub 的库里**，
而 worker 是**另一个进程**。让 worker 自己装配，意味着它要么直连那个 SQLite 文件
（两进程抢一个库，并把数据面细节泄漏进调度层），要么把读取逻辑写第二遍。

而 `POST /api/context-snapshots/assemble` 已经是**装配 + 持久化在同一个请求里完成**的
（PRT-407 就把它设计成这样，理由写在路由的注释里）。所以远程 worker 的
`buildContext` 就是**调那条路由**——于是本批交付了第二个工厂：

```js
createHubContextStage({ post, loadSources, canRead, clock })
```

它与本地路径的三处不同，都值得显式记下来：

1. **不假定 hub 客户端的形状**：`post(path, body)` 由调用方注入。
   在 worker 里假定其中一种客户端会把两边的接线绑死。
2. **权限必须明确回答**，含糊的回答（`undefined`/`'yes'`/`0`）**抛错**而不是
   翻译成"全不可读"——后者看起来会像一次正常的权限结果。
   三种明确回答分别映射到路由的 `canReadAll` / `canReadIds`，且**恰好给一个**。
3. **没有"默认放行"这回事**：`canReadDefaulted` 恒为 `false`，
   因为路由本身就拒绝不带权限的请求。本地路径的那个标志在远程路径上不存在——
   两条路都是"冻结成功了"，所以这个差别必须能被看出来。

**路由失败就是阶段失败**，且 hub 的具名码原样保留在 `assemblyCode` 上。
其中 `CONTEXT_TOO_LARGE` 被提升为 `CONTEXT_ASSEMBLY_FAILED` 而不是
`CONTEXT_PERSIST_FAILED`：前者回答"能不能靠精简输入解决"，
后者回答"存不存得下去"——两者对运维的动作完全不同。

### 顺带修掉的真实缺陷：`claim` 不发 `scope`

写远程阶段的用例时，`buildContext` 报「装配输入里没有 scope」。
查下去发现 `shapeAttempt()` **一直有** `scope`，而 `claim` 的响应体漏了它。

这不是"参数没传"那类能一眼看出来的错误。worker 拿不到自己的空间，
只有两条路：**拒绝一切**（看起来像一次正常的权限结果，来源全被排除），
或者**自己猜一个默认空间**（一次静默的越权）。两条都不会报错。

而权限判定**正是以空间为参照的**（spec §6.5）。所以 `scope` 跟着认领一起发出去，
不是一个便利字段，是这一步的前置条件。

### 第二批变红验证：8 处，8 处红

| 探针 | 破坏的判断 |
| --- | --- |
| ⑤③ | 认领响应又不带 `scope` |
| ⑤④ | 远程路径吞掉路由失败（快照没落库却继续） |
| ⑤⑤ | 远程路径把超限也报成 `PERSIST_FAILED` |
| ⑤⑥ | 权限回答含糊时偷偷当成"全可读" |
| ⑤⑦ | 远程路径的 `canRead` 变成可选 |
| ⑤⑧ | 装配路由的具名码被丢掉 |
| ⑤⑨ | 演练 worker 又用降级的空 `buildContext` |
| ⑥〇 | e2e 的真实 worker 又用降级的空 `buildContext` |

⑤⑨ 与 ⑥〇 值得单独说：它们破坏的不是断言，而是**接线**——
把真实 worker 的阶段换回降级的空实现。它们能红，说明这两条套件
**真的在走完整条链路**（走不到 `Running` 就直接失败），
而不是在断言一些关于链路的字符串。

### 这两处差点被记成"没红"——探针的**读数**也是要验证的

第一轮跑完，⑤⑨ 与 ⑥〇 报的是「红了但没有失败用例」。

真相是**反过来**的：破坏之后两条套件里的用例**确实都红了**
（`✖ ①`、`✖ ③`），只是——

> 套件里只要留了一个活着的子进程，`node --test` 就**永远不会打印
> `ℹ fail N` 那一行汇总**。

而我的探针脚本数的正是那一行。于是「用例红了」与「什么也没红」
在只读汇总的实现里**长得一模一样**。

这与本仓库已经踩过的那个坑是同一枚硬币的两面：
那边是"一个失败的断言伪装成一次卡住"，这边是
**"一次卡住伪装成一次通过的验证"**。
一条**没有验证过自己读数**的验证脚本，与一条正确的验证脚本，
在只读它的输出的情况下是区分不出来的。

修法是把读数从"汇总行"换成"逐行的 `✖ `"，并**两个都数、取大**：
汇总行给出权威计数，逐行给出在汇总行缺席时的下界。
（顺带发现：非零退出码本身也不够——`execFileSync` 超时被杀同样是非零，
而那说明的是"没跑完"，不是"跑红了"。）

同一条坑在别的探针上也出现过一次：⑤⑨ 第一次的失败信息是
`⚠️ 补丁应用了但用例没红`，而真实原因是 `node --test` 被 15 分钟超时杀掉；
**换一个有界超时**之后才看见那两行 `✖`。

## 7. 未交付

- **生产 CLI 入口仍未接上上下文阶段**。`orchestrator/worker/run.mjs` 的
  `executor` 默认是 `null`（RuntimeAdapter 接线是 PRT-253/311 的事），
  所以**今天没有任何真实部署走过这条路**——闸门目前只在用例、路由套件、
  真实 worker 演练与 kill-drill 里生效。
  这不是"故意不做"，而是如实记录：下一个接执行引擎的人会在这里被闸门拦住，
  而那正是它该起的作用。拦住时的错误是 409 `EVIDENCE_MISSING`，
  消息里点明缺 `contextSnapshot`——不是一次超时，也不是一条 500。
- **`workspace` 证据未实现**（见第 5 节，等 PRT-306）。
- **`runResult` / `approval` / `reconciliation`** 三条证据同样未实现，已显式列出。
- **PRT-410 的"回放"**：本批保证了同一份输入得到同一个哈希，
  但没有交付"拿一份历史快照重放并断言得到同样结果"的工具。
- **PRT-412 的端到端扩权验证**：`sources.mjs` 已保证不可信来源不能携带权限字段
  （PRT-402~406），但"从真实 hub 读到一份恶意 repo 文件、走完整条链路、
  断言审批策略没变"这一步未做。
- **`createHubContextStage` 的 `loadSources` 未接真实数据面**：
  当前 kill-drill 用它发零来源（`{ scope }`），得到一份合法的空快照。
  这是**诚实**的（"这次运行看了 0 个来源"可回答），但真实场景需要
  从 hub 读团队计划 / 员工清单 / 评论——那属于 PRT-412 与数据面接线。
