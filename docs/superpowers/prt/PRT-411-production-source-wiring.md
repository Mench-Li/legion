# PRT-411（收尾）：生产路径真的把来源装配接上了

> spec §6.5 / §6.4。上一批（PRT-402~406）交付了一个**可用的**来源装配器，
> 但它在**生产路径上没有被调用**——本批把它接上。

## §1 这一批要解决的问题

`createHubContextStage` 的 `loadSources` 默认是 `async () => ({})`，
`createProductionExecutor` 会把它透传下去——而 `productionExecutorProvider`
**从不传它**：

> 一个"零来源"的运行与一个"来源齐备"的运行，
> 在快照账本上都写着"已冻结"——
> 只不过前者的模型是在一个我们没告诉它任何事的世界里动手。

这与 `budgetActor` 是**同一类**接缝缺陷。那一个的教训已经写在
`executor-binding.mjs` 里：

> 闸门代码是对的、套件是全绿的、生产路径上这个变量**没有来源**。

本批的 `loadSources` 是完全相同的形状：装配器是对的、套件是全绿的、
生产路径上这个参数**从来没人传**。

## §2 判据不是"参数传下去了没有"

参数传下去而没人用，与没传，在结果上是一样的。所以本批的判据是：

> **经过生产入口之后，冻结出来的快照里到底有没有真来源。**

这要求用例起**真的 hub**——判据是"库里真的多了一条来源"，
假 hub 只能测"我们发出了一个形状正确的请求"。

## §3 新增的三处接线

| 位置 | 内容 |
| --- | --- |
| `executor-binding.mjs` | `readFromGet(get)`：把 hub 的 `{status, body}` 适配成装配器要的 `read` |
| `executor-binding.mjs` | `productionExecutorProvider` 无条件装上 `loadSources` |
| `sources-loader.mjs` | `withEpochMs`：在边界把 hub 的时间字段名补成 `*Ms` |

### 3.1 为什么适配层非有不可

`createHubSourceLoader` 的 `read` 契约是「**成功返回正文，失败抛错并带上
status**」；而 hub 的 `get` 是「**总是返回 `{status, body}`**」——
它把失败也当成一个正常返回值。

这个差别不只是形状问题，它是**本装配器唯一要紧那条纪律的落点**：

> 读失败（500/超时）与"真的没有"（404）必须分开。

`get` 把两者都变成一个带 status 的对象，于是"忘了检查 status"就等价于
"把 500 当成 404"——而后者会让这次运行静默地少掉一部分世界观。

把它收在一个函数里，是为了让"哪里可能把失败当成功"**只有一处可查**。

### 3.2 为什么**无条件**装上（不给开关）

装配器读不到东西时会**抛错**。那正是我们要的：一次读失败必须让这次
Attempt 失败，而不是静默降级成"上下文更少的运行"。

用开关关掉它，就等于把那个降级重新变成一个**可选项**——
而"可选项"在生产上意味着它迟早会被关掉。

## §4 ★ 接线才暴露出来的真缺陷：字段名错配

第一次跑通生产路径的用例，得到的是一个 **HTTP 400**：

```
Task 缺少取得时间（acquiredAtMs/createdAtMs/updatedAtMs 都不是整数毫秒）。
装配器不会用"现在"当默认值——那会让同一份输入产生两个不同的快照哈希。
```

`acquiredAt` 的拒绝是**对的**（拿"现在"兜底会让同一份输入产生两个快照哈希，
回放与篡改检测同时失效）。真正错的是**字段名**：

| 谁 | 用的名字 |
| --- | --- |
| `sources.mjs`（`taskSource`/`goalContextSource`/`publishedSources`） | `createdAtMs` / `updatedAtMs` |
| hub 的 `rowToTask` | `createdAt` / `updatedAt`（ISO 字符串） |

`acquiredAt` 其实**能**解析 ISO 字符串（内部会 `Date.parse`）——
错的是 `updatedAtMs` 与 `updatedAt` 是**两个不同的键**。
所以后果不是"少一个字段"，而是整条装配 400。

### 4.1 为什么以前没人发现

`taskSource` / `goalContextSource` / `publishedSources` 直到本批才**第一次**
被喂真实 hub 对象。在那之前它们只有用例里手搓的输入，
而那些输入恰好都用了 `*Ms` 的名字。

> 一个"用例里一直用对字段名"的模块，
> 与一个"只认自己发明的时间字段名"的模块，是同一个东西——
> 只不过前者的用例全绿，而它一接上真实数据就 400。

**修法**：在**边界**换名字（`withEpochMs`），不去放松 `acquiredAt` 那条拒绝。
只补**缺的**键——调用方已经给了 `*Ms` 时不动它（用例手搓的输入走这条）。

## §5 验证

- 套件 `executor-binding-sources`（8 例，**起真的 hub** + 绑定最小宿主端口）。
- 破坏性验证 **6/6**（65①–65⑥）：
  - 65① 拿掉 `loadSources` 接线 → 5 条用例红（退回零来源快照）
  - 65② 不再补时间字段名 → 4 条红（复现那个 400）
  - 65③ 适配层把非 200 当成功 → 红
  - 65④ 适配层丢 `status` → 红
  - 65⑤ 评论不带 epoch 时间 → 红
  - 65⑥ 任务 404 不再拒绝 → 红

### 5.1 探针过程本身的两处（如实记录）

**① 65⑥ 首轮 `fail=0`——跑错了测试文件。** 补丁打在 `sources-loader.mjs` 上，
却让它去跑 `executor-binding-sources.test.mjs`，而那条判据
（`TASK_NOT_FOUND`）在 `sources-loader.test.mjs` 里。这与前两轮
（PRT-711"锚点没命中"、PRT-712"跑错测试文件"）是**同一类**：
**探针自身的错误伪装成判据的缺陷**。

**② 判据放宽：红可以来自抛错，不必来自断言。** 原先的 harness 要求
`assertions > 0`，但这对**正确行为就是抛错**的判据不公平——
例如"适配层丢了 `status`"会让装配器抛 `READ_FAILED`，
用例于是以一个**非断言**的错误失败，而那同样是这条判据在起作用。

> 一个"红来自抛错所以不算数"的判定，
> 与一个"只在断言变红时才认账"的判定，会漏掉整整一类正确实现。

现改为：`fail > 0 && !importErr`，并把 `assertion` / `throw-red` 分别报出来
（仍然排除 import-error——那是补丁打坏了，不是判据变红了）。

## §6 诚实边界

- 生产路径仍要求 **DSH 宿主端口已绑定**（`bindDshRuntime`，PRT-214/215）。
  没有绑定时照旧 `EXECUTOR_HOST_PORT_REQUIRED` 且不认领——
  **本批没有放松那条拒绝**。所以这套用例是自己绑一个最小端口来驱动那条路的。
- 换句话说：**这条接线今天仍没有真实部署走过**。它能被证明的强度止于
  "一个绑定了最小宿主端口的进程里，生产入口真的从 hub 取了来源并冻结"。
- `withEpochMs` 只覆盖 `createdAt*` / `updatedAt*` 两族名字。
  hub 若新增别的时间字段（例如 `finishedAt`），需要同步——
  **没有测试能自动发现"又多了一个对不上的字段名"**。
- `readFromGet` 只认 `status === 200` 为成功。204 会被当成失败——
  而本装配器读的三个端点都返回 200，所以这是有意的严格。
