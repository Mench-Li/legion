# PRT-413 收尾：让"精确 tokenizer"真的能走进去

> `team-hub/server.mjs` 里有一个 `TOKENIZER_REGISTRY`，注释写着：
>
> > **默认为空**，因为本项目零依赖、拿不到任何供应商的词表。空表不是缺陷，
> > 而是如实。有词表时在这里 `set(model, defineExactTokenizer({ ... }))` 即可——
> > 本表的存在是为了让"精确"有一个**接入点**，而不是让默认值看起来精确。
>
> 前半段是对的：我们确实拿不到词表，零依赖 + 数据许可，两件事都不允许
> 把它打进仓库。但后半段只对了一半：
>
>   > 一个"留了接入点、但没有任何东西能走进去"的注册表，
>   > 与一个"根本没有注册表"的实现，在没人提供词表的时候是同一个东西——
>   > 只不过前者会让"精确 tokenizer 这条路径"看起来是**通的**。
>
> 本批把"走进去"那一段补上。

`PRT-413` 的三项里，**canonical JSON**（PRT-401）与 **tokenizer + 保守估算降级**
早已交付；未交付的是「为具体 ModelProfile 接入真实词表」。本批交付它，
并顺手挖出三个真缺陷。

---

## 1. 算法 vs 数据：为什么零依赖也能算对

关键观察：**字节↔可打印字符的映射是算法，不是数据。**

`bytesToUnicode()` 把 256 个字节值映射到可打印的 Unicode 码点（可打印字节原样保留，
其余按顺序挪到 256 以上）。这一段不含任何模型常量，所以：

- 它可以在零依赖下实现；
- `decode(encode(x)) === x` 是**可测**的（对任意 Unicode，包括 emoji 与控制字符）。

而**词表与 merge 规则**是数据——那部分必须由使用者提供。于是本模块里
**没有一个硬编码的模型常量**：

| 文件 | 是什么 | 谁能提供 |
| --- | --- | --- |
| `runtime/context/bpe.mjs` | 编码器（算法） | 本仓库，零依赖 |
| `*.tokenizer.json` | 词表 + merges（数据） | 使用者 |

**这就是为什么"拿不到词表"不再是"精确不可做"的理由**：拿不到的是数据，
而数据有了一条不经过改代码的装载路径。

## 2. ★ 手算可验的切分（否则与 `count = () => 1` 分不开）

测试用一份**手写的极小词表**，够算出可手验的结果：

```js
merges: ['h e', 'l l', 'he ll']
vocab:  { h:0, e:1, l:2, o:3, he:4, ll:5, hell:6, hello:7 }
```

`hello` → `h e l l o` → ① 合 `h e`(rank 0) → `[he, l, l, o]` ② 合 `l l`(rank 1)
→ `[he, ll, o]` ③ 合 `he ll`(rank 2) → `[hell, o]`。**2 个 token。**

> 一个"用假数据喂出来的 BPE 已验证"，
> 与一个"从来没验证过切分"的实现，在用例只断言"不抛错""返回正数"时
> 是同一个东西——只不过前者会让 `count = () => 1` 一路绿到生产。

另一条钉住的是 **merge 的优先级由次序决定**，不是"能合就合"：
`['a b']` 与 `['a b','ab c']` 对同一段 `abc` 给出不同切分。

## 3. ★★ 真缺陷一：未覆盖时**不能算 0 个**，而要算上界

某个合并出来的 token 不在词表里时，真正的 tokenizer 会把它继续拆成更小的片段，
也就是**更多** token。所以"查不到就当 0 个"是**低估**方向：

```js
if (id === undefined) {
  ids.push(-1)   // ★ 至少算一个；绝不能算 0
  if (!misses.includes(tok)) misses.push(tok)
}
```

> 一个"词表里查不到就不计 token"的计数器，
> 会在词表缺一段时**低估**预算，
> 而"低估"的代价在 PRT-413 的原始设计里写得很清楚：
> **以为放得下 → 把超限内容发出去 → 在供应商那一侧失败，而钱已经花了。**

### 3.1 ★ 被断验证逼出来的**第二件事**：那段"按字节数计"的循环是死的

这一段的**第一版**是这样写的：

```js
const bytes = [...tok].length
for (let i = 0; i < bytes; i += 1) ids.push(-1)   // ← 第一版
```

探针⑥⑤ 把它换成一个 `ids.push(-1)`，期望用例变红——**读数不变**。
原因是那个循环**永远不会转第二圈**：`bpePiece` 的结果来自 `Array.from(piece)`，
而在字节级串里一个字符就是一个字节。也就是说，"按字节数计"这件事是由
**上游的切分粒度**保证的，不是由这段代码再乘一遍保证的。

> 一个"看起来在按字节数计"的循环，
> 与一个"只 push 一次"的语句，在切分粒度恒为一时是同一个东西——
> 只不过前者会让人以为**那段代码**在保证上界，
> 于是有人改动 `bpePiece` 的切分粒度时，不会想到上界还能不能守住。

于是做了两件事：① 把死循环删掉，把上面那段理由写进注释；
② 把**真正的前提**写成一条会红的用例——「未覆盖片段必须恰好一个字节」
（`runtime/context/bpe.test.mjs`：「★★ "按字节数计"是由**切分粒度**保证的」）。
改切分粒度的人现在会红在那一行上。

## 4. ★ 坏产物一律拒绝，**不跳过**

`parseTokenizerArtifact` 校验 name / model / evidence / vocab / merges / pattern，
**失败一律抛错**。`loadTokenizerRegistry` 亦然。

"跳过"看起来更健壮：少一个模型，别的照用。但：

> 一个"坏产物就静默跳过"的装载器，
> 与一个"坏产物就让装载失败"的装载器，在每份产物都合法的时候是同一个东西——
> 只不过前者会让一个**拼错的词表文件名**变成"这个模型没有精确 tokenizer"。

同理，**没配置目录**与**配了但读不到**是两件事：

- 没配置（`null`/`''`）→ 空注册表 → 保守估算器，这是既有且如实的行为；
- 配了但读不到 → **抛错**，错误消息里明写"注意这与'没有配置目录'不同"。

`pattern` 也在**加载期**编译一次——坏正则会让每一次 `count` 都抛，
而那时错误发生在运行中间。

## 5. ★★ 真缺陷二：`status()` 有副作用，且"失败"被报成"已加载"

### 5.1 `loaded` 与 `attempted` 必须分开

第一版在读盘失败时写了 `loaded = new Map()`，于是：

1. `status().loaded` 报 `true`——**"读失败了"被报成"加载过了"**；
2. 一个空 Map 会成为后续 `get` 的答案来源。

> 一个"失败后把状态标成已加载"的惰性装载器，
> 与一个"加载成功但词表恰好为空"的装载器，
> 在 `status()` 这一个读数上是同一个东西——
> 只不过前者会让"配置写错了"看起来像"这个模型没有精确 tokenizer"。

现在 `attempted`（别再摸盘了）与 `loaded`（读到了什么）各管一件事，
失败是**粘住**的：不重试，也不给一个空答案。

### 5.2 诊断函数不该读配置

第一版把 `getDir()` 放进了 `status()`（"顺便报一下目录"）。

> 一个"报告状态的函数会顺手读一次配置"的实现，
> 与一个"只在装载时才读配置"的实现，在没人调用 `status()` 的时候
> 是同一个东西——只不过前者会让**排障**这件事本身产生副作用。

现在 `getDir()` 只在构造时调一次，用例断言 `status()` 前后调用次数不变。

## 6. ★★ 真缺陷三：**配置声明了、校验了、文档写了，但取值时少了一层**

`PRT-615` 的审批 TTL 有这么一段注释（就在同一处代码上方）：

> 一条写错的 `LEGION_APPROVAL_TTL_MS` 如果被静默换回默认值，表现是"配置改了但没生效"，
> 而这类问题的排查方向完全错误（运维会去看配置有没有被加载，而不是看那个值本身）。
>
>   > 一个「配置写错了就用默认值继续」的解析，
>   > 与一个「配置项根本没接线」的解析，在「改了到底有没有用」上是同一个东西。

**而那一行读的是 `CFG.approvalTtlMs`。** 解析后的值在 `CFG.values` 下面
（`loadConfig` 返回 `{values, sources, errors, warnings, ...}`）。
`CFG.approvalTtlMs` 恒为 `undefined`，而 `resolveApprovalTtlMs` 把 `undefined`
当成"用默认值"——**这条配置从来没有生效过**。

> 这正是上面那段注释所警告的那种失败，
> 而它偏偏发生在写那段注释的**同一个地方**：
> `values.dbFile` / `values.port` / `values.token` / `values.host` 都是对的，
> 只有这一处漏了 `.values`——**一个在四行正确代码里错了一行的解析**。
>
> 一个"配置声明了、校验了、文档写了、但取值时少了一层"的接线，
> 与一个"配置完全没接线"的实现，在用户改了配置之后是同一个东西——
> 只不过前者会让那条配置**看起来是支持的**（它有 schema、有区间校验、
> 有文档），于是没人会去怀疑它。

已修正为 `CFG.values.approvalTtlMs`。

## 7. ★★ 真缺陷四：**精确计数在人看的那句话里写着"约"**

`describeAssembly` 原本对**任何** kind 都写"约"：

```js
const parts = [`包含 ${snapshot.sources.length} 个来源（约 ${snapshot.tokens.tokens} token`]
```

于是接入精确 tokenizer 之后，一个精确计数在用户唯一会读到的那句话里仍然是"约"。

> 一个"对精确值也说约"的摘要，
> 与一个"对估算值也说约"的摘要，在两者都写着约的时候是同一个东西——
> 只不过前者会让 `tokens.kind` 这个**唯一用来区分两者的字段**失去作用，
> 因为它从来不出现在那句给人看的话里。

现在两种 kind 各自带上自己的名字：`（约 2 token，保守估算）` vs `（2 token，精确）`。
新用例断言精确的那条**不含"约"**、且**含"精确"**。

## 8. 接线：三处，缺一条就等于没做

| 环节 | 位置 | 变化 |
| --- | --- | --- |
| 声明 | `team-hub/config-schema.mjs` | 新增 `LEGION_TOKENIZER_DIR`（`type: 'path'`，默认 `''`） |
| 构造 | `team-hub/server.mjs` | 空 `Map` → `createLazyTokenizerRegistry(() => CFG.values.tokenizerDir \|\| null)` |
| 可观测 | `GET /api/config` | 新增 `tokenizer` 栏（`dir`/`loaded`/`count`/`models`/`error`） |
| 出口 | `runtime/context/index.mjs` | 导出 BPE 与装载器 |
| 用例 | `scripts/ci/run-ci.mjs` | 注册 2 个新套件 |

`/api/config` 那一栏是**必需的**，不是锦上添花：

> 一个"配了目录但没人能问出它生效了没有"的实现，
> 与一个"没配"的实现，在运维发现问题之前是同一个东西——
> 而能区分它们的那唯一的字段（`tokens.kind`）没人会去看，除非已经超限了。

★ `status()` **不读盘、不抛错**，所以这个免鉴权的探测端点不会因为一个坏词表目录
而变慢或 500；真正的读盘发生在第一次需要 tokenizer 时，失败在**那次请求**上抛出
（用例实测：坏目录 → 400 `TOKENIZER_BAD_ARTIFACT`）。

## 9. ★ 顺带修一个**误报的安全规则**

`scripts/config/config.test.mjs` 有一条安全网：

```js
if (/TOKEN|SECRET|PASSWORD|_KEY$/.test(f.env)) assert.equal(f.sensitive, true, ...)
```

`LEGION_TOKENIZER_DIR` 因为名字里含 `TOKEN` 被它拦下——而它是词表**目录**，
不是凭证。标成 `sensitive` 是错的：那会让它从 `/api/config` 里被抹掉，
而运维排查"我配了词表目录，到底生效了没有"时正是要看它。

**没有去改宽那条正则**（排除 `TOKENIZER`），因为那会让规则下一次再撞上同类误报时
**没有任何记录**；改成一个**逐条登记、每条写明理由**的豁免表，
并额外断言"进了豁免表就不能同时标 sensitive"（两者自相矛盾）。

### 10.1 ★ 探针工具本身也崩过一次，而崩的方式值得记下来

给这份 harness 追加新探针时，`_prt-handoff/prt402-breakverify.mjs` 的**运行段被截掉了**。
成因是我写了一个"回退上一次追加"的小脚本，它做的是：

```js
s = s.slice(0, bannerIndex) + '// ── 运行 ──…\n'   // ← 把 banner 之后的**全部**内容丢掉了
```

而运行段正好在 banner 之后。于是脚本**照常退出 0**，harness 变成"只定义探针、不跑"，
跑起来**零输出、退出码 0**——看起来像"全过了"。

> 一个"被截掉了运行段、于是什么都不跑"的断验证工具，
> 与一个"全部探针都咬住"的断验证工具，在只看退出码的时候是同一个东西——
> 只不过前者**永远绿**。

修法：把探针段与运行段**各自存成独立文件**（`probes-413.txt` / `runner-402.txt`），
重建时是 `head + probes + runner` 三段拼接，而不是"切掉尾巴再加一段"；
并且重建脚本**断言 runner 段存在**（`out.includes('const results = []')`）。
另加两条：探针工具启动时的 sha256 基线校验（不匹配即 `exit 2`，见 §10.2）。

### 10.2 ★ 同一天里第二次遇到"追加静默失败"

给 `PRT-PROGRESS.md` 的 PRT-413 行追加说明的脚本做的是：

```js
L[ri] = L[ri].replace(OLD_TAIL, '')          // 先把行尾的 ` | | |` 当成旧尾句删掉
L[ri] = L[ri].replace(/ \|$/, ADD + ' |')    // 再想往最后一个 ` |` 前面插
```

第一步删掉之后，行尾已经**没有** `|` 了，于是第二步的 `.replace` **静默什么都没做**，
而脚本打印的是"已更新"——整段写好的说明**从来不存在**，
并且那一行的结尾 `|` 也一起没了（markdown 容忍它，所以没有任何门禁拦下）。

> 一个"没匹配上就什么都不做"的字符串追加，
> 与一个"确实追加成功了"的追加，在目测的时候是同一个东西——
> 只不过前者会让一段写好的说明**从来不存在**，而脚本还报成功。

修法是**先断言匹配、再断言结果**（追加后必须能 `includes` 到那段话），
以及顺手修掉另外三行同样缺结尾 `|` 的行。

★ 更重要的是把这类损伤变成**可测**的：`scripts/prt/progress-check.mjs` 新增
`ROW_NOT_CLOSED` 判据（表格行必须以 `|` 结尾）。加这条判据时又踩到一个同形的坑——
第一版把 `problems.push(...)` 写在 `parseProgress` 里，而 `problems` 不在那个作用域，
于是它**只在真的要报错时**才抛 `ReferenceError`：

> 一个"只在出错时才崩"的校验器，
> 与一个"能正常报出错误"的校验器，在文件一直没问题的时候是同一个东西——
> 只不过前者会把"文件坏了"这件事，报成"校验器坏了"。

现已改成由 `parseProgress` 收集、`checkProgress` 合并，并实测负向有效
（去掉一个结尾 `|` → `ROW_NOT_CLOSED` + `exit 1`；补回 → `PASS`）。

## 11. ⚠️ 诚实边界

1. **词表仍然必须由使用者提供。** 本批做的是"从提供到用上不再需要改代码"，
   **不是**"自带词表"。仓库里**没有任何**供应商词表数据，一个 `.tokenizer.json`
   都不带——这是零依赖与数据许可共同决定的，不是没做完。
2. **pre-tokenize 的正则要由产物给。** 真实模型的分词先按正则切块再 BPE；
   `pattern` 缺省时整段按一个 piece 处理，切分**会与真实模型不同**。
   产物里必须带 `pattern` 才能与那个模型逐 token 对齐。
3. **BOM 会让产物被拒。** 用 PowerShell `Set-Content -Encoding UTF8`（PS 5.1）
   写出的文件带 BOM，`JSON.parse` 会失败、装载会报错（错误消息里点名文件与原因）。
   仓库自己的编码门禁也要求无 BOM，所以这里**刻意不做 BOM 兼容**——
   不做兼容的代价是一条清晰的报错，做兼容的代价是一类"看起来加载了"的静默差异。
4. **`encode` 对未覆盖片段给 `id: -1`（占位）。** 真实词表里不存在 `-1`，
   所以拿 `ids` 去喂模型是错的；`ids` 是**计数与诊断**用的，
   `misses` 只去重、不记次数（次数看 `ids` 里 `-1` 的个数）。
5. **注册表没有热重载。** 产物改了要重启进程。惰性加载 + 失败粘住意味着
   运行中换词表不会被察觉——这是刻意的（一个中途变更的 tokenizer 会让
   同一批快照的 token 数失去可比性）。
6. **`LEGION_APPROVAL_TTL_MS` 的修正没有新增用例。** 它被 `team-hub` 既有的
   审批 TTL 用例间接覆盖（那些用例走 `resolveApprovalTtlMs` 而不是走 `CFG`），
   所以**"配置真能改到那个值"这件事仍没有直接断言**。这是一个留下的缺口。
7. **`/api/config` 新增了一栏，属于平台契约变化**，`baseline-snapshot` 已记录。
   该端点免鉴权（P2-2），因此 `tokenizer.dir` 在远程监听时也是可读的——
   与既有的 `db` 路径同等暴露，口径一致，但确实是一处信息面。
8. **PRT-413 行原有的三条边界仍然成立**：估算器对英文高估约 3~4 倍；
   `defineExactTokenizer` 强制 `evidence`；`kind`/`note` 进快照进哈希。
