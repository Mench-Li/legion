# PRT-506：迁移现有非敏感模型配置

> `team-hub/model-migration.mjs`（**30 例**）+ `GET /api/model-migration/plan`
> + `POST /api/model-migration/apply`。
>
> 核心判断：**一次迁移最危险的产物，是一份看起来可用的配置。**

---

## 1. 老数据长什么样

产品化之前，"哪个岗位用哪个模型"存在两处：`agent_models` 表
（`(scope, role) → (provider, model)`）与 DSH 侧 `settings.yaml` 的 `model`。
目标形态是 `model_profiles`（档案）+ `model_bindings`（岗位绑定）。

一条老数据只有四个字段。而一个**能真正跑起来**的档案还需要：

| 需要的东西 | 老数据里有吗 | 猜的后果 |
| --- | --- | --- |
| `runtimeType`（必填） | ❌ | 以**错误的协议**发请求，报一个与配置无关的错 |
| `endpoint`（可选） | ❌ | 档案看起来"配好了"，直到**第一次运行**才炸 |
| 凭证 | ❌ | 界面显示一切就绪，而运行会失败 |

三种猜法的后果是**同一个**：产出一份看起来可用的配置。而 `endpoint` 尤其坏——
用户不会记得它是迁移来的，只会在某次运行失败时开始怀疑网络。

所以本模块的产物是「**确定的部分 + 待补清单**」，而不是"迁移完成"。

### 一条顺带发现的事实

`POST /api/models`（legacy 写入口）现在**已经被 PRT-252 的配置期校验挡住**：
一个档案都没有时它返回 400 `MODEL_CONFIG_NO_PROFILES`。

也就是说：**legacy 数据只存在于"升级上来的"安装里**，全新安装根本造不出它。
端到端冒烟因此直接写库来构造现场——那不是取巧，那正是真实的迁移场景。

---

## 2. 三条不许猜

### ① `runtimeType` 必填，且**不提供默认值**

```js
if (typeof runtimeType !== 'string' || runtimeType.trim() === '') {
  return finish(base, MIGRATION_CODES.RUNTIME_TYPE_REQUIRED, '...')
}
```

提供一个默认值就等于**替用户做了这个判断**——而这是一个只有用户知道答案的判断
（这批模型按哪种协议说话）。

### ② `endpoint` 不编造

构造出的档案 `endpoint` 为 `null`，并进 `needsAttention`：

```js
missing: ['endpoint', 'credential']
```

于是界面能说"这 2 个档案需要补 endpoint 与凭证**才能运行**"，
而不是一句"迁移完成"。

有一条用例专门盯措辞：总述里**不得**出现"迁移完成 / 全部完成 / 已就绪"。

### ③ 凭证不假设

迁移不碰密钥库。它只说"这个档案还没有凭证引用"。

---

## 3. 容易被忽略的失败：id 归一化会撞车

档案 id 有字符集限制，而供应商名/模型名里可能有别的字符，需要折叠。折叠**可能把
两个不同的模型压成同一个 id**：

```
p + m/n  → p.m-n
p + m-n  → p.m-n     ← 同一个 id
```

那是一次**静默合并**：两个岗位被绑到同一个档案上，而其中一个的模型名消失了。
所以这里主动检测并**拒绝整个计划**，而不是"先建的赢"。

长名字截断时（`MAX_ID_LEN`）附加一个短哈希——**截断必然让前缀相同**，
不加哈希就一定撞。

### 夹具本身也错过一次

这条用例第一版我写的撞车对是 `a/b` 对 `a-b`——它们折成 `a.b-c` 与 `a-b.c`，
**根本不撞**。于是那条用例测的是一件没发生的事，而它是绿的。
改成 `p,m/n` 对 `p,m-n` 并加了一行前提自检（断言这一对**确实**同 id）。

---

## 4. 非敏感迁移**不得**看到密钥

源里出现疑似密钥字段或疑似密钥值时，**拒绝整个计划**，而不是"跳过那一行继续"：

> 一次泄漏不该看起来像一次成功迁移。

值层面的检测也在（字段名无害但值像 `sk-...` 也拒绝）。同时也有一条反向用例，
防止这条闸门因为正常数据（`note: 'hello'`）而红。

---

## 5. 计划与执行之间：指纹

用户看到的计划与服务端真正执行的计划**必须逐字节相同**。

两种错法：
* 按**客户端送回来的**计划执行 → 那份可能过期，甚至伪造；
* 按**服务端重新算的**计划执行 → 用户确认的和实际得到的不是同一件事。

所以：服务端**重算**，然后要求它与用户确认过的 `digest` 一致，不一致就 **409**：

```
MIGRATION_PLAN_STALE：这份计划在确认之后已经变了……请重新看一眼再确认。
```

这与本仓库别处的 CAS 是同一个纪律（版本不符时报冲突，而不是替用户决定用哪一版）。

指纹只覆盖**会造成写入的内容**（要建哪些档案、要建哪些绑定）——多一条"没配过"的
老数据只影响 `skipped`，不该逼用户重新确认。

---

## 6. 执行纪律

* **只增不改**：已存在的档案与绑定一律跳过（迁移不是"把老的盖掉"）；
* **绝不删除源**：源数据保留到用户显式确认之后（有用例断言结果里没有删除动作）；
* **半途失败如实报告已写入的部分**：

```js
// 报成"整体失败"会让用户重跑，而重跑会因为"已存在"而跳过
// ——于是他永远不知道第一次到底做成了什么。
return { ok: false, code, message, created, bound, failed: { created: created.length, bound: bound.length } }
```

## 7. 端到端实测（真起 hub、真发请求）

```
⓪ 种入 3 条老数据（2 条有效 + 1 条空）
② 不给协议: 200 | ok=false | code=MIGRATION_RUNTIME_TYPE_REQUIRED
③ 计划: 200 | 待建=2 待绑=2 待补=2 | digest=2.2.6228ad19
   待补项 missing = ["endpoint","credential"]
   新建档案 endpoint = null
   summary: 将新建 2 个模型档案，建立 2 个岗位绑定，
            2 个档案需要补 endpoint 与凭证**才能运行**，1 项按原样保留。
④ 指纹不符: 409 | code=MIGRATION_PLAN_STALE
⑤ 执行: 200 | created=["custom-ds.deepseek-v4-pro-openai","zai-coding-cn.glm-4.6"]
            | bound=["default/assistant","default/reviewer"]
⑥ 重复计划: 200 | empty=true 待建=0          ← 幂等
⑦ 现有档案: endpoint 为 null
```

注意 ③ 的 summary **明确说了"才能运行"**——它不是"迁移完成"。

### 一处刻意的返回码选择

`GET .../plan` 在缺 `runtimeType` 时返回 **200 + 计划本身**（`ok:false`），不是 400。
理由：这是一个只读的"报告"，而"必须选一种协议"正是报告要告诉用户的第一件事。
返回 400 会让前端先撞一个错误、再猜该传什么参数。

同时顶层**刻意不放** `ok`：计划自己有一个 `ok`，两个 `ok` 在不同层级上是真正会读错
的东西（一个说"这次查询成功了"，一个说"这份计划能不能执行"）。

## 8. 变红验证（9 条）

```
基线 fail = 0
✔ 变红  fail=3  runtimeType 缺失时默认一个（猜协议）
✔ 变红  fail=1  凭空造一个 endpoint（看起来可用，运行时才炸）
✔ 变红  fail=1  id 撞车时静默合并（先建的赢）
✔ 变红  fail=3  源里有密钥时只跳过该行（泄漏看起来像成功）
✔ 变红  fail=1  指纹不符也照跑（执行用户没看过的计划）
✔ 变红  fail=1  半途失败不报告已写入的部分（用户会重跑）
✔ 变红  fail=1  「没配过」被报成「配错了」（错误的具体程度与实际不符）
✔ 变红  fail=1  总述谎称"配置已就绪"（掩盖待补项）
✔ 变红  fail=1  两处调用都删掉后，源码存在性断言才变红
```

**接线那条闸门的真实覆盖范围必须说清**：它只能发现"调用被**整体删除**"。
第一版我把 GET 那处写成 `void planModelMigration({...})`——正则仍匹配、用例全绿。
**一个没生效的变红验证，和一个通过的验证，在输出上完全一样**（本项目第三次）。
它**发现不了"调用了但结果被换成假的"**；那种情况只有端到端冒烟能抓。

## 9. 顺手修掉一处自己造成的损坏

`wire-506.mjs` 写路由时把已经带 CRLF 的字符串又过了一遍 `LF→CRLF` 转换，
于是往 `server.mjs` 里写进了 **104 处 `\r\r\n`**。

它不是"无害的重复"：`\r\r\n` 不是合法的行终止符，按 `\n` 切分时 `\r\r` 会变成
**内容的一部分**。这正是它当时造成的后果——我的变红脚本按行匹配，**匹配不上**。

修法与发现：先统计（HEAD 里本来就有 49 处，说明前几个提交也犯过同样的错），
再 `replace(/\r+\n/g, '\r\n')`，确认 `crcrlf = 0`、`bareLF = 0`、语法通过。

**一个顺带确认的既有问题**（未修，不属于本轮范围）：`team-hub/server.mjs` 的
每个提交都产生**整文件 diff**（HEAD 那次是 11013 行）。原因是 blob 里存的是 CRLF
而 `core.autocrlf=true` 会在比较时把工作区转成 LF。这不影响正确性，但它让这个文件的
**每一次评审都不可读**——而"改动可审"正是这些改动唯一的价值来源。修它需要一次
独立的、仓库级的行尾决策（改 `.gitattributes` 或统一 blob），不应混在功能提交里。
