# PRT-508：配置导入导出（排除密钥）

**对应 spec**：§6.6 第 403 行「配置导入导出；**导出不包含密钥**」、§3.1「模型密钥不进入提示词、业务数据库正文、日志、**导出证据**或能力包」
**交付物**：
- `runtime/contracts/config-bundle.mjs` —— 构造、校验、导入计划（**纯模块**，不做 I/O）
- `runtime/contracts/config-bundle.test.mjs` —— **27 例**
- `team-hub/server.mjs` —— 三条路由：`GET /api/config-bundle`、`POST /api/config-bundle/plan`、`POST /api/config-bundle/apply`
- `team-hub/config-bundle-routes.test.mjs` —— **18 例**（自起进程 / 库 / 端口）
- 副产品修复：`handleRun` 的**双写缺陷**（见 §5，它影响所有"在回调里自己写拒绝响应"的路由，包括 PRT-503 那批）

---

## 1. spec 原文与落地

> 配置导入导出；导出不包含密钥。

"不包含密钥"有三种强度，必须明确选一种：

| 强度 | 含义 | 问题 |
| --- | --- | --- |
| 脱敏 | 密钥值被替换成 `***` | 脱敏逻辑漏一处 = 密钥永久留在文件里 |
| 省略 | 密钥值不写，但**引用名**保留 | 引用名指向**本机**密钥库槽位，跨机器没有意义 |
| 剥离（本实现） | 值与引用名都不写，只保留"要不要凭证" | 同一台机器上恢复备份也要重新绑定一次引用 |

本实现取**剥离**，并把它做成**出口保证**而不是调用方的责任。

---

## 2. 为什么 `secretRef` 一定剥掉，而不是"保留但说明"

两条理由，第二条更根本。

**① 引用名本身是可枚举的攻击面。** 仓库里已经有过一次同样的判断——
`toModelDescriptor` 只暴露 `hasCredential`、不暴露引用名，注释写的就是
"引用名也是可枚举的攻击面"。**同一份判断不该在导出路径上放宽**：
导出文件比接口响应更容易被复制、粘贴、发微信、进 Git。

**② `secretRef` 是**本机**的配置，不是模型档案的属性。** 它命名的是
*这台机器*密钥库里的一个槽位。把它带到另一台机器上，那个名字什么也不指——
**最坏的结果是新机器上恰好有一个同名槽位，于是这条档案用上了一把完全无关的
钥匙，而且看起来一切正常**。

这种故障极难发现：没有报错、没有鉴权失败（那把钥匙是有效的，只是属于另一个
服务或另一个人），只有账单或者数据流向能暴露它。

于是导出物里：

- 保留 `credentialRequired` —— "这条档案**需要**凭证"，这是档案的属性；
- 丢掉 `secretRef` —— "从哪台机器的哪个槽位取"，这是那台机器的事。

**代价是明确的**：同一台机器上恢复备份也要重新绑定一次引用。这是有意换来的
——少一次点击，换"跨机器导入时不会悄悄接上一把无关的钥匙"。

## 3. 三条出口保证

### ① 有明文密钥 → **拒绝构造**导出包，而不是"剥掉再继续"

```js
const hits = findPlaintextSecrets({ kind, note, profiles, bindings })
if (hits.length > 0) throw new BundleError(BUNDLE_ERRORS.CONTAINS_SECRET, ...)
```

剥掉需要脱敏逻辑正确，而**脱敏漏一处就等于把密钥永久留在导出文件里**。
拒绝是 fail closed，且失败立刻可见。这与 `model-store.mjs` 的
`assertAuditClean` 是同一条理由——那里也是"宁可什么都不记"。

关键的顺序：**先查后返回**，不存在"已经返回了才发现要拒绝"的窗口。

### ② 显式再查一遍"引用名真的没了"

第一条查的是密钥**值**，第二条查的是引用**名**——两者不同。
`EXPORTABLE_PROFILE_FIELDS` 是由 `MODEL_PROFILE_FIELDS` **派生**的
（`filter(f => f !== 'secretRef')`），所以现在是安全的；但一份手抄的字段表会在
PRT-501 增删字段时漂移，而漂移的表现是"新字段静默地不被导出"。

**一条只在"代码写对了"时才有效的防线，需要一条能验它在不在的检查。**

### ③ 导入方向同样挡

一份被别人塞了密钥的文件不该进库：

- 整包 `findPlaintextSecrets` 查出疑似明文 → 拒绝；
- `containsSecrets: true` → 拒绝（这个声明本身就是"我有密钥"）；
- 逐条档案带 `secretRef` → 拒绝（那个名字在本机什么也不指）；
- 未知顶层字段 → **拒绝**，不是忽略（忽略会让密钥字段搭便车）；
- 版本不等于 1 → **拒绝**，不是尽力解析（尽力解析会把"格式变了"变成
  "少导了几条"，而少导几条是静默的）。

## 4. 导入为什么必须是两段式

导入会改变"哪条任务用哪个模型"。把绑定里的 `primaryProfile` 从 A 改成 B，
**同时**改变了三件事：

1. **成本**（单价不同，而预算是按运行预留的）；
2. **质量**（同一份提示词在两个模型上的产出不同）；
3. **数据去了哪**（这是最要紧的：换了供应商就换了数据出境目的地）。

一次性静默应用意味着这三件事都在无人看到的情况下变了
——而**换模型不是换配置，是换供应商**。

于是：

```
POST /api/config-bundle/plan   → 计划（dry run，**不写任何东西**）
POST /api/config-bundle/apply  → 应用（只做计划里 create/update 的那些）
```

`plan` 的返回值里同时带上 `applicable`（能不能直接应用），
否则前端要自己重算一遍"有没有冲突 / 悬空引用"，而**两份判定必然漂移**。

### 冲突策略：默认 `fail` 而不是 `keep`

| 策略 | 已存在且内容不同时 | 谁该选它 |
| --- | --- | --- |
| `fail`（默认） | 标 `conflict`，**不动**，409 | 任何"我不知道会覆盖什么"的场景 |
| `keep` | 标 `skip`，保留库里那份 | 只想补齐缺失的档案 |
| `overwrite` | 标 `update`，用包里的覆盖 | 明确知道这台机器要被这份包接管 |

**默认是 `fail` 而不是 `keep`，这一点是刻意的。** `keep` 看起来更安全，
但它会让一次本该报错的导入**静默地什么都没做**——用户以为配置已经导入了，
下次运行才发现用的还是旧模型。**报错至少是可见的。**

`keep` 还有一个陷阱：它把冲突转成 `skip`，于是 `summary.conflicts` 变成 0。
如果回执只报 `conflicts`，用户看到的是"零冲突、成功"，
而包里那些改动**一处都没进去**。所以：

- 每个被策略跳过的动作带 `keptLocal: true`（让它**可数**，而不只活在提示语里）；
- `summary.keptLocal` 单独计数；
- `apply` 的回执带 `keptLocal`。

### 不删除

导出包里没有的档案/绑定**保持不动**。导入是"补齐与更新"，不是"同步成这份包"
——后者会让一份不完整的包删掉整台机器的配置，而"不完整"是常态
（比如只导出一条模型做灰度）。

### 悬空引用 → 拒绝应用

包里的绑定引用了一条"包里没有、本机也没有"的档案时**拒绝应用**。
照单全收会存下一条跑不起来的绑定，而它要到运行时才被发现有错
——那时已经认领任务、烧掉一次尝试（与 PRT-502"主档案不可用直接 409"
同一条纪律：**能在写入时发现的错，不要在运行时发现**）。

注意判据是"包里**或**本机有"，不是"包里有"——只认包里会让一次
"只导入绑定"的操作永远失败。

## 5. 副产品：`handleRun` 的双写缺陷

### 怎么发现的

我在 `apply` 路由里沿用了仓库既有的模式——在 `handleRun` 的回调内部直接
`json(res, 409, ...)` 然后 `return`（PRT-503 的预算路由就是这么写的）。
因为 `json()` 没有"已发送"守卫，`handleRun` 之后还会再写一次 `200`。

而 `res.writeHead` 在响应已发出后会抛 `ERR_HTTP_HEADERS_SENT`，
那个异常被 `handleRun` 自己的 catch 再写一次响应（又抛），
最后逃到最外层被 `if (res.headersSent) res.end()` **静默吞掉**。

### 为什么测试看不到

**客户端拿到的响应完全正确**（第一个写出去的就是 409）。
这条缺陷在响应上没有任何痕迹，所以 18 条路由用例一条都没红。

我一开始以为"没有报错 = 没有发生"，直到把 `json()` 包了一层计数器直接数写次数：

```
守卫在位：  json() 写过的状态码 = [409]              ← 一次
守卫拿掉：  json() 写过的状态码 = [409, 200, 400]     ← 三次
           handleRun catch = ["Cannot write headers after they are sent to the client"]
           外层 catch      = ["Cannot write headers after they are sent to the client"]
```

**三次写、两次抛出、零条记录。**

### 修法

1. `handleRun` 成功分支：`if (!res.headersSent) json(res, 200, ...)`；
2. `handleRun` catch：`headersSent` 时**记一条**再 return，而不是静默 return；
3. 最外层 catch：`headersSent` 时 `console.error` 之后再 `end()`，
   不再无声无息地吞掉。

第 2、3 条是防"响应发出之后才炸"这种更难查的情况——它发生时客户端看到的是
一个**正常的响应**，而服务端没有任何记录。

### 这个修复的覆盖面

它不只修 PRT-508。**任何**在 `handleRun` 回调里自己写拒绝响应的路由都受影响
——包括 PRT-503/510/511 的十条预算路由。它们此前一直靠最外层那个吞异常的
`res.end()` 在兜底。

## 6. 抓到的缺陷（全部先验过会变红）

这一批一共抓到 **6 个缺陷 + 5 个测试自身的错误**。

### 真实缺陷

**① `secretPolicy: 'references-omitted'` 让**自己导出的包无法导入**。**

`findPlaintextSecrets` 会把"键名含 secret/token/key/credential/password
**且值是字符串**"判成明文密钥载体。于是导出物里那个描述凭据处理方式的
字符串字段，会让导入侧报
`导入包含疑似明文密钥（$.secretPolicy）：拒绝导入`——而那里一个密钥都没有。

改名为 `credentialPolicy` **仍然中招**（含 "credential"）。最终的修法是
**换成布尔**：`containsSecrets: false` + `credentialRefsIncluded: false`。

这比原来的枚举更精确（"有没有密钥值"与"有没有引用名"本来就是两件事），
而且布尔不在判据射程内。**让探测器保持严格，而不是为了一个字段名去放宽它**
——这与 PRT-102 的 `limits.maxTokens` 是同一类误判（键名像密钥载体、
值完全无害），只是那次的修法（要求值必须是字符串）这次不适用。

**② `toExportableProfile` 重算 `credentialRequired`，往返后信息静默消失。**

导出态里没有 `secretRef`，所以对**一份导出物**再导出时，
`credentialRequired` 是"这条档案要不要凭证"的**唯一**事实来源。
一律从 `secretRef` 重算会把它变成 `false`。

后果：一台新机器导入这份包时不会再提示去绑定引用，而它会在**第一次真实运行、
解密钥的时候**才发现。修法是"已经带了就原样保留"。

这条是**往返一致**用例抓到的，而且它只在那条用例里表现出来——
单独测导出或单独测导入都不会发现。

**③ `keep` 策略下"跳过了几处冲突"不可数。**

`keep` 把冲突转成 `skip`，于是 `summary.conflicts` 是 0。回执只报
`conflicts` 时，用户看到的是"零冲突、成功"，而包里那些改动一处都没进去。
修法是给这些动作加 `keptLocal: true` 并单独计数。

**④ `handleRun` 的双写**（见 §5）。

**⑤⑥** 见下（`json()` 无守卫导致的连带问题，与外层 catch 的静默吞掉）。

### 我的测试自身的错误（5 个）

**① 夹带密钥的用例放错了字段。** 我把密钥藏在 `note` 里，而 `note`
不在 `EXPORTABLE_PROFILE_FIELDS` 里——**白名单先把它扔了**，
`findPlaintextSecrets` 根本看不到。用例于是"通过"了一个从未被执行的检查。
修法：密钥必须放在允许列表**内**的字段值上。

这是一类值得记住的错误：**一个测不到东西的用例，和一个正确的实现，
在输出上完全一样。**

**② 未知字段用例选错了字段名。** 我用 `apiKey`，而它会被**整包密钥扫描**
先拦下（键名像密钥载体），报的是"疑似明文密钥"而不是"未知字段"。
两条门禁都在，先报安全那条更保守——所以修的是断言，而且顺手把这个**顺序**
本身用一条用例钉住了。

**③ overwrite 的 CAS 用例忘了给本机档案带 `version`。** 期望 `currentVersion === 1`，
而测试里的档案根本没有 `version` 字段。修法是给本机档案带上 `version: 7`
并断言 7，另加一条"没有 version 时如实给 `null`，不能编一个 `1`"。

**④ `keep` 策略下 `willWrite` 的期望错了。** 我写 0，而 `keep` 只影响**冲突**
的那些，不影响新增的——那条绑定本机不存在，仍然要创建。实际是 1。

**⑤ 用 CRLF 不敏感的锚点做"改坏源码"验证，导致验证静默失效。**

`server.mjs` 是 CRLF，我在 `node -e` 里用 `\n` 拼多行锚点做替换，
`String.replace` 找不到就**什么都不做**，于是"撤销守卫"这一步根本没生效，
测试当然全绿。我一度据此以为"守卫拿掉也不红"。

修法：改坏脚本一律先探测 EOL 再拼锚点（`break-doublewrite2.mjs`）。
这条对**所有**改坏验证都适用——**一个没生效的验证和一次通过的验证，
在输出上也完全一样。**

## 7. 十条判定的"变红"验证

`break-bundle.mjs`（契约层，9 条）：

| 改坏的东西 | 变红 |
| --- | --- |
| 导出保留 `secretRef`（跨机器会接上一把同名但无关的钥匙） | ✔（19 例红） |
| 出口不做密钥门禁（含明文密钥的配置照样导出去） | ✔ |
| 版本不兼容时尽力解析（把"格式变了"变成"少导了几条"） | ✔ |
| 未知顶层字段静默忽略（让密钥字段搭便车） | ✔ |
| 导入包里带 `secretRef` 也接受 | ✔ |
| 冲突默认覆盖而不是报冲突 | ✔ |
| 悬空引用不再拦 | ✔ |
| 对导出物再导出时重算 `credentialRequired` | ✔ |
| 导入时静默删除包里没有的档案 | ✔ |

`break-doublewrite2.mjs`（路由层，3 条）：**`handleRun` 成功分支的
"已写过就不再写"守卫单独拿掉 → 变红**（其余的 catch 日志是防更深一层的
情况，属纵深防御，不各自单独可验）。

## 8. 未交付

- **没有界面。** 三条路由都可调用，但 Workbench 的"导出配置"按钮、
  "导入前预览差异"对话框都还没有。**导入最需要界面**——`plan` 的价值
  就是"让人在执行前看到会变什么"，而在没有界面的情况下，
  调用方必须自己读懂 `actions` 数组。属 PRT-507。
- **导出文件没有落盘路径。** 接口返回 JSON，没有"导出到文件"、
  没有压缩、没有签名/校验和。尤其是**没有校验和**：一份被改过的导出包
  在导入时无法与原始包区分（密钥门禁挡的是"带没带密钥"，不是"有没有被篡改"）。
- **没有导出审计。** 导出是一次读取整台机器配置的动作，值得记一条
  ——目前只在 `GET` 里直接返回，不写审计。
- **导入的写入不是原子的。** 逐条 `modelStore.create/update` +
  `bindingStore.upsert`，没有包在一个事务里。中途失败会留下**半份导入**，
  而且第二次重跑要重新面对已经写进去的那些（好在幂等：内容相同的会 skip）。
  真正该做的是把整批放在一个事务里，或做两阶段（先写档案、全部成功后再写绑定）。
- **档案与绑定的导入顺序依赖调用方。** 计划里档案排在绑定前面，
  但应用时是按 `plan.actions` 顺序的；如果一份包只有绑定、档案在本机不存在，
  悬空引用检查会拦下——**这是对的**，但也就意味着"用一份包同时补档案和绑定"
  是唯一可行路径，无法"先导绑定、后导档案"。
- **`credentialRequired` 在库里没有落地。** 它是导出附加字段，写库前被摘掉
  （模型档案契约不认识它）。所以"这条档案需要凭证但还没绑定引用"这个状态
  **只在导入回执里出现一次**，之后查不到。要支持"配置页提示还有几条档案
  没绑引用"，需要一个独立存储或者从 `secretRef` 反推——而后者正是导出剥离掉的。
- **`perRunBudget` 的语义没有与 PRT-503 对账。** 绑定里的预算字段一路带过去，
  但账本侧的单价、币种、`priceTableVersion` 都没有在这次导入里校验。
  一份导入的绑定可能带着一个与当前价目表不兼容的预算币种。
- **`findPlaintextSecrets` 的键名判据偏严。** 它会拦下任何
  "含 secret/key/credential/password 的字符串字段"，包括完全无害的元数据。
  这次撞了两次（`secretPolicy`、`credentialRequired: 'yes'`）。
  收紧判据（比如要求值也像密钥形态）会让它漏掉真正的密钥，
  所以本批的处理是**改我的字段名/类型**，而不是放宽判据。
  但长期看，"元数据字段"与"密钥载体"的区分值得一条更明确的规则。
- **没有导出格式的向后兼容测试。** `version !== 1` 一律拒绝，
  所以任何格式演进都是一次**破坏性变更**，需要同时改导出与导入两侧。
  目前只有"拒绝不认识的版本"这一条。
