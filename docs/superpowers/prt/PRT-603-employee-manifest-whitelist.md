# PRT-603 接入 EmployeeManifest 工具白名单

> spec line 925：「`PRT-603`：接入 EmployeeManifest 工具白名单。」
> spec §6.9 line 489：员工 agent preset 属于 **agent 平面**，按 session 挂载，
> 内容是"岗位工具集、persona、提示段、skill 引用"。
> spec §6.9 line 488：ToolGuard hard floor、`tools/pre-execute` 策略 listener、
> approval answerer、Legion 自有 permission preset 表属于 **host 组合 / profile 层**。

状态：**已交付**（`runtime/dsh-composition/employee-manifest.mjs`；
判据 `runtime/dsh-composition/employee-manifest.test.mjs` 20 例）

---

## 1 唯一真正要紧的纪律：清单只能收窄

员工清单挂在 **agent 平面**（按 session 挂载），强制面挂在 **host 组合**。这是两个
不同的平面，所以清单里的任何一项都**不能**产生新的权限——它只能从"这个员工已经被
授予的东西"里减掉。

最自然的写法是"取交集"：

```js
permit.allowedTools = manifest.allowedTools.filter(t => grant.allowedTools.includes(t))
```

它在每一个用例里都是绿的，因为结果确实没有超出授予。但它把越权**丢掉了**：

> 一个「取交集、静默丢掉越权项」的清单合并，
> 与一个「岗位在申请一个它没有的工具、而没人知道」的清单合并，是同一个东西。

本模块的处置是：越权**抛**。四个方向都一样——工具、能力、风险上限、工作目录。

工作目录也收窄这件事容易被忽略：`workspaceRoot` 看起来只是一个默认值，
但如果清单能把它指到授予之外，那么**越界检查就是以清单为准**的：

> 一个「能把自己的工作目录指到别处」的清单，
> 与一个「越界检查其实以清单为准」的清单，是同一个东西。

还有一个方向相反的坑：授予**没有**限定工作目录，而清单指定了一个。那不是收窄，
是放宽（授予没说过不许）。同样抛。

## 2 字段必须**闭合**

spec §6.9 line 489 说清单携带的是"岗位工具集、persona、提示段、skill 引用"，
line 488 说强制面在别的平面。所以清单里出现 `hardFloor` / `denyTools` /
`sandbox` / `approvalPolicy` 这类字段时直接抛：

> 一个「岗位清单里写着 allow 工具 X」的清单，
> 与一个「岗位自己给自己发权限」的清单，是同一个东西——
> 只不过前者看起来像配置。

但只拒绝"我知道的那些强制面字段"是不够的：

> 一个「忽略不认识字段」的清单，
> 与一个「多打的一个字母让整条限制静默失效」的清单，是同一个东西。

`denyTools` 打成 `denyTool`，`allowedTools` 打成 `allowedTool` —— 前者绕过了
字段黑名单，后者让整个白名单变成空列表（然后 `every(...)` 对空集恒真，见 §3）。
所以两个方向都查：`FORBIDDEN_MANIFEST_FIELDS`（已知的越权字段）与
`MANIFEST_FIELDS`（未知字段一律拒绝）。装载自检还断言两者**没有交集**——
否则闭合检查自相矛盾。

## 3 白名单不能恒真

一个白名单唯一有意义的时候，是它**拒绝**某样东西的时候。四种写法会让它恒真，
前三种在配置里完全看不出来。

### 3.1 通配符

> 一个「支持通配 `*`」的白名单，
> 与一个「所有工具都被允许」的白名单，是同一个东西——
> 只不过前者在配置里看起来是有选择的。

`*`、`file*`、`file?`、空白串、非字符串——一律抛。`proveWildcardsRejected`
逐样本**实测**（不是声明"我们知道它会抛"）。

### 3.2 用"能力都在允许集合里"判定未知工具

这是本批最值得记下来的一条。未知工具的能力集合是**空集**，而空集是任何集合的子集：

```
[].every(c => allowed.includes(c)) === true
```

于是"它的能力都在允许集合里"对未知工具**恒真**。一个只按能力授权的清单，
对所有未知工具都是放行的：

> 一个「用'它的能力都在允许集合里'来判定未知工具」的白名单，
> 与一个「所有未知工具都被允许」的白名单，是同一个东西——
> 因为未知工具的能力集合是空的，而空集是任何集合的子集。

所以未知工具**必须被点名**。而且"点名"这件事要**先被演示出来**
（`assertEmptyCapabilityIsVacuouslyAllowed` 真的把 `every(...)` 在空集上算一遍、
把 verdict 留证）——否则这条规则看起来像多余的谨慎。

### 3.3 靠能力授权到达 hard floor 动作

> 一个「靠能力授权就能到达 hard floor 动作」的白名单，
> 与一个「删除文件这件事不需要在岗位清单里被点名」的白名单，是同一个东西。

`delete-file` / `git-push` / `write-secret` 即使能力已被授予，也必须被**点名**。

### 3.4 "至少一个能力匹配"

> 一个「至少一个能力匹配就放行」的白名单，
> 与一个「只要工具会干一件被允许的事，它干的其它事也被允许」的白名单，
> 是同一个东西——而它的方向是放行。

要求**全部**能力都在允许集合里。

## 4 规则的**先后**是有意的

风险上限先于一切其它规则。理由是它是最强的收窄，而且它是唯一**与是否被点名无关**
的规则——一个已点名但风险超限的工具仍然被拒，而且拒绝理由应当指向风险，
而不是指向"没在白名单里"（后者会让人去改错的地方）。

这带来一个具体的测试后果：验证"能力不都在允许集合里"这条规则时，夹具的 `maxRisk`
必须**高于**被测工具的风险，否则它先被风险规则拦下，那条规则**永远走不到**：

> 一个「被前一道更宽的规则挡住的探针」，
> 与一个「从没验证过这条规则」的探针，是同一个东西。

同样的形状在 PRT-610 出现过（一个更宽的判断挡住了更具体的诊断）。装载自检
`proveEveryRuleFires` 把 12 条规则逐条走到拒绝，并且断言：
① 每条都 `allowed === false`；② 规则码对得上；③ 理由文本包含该条特有的**锚点**；
④ 12 条理由文本**两两不同**。

第④条是必须的，因为三个探针共用 `employee-manifest-widens-grant` 这一个码：

> 一个「用规则码互不相同来证明逐条触发」的用例，
> 与一个「三条规则共用一个码、其实只有一条在兜底」的实现，是同一个东西。

## 5 与强制面的接线

白名单以 `whitelist` 参数接进 `createEnforcementBridge` 的 `preExecute`，并且
**跑在策略端口之前**，拒绝即定案：

> 一个「先问策略、策略说 allow 就放行」的桥，
> 与一个「岗位清单只在策略也说不的时候才生效」的桥，是同一个东西。

拒绝理由里必须带**规则名**：岗位清单与策略规则是**两处不同的配置**，值班的人要能
分清该改哪一个（同 PRT-602 §4 的"两种冲突分开"）。

白名单函数拿到的是**投影**（`canonicalHash` / `toolName` / `known`），不是原始
execution。让它自己解析字段，就是 PRT-602 那个漂移的重新引入。用例 ④ 断言
白名单收到的哈希与直接投影得到的是**同一个**。

返回非对象 / `allowed: 'true'` 这类值一律当拒绝（fail closed）。

## 6 本批抓到的三个真缺陷

### 6.1 ★★ 写一行 `version` 就跳过**全部**校验

第一版 `narrowToGrant` 写的是：

```js
const m = manifest?.version === EMPLOYEE_MANIFEST_VERSION ? manifest : normalizeManifest(manifest)
```

意图是"已归一化的清单不必再归一化一次"。但 `version` 是清单里**唯一一个不做任何
校验**就能写进去的字段（它是常量）。于是：

```yaml
version: legion/employee-manifest@1
allowedTools: ['*']
```

跳过了字段闭合、通配符、不认识的能力名、风险等级——**全部**校验。装载自检
（`EMPLOYEE_MANIFEST_CHECKED.readonlyEmployee`）第一次运行就撞上了它。

> 一个「看到 version 字段就认为它已经校验过」的校验，
> 与一个「在清单里写一行 version 就能跳过所有检查」的校验，是同一个东西。

修法：**总是**归一化。`normalizeManifest` 是幂等的（输出只含已知字段、取值都已合法），
所以重复调用无害——但这一点本身也要用例保证（见 6.2）。

### 6.2 ★ 归一化不幂等：`null` 变成了 `'null'`

`input.notes === undefined ? null : String(input.notes)` —— 第二次归一化时 `notes`
是 `null`（不是 `undefined`），于是 `String(null)` → `'null'`。`displayName` 同理。

> 一个「第二次归一化把 null 变成 'null'」的归一化，
> 与一个「每次经过一层就多出一点内容是'已处理'」的归一化，是同一个东西。

修法：显式判 `null`。并且幂等性用例必须**包含显式的 null**——第一版只测了缺省字段，
恰好绕开了所有 `null` 路径（破坏性验证发现：去掉那个 `|| === null` 一处都没红）。

> 一个「只测缺省值」的幂等性用例，
> 与一个「恰好绕开了所有 null 路径」的用例，是同一个东西。

### 6.3 ★ "逐条触发"的 12 个探针里有 3 个共用同一个规则码

不是实现缺陷，是**判据缺陷**：第一版自检写的是"12 条规则名两两不同"，而实际上
工具越权 / 能力越权 / 风险上限越权三条都抛 `employee-manifest-widens-grant`。
断言当场失败——但如果当初把那条断言写成"至少有一个规则名"就不会。见 §4 第④条。

## 7 诚实边界

1. **与 PRT-602 一样，本模块还没接到真实的 DSH 进程里**。清单的**读取**
   （从 agent preset 的 composition 里取出 `allowedTools`）不在本批范围内；
   本批交付的是**校验与判定**，以及它与桥的接线点。
2. **授予（`grant`）从哪来，本批没有回答**。它必须来自 host 平面，且**不能**从
   清单本身推导。`PROBE_GRANT` 是夹具，不是实现。这是 PRT-604/605/606 的前置：
   文件/目录范围、命令/网络/MCP 权限、外部 API 读写，都会扩展这个授予的形状。
3. **`maxRisk` 用的是工具的"有效风险"**（`resolveTool` 会给风险抬升，
   `riskRaised`）。风险抬升的来源（项目配置 / 路径敏感性）在 PRT-604 落地。
4. **工作目录比较是字符串前缀**，做了分隔符归一与大小写折叠（win32）。它**不是**
   符号链接安全的路径包含判定——那是 PRT-604 的题目。本批只保证"清单不能把自己
   的根指到授予之外"。
5. **清单里没有 `unattended` 的判定逻辑**。字段被保留、被归一化，但"无人值守时
   要不要降级"由 PRT-607（审批箱 + 无人值守策略）决定。本模块只把
   `unattended` 带进有效许可。
