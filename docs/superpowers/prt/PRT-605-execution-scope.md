## 1 三条通道的共同点

PRT-604 管的是"碰文件"。本模块管**另外三条出去做事的通道**：起进程、发请求、调 MCP 工具。
它们看起来是三件不同的事，但失败方式是同一个：

> **被检查的东西是一个字符串，而真正执行的东西，是那个字符串被某一层解释之后的结果。**

> 一个「检查字符串」的权限门，
> 与一个「检查完之后字符串才被解释成动作」的权限门，是同一个东西。

所以本模块的每一条规则都是"**不解释**"：

| 通道 | 不解释的形态 | 为什么 |
| --- | --- | --- |
| 命令 | 必须传**已分词的 argv 数组**，单一字符串直接拒绝 | 本模块不做分词——分词结果与执行时的分词器不一定一致 |
| 网络 | 用 `new URL()` 真解析，不做子串匹配 | `https://example.com@evil.com/` 里 `includes('example.com')` 为真 |
| MCP | 工具名必须**恰好一个** `__` 分隔符 | 按"第一个 `__` 切分"时，server 名带 `__` 就能伪装 |

## 2 命令：五种"检查的东西 ≠ 执行的东西"

### 2.1 整条命令当一个字符串

> 一个「把整条命令当成一个字符串去匹配白名单」的检查，
> 与一个「`ls; rm -rf /` 命中了 `ls` 这条白名单」的检查，是同一个东西——
> 而它的方向是放行。

`parseArgv` 对单一字符串直接抛 `NOT_TOKENIZED`；21 个 shell 元字符（含 `$`、`~`、`*`）
在**任何一个** argv 元素里出现都拒绝。拒绝通配是因为"展开之后是什么"取决于当时的工作
目录——**检查时看到的东西与执行时看到的不是同一个**。

**证据要挑能展示危险的样本。** 装载自检里有 8 条拼接写法，其中 **7 条**在"按空白切第一个
词再匹配白名单"的朴素实现下会命中 `ls`：

| 写法 | 朴素分词的首词 | 命中 `ls`？ |
| --- | --- | --- |
| `ls; rm -rf /` | `ls;` | ✗（唯一侥幸） |
| `ls && rm -rf /` | `ls` | ✓ |
| `ls \| tee /etc/passwd` | `ls` | ✓ |
| ``ls `id` `` | `ls` | ✓ |
| `ls $(id)` | `ls` | ✓ |
| `ls > /etc/passwd` | `ls` | ✓ |
| `ls\nrm` | `ls` | ✓ |
| `ls & rm` | `ls` | ✓ |

> 这条证据最初取的是 `'ls; rm -rf /'.split(' ')[0]`，得到的结论是 `false`——
> 它**恰好**证明了相反的事。挑证据时要挑能让危险显形的那一个，
> 而不是挑运气好的那一个。

### 2.2 `./rm` 与 `rm` 不是同一个东西

> 一个「按 basename 匹配程序名」的检查，
> 与一个「在工作目录里放一个叫 `rm` 的脚本、然后 `./rm` 就得到了权限」的检查，
> 是同一个东西——而它的方向是放行。

argv[0] 带路径一律拒绝，除非授权显式写了 `allowPath: true`（那时授权人做了一个决定）。

### 2.3 白名单里有 `sh` 就等于有任意命令

> 一个「白名单里有 `sh`」的检查，
> 与一个「白名单里有任意命令」的检查，是同一个东西。

60 个包装器/解释器（shell、`python`、`node`、`env`、`xargs`、`sudo`、`npm`、
`docker`、`ssh`…）要放行必须二选一：`allowsWrapper: true`，或者给出一个**子命令白名单**。

⚠️ **`denySubcommands` 不算收窄。** 黑名单天生不完整：

> 一个「用禁止清单来收窄一个能执行任意东西的程序」的授权，
> 与一个「禁止了 publish 就想当然认为 npm 不能干别的」的授权，是同一个东西——
> 而它的方向是放行。

### 2.4 ★ 规则顺序：子命令白名单曾经**永远走不到**

`npm` 既是包装器，又常配 `subcommands: ['test','run']`。第一版把包装器规则放在子命令之前，
于是 `npm test` 直接被 `WRAPPER_PROGRAM` 拦下——那条 allow-list 一次都没执行过：

> 一个「被前一道更宽的规则挡住」的规则，
> 与一条不存在的规则，在"它到底拦住了什么"上是同一个东西。

**这条是装载自检抓到的**（`npmWithSubcommandWhitelist.allowed` 是 `false`）。
修法：子命令/开关先判，包装器后判。并且留了一条 `subcommandRuleWins` 证据——
`npm publish` 必须报 `SUBCOMMAND_DENIED` 而不是 `WRAPPER_PROGRAM`；报什么码决定了值班的人
去改哪一处配置。

### 2.5 能设 `LD_PRELOAD` 就等于能执行任意代码

> 一个「能设 `LD_PRELOAD`」的权限，
> 与一个「可以执行任意代码」的权限，是同一个东西——只不过前者看起来像配置。

28 个会改变后续程序行为的环境变量一律拒绝（含 `PATH`、`NODE_OPTIONS`、`GIT_SSH_COMMAND`、
`GIT_EXTERNAL_DIFF`、`BASH_ENV`、`IFS`…）。它在**程序检查之前**判——配置错误要先报出来。

## 3 网络：六种"字符串里有它 ≠ 目标是它"

| 形态 | 为什么不检查就是放行 | 处置 |
| --- | --- | --- |
| `https://example.com@evil.com/` | `includes('example.com')` 为真 | 带 userinfo 一律拒 |
| `https://evil-example.com/` | 后缀匹配把 `evil-example.com` 当成 `example.com` 的子域 | 整段相等 |
| `https://example.com.evil.com/` | 看起来像子域名，其实**不**以 `example.com` 结尾 | 整段相等（诊断不同） |
| `https://example.com./` | FQDN 根点让它不等于白名单项 | 比较前去掉尾点 |
| `https://169.254.169.254/` | 域名白名单**管不住 IP 字面量** | IP 字面量默认拒；私有网段再拦一层 |
| `https://еxample.com/`（西里尔 `е`） | 同形异义 | 非 ASCII 域名拒 |

> 一个「用后缀匹配判断域名是否允许」的检查，
> 与一个「`evil-example.com` 也在 `example.com` 白名单里」的检查，是同一个东西——
> 而它的方向是放行。

> 一个「只查域名白名单」的检查，
> 与一个「`http://169.254.169.254/` 走 IP 字面量绕过域名白名单」的检查，
> 是同一个东西——而它的方向是放行。

跨 host 重定向必须**再判一次**：

> 一个「只在第一次请求时检查 host」的策略，
> 与一个「跟随一次 302 就出去了」的策略，是同一个东西。

### 3.1 ★ 非 ASCII 检查为什么从前**从不触发**

`new URL()` 会对非 ASCII 域名做 punycode。第一版从 `u.hostname` 上找非 ASCII 字符，
于是永远找不到——`еxample.com` 已经被转成 `xn--xample-2of.com` 了：

> 一个「在解析之后才检查非 ASCII」的检查，
> 与一个「解析器已经悄悄把它们转掉了、所以这条检查从不触发」的检查，是同一个东西。

修法：从**原始串**的 authority 段上读。装载自检把这件事留成了证据——
同一次解析里 `rawAuthority: 'еxample.com'`、`host: 'xn--xample-2of.com'`、
`nonAsciiInParsedHost: null`。最后那一项就是"从前为什么不触发"的答案。

### 3.2 非 ASCII 与"后缀"的两种情况

`evil-example.com` 与 `example.com.evil.com` 都会拒绝，但**诊断不同**
（`SUFFIX_NOT_ENOUGH` vs `HOST_NOT_ALLOWED`）。两条都留在自检里，因为
"看起来像子域名的攻击"有两种形状，而诊断不同则修复动作不同：

> 一个「把两种不同的域名攻击报成同一个码」的检查，
> 与一个「值班的人去改错误的那一处」的检查，是同一个东西。

## 4 MCP：必须成对

> 一个「只按工具名授权 MCP 工具」的检查，
> 与一个「任意一个 MCP server 暴露同名工具就得到权限」的检查，是同一个东西——
> 而它的方向是放行。

`fs__read_file` 被授权，不等于 `db__read_file` 被授权——哪怕工具名一样。
而且分隔符必须**恰好一个**：

> 一个「按第一个 `__` 切分」的检查，
> 与一个「server 名里带 `__` 就能伪装成另一个 server」的检查，是同一个东西。

### 4.1 ★ MCP 授权是**额外**收窄，不是替代

> 一个「拿到 MCP 工具授权就等于绕过路径与网络范围」的实现，
> 与一个「装一个 MCP server 就能读整块磁盘」的实现，是同一个东西——
> 只不过前者看起来像"这个岗位可以用这个工具"。

`checkMcp` 接受 `pathVerdict`（PRT-604 的判定）与 `networkVerdict`（本模块的判定），
任一不通过就拒。**本批真的接起来了**：一个 `path-scope-outside-write` 的判定会把
被授权的 `fs__read_file` 拦下（`MCP_BYPASS`）。

## 5 ★ 一次真实的教训：PowerShell 吃掉了源文件里的一个字符

这一批中途出了一次事故，值得单独记，因为它保护的东西**不会被任何现有检查发现**。

为抽查一个探针是否真的让用例变红，我用 PowerShell 做了一次源文件往返：

```powershell
$o = Get-Content $PS -Raw
Set-Content $PS -Value $n -NoNewline   # 打补丁
Set-Content $PS -Value $o -NoNewline   # 还原
```

还原之后 `git diff --stat` **什么都没有输出**——但那是假象：
`execution-scope.mjs` 当时还是**未跟踪**文件，`git diff` 对未跟踪文件什么都不说。

真实的损害：**338 个字符**变成了 U+FFFD。绝大多数藏在字符串字面量**内部**，
所以 `node --check` 只在一处（一个被吃掉的引号）报了 `SyntaxError`，
其余 337 处**语法完全正常**：

> 一个「在多字节字符被吃掉之后仍然能通过语法检查」的文件，
> 与一个「看起来没变、其实信息已经变了」的文件，是同一个东西。

危害在下一步才显形：那一轮针对它的破坏性验证报出 **40/40 全红**。
我当时觉得"全红得可疑"，去查了 `failCount` 分布，才发现每一条都是**整文件导入失败**
（模块顶层语法错误），而不是用例断言变红——**那一整轮验证是无效的**。
如果不去查，"一套 40 处全红的探针"会被当成覆盖率证据写进文档。

修法是重写整个文件（不是逐处补），并把这次事故固化成一道门禁。

### 5.1 新增门禁 `scripts/ci/encoding-check.mjs`

挂在 `run-ci.mjs` 的 **env 阶段**（`encoding: PASS/FAIL`）。它检查二件事：

1. **U+FFFD** —— 解码失败的残留，也是**所有**非法 UTF-8 序列的兜底（见 §5.2）
2. **NUL 字节** —— 文件多半被写成 UTF-16 或二进制

同时它区分**两种严重度**，因为仓库里有 37 个历史遗留：

| 对象 | 判据 |
| --- | --- |
| 代码/配置（`.mjs`/`.ts`/`.json`/`.yml`/`.sql`/`.sh`…）里出现 NUL | **FAIL** |
| 采集类文档（`.md`/`.txt`）里出现 NUL | **note**，仍逐条列出，不 exit 1 |

37 个历史遗留是 36 个验收证据 `.txt` 加 `scratch/baseline/RESEARCH-T096.md`，
都是早期用 PowerShell 重定向/`Set-Content` 写出的 UTF-16LE（`fffe` BOM）：

> 一个「为了让门禁变绿而不再检查」的检查，
> 与一个「把历史遗留当成新回归、于是门禁永远红」的检查，是同一个东西——
> 两者都让这道门禁不再说话。

所以仍然**报出来**（计数 + 逐条文件名），只是不判失败。要不要把历史采集物转成 UTF-8
是一件独立的事（会重写文档历史），不该由这道门禁顺手决定。

### 5.2 ★ 一条**不可能触发**的规则，被删掉了

第一版还查"孤立代理项"。写用例时发现测不出来：`Buffer.from('a\uD800b','utf8')` 得到的
字节是 `61 efbfbd 62`——编码器**已经**把它换成 U+FFFD 了。于是实测解码侧：

| 字节 | 含义 | `toString('utf8')` 的结果 |
| --- | --- | --- |
| `ED A0 80` | CESU-8 形式的 U+D800 | `U+FFFD ×3` |
| `ED B0 80` | CESU-8 形式的 U+DC00 | `U+FFFD ×3` |
| `F0 8D A0 80` | 4 字节形式，仍解成 U+D800 | `U+FFFD ×4` |
| `E4 B8` | 截断的三字节序列 | `U+FFFD` |
| `C0 80` | 过长编码 | `U+FFFD` |

Node 的解码器把**所有**非法序列换成 U+FFFD。唯一入口是
`readFileSync(...).toString('utf8')`，所以结果里**永远不可能**出现孤立代理项：

> 一个「检查一个不可能出现的值」的检查，
> 与一条不存在的检查，在"它到底拦住了什么"上是同一个东西。

**删除**了那条规则，并把"不可达"这件事写进用例钉住：如果哪天 Node 换了行为
（解码器开始透出代理项），那条用例会变红，那时才需要把检查加回来。
同时补了反向用例：合法的 4 字节字符（`𝄞`、emoji）与中日韩内容必须**安静通过**——

> 一个「把合法非 BMP 字符也判成损坏」的检查，
> 与一个「见到 4 字节就报警」的检查，是同一个东西——而它会训练人忽略这道门禁。

门禁自己有判据套件（`scripts/ci/encoding-check.test.mjs`，6 例），
因为**这道检查保护的正是"不会被别处发现"的那类损坏**，它自己的判据必须是被钉住的。

## 6 授权表

字段闭合（`version` / `command` / `network` / `mcp`），版本值也校验，
`normalizeGrant(normalizeGrant(x))` 幂等——与 PRT-603/604 同一条纪律：

> 一个「看到 version 字段就认为它已经校验过」的校验，
> 与一个「在授权表里写一行 version 就能跳过所有检查」的校验，是同一个东西。

`network.hosts: []` 是**合法且安全**的（什么都不许出网），但 `hosts` 不是数组要抛——
否则 `null` 被兜底成空数组会让"配置写错"与"刻意什么都不许"看起来一样。

## 7 诚实边界

1. **本模块产出的是判定，不是执行。** `checkCommand` / `checkNetwork` / `checkMcp` 都返回
   一个判定对象；把它们接到真实的进程启动、HTTP 客户端与 MCP 客户端上，是 PRT-612 的
   固定映射落地时的接线工作。**目前没有任何一次真实的出网请求或子进程被本模块拦下过。**
2. **命令检查建立在一个前提上：调用方给的是已分词的 argv，且执行时不经 shell。**
   如果下游把 argv 拼成一个字符串交给 `shell: true`，本模块的全部保护都失效。
   这个前提必须在接线处（PRT-612）显式断言，本模块只能拒绝"看起来没分词的输入"。
3. **`denyFlags` 是黑名单，天生不完整。** 它拦的是"已知会改变语义的开关"
   （`--force` 等）；一个未知的危险开关不会被拦。要完整覆盖只能反过来用白名单。
4. **非 ASCII 域名是"拒绝"而不是"规范化"。** 零依赖规则下不做 punycode 转换，
   所以合法的非 ASCII 域名（如中文域名）也用不了。方向是安全，但这是真实的功能损失。
5. **IPv6 与非十进制 IP 记法没有覆盖。** `isPrivateV4` 只认点分四段；
   `[::1]`、`0x7f.1`、`2130706433` 这类写法不会被 `PRIVATE_V4` 命中。
   *一个「只认点分四段的私有网段检查」，与一个「`0x7f000001` 绕过了它」的检查，
   是同一个东西* —— 留给 PRT-606 的外部 API 读写细分。
6. **重定向判定要求调用方把上一跳的 host 传进来。** 本模块看不到 HTTP 客户端内部的
   跳转历史；不传 `redirectFrom` 就不会触发这一层。
7. **包装器名单是"已知会重新引入任意执行"的清单，不是完备集合。** 任何一个能
   `exec` 的程序（例如一个自研的 `mytool`）都不在里面。名单的价值在于覆盖常见路径，
   真正的收窄要靠"只给需要的程序"这个默认姿态。
8. **编码门禁只扫受版本控制的文本文件**（`--all` 可含未跟踪）。它不检查二进制、
   不做内容规范化，也不判断"这个文件该不该存在"。
