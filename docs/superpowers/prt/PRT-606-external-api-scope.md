# PRT-606 区分外部 API 读取与写入权限

> spec line 928：「`PRT-606`：区分外部 API 读取与写入权限。」
> spec §6.6 line 465：权限至少覆盖「外部 API 读取与写入」。
> spec §6.6 line 466：权限至少覆盖「发布、付款、删除等高风险动作」。
> spec §6.6 line 944：完成标准「未批准高风险写操作为零」。
> spec §6.6 line 468：不允许改写工具参数；审计、UI 与实际执行必须看到相同输入。

状态：**已交付**（`runtime/dsh-composition/external-api-scope.mjs`；
判据 `runtime/dsh-composition/external-api-scope.test.mjs` 24 例）

---

## 1 这一批要防的是"一串看起来是读的东西"

PRT-604 管文件、PRT-605 管进程/网络/MCP。本模块管**第四种**通道：对外部服务的有语义的
调用。它有方法、有路径、有请求体，而"读"与"写"的区别就藏在这三者里。

问题是：**一条读权限变成写权限，从来不是靠"权限表写错了"**，而是靠七种"看起来是读"的东西。

| 形态 | 为什么看起来是读 |
| --- | --- |
| `GET /api/items` + `X-HTTP-Method-Override: DELETE` | 请求行写着 GET |
| `GET /api/items?_method=DELETE` | 同上，藏在查询参数里 |
| `GET /api/items` + body `{"a":1}` | 方法名是 GET |
| `GET /api/items?action=delete` | 方法名是 GET |
| `POST /api/items` 打一条只授权了读的端点 | 端点对上了 |
| `GET /api/items/1/delete` | 前缀对上了 |
| `POST /api/orders` + `dry_run=true` | 调用方说自己没副作用 |

> 一个「只看请求行上的 method」的检查，
> 与一个「`GET /api/items/1` + `X-HTTP-Method-Override: DELETE` 真的删掉了」的检查，
> 是同一个东西——而它的方向是放行。

所以本模块的结论不是"这个请求是读还是写"这么简单——它先把上面每一种"看起来是读"的
形态**拒掉**，然后才给出 effect。

## 2 本批抓到的真问题

### 2.1 ★★ 复用文件系统路径规范化器——一次类别错误

第一版复用了 PRT-604 的 `normalizeForCompare`，理由听起来很对："同一套路径规范化，
不要两处各写一份，否则权限表与请求两侧的规范形式会分叉"。

装载自检在 Windows 那一支直接否掉了它：

```
path-scope-not-absolute: 路径 "/API//Items/./1/" 没有盘符（反斜杠开头表示"当前盘的根"）
```

**一个 URL 路径永远不会有盘符**，而一个文件系统路径在 Windows 上**必须**有。
两者的规则在这一点上直接相反。还不止：

| | 文件系统路径 | URL 路径 |
| --- | --- | --- |
| Windows 上的绝对性 | 必须有盘符 | 无关（永远以 `/` 开头） |
| 大小写 | 跟着平台折叠（win32 折） | 按 RFC 3986 **永远敏感** |
| 平台参数 | 必需 | 不存在 |

> 一个「把文件系统路径规范化器复用到 URL 路径上」的复用，
> 与一个「在 Windows 上 URL 路径因为没有盘符而被判成非法、
> 在 Linux 上又悄悄折叠了大小写」的复用，是同一个东西。

修法是**写一个独立实现**，并把"这两件事不同"这件事钉进用例（第 ⑯ 例）：
用例直接断言 PRT-604 的规范化器在 win32 上会抛，以及本模块的源码里**不能**出现
对它的 import——但注释里**必须**留下那次报错（否则删了引用连原因一起删了）。

教训的一般形态：**"不要重复自己"在"两个东西其实不同"时会变成最危险的建议**。
判断该不该复用，看的是"它们是不是同一件事"，不是"它们的代码长得像不像"。

### 2.2 ★★ 授权表的错被报成请求的错

写过一版只在 `checkExternalApi` 里解析端点模式。后果是：一份授权表里写着
`/api/items/../admin` 或 `/api/*`，**建表成功**，直到某次请求才报出 `PATH_ESCAPE`。

而那个码看起来像是**这次请求**的问题，于是值班的人去改请求，而真正该改的是那张表。

> 一个「把授权表的错报成请求的错」的诊断，
> 与一个「值班的人去改请求、而配置一直错着」的诊断，是同一个东西。

修法：`normalizeApiGrant` 里就解析模式，把 `parsed` 挂在归一化端点上；
`checkExternalApi` 优先用它（手写裸端点仍然会解析，诊断照给）。
副作用是每次调用少一次解析，而且"建表时校验过"这件事在数据结构上看得见。

### 2.3 ★★ 把 `..` **折叠**掉会让一条只读规则落到另一个端点

这是 PRT-604 真缺陷 ① 的外部 API 版本，但**方向更清楚**：在文件系统里折叠 `..` 会让
路径"永远往深处走"；在这里，折叠会让一条写着 `..` 的规则**变成对另一个端点的授权**：

| 授权表里写的 | 折叠之后 | 实际授权了什么 |
| --- | --- | --- |
| `/api/items/../admin`（`effects: ['read']`） | `/api/admin` | `/api/admin` 的读 |
| `/api/public/../internal/secrets` | `/api/internal/secrets` | 高敏感端点 |
| `/api/orders/../../billing/pay`（`write`） | `/billing/pay` | **付款端点** |

字面上这些规则**什么都不匹配**（除非真有一段叫 `..`）；折叠之后它们落到了别处。
所以本模块的处置是**拒绝**（`PATH_ESCAPE`），而不是折叠：

> 一个「把模式里的 `..` 折叠掉」的规范化，
> 与一个「`/api/items/../admin` 这条只读规则变成 `/api/admin` 的读授权」的规范化，
> 是同一个东西——而它的方向是放行。

请求侧同理，而且多一层：`%2e%2e` 是**编码后**的 `..`，所以必须在匹配之前解码，
解码之后再判 `..`。

### 2.4 ★★ 前缀匹配：两种形态，不是一种

`startsWith` 在两条样本上都给出错误答案，但**错法不同**：

| 形态 | 样本 | 段数 | 正确的判据 |
| --- | --- | --- | --- |
| 更深一段 | `/api/items` vs `/api/items/1/delete` | 2 vs 4 | 段数必须相等 |
| 前缀边界 | `/api/items` vs `/api/items-other` | 2 vs 2 | **整段**相等 |

（第二条正是 PRT-604 的 `assertBoundaryNotPrefix` 想说的那件事。）

> 一个「把两种不同的前缀错法当成一种」的用例，
> 与一个「只修好了其中一种」的用例，是同一个东西。

所以用例把两形态**分开断言**：三条"更深一段"要段数不同，而"边界"那一条要段数**相同**
且 `startsWith` 仍然为真——证明拦不住它的是整段相等，不是段数。

### 2.5 ★★ `dry_run` 是调用方在给自己发免罚单

> 一个「请求里写了 `dry_run` 就当成读」的分类，
> 与一个「由调用方自己声明自己没有副作用」的分类，是同一个东西。

**是否真的没有副作用是服务端的事。** 12 个 `dry_run` 变体（`validate`、`preview`、
`noop`、`check_only`…）逐个探过：每一个都仍然是 `write`、仍然是 `highRisk`。

但它们不是被忽略的——`downgradeAttempt: true` 会把"有人试图让一次写看起来像读"
带进判定对象。审计能看到这件事，而效果不会被它改动。

### 2.6 ★★ 高风险类别必须被点名

> 一个「用路径里有没有 delete 这个词判断高风险」的分类，
> 与一个「`/api/items/delete-preview` 被当成删除动作」的分类，是同一个东西。

证据留在自检里：路径 `/api/items/1/delete-preview` 里确实含 `delete`（
`inferredFromPath: ['delete']`），但它的声明是 `effects: ['read']`，所以
`highRisk: false`、`riskClass: null`——**猜会猜错**。

反过来，`POST /api/orders` 的路径里一个高风险词都没有，但声明了
`riskClass: 'payment'` ⇒ `highRisk: true`。这是 §6.6 line 466 点名的那类动作。

## 3 路径规范形式：拒绝，而不是折叠

URL 路径的规范形式有八条要求，**每一条都拒绝而不是改写**。理由同 §2.3：

| 要求 | 码 | 不改写会出什么事 |
| --- | --- | --- |
| 以 `/` 开头 | `NOT_ABSOLUTE` | 相对路径解析到哪个端点取决于调用方 |
| 不以 `/` 结尾 | `TRAILING_SLASH` | `/api/items/` 与 `/api/items` 可能是两个端点 |
| 没有连续 `/` | `EMPTY_SEGMENT` | 某些服务端把 `//api/items` 当根路径 |
| 没有 `.` 段 | `DOT_SEGMENT` | 服务端不折叠时 `.` 成了合法的 `{id}` |
| 没有 `..` 段 | `PATH_ESCAPE` | 见 §2.3 |
| 没有 `\` | `BACKSLASH_IN_PATH` | 服务端也把 `\` 当分隔符就少切一段 |
| 没有 `?` / `#` | `PATH_HAS_QUERY` | 见下 |
| 没有控制字符 | `CONTROL_CHAR` | 服务端把 `\n` 当段分隔 |

`?` 那一条值得单说：如果接口允许 `path` 里带 `?`，那么
`GET /api/items?action=delete` 的动作**从来没进过 `query` 对象**，
第 ④ 条动作检查就看不到它。

> 一个「允许 path 里带 ?」的接口，
> 与一个「`?action=delete` 从来没进过 query 对象、于是动作检查看不到它」的接口，
> 是同一个东西——而它的方向是放行。

### 3.1 两次编码

> 一个「解码一次就比路径」的检查，
> 与一个「`%252e%252e` 解码一次还是 `%2e%2e`、服务端解码第二次就成了 `..`」的检查，
> 是同一个东西——而它的方向是放行。

所以解码之后如果**还剩**百分号三元组，就拒绝（`DOUBLE_ENCODED`）。

同时逐段按 UTF-8 解码，所以 `%E4%B8%AD` 正确地变成「中」，
而 `%E4` 单独出现（截断的 UTF-8）报 `BAD_PERCENT`。

### 3.2 ★ 规范化必须接受自己的输出

> 一个「接受不了自己输出」的规范化，
> 与一个「第二次经过就抛」的规范化，是同一个东西。

具体的坑：`/api/50%25off` 解成 `50%off`。若 key 直接用解码后的字面量
（`/api/50%off`），第二次经过会因为 `%of` 不是合法十六进制而抛。

本模块的 key 把段内的 `%` 写回 `%25`，于是 `normalize(normalize(x).key).key === x.key`。
自检同时留了**反面证据**：拿解码后的字面量当 key，`naiveThrowCount > 0`，
而且报的正是 `BAD_PERCENT`。

### 3.3 大小写永远敏感

> 一个「在大小写敏感的地方也折叠大小写」的匹配，
> 与一个「`/API/x` 与 `/api/x` 被当成同一个端点」的匹配，是同一个东西。

`urlPath.caseKeys` 的三条拼法得到**三个**不同的键（`distinctCaseKeys: 3`）。
这是 §2.1 的另一个侧面：文件系统在 win32 上折叠，URL 永远不折叠。

## 4 授权表：三条"显式"纪律

### 4.1 `effects` 必须显式列出

> 一个「没写 `effects` 就默认允许读」的端点表，
> 与一个「每条端点都至少允许读」的端点表，是同一个东西。

不写就报错。这不是严格——**"默认是读"本身就是本模块要防的那个错误**。

### 4.2 `host` 是必需的

> 一个「`host` 可以省的端点表」，
> 与一个「这条授权其实对所有 host 生效」的端点表，是同一个东西——
> 只不过前者在配置里看起来是有边界的。

`host` 规范化：小写、去 FQDN 根点。

> 一个「把 `example.com.` 当成另一个域名」的检查，
> 与一个「FQDN 根点让它绕过白名单」的检查，是同一个东西。

### 4.3 写端点必须声明幂等性

> 一个「没声明幂等性的写端点」，
> 与一个「重试算第二次写、但只审了一次」的端点，是同一个东西。

而且 `idempotent: false` 的端点带了幂等键就**拒绝**：

> 一个「带了幂等键就以为重试安全」的判定，
> 与一个「服务端不认这个键、于是每次重试都真的执行一遍」的判定，是同一个东西。

码名是 `IDEMPOTENCY_NOT_HONORED`（这个端点的幂等声明**不被兑现**），
不是"缺少幂等键"——后者会把值班的人引向"给它加个键"，而正确的动作是"别重试"或"换个端点"。

### 4.4 字段闭合，不忽略多余字段

> 一个「忽略不认识字段」的授权表，
> 与一个「多打的一个字母让整条限制静默失效」的授权表，是同一个东西。

根字段（`version`/`endpoints`）与端点字段（`host`/`pattern`/`effects`/`riskClass`/
`idempotent`/`notes`）都闭合。`notes` 是唯一的自由文本，且不参与任何判定。

## 5 判定里的三条"不要猜"

### 5.1 未知方法 fail-closed

> 一个「不认识的方法就按读处理」的分类，
> 与一个「自研的上传方法 `UPLOAD` 被当成读」的分类，是同一个东西——
> 而它的方向是放行。

`UPLOAD`/`PURGE`/`FROBNICATE`/`LOCK`/`COPY`/`REPORT` 六种都在"默认按读"下会**被放行**
（证据：`assumedReadWouldAllowCount: 6`）。本模块对它们**没有默认值**。

大小写与首尾空白正常规范化（`get`/` Get `/`\tpost\n` 都工作）——那是同一个方法，
把它当成未知只会训练人去绕过。

### 5.2 歧义匹配拒绝，不取第一条

> 一个「多条规则命中时取第一条」的匹配，
> 与一个「换个遍历顺序结论就变」的匹配，是同一个东西。

`/api/items/{id}` 与 `/api/{collection}/1` 同时命中 `/api/items/1` 时拒绝，
理由里列出**所有**命中的模式。

码是 `AMBIGUOUS_MATCH` 而不是复用 `BAD_GRANT`：

> 一个「把'请求匹配到多条规则'报成'授权表格式错误'」的诊断，
> 与一个「值班的人去改授权表的语法、而其实该做的是让模式互不重叠」的诊断，
> 是同一个东西。

### 5.3 占位符恰好一段，且必须整段

`{id}` 只匹配**恰好一段**（段数不等就拒）。

> 一个「`{id}` 能吃下若干段」的模式，
> 与一个「`/api/items/{id}` 的读权限覆盖了 `/api/items/1/delete`」的模式，
> 是同一个东西——而它的方向是放行。

半段占位符（`/api/{id}-x`、`/api/x{id}`、`/api/{id}{x}`）一律拒绝，否则它就是一个通配。
通配字符本身（`*` `?` `[` `]` `(` `)` `|` `^` `$` `\` `+` `<` `>`）全部禁止：

> 一个「支持 `*` 的端点表」的授权，
> 与一个「所有端点都被允许」的授权，是同一个东西——
> 只不过前者在配置里看起来是有选择的。

## 6 ★ 一条"从未发出"的错误码不变量

> 一个「声明了但从不发出」的错误码，
> 与一个不存在的错误码，在"它到底告诉过值班的人什么"上是同一个东西。

用例在**模块源码**里数 `API_CODES.<NAME>` 的出现次数，为 0 就是死码。同时校验：
码值唯一（两个名字指向同一个值会让审计无法区分）、全部带 `api-scope-` 前缀
（方便在日志里筛出来）。

这条不变量当场抓到了 26 个"从未发出"——但那是我自己的判据写错了：
第一版数的是**字符串值**（`'api-scope-malformed'`）的出现次数，而每个值在
`API_CODES` 声明里只出现一次。改成数标识符用法之后是 0 个死码。

> 一个「数一个只出现一次的东西」的判据，
> 与一个「永远报同一批结果、于是永远不看内容」的判据，是同一个东西。

## 7 ★ 装载自检抓到的四件事

1. **§2.1 复用是类别错误**——win32 上直接抛。
2. **§2.6 的夹具**：`hostShapes` 逐形态列码。
3. **`OPTIONS: 'write'`**：装载自检里 `unknownMethod.normalized` 那条
   （`['get',' Get ','HEAD','delete','\tpost\n']` ⇒ `['read','read','read','write','write']`）
   是"分类器真的在工作"的证据；把 `OPTIONS` 改成 `write` 会让正常调用被拒，
   破坏性验证确认这会让用例变红。
4. **自检证据的方向**：`naiveFirstTokenMatches` 那类教训（PRT-605）在这里的对应物是
   §3.2 的 `naiveThrowCount`——证据要能**展示**危险，不是展示运气。

## 8 诚实边界

1. **本模块产出的是判定，不是执行。** 它把判定交给 PRT-607 的审批门（`highRisk` /
   `riskClass`）与 PRT-602 的投影。**目前没有任何一次真实的外部 API 调用被本模块拦下过。**
2. **HTTP 层的其他"看起来是读"的形态没有覆盖**：`Content-Type` 的分歧
   （同一段 body 被当成 XML 或 JSON 时语义不同）、`multipart/form-data` 里的
   `_method` 部件（**本模块只查 `query` 与 `headers`，不解析 body**）、
   `X-HTTP-Method-Override` 之外的厂商自定义头。
   第 2 条尤其要紧：一个把方法覆盖放在 body 部件里的框架会绕过本模块的头/查询检查。
3. **`host` 的规范性只做最基本的一层**：不做 punycode（非 ASCII 直接拒）、
   不认 IPv6 字面量、不处理 `xn--` 前缀与 Unicode 域名的等价关系。
   合法的中文域名因此用不了——方向安全，但是真实的功能损失。
4. **端口被完全禁止**（`host` 里出现 `:` 即拒）。所以"同一个服务的非标准端口"
   无法表达；这也顺带拒掉了 IPv6 字面量。
5. **`dry_run` 名单是不完备的。** 它列的是常见拼法；任何服务端自创的
   "我只想预演"参数都不在里面。真正的判据是服务端的实现，本模块只能拒绝已知的形态。
6. **`RISK_CLASSES` 是一个封闭清单。** 新出现的高风险类别（例如"订阅"、"转账审批"）
   必须**先加清单**才会被识别；在此之前那条端点会被当成普通写。
7. **`idempotent: false` 的处理是"带键就拒"，而不是"禁止重试"。**
   不带幂等键的重试仍然是允许的——本模块没有重试计数。
8. **百分号解码的归一化只保证"按 UTF-8 解一次"。** 一份用 GBK 编码的 `%XX`
   不会被正确解码（会报 `BAD_PERCENT`），方向是拒绝。
9. **`notes` 字段不参与任何判定**，也不做长度限制。
