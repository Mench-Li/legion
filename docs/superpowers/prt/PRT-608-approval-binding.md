# PRT-608 审批绑定规范化操作哈希

> spec 阶段 6：「`PRT-608`：审批绑定规范化操作哈希。」
> 完成标准：「改变已批准操作的任一关键字段后无法继续执行。」
>
> `team-hub/approval-binding.mjs`（新增）+ `team-hub/server.mjs`（迁移 + 两个生产点），
> 套件 `approval-binding`（33 例）。

## 1. 本模块唯一真正要紧的那条纪律

**绑定的哈希必须被写下来，而不是每次验证时重新算。**

PRT-611 已经把「两次调用是不是同一个操作」从 `JSON.stringify` 换成了规范化指纹。
但如果审批行里**只存操作 JSON**、验证时再算一遍指纹，那么：

> 审批的「身份」是由**今天这份代码**定义的。

后果是具体的。假设有人往 `OPERATION_KEYS` 里加了一个字段（这正是 PRT-611 的加载时
自检在鼓励的事），那么**所有还在等待的审批**会在一夜之间悄悄改变含义：昨天批准的
那次调用，今天可能对不上；更糟的是反过来——一个原本不匹配的调用，可能因为规范化
变了而匹配上。整个过程没有任何一条日志，因为每一次验证都在「用当前规则算一遍」。

> 一个「每次验证时按当前规则重算身份」的审批绑定，
> 与一个「审批的含义由你读它的那一刻的代码决定」的绑定，
> 是同一个东西——只不过前者的失效方式是**静默重绑**。

所以：批准的那一刻算出哈希、**存进那一行**，之后一切都以那一行为准。规范化规则改了，
旧行的哈希就是一个**旧规则下的字符串**，于是它对不上、于是它 fail-closed、于是有人
看得见。这正是我们要的。

哈希**就是** F-02 的 `operationFingerprint`——不是另算一份。一个与 F-02 各算一份的
绑定哈希，与一个「审批绑的东西和执行时看的东西不是同一个东西」的绑定，是同一个东西。

## 2. 第二条纪律：没有哈希的审批行一律拒绝

迁移会留下一批 `bindingHash` 为 NULL 的老行。对它们只有两种处理方式：

| 处理 | 方向 |
| --- | --- |
| 「这行没哈希，那就跳过哈希校验」 | 危险 |
| 「这行没哈希，所以它绑定了什么我不知道」 | 拒绝 |

> 一个「老的审批行没有哈希，那就跳过哈希校验」的回退，
> 与一个「任何审批都放行」的回退，是同一个东西。

所以 NULL 哈希是一个**独立的拒绝码**（`approval-unbound`），而不是「不检查」。
把它混进「操作变了」里也不行：那会让一次迁移遗留看起来像一次用户改参数，
值班的人会去查错了方向。

### 有意**不回填**

回填意味着「用今天的规范化规则，替一批旧行算出它们的身份」。而那些行的身份本来就是
按**旧规则**定的——回填会把一次规则变更的影响静默抹平。

> 一个「给旧行补算哈希」的迁移，与一个「把旧审批的含义改写成今天的含义」的迁移，
> 是同一个东西——而它的方向是**放行**。

代价是迁移瞬间仍然 `pending` 的那些请求变成「没有哈希」，被以 `approval-unbound`
拒绝（fail-closed），用户需要重新发起。审批 TTL 是 15 分钟，所以受影响的窗口最多
15 分钟。

## 3. 校验的**顺序**是有意的

```
找不到行 → 已消费 → 已过期 → 不是已批准 → 没有哈希 → 哈希对不上 → 时间
```

- **绑定检查排在过期检查之前**：一条**绑错了**的审批，如果先被过期检查拦下，
  日志里写的理由是「过期」，值班的人会去查 TTL 配置，而真正的问题是这次调用
  根本不是那条审批覆盖的。
- **没有哈希排在算哈希之前**：反过来的话，一条没有哈希的行会先走到「操作比对」里，
  用一个重算出来的哈希与自己做比较——于是它**恒等**，于是它通过。那正是本模块
  要防的那件事。

拒绝码两两不同，每一种拒绝都有自己的话：`not-found` / `unbound` /
`operation-changed` / `not-approved` / `expired` / `already-consumed`。

## 4. 哪些拒绝该大声报错、哪些该继续走策略

这是一个有意的划分：

| 情形 | 处理 | 为什么 |
| --- | --- | --- |
| `operation-changed` / `unbound` / `expired` | **抛错** | 调用方**声称**自己持有一次对这次调用的批准，而那个声称不成立。静默落回策略会把「你拿的这张票不对」伪装成「这次需要新的批准」，于是没有人会去看那张票为什么不对 |
| `not-approved` / `already-consumed` / 找不到行 | **继续走策略** | 调用方只是**提起**了一个请求，而这次调用本来就还没被批准（或那次一次性批准已经用掉了）。落回策略会正常产生一条新的待批准请求——这正是「一次性」该有的样子 |

**第二行是一个被既有用例救回来的决定。** 我最初把 `already-consumed` 也放进抛错那一组，
`permissions.test.mjs` 立刻红了——它断言「消费一次之后再调用得到
`allowed: false`」，而抛错让那个断言变成一个异常。把「用掉之后再发起」变成一个错误是
错的，因为它其实是一次**正常的申请**。所以改的是代码，不是测试。

## 5. CAS 与「没抢到」

消费走一条原子 UPDATE：

```sql
UPDATE permission_requests SET status='consumed', consumedAt=?
 WHERE requestId=? AND status='approved' AND bindingHash=?
```

带哈希与带状态是两件不同的事：`status='approved'` 挡的是「这条已经被别人用掉了」，
`bindingHash=?` 挡的是「这一行在我校验之后被换成了另一条绑定」。

没抢到时**抛错**，不落回策略——落回策略会给出一条新的待批准请求，让调用方以为
「这次只是需要新的批准」，而真相是它已经在别处被放行过。这条路径同时写
`permission:binding-lost-race` 审计。

`consumeBinding` 被**单独导出**，是为了让这条路径可以被**真的走到**：

> 一个只能靠并发时序才能触发的分支，与一个不存在的分支，
> 在「它到底拦不拦得住」上是同一个东西。

## 6. `expired` 不再有两个说法

`listPermissionInbox` 原来返回一个**算出来的** `expired` 字段，而 `status` 仍然是
`pending`——同一件事有两个说法，而两个说法会在某个时刻不一致。现在过期是
**先写库再返回**：`status` 变成 `expired`，视图里不再有第二个真相。

## 7. 一个可注入的接缝

`checkPermission(input, { consume })` 收一个可注入的消费者（默认
`consumeBinding`）。存在的唯一理由是让「CAS 没抢到」那条路径可测——它不可能被
HTTP 调用方利用：函数不能经 JSON 传进来，而路由只传请求体。这与 `createLauncher` /
`createWizard` / `createTray` 收依赖的方式是同一套。

## 8. 变红验证：25 处，25 处红

重点是：★★ 没有哈希的行跳过校验 / ★★ 没有哈希的行「恒等」通过 /
★★ `unbound` 与 `operation-changed` 混码 / ★★ 过期检查排到绑定检查之前 /
★★ 绑定哈希另算一份 / ★★ 加载时自检不比对 / ★ 自检样本被写死 /
★ `isBoundHash` 什么都收 / ★★ 操作字段变了仍放行 / ★ 拿原始 JSON 比对 /
★ 恰好到期算没过期 / ★ `consumed` 与 `expired` 混码 / ★ 非正 TTL 被接受 /
★ 数组被当成合法操作 / ★ 解析不出来返回空对象 / ★★ 新建时不写哈希 /
★★ CAS 不带哈希 / ★★ 允许批准没有哈希的请求 / ★★ 去重不比哈希 /
★★ 审计不带哈希 / ★★ 被拒不留痕 / ★★ `expired` 退回视图算 /
★ 视图藏起哈希 / ★★ CAS 失败静默落回策略。

### 三条探针被「改良」过，性质各不相同

1. **㉛⑦ 自检样本被写死**：第一版补丁把**两个值都换成同一个常量**——那恰好满足了
   不变式，于是「没咬」。改成「一个常量 + 一个真算的值」后，两者必然不等，
   模块加载时就抛。
2. **㉛⑩ 拿原始 JSON 比对**：第一版补丁只是把 `operation` 过了一遍
   `JSON.parse(JSON.stringify(...))`——键序被保留，而 `computeBindingHash` 内部本来
   就会排序，所以那是**语义等价的空操作**。改瞄真正的缺陷类：比原始字符串。
3. **㉛⑥ 加载时自检不比对**：原来自检是模块级的
   `if (a !== b) throw`，而两个值由同一个算式算出——那条 `if` 永远只在「已经出事了」
   的时候才跑，用例根本碰不到它。处置是把自检**做成带参数的函数**
   （`assertBindingHashShared`），用例喂一对故意不一致的哈希进来。

## 9. ⚠️ 本批**没有**解决的事

- **TTL 仍然是写死的 15 分钟**，没有进配置 Schema。PRT-615 要求它是配置项。
- **`AwaitingApproval` 期间 heartbeat 继续 + `Attempt` 转 `blocked`** 这一整条
  生命周期**没有做**（PRT-615 / PRT-302 的范围）。本批只做了审批行自身的过期，
  没有碰 Attempt 状态机。
- **审批过期时没有「通知用户」**。
- **没有给 `permission_requests` 加索引或迁移框架**：加列用的是一个幂等的
  `PRAGMA table_info` 检查 + `ALTER TABLE`。真正的迁移框架是 PRT-807。
- **没有回填**是刻意的（见 §2），但这意味着升级瞬间在途的 `pending` 请求会被拒，
  用户要重新发起。这一点没有被任何自动化提示告知用户。
- **`sameOperation` 不再是 `server.mjs` 的依赖**——生产消费路径现在完全走哈希比对；
  `sameOperation` 仍被 `consumeDecision` 使用。
- 平台契约不变：**路由 136 / 数据表 32 / 任务状态 7（20 条迁移）/ 目标状态 4 /
  权限模式 5**。基线快照里只有 `team-hub/server.mjs` 的**源文件哈希**变化
  （新增的 `approval-binding.mjs` 不在基线覆盖的文件清单里）。
  **没有新增任何 HTTP 面。**
