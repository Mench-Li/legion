# PRT-609 字段变化使审批失效

> spec §6.5：「审批绑定不可变 `ToolExecution` 参数的 canonical operation 哈希；
> **任一授权关键字段变化都会使审批失效**。」
> 阶段 6 完成标准：「改变已批准操作的**任一**关键字段后无法继续执行。」

状态：**已交付**（`team-hub/permission-engine.mjs`；
判据 `team-hub/field-invalidation.test.mjs` 16 例）

---

## 1 一句全称命题不能用"我试了三个字段"来交付

完成标准里的「**任一**」是全称的。而全称命题最容易被一种看起来很扎实的测试
悄悄放过：

> 一个覆盖了 6/7 个字段的测试，与一个 0/7 的测试，
> 在「剩下那个字段改了会怎样」上是同一个东西：**没有答案**。
> 而"我测了 6 个"读起来像是"我测过了"。

所以 `assertEveryKeyAffectsFingerprint` 对 `OPERATION_KEYS` 里的**每一个**字段造一个
确实不同的值，逐个实测"指纹必须改变"。这是一句全称命题的**构造性**证明。

---

## 2 PRT-611 的那条自检拦不住什么

`assertOperationKeysAligned`（PRT-611）比的是**字段名**：

- `normalizeOperation` 产出的字段，必须都在 `OPERATION_KEYS` 里；
- `OPERATION_KEYS` 里的字段，必须都被产出。

它能拦住"加了字段却忘了加进名单"。它**拦不住**这一种：

```js
// canonicalOperation 里
for (const key of OPERATION_KEYS) {
  if (key === 'taskId') continue     // ← 名字对齐仍然通过，taskId 也确实在名单里
  out[key] = operation[key]
}
```

`assertOperationKeysAligned` 完全绿，`taskId` 也确确实实在名单里——
**但它不再进入指纹**。改了 `taskId` 的调用会命中同一张审批票，
而"任一关键字段变化都会使审批失效"这句话在 `taskId` 上变成了一句空话。

> 一个「名单里有、但值根本不进指纹」的字段，
> 与一个「不在名单里」的字段，是同一个东西——
> 只不过前者看起来是被保护着的。

两条自检是**两层**，都要在：前者拦"字段没进名单"，后者拦"进了名单但没进指纹"。

---

## 3 两个读数证明的是不同的事

`assertEveryKeyAffectsFingerprint` 对每个字段留下**两个**读数：

| 读数 | 证明什么 | 为假时的后果 |
| --- | --- | --- |
| `mutatedCanonicalDiffers` | 这次变异**不是空操作** | 下面那条读数**恒为真**，等于没测 |
| `affectsFingerprint` | 这个字段**真的进了指纹** | 改它审批照样通过（**危险方向**） |

只有后者会让人以为前者也成立：

> 一个「变异本身就是空操作」的逐字段测试，
> 与一个「每个字段都能影响指纹」的测试，在读数上完全一样。

### 3.1 这一次不是假想 —— 实测踩到了

端到端用例第一版用一张**固定的**变异表 `FIELD_MUTATIONS`（相对 `MUTATION_BASE`
定义，其中 `unattended: true`）去变异夹具的基准（`unattended: false`）。

`false → false` 是一次**空操作**，于是 `unattended` 那个字段"通过了"逐字段检查，
**而它其实一次都没被改过**。三条用例同时红在这里。

> 一张「相对于某个基准定义」的变异表，
> 与一张「换个基准就变成空操作」的变异表，是同一个东西——
> 只不过后者不会报错，只会让用例绿得毫无意义。

修法是 `mutateField(base, key)`：**按给定基准**造值。`unattended` 取反、`metadata`
加一个探针键、`null` 换成 `'mut'`、其余拼一个能挺过 `nfc`/`trim` 的 `~` 后缀。

## 4 一个自己也不触发的复核

`mutateField` 里原本内联着一次复核：

```js
if (operationCanonicalText(mutated) === operationCanonicalText(base)) throw …
```

破坏性验证把它改成 `if (false)` —— **一处都没变红**。原因很直接：
`mutateField` 自己构造的变异**永远**有效（每个分支都附了挺得过规范化的后缀），
所以这个判断在自己的调用路径上**永远不触发**。

> 一个永远不会触发的复核，与没有复核，
> 在「它到底拦不拦得住」上是同一个东西。

处置：抽成导出的 `assertMutationNotNoop({base, mutated, key})`，让它**可以被直接调用**。
用例喂一对相同的 base/mutated 进去，验它真的会抛（探针 ㉞⑩）。
这样它对 `mutateField` 未来被改回"查表式"的写法也仍然有效——而那正是 §3.1
那次假绿发生过的形状。

### 4.1 另一处：被删掉的等价补丁

原本还拟了一条探针，想验"`-0` 与 `0` 被判成不同"，补丁是
`{ ...x }` → `Object.assign({}, x)`。这两者**完全等价**，探针不可能变红。

> 一个「变了但什么都没变」的探针，
> 与一个「永远不会变红」的探针，在「我到底测没测到」上是同一个东西。

该探针**删除**，不充数。`-0`/NFC/键序这三条规范化保证由 PRT-611 的
`permission-engine.canonical.test.mjs` 直接覆盖（本批回归也在跑它）。

## 5 端到端：完成标准的直接读法

对 `OPERATION_KEYS` 里的每个字段：

1. 造一个基准操作，走真实路径申请 → 批准；
2. 改**那一个**字段，带上原票再调一次；
3. 断言**必须被拒**，且拒绝理由是 `approval-operation-changed`。

`action` 是唯一的例外：改了它就是一个**另一个操作**（策略规则也对不上），
所以允许拒绝路径是"需要新的批准"——但**仍然必须不能放行**。

配套的三条，防止这套"被拒"变成空话：

- **没改字段时那张票确实能用** —— 一个"所有调用都被拒"的实现也能让上面的用例全绿；
- **被拒之后票没有被消耗** —— 否则用户会看到"我批准的票被一次失败的调用吃掉了"；
- **被拒的调用不改写那一行绑定的操作** —— spec §6.5：「Legion 如需改变参数，
  只能拒绝当前调用并要求模型或工具定义产生一个新的 Tool Call，**不能在审批后静默改写**」。

再加一条把两套算法钉在一起：**票上绑的哈希必须等于 `operationFingerprint`**。
审批绑定若与逐字段自检用的不是同一个函数，那自检证明的是"某个*别的*函数"对字段敏感
（探针 ㉞⑮）。

## 6 审计

改字段被拒时写 `permission:binding-rejected`，`detail` 里带**两个**哈希：

- `bindingHash` —— "票上绑的是哪个操作"
- `actualHash` —— "这次调用是哪个操作"

只留一个的话，值班的人知道"操作不匹配"，但**看不出改了什么**。

## 7 诚实边界

1. **`OPERATION_KEYS` 之外的东西没有被覆盖**。逐字段自检验的是"名单里的每个字段
   都进指纹"，它**不**回答"名单是不是完整的"——一个新加的、根本没被放进
   `normalizeOperation` 的字段，两条自检都看不见。这一层的兜底是 spec 的字段闭合
   要求（PRT-610：持久化 tool call 参数）与代码审查，不是本模块。
2. **"关键字段"的定义就是 `OPERATION_KEYS`**。它今天有 7 个字段。名单本身要不要
   增减是一个**产品决定**，本模块只保证"名单里写了什么，就真的绑定了什么"。
3. **端到端的"改字段"是在同一进程内顺序调用的**，不是并发。并发路径由 PRT-616
   的占位覆盖。
4. `action` 那个例外的拒绝理由**没有**被断言为 `operation-changed`（见 §5）——
   这是有意的放宽，因为改 action 同时也让策略规则不匹配。若要收紧，需要先决定
   "改 action 算不算同一个操作的字段变化"，那是产品语义问题。
