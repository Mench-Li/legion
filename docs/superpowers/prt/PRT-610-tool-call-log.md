## 1 四个判据，各自对应一个安静的失效

| 判据 | 不这么做的表现 |
| --- | --- |
| ① 来源闭合且与强制点语义一致 | 事后分不出"策略拒绝"与"沙箱兜底拒绝"，修复动作会做错 |
| ② 原始输入与 canonical 输入同时存 | 答不出"模型当初要它做什么"；或执行时按**当前**规则重推 |
| ③ 幂等键按 `callId`，不含观察 metadata | 一次合法重试被读成"已经执行过了"（或反过来：重复执行） |
| ④ 结果四态，`unknown` 独立 | 崩在派发之后的写操作被读成"没执行过"，重试即做两遍 |

## 2 来源列：闭合，且要与强制点的语义一致

### 2.1 引用那份列表，不抄一份

`DECISION_SOURCES` 就是 `ENFORCEMENT_SOURCES`（`runtime/dsh-composition/enforcement.mjs`）
**同一个对象**，不是内容相同的两份。

> 一个「把来源列表抄一份」的表，
> 与一个「两份列表迟早不一样」的表，是同一个东西——
> 而它的表现是「新的强制点在审计里根本不存在」。

### 2.2 `source='guard', decision='allow'` 必须被拒

这条直接来自 §6.8 line 479。guard **只有降级语义**：它返回拒绝理由或什么都不做，
**永远没有"允许"这个返回值**（这正是它与 pre-execute 能顺序无关的原因）。

一条 `{source:'guard', decision:'allow'}` 的记录在语义上是不可能的。而接受它：

> 一个「接受 `source='guard', decision='allow'` 的表」，
> 与一个「来源列永远说得通」的表，是同一个东西——
> 只不过前者让你在审计里看到一次"hard floor 批准了这个操作"。

同理 `sandbox` 只会拒绝（它是"策略没给确定答案时环境替你拒绝了"），
不可能产出 `allow` 或 `ask`。

### 2.3 每条来源都要有一张**查得到**的修复动作表

`SOURCE_REPAIR_ACTIONS` 就是 §6.8 line 480 那句"两类的修复动作不同"的落地：

| 来源 | 修复动作 |
| --- | --- |
| `pre-execute` | 改策略规则（`permission_rules` / 策略门端口） |
| `guard` | 改 hard floor 或工具声明（静态下限不接受审批影响） |
| `approval` | 改审批链（answerer / 审批箱 / 无人值守策略） |
| `sandbox` | **改沙箱配置**（这不是策略问题，改策略不会有任何效果） |

`sandbox` 那一行是这个模块最值钱的一条：没有它，值班的人会去改策略，
改完什么都不会变。

> 一个只记录来源、却不给出动作的日志，
> 与一个没有来源的日志，在「值班的人拿到它之后做了什么」上是同一个东西。

装载时自检 `assertSourcesCovered` 逐个来源核对：**有决定表**、**有动作表**、
**至少能产出一次 deny**（否则它的修复动作永远不会被读到），以及反向的
"动作表里没有已不存在的来源"。

## 3 原始输入与 canonical 输入

### 3.1 两份都要存

只存 canonical：事后回答不了"模型当初到底要它做什么"（UI 与审计需要回答）。
只存原始输入：执行时就得**按当前规则重新推导** canonical。

> 一个「执行时按当前规则重新推导 canonical 输入」的实现，
> 与一个「审批的含义由你执行它的那一刻的代码决定」的实现，是同一个东西。

### 3.2 两份必须能**对起来**

若可以随便存两份不一致的东西，"同时保存"退化成"存两份"：

> 一个「两份输入都可能对、也可能不对」的表，
> 与一个「只有一份输入」的表，
> 在「事后能不能证明执行的是被批准的那次」上是同一个东西。

`assertCanonicalMatchesRaw({rawInput, canonicalInput, project})` 用**注入的**
投影函数复核。`project` 可注入的理由与前几批相同：正确实现下这份不一致恒为假，
那段断言永远不触发——

> 一段永远不会触发的断言，与一段不存在的断言，
> 在「它到底拦不拦得住」上是同一个东西。

## 4 幂等键

### 4.1 按 `callId`，**不按** canonical 哈希

§6.5 line 478 明说两者不是一回事：授权身份是**内容**（同一 Attempt 内同一
canonical 哈希只放行一次，PRT-616），执行身份是**这一次调用**。用错键的两个方向：

- 拿内容当执行键 → 一次崩溃后的合法重试被**永久**读成"已经执行过了"（拒绝方向）
- 拿 `callId` 当授权键 → PRT-616 那个"同一操作放行两次"的洞（放行方向）

> 一个「把授权账本的键拿来当执行幂等键」的表，
> 与一个「一次合法重试永远做不了、而另一个操作却能做两次」的表，是同一个东西。

### 4.2 键里不能混进观察 metadata

不含时间戳、`attemptId`、重试次数：包含它们就等于给每次重试发一个新键，
而"重试"恰恰是幂等键存在的理由。

> 一个「把时间戳算进幂等键」的幂等键，
> 与一个「每次重试都是全新调用」的幂等键，是同一个东西——
> 只不过它坏在"重试"这条路径上。

装载时留下的证据是一对**输入不同、键相同**的样例
（`TOOL_CALL_LOG_CHECKED.keyIgnoresObservation`）。

### 4.3 同一个 `callId` 重放**不新增行**，只把 `attempts` 加一

> 一个「同一个调用被写了两次」的表，
> 与一个「事后数不出到底调用过几次」的表，是同一个东西。

而同一个 `callId` 带着**不同的工具名**或**不同的 canonical 哈希**回来，必须抛：

> 一个「同一个 callId 第二次带着不同的工具名进来、被当成同一次调用」的表，
> 与一个「审计里的工具名可以是任意值」的表，是同一个东西。

后者还同时是 §6.5 那句"不得在审批后静默改写"的守卫：重试必须是**同一次调用**的重试。

## 5 结果：四态，`unknown` 不可省

```js
RESULT_STATUSES = { NONE:'none', OK:'ok', ERROR:'error', UNKNOWN:'unknown' }
```

`unknown` = "已经派发出去了，但结果没有回来"（进程被杀、超时、连接断）。
它**必须**与 `none`（确定没派发过）分开：

> 一个只有「成功/失败」两态的结果列，
> 与一个「把崩在中途的写操作读成『没执行过』」的结果列，是同一个东西——
> 而它的表现是重试一次外部写操作。

### 5.1 先落库再派发

`markDispatched` 把 `none → unknown` 并写下 `dispatchedAt`，**必须发生在真的派发之前**：

> 一个「先派发再记账」的顺序，
> 与一个「把已经发生的副作用记成『还没发生』」的顺序，是同一个东西。

重复派发、以及"没派发过就落结果"都要抛。

### 5.2 重试安全性

| 状态 | 可自动重试 | 理由 |
| --- | --- | --- |
| `none` | ✅ | 确定没派发过 |
| `ok` | ❌ | 已经做完了，应当返回**缓存结果**，不是重做 |
| `error` | 仅当工具声明幂等 | 外部写可能"部分生效" |
| `unknown` | ❌ **永不** | 再执行一次就可能把同一个外部写做第二遍 |

`unknown` 即使工具声明幂等也不自动重试：**不确定的状态不是幂等性能解决的**。

## 7 诚实边界

1. **本模块只提供持久化原语，还没有接到真实的 DSH 强制面上**。今天的调用者是
   用例。把 `createPreExecutePolicy` 的 `onDecision` 回调接到 `recordToolCall`
   属 PRT-602/612 的接线工作。
2. **`recordToolCall` 与"真的执行"之间没有事务**。`markDispatched` 提供了正确的
   **顺序**契约，但一个在 `markDispatched` 提交之后、真正派发之前被杀的进程会留下
   一条 `unknown`——这正确（保守），但也意味着**需要人来裁决**，本模块不自动恢复。
3. **"工具是否幂等"是一个外部输入**（`{toolIsIdempotent}`），本模块不推断它。
   推断会在工具改名或语义变化时静默失效——与 hard floor 里"只检查参数里确实出现的
   路径，不推断工具语义"是同一条纪律。
4. **`arguments` 的规范化不在本模块**。它属于 DSH 侧的 `CANONICAL_OP_KEYS`
   （已含 `toolName`/`callId`/`arguments`）；F-02 侧是 `OPERATION_KEYS`
   （含 `unattended`/`metadata`）。两者**有意不同**（§6.5：不同的 Schema 与 domain
   separator），本模块只负责把两侧都存下来。
5. **没有保留策略**。`tool_calls` 会随时间增长；按 Run 归档属运维面，未交付。
