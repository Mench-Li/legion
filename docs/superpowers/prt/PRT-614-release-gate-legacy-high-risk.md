# PRT-614：legacy 高风险工具禁用与发布门禁

**spec**：line 936；§6.6 line 472；§5 line 64、121
**状态**：✅ 已交付
**证据**：`.ci/prt-614/`

---

## 1 一句话

把"未批准高风险写操作为零"从一个**看起来通过的指标**，变成一个**在门禁满足前
拒绝给出读数**的东西。

---

## 2 这个任务真正难的地方不是"建门禁"

spec line 472 把三件事写在同一个句子里，而它们的**关系**才是重点：

> 无人值守模式下，要求人工审批的操作默认拒绝或保持等待，不自动降级为允许。
> legacy 路径在完成 DSH 强制面接线前禁止高风险工具；
> **"未批准高风险写操作为零"只在该门禁满足后成为发布指标。**

最后半句是一个**关于指标本身**的断言。它在说：那个数字在门禁满足前不是证据。
理由很具体：

- 强制面没接线时，"未批准的高风险写"是**零**，因为没有一条高风险写能走到审批
  那一步（`tool_calls` 里根本没人在记 `decisionSource`）；
- 更彻底的是：既然本批按 spec **禁止**了 legacy 上的高风险工具，那个数字当然是零
  ——**是我们把它变成零的**。

于是会得到一个一切正常的发布报表，而系统里一次高风险写都没被真的管控过：

> 一个「报表上写着'未批准高风险写操作为零'」的发布门禁，
> 与一个「因为没有一条高风险写被真的试过、于是那个数字当然是零」的发布门禁，
> 是同一个东西——只不过前者看起来是一个通过的指标。

## 3 实现

### 3.1 `runtime/dsh-composition/release-gate.mjs`（判据）

| 导出 | 作用 |
| --- | --- |
| `READINESS_ITEMS` | 7 项就绪清单，每项带 `code` / `label` / `why` |
| `evaluateReadiness(evidence)` | 逐项结论 + 未就绪名单 + 可归因理由 |
| `legacyHighRiskPolicy({risk, gate, path, toolName})` | spec line 472 的"接线前禁用" |
| `evaluateReleaseMetric({gate, observations})` | 发布指标，**门禁先于数字被检查** |
| `isHighRisk(risk)` | `>= high`；**未知等级按高风险**（fail closed） |
| `RELEASE_GATE_CHECKED` | 装载期自检（留下算出来的值，不是布尔） |

7 项就绪：`patch-layer` / `runtime` / `sandbox` / `mapping` / `decision-source` /
`legacy-high-risk` / `scheduler`。

前 4 项**直接取自 `startupSelfCheck` 的逐项结论**，不重新判断一遍——
重判一遍就是造出"两处对同一件事的判断"，它们迟早不一样。

### 3.2 ★ 顺序：门禁**先于**数字

```js
if (gate?.satisfied !== true) return { verdict: 'not-a-metric-yet', metricValid: false, ... }
if (attempted === 0) return { verdict: 'no-evidence', ... }   // 0/0 也不是证据
if (unapproved > 0) return { verdict: 'fail', ... }
return { verdict: 'pass', ... }
```

两个方向都要挡：

- 门禁未满足 + `unapproved === 0` → **不是** `pass`（那个零是造出来的）；
- 门禁未满足 + `unapproved === 3` → **也不是** `fail`。
  *来源不明的计数不能用来定罪，正如它不能用来洗清。*

所以探针**两侧都打**（㊼①打零那侧，㊼②打整个判据），而不是只测危险的那一半。

### 3.3 ★ `0 / 0` 不是证据

一个从没被尝试过的类别，与一个被尝试且全部合规的类别，在报表上是同一个 `0`：

> 一个「0 次未批准」的读数，
> 与一个「0 次尝试」的读数，是同一个东西——只不过前者会被当成"很干净"。

所以成功读数要求 `attempted > 0`；否则报 `no-evidence`。

### 3.4 ★ legacy 禁用是**临时的**，product-runtime 上不禁

spec 说的是"在完成接线**前**禁止"。所以 `legacyHighRiskPolicy` 只在
`path === 'legacy'` 且门禁未满足时拒绝；product-runtime 上返回 `enforced`
（交给正常强制面），门禁满足后的 legacy 也放开。

如果 product-runtime 上也禁，就变成了永久禁用——而"接线完成后放开"这件事
永远不会发生。探针 ㊼⑥ 专打这一条。

### 3.5 ★ 未知风险等级按高风险

`isHighRisk('不认识的等级') === true`。这个函数的两个错误方向不对等：
当作低风险是**放行**。缺席的等级同样是 `UNKNOWN_TOOL_RISK = 'critical'`。

### 3.6 "缺失"与"空"是两件事（两处）

- `legacyHighRiskTools` 未提供 ≠ 空数组。前者是"没说"，后者是"没有"。
- `schedulers.length === 0` **不算**通过。没有调度器时"唯一"是空话。
- `selfCheck` 未提供时 4 项全部按未就绪处理——"没检查"不等于"检查通过"。

三条各有一个探针（㊼⑧ / ㊼⑨ / ㊼⑩）。

## 4 ★ 可执行发布检查单：`scripts/prt/release-gate.mjs`

判据模块本身如果没人跑，就只是文档：

> 一个「写好了一份发布门禁判据」的实现，
> 与一个「没有任何东西会在发布前跑它」的实现，是同一个东西——
> 只不过前者在代码审查里看起来是"门禁已经建立"。

所以有一个 CLI，也是判据模块在本仓库里**唯一的生产调用方**：

```
node scripts/prt/release-gate.mjs --evidence <file.json> [--json]
```

- 退出码 **0 = 门禁满足 / 1 = 未满足 / 2 = 用法或证据文件错误**；
- **退出码由门禁决定，不由指标决定**——指标是报表，门禁是闸门。
  探针 ㊽① 把退出码改成看 `metric.verdict`，用例立刻红。
- 证据文件不存在时**不用空证据继续**（退出 2）。空证据会被读成"全部未就绪"，
  那是正确的结论，但把它伪装成"我们查过了"会让真因（打错路径）被更响的结论盖住。
  探针 ㊽③ 专打这一条。
- 未知参数**报错**（退出 2），不静默忽略。否则 `--evidnce` 这种拼错会退化成
  "没给证据"，同样被一条更响的结论盖住。
- 报表**永远**带 `verdict` 打印，不只是那个数字。探针 ㊽④ 专打这一条。

无证据时的输出（真跑过）：

```
门禁：不满足（未就绪 7 项）

发布指标「未批准高风险写操作为零」：
  verdict : not-a-metric-yet（这个数字目前不是证据）
  尝试    : 0
  未批准  : 0
```

## 6 诚实边界

1. **"禁用 legacy 高风险工具"在本仓库里只是判据，不是执行。** 真正的工具派发发生在
   DSH 宿主里（`legacyHighRiskPolicy` 需要一个调用方）。本批交付的是：判据 + 一个
   可执行的发布检查单。**没有任何本仓库的代码路径会因为本模块而拒绝一次工具调用。**
   与 PRT-611 补记的边界是同一条：**判据与调用方齐全，宿主接线敞开。**

2. **`legacyHighRiskTools` 这份清单是外部给的，本模块不自己发现。** 谁去枚举
   "legacy 上还剩哪些高风险工具"没有实现——本模块只判断这份清单空不空。
   一份**过时的**空清单会让门禁错误地满足，而本模块没有机制能发现它过时了。

3. **`decisionSourceRecorded` 是一个布尔，不是一次实测。** 证据文件里写
   `true` 就会被采信。没有做"真的查一次 `tool_calls` 的 schema"这件事——
   那需要数据库连接，超出发布检查单的范围。

4. **`scheduler` 那一项问的是"清单里有几个"，不是"它们真的在扫描"。**
   一个配好了但没在跑的调度器会通过这一项。

5. **`path` 是外部给的，无法验证。** 声称 `product-runtime` 而实际跑 legacy
   会让门禁满足——这一项是信任边界，不是检查。

6. **未做**：把发布检查单接进 `run-ci.mjs` 作为一个阶段。它需要外部证据文件，
   而 CI 里没有真证据；接进去只会得到"永远不满足"的噪声。
   它由发布流程手工触发。

7. **未做**：`READINESS_ITEMS` 与 `startupSelfCheck` 的检查项之间的**双向**对应
   没有做机器校验（目前靠名字字符串配对，改了自检项名会安静地失配，届时
   那一项会报"自检里没有 X"从而不满足——方向是 fail closed，但报出来的原因是
   误导性的）。
