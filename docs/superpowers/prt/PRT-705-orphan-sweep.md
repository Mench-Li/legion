# PRT-705 优雅关闭与僵尸进程清理

> 本文记录「僵尸进程清理」那一半（`product/launcher/run-record.mjs` 及其接线）。
>
> 「优雅关闭」那一半此前已经做完并在 `product/launcher/supervisor.mjs` 里：
> `SIGTERM` → 等 `graceMs` → 仍在则**杀进程树**（Windows 走 `taskkill /T /F`）。
> 之所以要杀树，是因为 Legion 的进程会再拉起孙进程，而
> 「重启产品之后端口仍然被占用」的根因正是那些孤立的孙进程。

## 1. 缺的那一半：Launcher 自己被强杀时

`stop()` 只能清理**它自己还活着时**启动的那些进程。如果 Launcher 被强杀
（任务管理器结束进程、断电、崩溃），它的子进程会活下来继续占端口。
而下一次启动时，用户看到的是一句：

> 进程 team-hub 的端口 8788 被其他进程占用。请关闭占用它的进程，或为该进程
> 配置另一个端口后重试。

用户打开任务管理器，看到几个**没有任何标识的** `node.exe`。
真实原因是「上一次 Legion 没退干净」，但这句提示把它和
「一个不相干的程序占了这个端口」说成了同一句话——而两条路的处置完全相反：
前者应当由产品自己收拾，后者**绝对不能碰**。

> 一个把「我上次没退干净」与「别人占了这个端口」说成同一句话的提示，
> 把一件产品该自己收拾的事，变成了一件要用户去猜的事。

做法：启动时把「我们起了哪些 pid、每一个的**映像名**是什么」写进 DataDir
（`launcher-run.json`），正常停止时删掉。下次启动读它，逐个判。

## 2. 唯一真正危险的那个错：PID 会被回收

记录里写着 `pid=4321`、`image=node.exe`。那个进程退出了。
系统把 4321 分配给了用户的编辑器。

**如果按号码去杀，我们杀掉的是编辑器。** 这不是「清理得不干净」，
这是**毁掉一个不相干的程序**，而且不可撤销。

所以本模块的绝对纪律是：

| 结论 | 判据 | 处置 |
| --- | --- | --- |
| `gone` | `isAlive` 为假 | 什么都不做 |
| `verified` | 活着 **且** 映像名与记录一致 | **很可能是我们的** → 显式要求清理时才杀 |
| `recycled` | 活着 **且** 映像名对不上 | **★ 无论调用方怎么要求都不杀** |
| `unknown` | 活着 **但** 映像名读不出来 | 默认不杀；要杀得显式 `allow-unverified-sweep` |

四个结论是**四个**，不是两个：

- 「读不出来」不是「已经没了」，也不是「是我们的」；
- 记录里**没有**映像名时也判 `unknown`——**没有任何依据**说这个号码还是我们的。

> 一个按号码去杀的清理动作，与一个随机杀进程的动作，
> 在「会不会误伤」上是同一个东西——只是前者看起来有理有据。

### 为什么 `recycled` 要单独报出来

因为它正好解释了「为什么端口占用提示帮不上忙」：那个号码现在是别人的，
所以我们不会去动它，用户也不该去找它。这条诊断必须是独立的一条，
并且要写清「这些进程本身不需要处理」——否则用户会去任务管理器里
找一个并不存在的「残留」。

## 3. 「记录坏了」≠「没有记录」

三条不同的失败分开报：

| 情形 | 报什么 | 为什么 |
| --- | --- | --- |
| 文件不存在 | **不报** | 这确实是干净的情况 |
| 读不出来（EACCES/IO） | `RUN_RECORD_UNREADABLE` | 「读不出来」**不等于**「上次没有残留」，只是我们无从判断 |
| 不是合法 JSON | `RUN_RECORD_CORRUPT` | 很可能是上次退出时正在写 |
| 形状/版本不认识 | `RUN_RECORD_CORRUPT` | **不能按一条残缺记录去清理**：它可能少列了进程，按它清理会留下真正的残留 |

一条写了一半的记录（比如断电时正在写）会让我们以为「只有两个进程要清」，
而实际上有五个。宁可说「记录坏了、不知道上次起了什么」，
也不要按一条残缺记录去动手。

## 4. 默认不清理

`sweepOrphansOnStart` 默认是 `false`。清理要显式要求（`--sweep-orphans`）。

> 一个「默认会杀进程」的启动路径，与一个会在用户没要求时动手的路径，
> 在「用户能不能预料到发生了什么」上是同一个东西。

「允许未验证的也清理」（`--allow-unverified-sweep`）要**单独**要求，
它不是一个连带的开关。

### 记录会变旧，但陈旧是**有界**的

记录在「就绪后写一次 + 每次日志轮转时刷新」。进程重启过之后 pid 会变，
所以记录里可能是旧 pid。

这个粒度是刻意选的，因为陈旧的危害是有界的：旧 pid 要么已经没了（`gone`），
要么被系统回收给了别人（`recycled` → 我们拒绝动手）。
**陈旧只会让报告变吵，不会让我们杀错。**

`persistRunRecord` 写下的 `image` 是 `null`——这不是遗漏：
此刻拿不到映像名，于是下次只能判 `unknown`，而 `unknown` 的处置是不动手。
**这正是安全的那一侧。**

## 5. 停止 / 早退路径都要删记录

两处都补了，第二处是一次**真缺陷**：

- `stop()` 的 `supervisor === null` 早退路径与正常路径都要删。顺序也不能反：
  **先删的话**，如果 `stopAll` 中途失败（某些进程没杀掉），我们就失去了
  「还有谁活着」的唯一线索，而那些进程正好是下一次启动需要认出来的。
- `start()` 在 `preflight` 失败时的早退路径也要删。这条是我写接线用例时
  量出来的：那一路上什么都没起来，所以记录描述的**只可能**是上一次运行。
  留着它，下次启动会把同一批残留再报一遍，用户会以为残留一直在长。

这与 `stop()` 那条早退是同一个形状的问题：

> 「什么都没起来所以不用收尾」这个判断，两次都把该做的事漏掉了。

## 6. 顺带修掉的结构问题：CLI 有两份要手工同步的名单

`parseArgs` 里原本有两个手工维护的数组（布尔开关一份、取值开关一份），
而 `--help` 的正文是第三处 `CLI_FLAGS`。加 `--sweep-orphans` 时我只改了
`CLI_FLAGS`，于是它在帮助里写着、用起来报「无法识别的参数」。

原来那句注释甚至写着：

> 「列在这里而不是散在 if 里：新开关漏加会让它被当成未知参数。」

**警告的正是这件事，而写注释的人照样漏了。** 这不是记性问题，是结构问题。

> 一份要写两处的名单，第二处总有一天会忘。
> 一个必须靠人记得去同步的名单，与一个迟早会不同步的名单，
> 在「新加的开关能不能用」上是同一个东西。

现在两份名单都从 `CLI_FLAGS` **派生**，报错信息也从名单生成
（那句硬编码的「支持 --check/--json/--help」已经与真实名单不一致过一次）。
另加两条断言把「声明了的就必须能用」钉住。

## 7. 变红验证：29 处，29 处红

重点几处：

- ★ **映像名对不上时判成 `gone`** → 把别人的程序当「已经没了」；
- ★ **映像名读不出来时判成 `verified`** → 不知道就当成是我们的；
- ★ **`recycled` 也参与清理** → 杀掉一个不相干的程序；
- ★ **`unknown` 默认就杀** → 「不知道它是谁」变成「那就杀了吧」；
- ★ **默认就清理** → 用户没要求却动了手；
- ★ **启动时不查上一次运行** → 模块写好了但没接上；
- ★ **探针被换成一个永远「活着 + 映像名一致」的桩** → 清理变成无条件杀。

### 两处"没咬"，两种不同的处置

| 探针 | 为什么没红 | 处置 |
| --- | --- | --- |
| ㉑㉘ `=== true` → 真值判断 | `parseArgs` 对这个键只有 `true`/`undefined` 两种取值，**两者在 `=== true` 与真值判断下完全一致**。我想守的「拼错的开关不该打开清理」根本走不到这里（拼错的开关会被 `parseArgs` 直接拒绝，更早就返回了） | **撤销探针**，并写明 `=== true` 不是一道防线 |
| ㉑㉚ 取值名单换回历史上那份手工数组 | 那份数组今天**恰好与 `CLI_FLAGS` 一字不差**，两种实现不可区分 | **重瞄**：改成模拟真正的**漂移**（少一个成员）。这才对应「有人加了开关、忘了同步第二处」的现场——也正是加 `--sweep-orphans` 时真实发生过的 |

> 一个在它唯一可能的输入集合上与原式等价的「加固」，
> 与没有这个加固，在「它到底防住了什么」上同形。

这条与 ⑱㉖ / ⑲③ / ⑲㉗ 是同一类判断：
**分不清「探针写错了」与「这里本来就没有防线」，就会把力气花在错误的加固上。**

## 8. 本批**没有**解决的事

- **没有"进程组"级别的兜底**：如果某个孙进程脱离了自己的进程组
  （自己 `detach` 或换了 `setsid`），`taskkill /T` 与运行记录都认不出它。
  这类残留只能靠端口占用检查发现。
- **映像名是唯一的身份依据**：用户同时开着另一个 `node.exe` 时，
  如果号码被回收给了那个进程，我们会判成 `verified` 并（在被要求清理时）杀掉它。
  要真正区分只能靠进程启动时间或内核级句柄，零依赖下拿不到。
  **这条是已知的、有界的残余风险**，`--sweep-orphans` 不是默认行为正是为此。
- **记录只覆盖"我们起的进程"**：手工在终端里起的 `node` 不在此列。
- **Workbench 界面上没有"发现残留 / 清理残留"的入口**，只有 CLI 开关。
- **`launcher-run.json` 没有做 ACL 加固**：它含 pid 与映像名，
  不含密钥，但也没有走 `security/secrets/acl.mjs` 那套。属 PRT-509 的范围。
