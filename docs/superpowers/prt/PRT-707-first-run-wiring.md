# PRT-707（接线批）：把首次运行向导接到真实模块上

> `wizard.mjs` 早就交付了六步状态机、40 条用例、以及三条纪律。但它的六个动作
> **全部是注入的空值**——`checkEnvironment = null`、`initialize = null`、`start = null`…
>
> > 一个"六步都对、但没有一步真的连着东西"的向导，
> > 与一个"只有六个按钮"的界面，在用户第一次运行的时候是同一个东西——
> > 只不过前者的用例是绿的。
>
> 本批给出那六个动作的真实实现（`product/launcher/first-run.mjs`，37 条用例）。

---

## 1. ★ 动工第一天撞上的是一条真缺陷，不是"缺个接线"

我把六个动作写成 `async`，接上真实的 `initializeProductDir` / `launcher.start()`，
然后 14 条用例一起红，报的都是同一句话：

```
检查运行环境没有成功：运行环境不满足要求（目录不可写、端口被占或 Node 版本过低）
```

那句话是 `WIZARD_STEP_DEFS.environment.blockingReason`——**写死的文案**，
而不是我的探测函数返回的原因。查下去，`stepOnce()` 里是这样：

```js
let r = null
try {
  r = runAutomatic(current, fn)      // ← 没有 await
} catch (e) { … }
if (r === null || r?.ok !== true) { … }
```

`runAutomatic` 返回的是 `fn()` 的结果。动作是同步函数时它就是一个普通对象，
一切正常；动作是 `async` 时它是一个 **Promise**，而 `Promise?.ok` 是 `undefined`，
于是 `r?.ok !== true` 成立，**每一步都被报成"没有成功"**。

> 一个"支持异步动作"的向导，与一个"只在动作恰好同步时才对"的向导，
> 在动作都很小的时候是同一个东西——只不过后者会在接入真实模块
> （`initializeProductDir`、`launcher.start()` 几乎都是异步的）那一天，
> 把每一步都报成失败，还说不出为什么。

修法是加一个 `await`。但值得记下来的是**它为什么能藏这么久**：40 条既有用例
全都传同步替身（`() => ({ok:true})`），而那个形状恰好是唯一不受影响的一种。
用例全绿与"这段代码支持异步"之间，原来没有任何关系。

## 2. ★ 三处契约错误——都是**读**出来的，不是跑出来的

接线这类活的危险不是"跑不起来"，而是"跑起来了、参数不对、服务端默默收了别的"。
本批有三处，每一处都值得单独说。

### 2.1 hub 客户端的 `call` 只发 POST

`orchestrator/worker/run.mjs` 的 `createHubClient` 只有 `call(path, body)`，
里面写死 `method: 'POST'`。而模型档案的更新端点是 `PATCH`/`PUT`。

`PATCH /api/model-profiles/<id>` 与 `POST /api/model-profiles` 是**两条不同的路由**。
用 POST 打过去不会得到 405——它会落到创建那条上，报出一个"档案已存在"或者
"字段非法"的错，而调用方要问的是"更新"。

> 一个"只会发 POST"的 hub 客户端，与一个"能发 PATCH"的客户端，
> 在只读场景里是同一个东西——只不过前者会在第一次要改一份已有配置时，
> 报出一个与"要改配置"毫无关系的错。

本批把 `call` 拆成 `send(method, path, body)`，导出 `call`（POST）与 `patch`（PATCH）。
`createFirstRun` 把 `patch` 列为**构造期必需**：重跑向导是正常路径，那时档案已存在，
必然要走更新端点；少了它的后果不是"重跑报错"，而是"重跑时档案悄悄停在旧值"。

### 2.2 绑定的字段名不是 `role` / `profileId`

hub 契约是：

```js
bindingStore.upsert({
  scope, employeeRole, primaryProfile, fallbackProfiles, perRunBudget,
}, { actor })
```

我第一版写的是 `{scope, role, profileId}`。这种错**不会报错**——`upsert` 收到
`employeeRole: undefined`，`requireKey` 抛 `ROLE_REQUIRED`，于是报出来的是一句
"缺少岗位"，而调用方明明传了一个叫 `role` 的东西。

### 2.3 ★ `secretRef` 是**算出来的**，不是读出来的

同一批我还写了一句"从 API 读回 `secretRef` 再去库里查"。读契约才发现那是**做不到**的：

```js
// team-hub/model-store.mjs:15
//   ② **读出去的东西不含 `secretRef`**。`toModelDescriptor` 连引用名都不给
//      （只给 `hasCredential`）。引用名也是可枚举的攻击面：知道引用名就离
//      猜到密钥库里的条目更近一步，而它没有必要出现在界面上。
```

`get(id)` 明确只返回 descriptor（`:193 /** 对外的单条读取：descriptor，不含 secretRef。 */`），
需要凭证的地方走单独的 `internalGet`。

所以正确的走法是另一条：档案 id → `modelSecretRefFor(id)` → 问密钥库 `has()`。
这不只是绕开了一个（正确的）信息隐藏，还**更强**——它检验的正是
"引用名确实按命名约定生成"这件事。

> 一个"从 API 读回 secretRef 再去库里查"的实现，
> 与一个"按约定算出 secretRef 再去库里查"的实现，
> 在库是按约定写入时是同一个东西——只不过前者在 API 决定不再暴露这个字段的
> 那一天，会静默地永远返回 false（于是每次都要重配密钥），或者更坏：永远返回 true。

### 2.4 顺带：`startResultIsBlocking` 的语义和我猜的相反

我把它读成"`phase:null` = 部分起来了、还能用"。实际是：

```js
if (result?.ok === true) return false
if (result?.phase === null || result?.phase === undefined) return true   // ← 阻塞
return hasBlockingDiagnostic(result.diagnostics ?? [])
```

`phase:null` 是**阻塞**——"不知道哪儿坏了，但确实坏了"。我的用例写反了，
是**用例**错，不是实现错。这正是"读契约再做断言"的价值。

## 3. ★ 环境检查必须探测**存在的最近祖先**

`environment` 跑在 `initialize` **之前**。在一台干净的机器上 `DataDir` 还不存在，
而"对还不存在的目录做可写探测"必然失败——于是这条检查会在**唯一需要它的那一次**
把一台正常的机器判成"环境不满足"。

> 一个"对还不存在的目录做可写探测"的环境检查，
> 与一个"环境不满足"的判定，在第一次运行那台干净机器上是同一个东西——
> 只不过前者会在唯一需要它的那一次，把一个正常的机器判成不满足。

`nearestExistingDir()` 向上找到最近一个存在的目录去探测：**那条路径能不能被创建**，
才是它要说的事。断验证的探针②专门钉这条（而且它一次红两条：直接探目标目录时，
三个目录各探各的，去重那条也一起破——半径宽本身就是"这条性质被多处依赖"的信息）。

## 4. ★ 前提（`preconditions`）：给 `PRECONDITION_UNMET` 一个产出方

`WIZARD_CODES.PRECONDITION_UNMET` 此前**没有任何调用方会产生它**（PRT-707 的既有
诚实边界里写着的）。本批补上，并且定在**第一步之前**判。

理由不是"早一点更好"，而是**前提不成立时的症状会在别处露面**：没有 hub 凭证 →
`configure-model` 写不进档案 → 到 `verify` 报"模型没有通过解析"。用户顺着这句话
去查自己的 API key，而 key 本来是对的。

> 一个"先跑第一步、再在第三步发现前提不成立"的向导，
> 与一个"在第一步之前就说清前提不成立"的向导，
> 在最终都报"没配好"这件事上是同一个东西——
> 只不过前者会让人去改一个本来没错的东西。

三条判定纪律：① **每次 `run()` 都重查**，不缓存（用户就是去把 hub 打开再点一次的）；
② 前提函数**抛错一律算不成立**；③ 前提不成立时**一步都不跑**——
于是"还没开始"与"开始到一半失败"能被区分。

### 4.1 ★ 附加前提**叠加**，不是替换

第一版我写成"调用方传 `preconditions` 就替换内置的"。这意味着一个为了加
"许可证已接受"这一条而传进来的函数，会**顺手**把布局/hub/密钥库三条检查全删掉——
而它看起来只是"多了一条"。

> 一个"附加前提替换掉内置前提"的接口，
> 与一个"附加前提叠加在内置之上"的接口，
> 在调用方只想多加一条的时候是同一个东西——
> 只不过前者会让那次改动同时删掉三条没人打算删的检查。

改成 `extraPreconditions`，与内置的合并（探针⑨钉这条）。

## 5. ★ 一处**测试自己是弱的**——探针找出来的

断验证的探针⑪把"密钥引用按约定算"改成"读 API 的 `secretRef`"。它咬住了，
但红的**不是我预期的那一条**。查下去，我那条用例是这么写的：

```js
assert.equal(await fr.isModelConfigured(), true)
```

而 `has` 的替身是 `async has() { return has }`——**对任何入参都返回同一个值**。
所以"读回来是 `undefined`、于是引用变成 `null`、于是什么都没查到"这条路径
**也让断言通过**。

> 一个"对任何入参都返回 true"的替身，
> 让"按约定算引用"与"算错了/没算"在那条断言上是同一个东西——
> 只不过后者会让密钥永远查不到。

补上 `assert.deepEqual(hasCalls, ['legion/model/default'])` 之后，探针立刻红了两条。

**这不只是补一条断言**：它说明"我的用例覆盖了这个设计"这句话，
在替身足够宽容时是不成立的。断验证的价值恰恰在这里——它不问"用例绿不绿"，
它问"把实现改坏，用例会不会红"。

## 6. ★ 写入顺序：先密钥，后档案，最后绑定

两个写入都可以失败，中间态不可避免。选顺序的标准是**中间态长什么样**：

| 顺序 | 失败时的中间态 |
| --- | --- |
| 先密钥后档案 | 一个**没人引用的密钥**——看不见、无害、重试即覆盖 |
| 先档案后密钥 | 一份**指向空处的档案**——界面上显示"已配置"，`resolve` 也成功返回 |

后者更坏：它让 §2.3 那个"档案且密钥"的判定与界面**对同一件事给出不同答案**。

> 一个"密钥写了、档案没写"的中间态，与一个"档案写了、密钥没写"的中间态，
> 在重试一次之后都会消失——只不过后者在那之前会让产品声称模型已经配好了。

## 9. ⚠️ 诚实边界

1. **向导仍然没有"生产调用方"。** 本批交付的是**动作实现**与**装配函数**
   （`createFirstRun`），它需要调用方提供 `layout` / `hubUrl` / `hubToken` /
   打开的密钥库 / `launcherFactory`。`team-hub/server.mjs` 里出现 `createWizard`
   字样只是**注释**（`L1734`，讲依赖注入风格），不是调用。
   界面（Workbench 首次运行页）与 CLI 入口**仍未接**。
2. **`launcherFactory` 在生产里要传什么还没定。** `createLauncher` 目前只有
   测试与 `cli.mjs` 在调；向导要拿到的是**同一个** launcher 实例
   （否则 `start()` 起的进程与 `status()` 看的进程不是同一个）。本批用
   `async () => launcher` 把这个要求写进了签名，但接线位置仍是 PRT-707 的下一步。
3. **`isModelConfigured` 的档案 id 来自绑定解析或向导自己的 `profileId`。**
   若用户此前配的是**第三个** id 且没有绑定，判定会是 false → 向导再问一次密钥。
   方向是保守的（宁可问，不可跳过），但确实会打扰。
4. **环境探测只查可写性与 Node 主版本。** spec 说的"端口被占"不在其中——
   那是 `launcher.preflight()` 的职责，向导的 `start` 那一步会把它报出来。
   两道关卡对这一项的分工是**有意**的，但向导自己**不**报端口冲突。
5. **`probeWritable` 是"写一个临时文件再删掉"**，在只读介质上会失败，
   在写满的盘上会成功（写一个 5 字节的探测文件不需要多少空间）。因此它能回答的
   是"有没有写权限"，**不是**"有没有空间"。
6. **断验证的 11 个探针只覆盖用例断言到的东西。** 例如
   `configuredProfileId()` 里"绑定解析返回 `ok:false` 时回退到 `profileId`"
   这条分支没有被任何探针检验。
7. **本批改动了 `orchestrator/worker/run.mjs`（新增 `patch`）。**
   既有 `call` 的调用方一行未改（`send` 默认行为与原来完全一致），
   但这是**执行面**文件，属于 PRT-108 边界关注的目录。
