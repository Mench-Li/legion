# PRT-707 首次运行向导

> spec §6.10 完成标准：「干净 Windows 机器**不打开终端**即可完成
> 安装后启动、模型配置、运行和停止。」
>
> `product/launcher/wizard.mjs`。六个步骤：
> `environment → initialize → start → configure-model → verify → done`。
> 向导覆盖前三件加模型配置与运行验证；「停止」由 Launcher 的 `stop()` 提供。

## 1. 唯一真正要紧的那条纪律

**向导说「完成」，与产品真的能跑，不是同一件事。**

一个向导最容易犯的错，是把「每一步都返回了 ok」当成「产品可用了」：

- `start()` 说它启动了 —— 那说的是「我发出了 spawn」，不是「进程起来了、
  端口在听、健康检查过了」；
- 模型配置写进去了 —— 那说的是「我写了一条记录」，不是「这条记录能被
  解析成一个可用的模型」；
- 所有步骤都没报错 —— 那说的是「没有异常冒到这一层」。

于是用户看到「✅ 安装完成，一切就绪」，然后第一次点「运行」就失败。
而这时他已经关掉了向导，不知道从哪儿查起。

> 一个「每一步都返回成功就报完成」的向导，
> 与一个「不管做没做成都说完成了」的向导，
> 在「用户第一次点运行的时候会不会成功」上是同一个东西。

所以最后一步**不是汇总前面几步的返回值**，而是**重新去看一眼产品**。

## 2. `verify`：独立观测，只有正面结论才算过

`observe()` 返回 `{ runtimeState, modelResolved }`。**两条都要正面成立**：

| 情形 | 结论 |
| --- | --- |
| `runtimeState === 'ready'` 且 `modelResolved === true` | ✅ 过 |
| `runtimeState` 是 `starting` / `degraded` / `unavailable` / `incompatible` / `upgrading` / 未知 | ❌ 不过 |
| `modelResolved !== true` | ❌ 不过 |
| `observe` 抛错 | ❌ 不过 |
| `observe` 返回 `null` / 字符串 / 数 | ❌ 不过 |
| **没有配置 `observe`** | ❌ 不过（宁可卡住，也不说假话） |

`degraded` **不算通过**：它说的是「部分能力不可用」，而首次运行向导的承诺是
「产品可用了」。把 `degraded` 放过去，用户会在一个缺了能力的产品上开始干活。

`modelResolved` 是**必须**单独查的一条：**「我写了一条记录」与「这条记录能用」
是两件事。**

观测抛错也**不算过**——一个在观测失败时放行的向导，与一个不做观测的向导，
在「用户第一次运行会不会成功」上是同一个东西。

## 3. 需要用户输入的那一步必须**真的挡住**

「配置模型」需要用户提供一个密钥。一个「跳过它继续跑」的向导会在最后报
「完成」，而产品其实没有模型可用——于是用户第一次运行任务时失败，
且不知道是模型没配。

所以没拿到输入时**停在原地**，且 `status().awaiting` 要明确说出**在等什么**。
有一条用例断言「没给输入时 `observe` 一次都没被调用」。

### 新增的一道闸：「是不是已经配好了」

向导天然会被重跑（用户中断过、重启过、点错了）。每次都要求重新输入密钥，
会让人以为「上次配的没了」，于是反复重配。

所以加了一个可选的 `isModelConfigured()` 核对。但它**只在恰好返回 `true` 时**
才允许跳过输入：

- 返回 `undefined` / `'yes'` / `1` / `[]` / `{}` —— 一律**要输入**；
- 抛错 —— 一律**要输入**。

**这条是本轮写测试时量出来的**（`⑤ ★★` 那条用例先红）。原因是：一个「大概
配过了」的判断会跳过唯一的配置入口，然后走到 `verify` 去发现模型不可用——
而用户此时**已经没有任何地方可以填密钥了**。

> 一个「看起来配过了」的判断，与一个「确实配好了」的判断，
> 在「用户能不能把产品配起来」上是同一个东西——只是前者让人无路可走。

## 4. 失败就停，不跳步

任何一步失败（返回非 `ok`、抛错、**或根本没有配置动作**）都**停下**，
报出「卡在哪一步、为什么」，且不碰后面的步骤。

「没配置动作」也算失败：**缺依赖不是「没问题」**。一条用例断言
`environment` 失败时 `verify` 一次都没被碰过。

「返回非 `ok`」包含返回 `undefined` 的情况：**「没返回错误」与「成功了」
不是同一件事。**

## 5. 断点续跑：只恢复**位置**，不恢复**结论**

首次运行向导天然会被打断（用户去拿密钥、去装东西、去重启）。
状态存在 `first-run-wizard.json`，重跑时从断点继续——不是从头再来一遍。
一个每次都从头开始的向导，会在「删掉上次建了一半的东西」这件事上
制造出比它解决的问题更多的问题。

**关键**：恢复的只有**步骤位置**，绝不恢复「某一步已经过了」。
上一次的 `verify` 结论对这一次的产品状态**没有任何说服力**。

> 状态文件里写着 `finished: true`，而这次产品其实是坏的——
> 有一条用例专门测这个：重启后必须**重新观测**，且观测到
> `unavailable` 时**不能**报完成。

坏掉的进度文件**不猜**：回到第一步（各步幂等，从头是安全的），
版本不认识也一样。**猜一个步骤出来才危险。**

进度写不下来时**照样能跑完**（只是下次会从头开始），并留一条诊断——
一个「存不了进度就什么都做不了」的向导，会把一个非致命问题变成致命问题。

## 6. 变红验证：22 处，22 处红

重点：★★ **`verify` 直接放行**（报「完成」时根本没看过产品）/
★ 实测状态不是 `ready` 也算过 / ★ `degraded` 也算通过 /
★ 不检查模型能否解析 / ★ 观测抛错时放行 / ★ 观测返回 `null` 时算过 /
★ 没给输入时自动跳过模型配置 / ★ 在错误的步骤上也接受输入 /
★ 恢复时把上一次的 `finished` 当成这一次的结论 /
★ 「看起来配过了」就跳过输入 / ★ 完成标准里的「模型配置」整个从流程里消失。

### 一处「没咬」：**另有别的地方也拦着**

㉕⑦ 删掉 `observe` 的类型检查后，`await null()` 抛的 TypeError 被 catch 接住，
结果同样是「卡在 `verify`」——而用例当时只断言了「卡住」。处置是
**改成断言具体那句话**：显式检查给的是「没有配置观测方式」（装配问题），
catch 给的是「观测产品时出错：observe is not a function」（看不出该修哪里）。

> 「卡住了」与「卡住了，且理由是那一件事」是两个不同强度的断言。

这与 PRT-713 的 ㉔⑥/㉔⑮ 是同一类处置。

## 7. 本批**没有**解决的事

- **没有界面**：向导是一个状态机，`status()` / `submit()` / `run()` 是它的
  驱动接口，但**没有任何 UI 或 CLI 子命令**在用它。所以「不打开终端」
  这个完成标准的**呈现层还不存在**——这是本任务最大的边界。
- **没有接进 Launcher**：`launcher.mjs` 还没有在首次运行时创建向导。
- **`checkEnvironment` / `initialize` / `start` / `submitModelConfig` /
  `observe` / `isModelConfigured` 六个依赖全部由调用方注入**，
  产品里还没有把它们接到真实的 `init.mjs` / `launcher.mjs` /
  `security/secrets` 上。
- **没有把密钥写进密钥库的实现**：`submitModelConfig` 是注入的，
  所以「密钥写进密钥库而不是配置文件」这句话目前**只是注释**。
- **`WIZARD_PRECONDITION_UNMET` 没有调用方会产生**：前置条件目前靠
  「上一步失败就停下」实现，这个码是为将来显式的跨步骤前置检查留的。
- **`reset()` 只是重置向导状态**，不会撤销 `initialize` 建过的目录——
  这一点是刻意的（删数据不该由「重来一次」触发），但界面上需要一个
  更明确的说法。
- **没有「停止」这一步**：spec 的完成标准包含「停止」，而它由
  Launcher 的 `stop()` 提供，向导不覆盖。
