# PRT-707 首次运行向导

> spec §6.10 完成标准：「干净 Windows 机器**不打开终端**即可完成
> 安装后启动、模型配置、运行和停止。」
>
> `product/launcher/wizard.mjs`。六个步骤：
> `environment → initialize → start → configure-model → verify → done`。
> 向导覆盖前三件加模型配置与运行验证；「停止」由 Launcher 的 `stop()` 提供。

## 1. 唯一真正要紧的那条纪律

**向导说「完成」，与产品真的能跑，不是同一件事。**

一个向导最容易犯的错，是把「每一步都返回了 ok」当成「产品可用了」：

- `start()` 说它启动了 —— 那说的是「我发出了 spawn」，不是「进程起来了、
  端口在听、健康检查过了」；
- 模型配置写进去了 —— 那说的是「我写了一条记录」，不是「这条记录能被
  解析成一个可用的模型」；
- 所有步骤都没报错 —— 那说的是「没有异常冒到这一层」。

于是用户看到「✅ 安装完成，一切就绪」，然后第一次点「运行」就失败。
而这时他已经关掉了向导，不知道从哪儿查起。

> 一个「每一步都返回成功就报完成」的向导，
> 与一个「不管做没做成都说完成了」的向导，
> 在「用户第一次点运行的时候会不会成功」上是同一个东西。

所以最后一步**不是汇总前面几步的返回值**，而是**重新去看一眼产品**。

## 2. `verify`：独立观测，只有正面结论才算过

`observe()` 返回 `{ runtimeState, modelResolved }`。**两条都要正面成立**：

| 情形 | 结论 |
| --- | --- |
| `runtimeState === 'ready'` 且 `modelResolved === true` | ✅ 过 |
| `runtimeState` 是 `starting` / `degraded` / `unavailable` / `incompatible` / `upgrading` / 未知 | ❌ 不过 |
| `modelResolved !== true` | ❌ 不过 |
| `observe` 抛错 | ❌ 不过 |
| `observe` 返回 `null` / 字符串 / 数 | ❌ 不过 |
| **没有配置 `observe`** | ❌ 不过（宁可卡住，也不说假话） |

`degraded` **不算通过**：它说的是「部分能力不可用」，而首次运行向导的承诺是
「产品可用了」。把 `degraded` 放过去，用户会在一个缺了能力的产品上开始干活。

`modelResolved` 是**必须**单独查的一条：**「我写了一条记录」与「这条记录能用」
是两件事。**

观测抛错也**不算过**——一个在观测失败时放行的向导，与一个不做观测的向导，
在「用户第一次运行会不会成功」上是同一个东西。

## 3. 需要用户输入的那一步必须**真的挡住**

「配置模型」需要用户提供一个密钥。一个「跳过它继续跑」的向导会在最后报
「完成」，而产品其实没有模型可用——于是用户第一次运行任务时失败，
且不知道是模型没配。

所以没拿到输入时**停在原地**，且 `status().awaiting` 要明确说出**在等什么**。
有一条用例断言「没给输入时 `observe` 一次都没被调用」。

### 新增的一道闸：「是不是已经配好了」

向导天然会被重跑（用户中断过、重启过、点错了）。每次都要求重新输入密钥，
会让人以为「上次配的没了」，于是反复重配。

所以加了一个可选的 `isModelConfigured()` 核对。但它**只在恰好返回 `true` 时**
才允许跳过输入：

- 返回 `undefined` / `'yes'` / `1` / `[]` / `{}` —— 一律**要输入**；
- 抛错 —— 一律**要输入**。

**这条是本轮写测试时量出来的**（`⑤ ★★` 那条用例先红）。原因是：一个「大概
配过了」的判断会跳过唯一的配置入口，然后走到 `verify` 去发现模型不可用——
而用户此时**已经没有任何地方可以填密钥了**。

> 一个「看起来配过了」的判断，与一个「确实配好了」的判断，
> 在「用户能不能把产品配起来」上是同一个东西——只是前者让人无路可走。

## 4. 失败就停，不跳步

任何一步失败（返回非 `ok`、抛错、**或根本没有配置动作**）都**停下**，
报出「卡在哪一步、为什么」，且不碰后面的步骤。

「没配置动作」也算失败：**缺依赖不是「没问题」**。一条用例断言
`environment` 失败时 `verify` 一次都没被碰过。

「返回非 `ok`」包含返回 `undefined` 的情况：**「没返回错误」与「成功了」
不是同一件事。**

## 5. 断点续跑：只恢复**位置**，不恢复**结论**

首次运行向导天然会被打断（用户去拿密钥、去装东西、去重启）。
状态存在 `first-run-wizard.json`，重跑时从断点继续——不是从头再来一遍。
一个每次都从头开始的向导，会在「删掉上次建了一半的东西」这件事上
制造出比它解决的问题更多的问题。

**关键**：恢复的只有**步骤位置**，绝不恢复「某一步已经过了」。
上一次的 `verify` 结论对这一次的产品状态**没有任何说服力**。

> 状态文件里写着 `finished: true`，而这次产品其实是坏的——
> 有一条用例专门测这个：重启后必须**重新观测**，且观测到
> `unavailable` 时**不能**报完成。

坏掉的进度文件**不猜**：回到第一步（各步幂等，从头是安全的），
版本不认识也一样。**猜一个步骤出来才危险。**

进度写不下来时**照样能跑完**（只是下次会从头开始），并留一条诊断——
一个「存不了进度就什么都做不了」的向导，会把一个非致命问题变成致命问题。

## 6. 变红验证：22 处，22 处红

重点：★★ **`verify` 直接放行**（报「完成」时根本没看过产品）/
★ 实测状态不是 `ready` 也算过 / ★ `degraded` 也算通过 /
★ 不检查模型能否解析 / ★ 观测抛错时放行 / ★ 观测返回 `null` 时算过 /
★ 没给输入时自动跳过模型配置 / ★ 在错误的步骤上也接受输入 /
★ 恢复时把上一次的 `finished` 当成这一次的结论 /
★ 「看起来配过了」就跳过输入 / ★ 完成标准里的「模型配置」整个从流程里消失。

### 一处「没咬」：**另有别的地方也拦着**

㉕⑦ 删掉 `observe` 的类型检查后，`await null()` 抛的 TypeError 被 catch 接住，
结果同样是「卡在 `verify`」——而用例当时只断言了「卡住」。处置是
**改成断言具体那句话**：显式检查给的是「没有配置观测方式」（装配问题），
catch 给的是「观测产品时出错：observe is not a function」（看不出该修哪里）。

> 「卡住了」与「卡住了，且理由是那一件事」是两个不同强度的断言。

这与 PRT-713 的 ㉔⑥/㉔⑮ 是同一类处置。

## 7. 本批**没有**解决的事

- **没有界面**：向导是一个状态机，`status()` / `submit()` / `run()` 是它的
  驱动接口，但**没有任何 UI 或 CLI 子命令**在用它。所以「不打开终端」
  这个完成标准的**呈现层还不存在**——这是本任务最大的边界。
- **没有接进 Launcher**：`launcher.mjs` 还没有在首次运行时创建向导。
- **`checkEnvironment` / `initialize` / `start` / `submitModelConfig` /
  `observe` / `isModelConfigured` 六个依赖全部由调用方注入**，
  产品里还没有把它们接到真实的 `init.mjs` / `launcher.mjs` /
  `security/secrets` 上。
- **没有把密钥写进密钥库的实现**：`submitModelConfig` 是注入的，
  所以「密钥写进密钥库而不是配置文件」这句话目前**只是注释**。
- **`WIZARD_PRECONDITION_UNMET` 没有调用方会产生**：前置条件目前靠
  「上一步失败就停下」实现，这个码是为将来显式的跨步骤前置检查留的。
- **`reset()` 只是重置向导状态**，不会撤销 `initialize` 建过的目录——
  这一点是刻意的（删数据不该由「重来一次」触发），但界面上需要一个
  更明确的说法。
- **没有「停止」这一步**：spec 的完成标准包含「停止」，而它由
  Launcher 的 `stop()` 提供，向导不覆盖。

# 收尾批：把向导接上一个真的界面

上面第 7 节里最大的那一条是「**没有界面**……**没有任何 UI 或 CLI 子命令在用它**」。
这一批把它接到 CLI 上。

先把话说清楚：**CLI 仍然是终端**，所以「不打开终端」那一条**没有被消灭**——
它留在诚实边界里。被消灭的是另一件事：**零调用方**。

> 一个只有测试会调用的状态机，它的每一次改动都只能靠读代码来确认；
> 而「这条边界写在任务行里」这件事本身，也会一直是「对的」，
> 直到有人真的把它接上。

## 8. 三件事，以及每一件为什么不是「加个参数」

### 8.1 「读不到输入」与「空回答」必须分开

没有 tty（管道、CI、双击运行）时 `readLine` 返回 `null`，界面**停下来并说清原因**。
返回空字符串的话，向导会带着一个空密钥一路走到 `verify`，报「模型不可用」——
而**那时用户已经没有任何地方可以填密钥了**。

> 一个「读不到输入」被当成「用户按了回车」的界面，
> 与一个把用户困在没有配置入口的界面，在用户眼里是同一个东西——
> 只不过前者会让他反复检查自己那份没有问题的密钥。

### 8.2 「没问过」与「用户拒绝了」必须分开

不给 `--wizard-consent` **不等于**回答了「不要」。前者是「没有问过」，
后者是「问过了、选了不要」。两者都**不写**同意记录，但在 `status().optIn` 里是
**两个不同的读数**：

| 情形 | `optIn['heartbeat-consent']` | 同意记录 |
| --- | --- | --- |
| 默认（没问） | `{asked: false}` | 无 |
| 问过，用户选「不要」 | `{asked: true, answered: true, enabled: false}` | 无 |
| 问过 / 预先回答「要」 | `{asked: true, answered: true, enabled: true}` | **有** |

合并成一个读数的话，「心跳没开」就永远无法区分「用户拒绝」与「向导没问」——
**而这两件事要修的地方完全不同**。

> 一个把「没问」记成「用户拒绝」的界面，
> 会让一次界面缺陷看起来像一次用户选择。

### 8.3 拒绝**不需要**署名

「要开通」必须署名（一条没有署名的同意事后无法查证）；「不要」不需要。
要求了的话，**「不接受」就比「接受」多一道门槛**——而那道门槛推着用户往同意那边走。

> 一个「拒绝也要先填表」的可选项，与一个默认打开的可选项，
> 在「用户最后同意了没有」上是同一个结果——
> 只不过前者的同意看起来像是他自己选的。

## 9. 动工时撞上的一条**真缺陷**

第一版把可选步骤写成「**绝不阻塞**，没回答就按默认继续」。用例立刻量了出来：
`run()` 会一路推进到完成，于是**没有任何地方能 `submit`**——它一次都收不到回答。

> 一个「不阻塞的可选步骤」，与一个「根本不存在这一步」，
> 在「用户有没有被问过」上是同一个答案——只不过前者看起来是把选择权交出去了。

修法是给它**两种模式**，由调用方选：

- `askOptIn: false`（默认）——**不问**，记 `{asked: false}`
- `askOptIn: true`——像 `INPUT` 一样**停下等回答**

CLI 走的是**预先回答**（`presetOptIn`），与当场回答走**完全同一条**路
（同样的判据、同样的动作）。预先回答也要过同一道判据——
*一条没署名的「预先同意」与一条没署名的当场同意，
在「事后能不能查证」上是同一个东西*。

默认 `false` 的理由：**一个默认去问的向导，会把每次运行都变成一次需要人坐在旁边的操作**，
而大多数运行是重跑、脚本化或无人值守的。

## 10. 断验证量出的五处「看起来一样、其实不一样」

第一轮 **147/153，6 条没咬住**。逐条查下去，其中五条是**我的用例自己写弱了**：

1. **`consentPath` 收的是布局对象**，而用例写的是 `consentPath(homeB)`
   （一个字符串）→ 返回 `null` → `existsSync(null)` 就是 `false`。
   那条断言**永远为真**，包括「拒绝也写了一条记录」的实现。

   > 一个传错参数类型却仍然返回「文件不存在」的断言，
   > 与一个真的守住了「没有写文件」的断言，在报告上是同一个读数。

2. **「密钥不回显」在假 tty 上是空断言**（假 tty 本来就不回显任何东西），
   把 `secret` 整个忽略掉也照样绿。改成断言**原始模式的进出历史**。

3. **「空密钥要停下」只断言了「最后失败了」**——而那是测不出的：
   即使空密钥被放过去，下游 `validate`（「缺少模型密钥」）也会把它拦下，
   结果同样是失败。改成断言**「它有没有继续往下问模型名」**。

   > 一个「下一层也拦得住」的实现，会让上一层的用例**看起来**守住了。

4/5. **`--wizard-consent` / `--wizard-reset` 两条守的是源码文本正则**。
   把整段逻辑删掉、只要那几个词还留在注释里，它照样绿。
   故把翻译逻辑抽成纯函数 `wizardOptionsFrom`，用例**直接断言它的产出**。

   > 一条「匹配源码文本」的断言，与一条「匹配注释文本」的断言，
   > 在实现被删掉的那天是同一个读数。

第二轮 **153/153 咬住、0 无效、0 没咬住、逐字节还原、工作区无污染**。

### 10.1 一处「守住边界」的必要更正

探针 ⑤㊿ 断言 `cli.mjs` 里不出现 `wizard-model-key`——但那段代码的**注释里
故意写着**这个反例（解释为什么不提供它）。断言「文件里没有这个词」
会把那条说明也一起禁掉，于是下一个人只能删掉注释来让它变绿。
改判 `parsed.flags[...]` 的形状：**要禁的是那个入口，不是那四个字**。

## 11. 收尾批之后的诚实边界

- **仍然是 CLI，不是图形界面**——「不打开终端」这个完成标准**没有被这一批消灭**。
  spec 里那个「双击图标就能配好」的向导仍然不存在。本任务最大边界**只收窄了一半**
  （零调用方 → 有调用方）。
- **`--wizard` 只驱动状态机**，**没有**把向导接成「用户双击产品时自动弹出」的东西。
- **向导不覆盖「停止」这一步**（由 Launcher 的 `stop()` 提供）。
- **`createStdinReader` 的原始模式路径只在假 tty 上被验证过**——
  真实的 Windows 终端有没有把 `setRawMode` 走到、`\u0003` 是不是真的会
  作为数据到达，**没有在真终端上量过**。
- **预先回答无法区分「本人答的」与「别人代答的」**
  （与 PRT-713 的 `who` 不可验证是同一条）。
- **没有并发保护**：两个向导同时跑，后写的状态文件赢。
- **进度文件（`first-run-wizard.json`）的写入失败只留一条诊断**，界面不会因此停下。
- **`--wizard-reset` 只丢位置、不删任何产品数据**（刻意），
  但**界面上没有说清这一点**。
- **`WIZARDCLI_ALREADY_DONE` 目前没有调用方会产生**：
  向导重跑时会自己跳过已完成的步骤，这个码是为「已经就绪就直接返回」
  那条更快的路径留的，不要读成「已经支持了」。
