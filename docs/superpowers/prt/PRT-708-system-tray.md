# PRT-708 系统托盘与「打开 Workbench」

> spec §6.10：「系统托盘入口和打开 Workbench」。
>
> `product/launcher/tray.mjs`。五个菜单动作：
> `open-workbench` / `status` / `start` / `stop` / `quit`。

## 1. 唯一真正要紧的那条纪律

**托盘上的「退出」必须真的把产品停掉，而不只是把图标藏起来。**

这是托盘类功能最经典的失败：用户右键 → 退出 → 图标消失了。他合理地认为
「产品关了」。而实际上子进程还在跑、还在占端口、还在花他的钱。
等他下次启动，会看到「端口被其他进程占用」——一句与他的操作毫无关系的话。

> 一个把图标藏起来、进程还在跑的「退出」，
> 与一个根本没有退出按钮的托盘，
> 在「用户以为关了的时候产品还在不在跑」上是同一个东西。

所以 `quit` 不是「关闭窗口」，而是一次**有结果的停止动作**：

1. 调 `stop()`；
2. **重新观测**产品是不是真的都不在了；
3. 观测到 `unavailable` 才 `exited: true`；
4. 没停就**报出来**（`TRAY_QUIT_UNCONFIRMED`，error 级诊断），
   并**继续保持托盘在**——用户还能再试一次。

四种情况一律**不确认退出**：

| 情形 | 为什么 |
| --- | --- |
| `stop()` 返回成功但产品还在跑 | 「我说我停了」不是「停了」 |
| 停完观测到 `starting`/`degraded`/`ready`/`upgrading` | 只有 `unavailable` 算停 |
| 停完**观测失败** | 「看不出来」与「停掉了」是两件事 |
| 没配置 `stop` | 不能因为「没得停」就说停了 |

`quit` 的菜单标签刻意**不是**「退出」两个字，而是
「退出 Legion（会停止所有组件）」——「退出」会被读成「关掉窗口」。

## 2. 菜单的可用性来自**观测**，不来自假设

「我记得我启动过了」不是一个可以拿来决定按钮灰不灰的依据：用户可能在任务
管理器里把进程杀了、上一次启动可能就失败了、可能有别的实例在跑。
菜单是用户与产品之间最短的那条反馈回路，**它一旦说了假话，用户就失去了
唯一的判断依据。**

所以 `menu()` **每次都重新观测**（不缓存），且：

- `start` 与 `stop` **互斥**——两个都能点会让用户点到一个与当前状态相反的动作；
- `unavailable` **不算**在跑（图标还在不等于产品活着）；
- 状态未知时 `start` **可点**（那正是「用户觉得没跑」的时候，而 `start()`
  自己会对已在跑的情况给出结论）；
- **`quit` 永远可点**——一个「因为状态不明所以退不出去」的托盘，
  会把用户困在一个他无法关闭的产品里；
- 每个灰掉的项**都给出 `disabledReason`**：一个灰掉的菜单项不解释自己，
  用户只会以为坏了。

不认识的运行时状态**不冒充**成已知的那一个（会显示「未知状态（wat）」）。

## 3. 「打开 Workbench」用**观测到的**地址

用配置里的默认端口去拼 URL，在端口被占用而产品改用了别的端口时，会打开一个
打不开的页面。用户看到的是「浏览器打不开」，而真正的原因在产品这边。

所以地址从 `observe()` 里取，**取不到就不打开**（`TRAY_WORKBENCH_NOT_READY`），
并且菜单项也是灰的、也说明了原因。空字符串不算地址。

## 4. 观测失败时，除退出外的动作都不执行

在不知道产品处于什么状态的情况下点「启动」或「停止」，结果可能与用户的意图
**相反**。所以观测失败时这四个动作一律拒绝（`TRAY_OBSERVE_FAILED`）。

`quit` 是例外：状态不明时更需要能退出。

## 5. 动作串行化，不排队

两个动作同时跑（用户连点、「退出」与「停止」撞上）会让观测与动作交错，
得出的结论谁也不算数。但**不排队**：一个排队的「停止」会在「启动」之后才执行，
而用户看到的是最终状态与他的操作相反。所以第二个动作直接被拒（`TRAY_BUSY`）。

`dispose()` 之后所有动作都拒绝——一个释放后仍能点「启动」的托盘很危险。

## 6. 变红验证：20 处，20 处红

重点：★★ **退出时不确认是否真的停了** / ★ 只看 `stop()` 的返回值 /
★ 观测失败也算「停掉了」/ ★ `degraded` 也算停下来 / ★ 退出不调 `stop()` /
★ `unavailable` 也算「在跑」/ ★ `start` 与 `stop` 同时可点 /
★ 没有地址也能打开 Workbench / ★ `quit` 在状态未知时不可点 /
★ 观测失败时照样执行动作 / ★ `menu()` 缓存观测结果 / ★ 忙碌时排队执行 /
★ `dispose()` 之后动作照常执行。

## 7. 本批**没有**解决的事

- **没有真正的托盘图标**：`createTray` 产出的是**菜单模型与动作分发**，
  没有任何东西把它画到系统托盘上。零依赖的 Node 拿不到原生托盘 API，
  所以真实实现需要一个原生模块或平台脚本——**这一层完全没有做**。
  本模块是「托盘该有的行为」，不是「托盘本身」。
- **没有接进 Launcher**：`observe` / `start` / `stop` / `openExternal`
  四个依赖全部由调用方注入，产品里还没有把它们接到 `launcher.mjs`
  与平台的「打开浏览器」上。
- **没有单实例保护**：两个 Legion 实例会各有一个托盘图标，
  且各自的 `observe()` 看到的是同一批进程。这需要一把锁（PRT-706 的范围）。
- **`TRAY_NOT_SUPPORTED` 与 `TRAY_OPEN_FAILED` 的区分**只在注入层成立：
  `openExternal` 抛错归在 `OPEN_FAILED`，没配置 `openExternal` 才是
  `NOT_SUPPORTED`。平台真不支持打开浏览器这件事目前**没有探测**。
- **`supported` 只是按平台名判断**（win32/darwin/linux），
  没有验证托盘能力真的可用。一个在无桌面 Linux 上跑起来的实例
  会报 `supported: true` 却什么也画不出来。
- **没有「开机自启」与「最小化到托盘」**：spec 没要求，但托盘产品通常有，
  这里明确不做。
