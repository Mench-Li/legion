> 状态：✅ 完成（2026-09-13）
> 依赖：PRT-709（日志 sink / 轮转 / 接线）、PRT-710（配置与诊断纪律）
> 对应 spec：§6.4「日志：轮转、保留期、磁盘紧张时的取舍」

---

## 0. 这一批补的是什么

PRT-709 的正文里留着一句**自我更正**：

> ⚠️ **诚实边界**：……`logPolicy` **已**接在产品配置文件的键上
> （`log.maxFileBytes`/`log.maxTotalBytes`/`log.keepFiles`/`log.minFreeBytes`
> → `product/config.mjs:349-362` → `launcher/cli.mjs:277` → `launcher.mjs:189,457`，
> 且有用例钉住）——**本批复核更正**：旧话写的"还没接到"是错的。
> 真正还缺的是**改它们的界面**（用户得手编配置文件）。

这一批补的就是那个界面。但做的过程中发现，"手编配置文件"的问题**不止是麻烦**：

配置有四层（builtin-defaults / product-config / workspace-config / user-settings），
后一层覆盖前一层；而 `log.*` **只从 product-config 读**。于是最常见的一幕是：

```
用户在工作空间配置里写了 log.keepFiles: 20   →  什么都没发生
```

产品**不会**告诉他"这个键只从产品配置读"。

> 一个"改了但没有任何反应"的配置界面，
> 与一个"这个键根本不生效"的配置界面，在用户看来是同一个东西——
> 只不过前者会让他反复改同一个地方。

所以这一层有**两**件事要做，而第二件比第一件重要：

- ① 能改（`--set-log-policy`）；
- ② 能看懂**现在到底是什么值、它是谁给的**（`--log-policy`，带 provenance）。

## 1. 交付

### 1.1 `product/launcher/log-policy-cli.mjs`（新）

| 导出 | 职责 |
|---|---|
| `LOG_POLICY_KEYS` | 认识的四个键 → 配置路径（`keepFiles` → `log.keepFiles`） |
| `LOG_CLI_CODES` | 六种具名结果码 |
| `parsePolicyAssignments(spec)` | `k=v,k=v` → `{keepFiles: 10}` |
| `effectiveLogPolicy(merged)` | 实际生效的值（缺省补默认，**坏值不进**） |
| `describeLogPolicy({...})` | 渲染成可读文本，**每一项带来源** |
| `applyLogPolicy({configPath, values})` | 原子写入 |

### 1.2 CLI

| 参数 | 作用 |
|---|---|
| `--log-policy` | 打印当前生效的日志策略 + 每项的来源 |
| `--set-log-policy=<k=v,...>` | 改并写入产品配置文件 |

两个入口都排在**配置校验之前**——与诊断包、心跳同意同一条理由，
而这一条尤其要紧：一个"配置有问题"的产品，最需要用户能**看一眼现在的值**。

> 一个只在配置正确时才可用的配置查看器，
> 与一个不存在的配置查看器，在用户最需要它的那一刻是同一个东西。

### 1.3 写这一层守住的四件事

1. **先校验再写。** 复用 `validateLogPolicy`，且校验的是**写完之后的完整策略**——
   只校验"要改的那几个键"是不够的，有些问题要两份值放在一起才看得出来。
2. **配置坏掉时拒绝写。** 读不出来的配置（坏 JSON）如果被"顺手重写一遍"，
   用户的原始内容就**永久没了**——而它可能只是少了一个逗号。
3. **原子写**（临时文件 + rename）：写到一半断电会留下半截 JSON，
   而半截 JSON 在配置层里等于**整份配置回到默认值**。
4. **不认识的键原样保留。** 这一层只认识 `log.*` 四个键，
   重写出去时别的键（包括这一层不认识的）必须一个不少。

## 2. 这一批真的抓到的坑

### 2.1 ⚠️ 查看器把"配置被整份忽略"渲染成了"一切正常"（真实 CLI 冒烟量出来的）

`loadProductConfig` 在配置是坏 JSON 时会报 `CONFIG_INVALID_JSON`，
并且**让整份配置被忽略**。而查看器第一版只把 `merged` 拿来渲染，于是四项全都写着
`（默认值）`：

```
当前生效的日志策略：
  maxFileBytes   8388608（8 MiB）               （默认值）
  maxTotalBytes  134217728（128 MiB）           （默认值）
  keepFiles      5                            （默认值）
  minFreeBytes   536870912（512 MiB）           （默认值）
```

那份输出**看起来完全正常**。用户会得到"一切正常、都是默认值"这个结论，
而真相是"你的配置文件根本没被读进去"。

> 一个把"你的配置被整份忽略了"渲染成"一切正常"的查看器，
> 与一个"配置确实没问题"的查看器，在屏幕上是同一份输出——
> 只不过前者会让用户放心地走开。

**这正是本任务要消灭的「改了但没反应」，只是换了个位置发生。**

已修：报错块排在最前（顺序反过来用户只看前几行就走了）、默认值的来源改标
`← 默认值（配置未生效）`、退出码 6（与主流程里"产品配置有问题"**同一个码**——
同一件事不该有两个码，否则脚本要判两次）。

这个 bug **不是**单元测试发现的：它需要"真把 CLI 跑起来、把配置弄坏、再读一次输出"。
所有 24 条用例当时全绿。

### 2.2 `--set-log-policy` 之后 `--log-policy` 显示旧值（同一次调用）

`options` 是在 `run()` 开头算好的。`--set-log-policy` 与 `--log-policy`
写在**同一次调用**里时，用它就会显示改之前的值——而用户会把那一幕读成
"我的修改没生效"。

> 一个"在改完之后仍然显示旧值"的查看器，
> 与一个"修改根本没生效"的产品，在用户下一步要做什么上是同一个读数。

已改成重新读盘。**但更值得记的是用例的形状**：我最初写的用例跑的是**两次**
`run()`，而每次调用都会重新解析配置——所以它拿到新值**与实现无关**，
换成陈旧读取它照样绿。

> 一个"分成两次调用"的用例，测不到"同一次调用里的陈旧读取"——
> 它看起来在守那条纪律，其实守的是进程边界。

补了一条同一次调用的用例（并且反面断言不能出现旧值 `5`）。

### 2.3 ⚠️ 断验证探针**污染了工作区**（这一类残留第一次出现）

探针 ⑤㊳ 的替换文本是 `configPath = './product.config.json'`。
它在断验证里**真的在仓库根目录创建了** `product.config.json`，
内容是 `{"log":{"keepFiles":1}}`——正是那条用例传进去的值。

harness 只还原**源文件**，它不知道探针会让被测代码在别处留下东西。

> 一个"会改工作区"的探针，与一个"只改源码"的探针，
> 在还原校验里长得一样——前者的残留要等到下一次 `git status` 才现形。

已把替换文本改成写进**系统临时目录**（仍然演示"凭猜的位置写入"，但不污染仓库），
并删掉了那个残留文件（它已经被 `git add` 过，是 `scan` 的"未处理字面量 `CONFIG`"
之外的另一个信号：`scan` 只扫 tracked 文件，所以它**真的**进了索引）。

### 2.4 一处探针期望写错（纵深防御让它"没咬住"）

探针 ⑤㉗ 把解析层的数字校验改成 `if (false)`，期望 CLI 那条用例也红。
它没红——而这是个**好消息**：`2.5` 绕过解析层之后，
`applyLogPolicy` 里那次 `validateLogPolicy` 仍然会拒掉它，CLI 照样给出退出码 2。

> 一个"下一层也拦得住"的实现，会让上一层的探针**看起来**没咬住——
> 而那正是纵深防御该有的样子；要断言的是"上一层自己也拦"。

已把期望收窄到单元层那条用例。

### 2.5 正文里"按进程分文件命名未做"这句话是**错的**

PRT-709 的行里写着「按进程分文件命名与按天保留期都未做」。核实后：
`logFilePath(logDir, stream)` **已经**产出 `<进程>.<流>.log`
（`team-hub.stdout.log` / `team-hub.stderr.log`），且 `sink.test.mjs:296` 早就钉住了它。

所以那句话里的"按进程分文件命名"应当删掉（"按天保留期"是对的，属 PRT-904）。
新增一条用例把这件事钉住，免得它再被写成"未做"。

## 4. 诚实边界

1. **没有图形界面。** 两个参数都是命令行的；Workbench 里看不到日志策略，
   也改不了它。spec §6.4 的"设置页"没有做。
2. **`log.*` 仍然只从产品配置读。** 这一批做的是**把这个事实说出来**，
   不是改变它——四层配置的优先级规则不属于本任务。
3. **按天保留期没做**（属 PRT-904）。轮转仍然是按份数（`keepFiles`）。
4. **`--log-policy` 显示的"来源"是产品配置文件**，不是"哪个具体文件行"。
   用户知道是 `product-config` 这一层，但不知道是哪一行。
5. **改完不会让正在跑的进程生效。** 日志策略在启动时读一次；
   改完必须重启产品。产品不会提示这一点（它不知道有没有在跑）。
6. **没有并发保护。** 两个进程同时改配置文件时，原子 rename 保证不会是半截 JSON，
   但**后写的那次赢**，而先写的那次不会知道自己的修改被覆盖了。
7. **写失败只报一句话**（权限/磁盘），没有区分"目录不存在"与"磁盘满了"——
   用户拿到的是 `e.message`，而它的可读性取决于 Node 在那个平台给出的文本。
8. **`JSON.stringify(nextRoot, null, 2)` 会重排键序**，也会丢掉原始文件里的注释
   （JSON 本来就没有注释）与缩进风格。用户手写的格式在第一次 `--set-log-policy`
   之后就不再是原来的样子了。
