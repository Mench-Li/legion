# PRT-709 日志轮转与磁盘保护

> 本文记录 `product/logging/rotation.mjs`、`product/logging/sink.mjs`，
> 以及它们与 `product/launcher/` 的接线。
>
> spec 在 §（日志轮转和磁盘容量保护）与 §（日志、事件和产物设置容量上限与
> 保留策略）两处提到这件事。但落地时先撞上的是**一个比"没有轮转"重得多的
> 问题**，见 §1。

## 1. 先修的是一个会卡死子进程的 bug

动工之前，`product/launcher/` 里**没有任何地方读 `child.stdout` / `child.stderr`**
（`git grep` 无命中），而监督层是按

```js
stdio: spawnOptions.stdio ?? ['ignore', 'pipe', 'pipe']
```

起子进程的。两个后果，第二个重得多：

1. 子进程的全部输出**没有人看**——运行时诊断（排查最需要的东西）消失在管道里；
2. 管道缓冲区写满之后，**子进程会阻塞在 `write` 上**。Windows 上的管道缓冲区
   是几十 KB 量级，所以一个话多的进程会在启动几秒后**永久卡住**：
   不退出、不报错、也不再干活。

后果 2 之所以严重，是因为它**让所有与"卡住"有关的机制一起失效**：

- 熔断器看不到失败（没有退出码、没有错误）→ 永远不会介入；
- 就绪探针只会一路超时 → 报成"没起来"，而不是"起来了但堵住了"；
- 没有日志 → 排查看不出任何线索。

> 一个把子进程的输出丢掉、并且在它写满缓冲区时让它卡住的启动器，
> 与一个"进程跑着但什么也不干"的启动器，在用户眼里是同一个东西。

所以 `attachDrain` 的第一条纪律是：

> **排空管道这件事，不许依赖"日志有没有被配置好"。**

即使调用方一个 sink 都没给，`onData` 为 `null`，也必须接上 `data` 并 `resume`。
丢掉是浪费，卡住是故障。

这条用**真实子进程**验证（`log-wiring.test.mjs`）：一个写 2 MiB 到 stdout 的
子进程，在**不接 sink** 的情况下必须跑完。用假 stream 测不出来——
**假 stream 不会满**。

## 2. 轮转：磁盘写满时不许做错事

顺序不能反：

1. 先**轮转**（把写满的活动文件挪走）；
2. 再**修剪**（按保留代数与总量预算删最旧的**已轮转**文件）；
3. 最后**如实报告**还差多少。

反过来（先删再轮转）会在一瞬间出现"当前日志没了、新日志还没建好"的窗口，
而那正是故障时刻。

### 三条绝不做的事

| 不做 | 为什么 |
| --- | --- |
| **绝不删活动文件** | 它是正在写的那一份。在磁盘写满的时刻删掉当前日志，等于把证据和空间一起弄没了 |
| **绝不删代数 1** | 删了它，`keepFiles=0` 或预算极小时"轮转"就只剩"把日志扔掉"这一个效果——转一圈什么也没留下 |
| **绝不把"没做成"报成成功** | Windows 上另一个进程持有句柄时 `rename` 会失败（EPERM/EBUSY），这时不能假装轮转成功，也**不能**转而删掉活动文件来"腾地方" |

第三条有专门的用例：`renameFails` 一个文件被占着的 fake fs，断言
失败码是 `LOG_ROTATE_FILE_IN_USE`、消息里写着"没有删它"、并且活动文件**仍在**。

### 位移必须从最大代数往下

`n → n+1` 时 `n+1` 必须已经被腾空。反过来的话，**第一次 rename 就会覆盖掉
还需要的旧日志**（破验证 ⑲⑧ 量到了）。用例断言的是**内容**整体后移一代：

```js
assert.equal(fs.map.get(`${D}/a.log.2`)?.body, 'one')   // 原本在 .1
assert.equal(fs.map.get(`${D}/a.log.3`)?.body, 'two')   // 原本在 .2
```

### 「读不出来」与「没查」都不是零

两条都是"把一个未知数记成了一个已知的零"：

- **读不出目录 ≠ 目录是空的**：`readdirSync` 抛错时报 `LOG_UNREADABLE`，
  消息明写"**读不出来不等于没有日志要轮转**"。报成 `ok: true` 会让用户以为
  无事可做（破验证 ⑲⑨）。
- **没查磁盘 ≠ 空间充足**：`statfsSync` 不可用时 `freeBytes` 是 `null`，
  磁盘保护那一整段被跳过，并附一条 `FREE_SPACE_UNKNOWN`，消息明写
  "不要把这条读成'空间充足'"。`freeBytesFromStatfs` 对 `null` 返回 `null`，
  **不是 0**——0 会被读成"磁盘满了"（破验证 ⑲⑩ / ⑲⑪）。

### 一次成功的清理，不是"磁盘没问题"的证据

第一版只在"仍然超预算或一点也没腾出来"时才报磁盘紧张，于是
**"磁盘快满了但我们顺手删了几百 KB"这种情况完全没有提示**——而它正是最需要
提示的一种：风险还在（盘快满了），用户却因为看到一次成功的轮转而以为没事。

现在只要低于下限就报，并且腾出空间时消息写的是
"已额外腾出 N 字节，但这**不代表磁盘就够用了**"（破验证 ⑲⑫）。

### 认不出的文件一个都不动

日志目录里出现一个 `notes.txt`，与它是"最旧的那一代"完全是两回事——
**"最旧"对一个不认识的文件没有定义**。所以它们既不轮转也不删除，
并留一条 `FOREIGN_FILES` 说明（破验证 ⑲⑮）。

## 3. 写入侧：按行脱敏、切断巨型行、不炸启动器

### 按行脱敏，不按块

一个密钥被拆在两个 `data` 块之间时，逐块跑正则**认不出来**。
所以 sink 按行聚合再脱敏——这不是"更彻底"，而是唯一的正确做法
（`redactText` 是行内判据）。用例把 `sk-abcdefghij` / `klmnopqrstuvwxyz012345`
分两块写进去，断言**跨块的那一次命中被算出来了**（破验证 ⑲⑰）。

### 行不能无限聚合

一个不换行的巨型输出会把内存吃光。所以有 `maxLineBytes`（64 KiB）：
超了就先脱敏再落盘，并记一条 `LOG_SINK_LINE_TOO_LONG`。消息里必须写清
"**这不是丢日志**"——否则读的人会以为日志缺了一段。

### 脱敏抛错时写占位符，不写原文

这是 §6.7 的直接要求。脱敏本身抛错时（模式表坏了之类），
写原文出去是最坏的选择。所以：

```js
return { text: `[本行脱敏失败，已丢弃：${REDACTED}]\n`, hits: 0 }
```

这条防线**只有靠注入才走得到**（真表对字符串不会抛），所以
`createLogSink` 把 `redactText` 做成可注入的。用例注入一个每次都抛的"坏表"，
断言原文**没有**出现在日志里，且 sink 继续工作（第二行照样被处理）。

### 写入失败绝不抛回子进程的数据处理器

`data` 回调里抛错会冒泡到 launcher 主流程。日志写不进去是**产品的问题**，
不是"让启动器崩掉"的理由。所有写入错误都转成 `onDiagnostic`，
消息里还必须写清"**这条本身也写不进日志**"——否则用户会去日志里找它。

## 4. 接线：日志的生命周期不依赖启动成功

这是本批**第三处**"必须排在校验之前"的地方（前两处是 PRT-710 的诊断入口、
以及 Launcher 的密钥库自检）。三个都栽在同一个坑上：

> 一个只在产品健康时才可用的东西，与一个不存在的东西，
> 在最需要它的那一刻是同一个东西。

具体到日志，破验证量出了两处**走不到的代码**：

- **sink 建在 `preflight()` 之后** → 启动在体检就失败时，`start()` 早退，
  sink 从未创建。而**失败启动的日志恰恰是最该留下的那一份**。现在
  `ensureLogSink()` 是 `start()` 的**第一步**。
- **轮转定时器挂在 plan 走通之后** → 同一个问题。现在它跟着 sink 一起起。

`stop()` 也修了：原来 `supervisor === null` 时直接返回，
于是"启动在体检就失败"这一类场景**既不会 flush（最后几行丢掉）也不会轮转**
（一个写满的文件留给下一次启动继续写）。

> 「没起来所以没什么可记的」这个判断，恰好把最该记的那一次排除掉了。

### 定时器必须 `unref`

一个被引用的定时器会让启动器进程**永远不退出**，于是"命令跑完了但不返回"
会成为一个莫名其妙的现场。定时器只在跑着的时候有意义，不该拦住退出。
为了让它**可观测**，`setIntervalImpl` / `clearIntervalImpl` 可注入，
用例断言 `unref` 被调用过。

### 停止时先 `dispose`，`dispose` 摘掉排空句柄

`dispose()` 之后不该再往 sink 里送数据——那时调用方很可能已经 `close()` 了
sink（launcher 的 `stop()` 就是先 dispose 再收尾日志）。继续送只会往一个
已经关掉的对象里写。

## 5. 变红验证：27 处，27 处红

覆盖：排空退回"只在配了 sink 时才接"、干脆不接排空、活动文件进修剪候选、
代数 1 失去保护、被占着时假装成功、被占着时改删活动文件、位移从最小代数开始、
读不出目录当空目录、`statfs` 读不出记成 0、`freeBytes: null` 当成 0、
腾出空间就不报、超预算不报、策略负值被静默纠正、认不出的文件当可删日志、
预算只删一个就收手、逐块脱敏、脱敏抛错写原文、写入错误抛回数据处理器、
流名不清洗、单行上限失效、`close()` 不 flush、默认脱敏被关掉、
`detach` 不生效、停止不收尾、定时器不 `unref`、`dispose` 后仍送数据、
sink 建在早退之后。

### 五轮"没咬"，五种不同的原因

| 探针 | 第一版瞄了什么 | 为什么没红 | 处置 |
| --- | --- | --- | --- |
| ⑲③ | `handleExit` 里的 detach | 那句是**冗余**的（下一次 spawn 开头就会摘旧的） | 改瞄 `attemptStart` 的 detach |
| ⑲③（二次） | `attemptStart` 的 detach | 每次 attemptStart 都 spawn **全新 child**，"往死流上累积监听器"根本不会发生 | **删代码**（注释里写着"会累积成千上万个"，是假的危险） |
| ⑲④ | 把活动文件推进 `rotated` | 推的时机在 `byBase` 构建**之前**，等于没推——**探针写错了** | 改瞄预算候选那一处（真正的闸门） |
| ⑲⑪ | `(freeBytes ?? 1e18) < min` | 与原式**语义等价**（都排除 `null`）——**探针写错了** | 改成把 `null` 当成 0 |
| ⑲⑳ | 只断言"路径以日志目录开头" | `C:/log/../../evil.log` **也过得了那一关**——**用例太弱** | 断言改成判"逃逸**段**"（`..` 作为路径段才危险，`..-..-evil.log` 只是个普通文件名） |
| ⑲㉗ | 把"解析后复核"改成 `if (false)` | 清洗那一层是全的，复核**永远为真** | **删代码**，改成对着唯一实现路径的**性质断言** |
| ⑲㉕/⑲㉖ | 停止收尾 / 定时器 unref | 瞄在了**走不到的代码**上（plan 段从未执行） | 先改实现（生命周期不再依赖启动成功），再瞄改好之后的代码 |
| ⑲㉘ | 把 `ensureLogSink()` 挪到 `preflight()` 之后 | `preflight()` 自己就返回 `phase:'plan'`；挪到它后面但仍在早退**之前**，照样会建 | 挪到早退**之后** |

⑤ 与 ⑲㉗ 是同一种处置，这一批一共**删掉了三段不可观测的代码**：

> 一个永远不会触发的复核，与没有复核，在"它到底拦不拦得住"上同形。

留着的代价不是性能，是**误导**：下一个人会以为"还有一道兜底"，
从而在真正决定行为的地方（那条清洗正则）少想一层。
现在守那一层的是 `sink.test.mjs` 里的一组**性质断言**——喂一批恶意流名，
断言结果一律落在日志目录内。

## 6. 本轮实现的真 bug（用例先红、实现后改）

- **`stop()` 里 `const log = await finalizeLogs()` 遮蔽了顶层 `log()` 函数**，
  导致 `stop` 体**开头**那句 `log('info', …)` 抛
  `Cannot access 'log' before initialization`（15 个 launcher 用例红了 4 个）。
  > 一个遮蔽了外层函数的名字，会让那个函数在**整段**作用域里消失，
  > 而不只是在你写的那一行之后。
- **两处名字不一致**：`logRotationTimer`（声明处）vs `logRotateTimer`（使用处）。
- **`options.layout` 在 `createLauncher` 里根本不存在**（参数是直接解构的
  `layout` / `logPolicy`），sink 因此从未建起来。
- **sink 失败诊断只带 `e.name`**，界面上只剩"ReferenceError"四个字——
  就是这条让上面那个 bug 多花了一轮才定位。现在带上 `e.message`。
- **磁盘压力在成功腾出空间后不报**（§2）。
- **`dispose()` 后仍往 sink 送数据**（§4）。

## 7. 本批**没有**解决的事

- **日志内容没有进 Workbench 界面**：sink 写盘、`logStatus()` 可查，
  但界面上没有"看日志"的入口。属 Product Launcher 的前端一半。
- **`logPolicy` 没有接到产品配置文件**：`createLauncher` 接受它，
  但 `product/config-schema.mjs` 里还没有对应的键，所以用户改不了
  单文件上限/保留代数/总预算。默认值在 `DEFAULT_LOG_POLICY` 里。
- **`--diagnostics` 不会自动带上日志之外的东西**：PRT-710 的诊断包会收
  日志文件（受 8 MiB/文件、64 MiB/包约束），但"启动失败时自动出包"仍未做。
- **按进程分文件的日志命名未做**：当前是 `${processKey}.${stream}.log`，
  同一个进程的多次重启写同一个文件（这正是 `FILE_IN_USE` 那条错误信息里
  建议的替代方案）。
- **没有保留期（按天/按周）**，只有按代数与字节预算。PRT-904 的范围。
- **`statfsSync` 在部分平台上不可用**：那时只按字节预算保护，
  磁盘写满这一类风险不被覆盖（会有一条 `FREE_SPACE_UNKNOWN` 明说）。
