# PRT-710 收尾　启动失败时自动出诊断包

> 状态：✅ 完成（2026-09-13）
> 依赖：PRT-710（脱敏诊断包导出本体）、PRT-709（日志轮转与磁盘保护，本条被它显式指到 PRT-710 名下）
> 对应 spec：§6.7「密钥不得出现在诊断包里」+「产品坏掉时仍然拿得到证据」

---

## 0. 补的是哪一步

`--diagnostics=<dir>` 早就能用，而且入口位置是对的（排在布局校验与配置校验**之前**，
理由见 PRT-710 的正文）。缺的是**用户不必想起来**的那一步。

PRT-710 自己的定位是：

> 诊断包最需要在什么时候拿到？**产品坏掉的时候。**

而 `--diagnostics` 要求用户在**产品已经坏掉之后**还想起来、并且能够，手工敲一次命令。

> 一个"坏掉之后可以手工导出"的诊断包，
> 与一个"坏掉时会自动留下证据"的诊断包，
> 在用户记得去敲那条命令的时候是同一个东西——
> 只不过前者会在用户不记得、或者产品坏到连命令行都进不去的时候，
> 恰好什么都不留下，而"这次没有证据"与"这次没什么可记的"长得一样。

PRT-709 的行里早就把这条指了过来：「"启动失败时自动出诊断包"未做（属 PRT-710 的范围）」。

## 1. 交付了什么

### 1.1 新模块 `product/diagnostics/auto-export.mjs`

| 导出 | 职责 |
|---|---|
| `AUTO_EXPORT_CODES` | 四个失败码：`AUTO_NO_BASE_DIR` / `AUTO_DISABLED` / `AUTO_BASE_DIR_FAILED` / `AUTO_EXPORT_FAILED` |
| `AUTO_EXPORT_DEFAULTS` | `keep: 3` / `prefix: 'diag-'` / `dirName: 'diagnostics'` / `maxScan: 2000` |
| `stampOf(date)` | `YYYYMMDD-HHMMSS`（本地时间、定宽 → 字典序 == 时间序） |
| `isOwnPackageName(name)` | "什么是我认得的东西"的**唯一定义** |
| `planAutoExport(deps)` | **纯**判定：写哪个名字、删哪些、哪些碰都不碰 |
| `runAutoExport(deps)` | 碰文件系统的那一半（**永远不抛**） |

判定与 IO 分开，理由与 `redact-package.mjs` 拆出 `planPackage` 完全同一条：
**落盘那一步无法在用例里逐条验证，判定那一步可以。**

### 1.2 CLI 接线

启动失败那条路上（`cli.mjs` 的 `result.ok !== true` 分支）自动调用一次，
位置在**打印完启动失败之后**：

```
✖ 启动失败（阶段：readiness）
  ✖ [team-hub] READINESS_TIMEOUT：原来的原因
  ⤷ 已自动留下诊断包：<产品家目录>/diagnostics/diag-20260913-090503
```

### 1.3 默认开着，只有一个「关」的开关

- 默认**开**：诊断包只写在本机 `<产品家目录>/diagnostics/`、**不外发**，
  而它的全部价值就是"用户没想起来的时候它也在"。
- `--no-auto-diagnostics` 显式退出。
- `--auto-diagnostics-keep=<n>` 设保留份数。

**刻意没有** `--auto-diagnostics` 这个"开"的开关：它已经是默认值，
那样的参数**没有任何效果**，而一个没有效果的参数比没有这个参数更坏——
它会让读帮助的人以为"这件事是要显式打开的"。有一条用例专门钉住这一点。

## 2. 这一条同时引入的危险（本模块一半的代码在防它）

自动写盘 = **在失败循环里自动写盘**。一个每次启动都失败的产品，
如果每次失败都留一个包，就会把磁盘写满——而 PRT-709 整条任务就是在守这件事。

### ① 磁盘有界，且**先清理再写**

`keep` 默认 3（3 × 64MB ≈ 最坏 192MB）。清理跑在写入**之前**：
顺序反过来的话，崩溃循环里最坏的那一刻是"刚写完第 N+1 个，然后进程死了"，
于是清理永远没机会跑。有一条用例在**每一轮之后**都数一遍，
断言占用是**收敛**的而不是先涨后清。

### ② 只清理自己认得的东西

目录名必须匹配 `diag-YYYYMMDD-HHMMSS(-N)?`。认不出的条目进 `foreign` 列表、
**一个都不动**——"最旧"对一个认不出的东西没有定义。这与 PRT-709 的
`FOREIGN_FILES` 是同一条纪律。

要紧的是：**收紧这个正则安全，放宽它危险**（放宽 = 允许删掉别人的东西）。
所以它有一条专门的用例，逐个拒绝 `diag-abc` / `credentials.yaml` /
`diagnostics` / 位数不对的各种形状，还有一条真文件系统的用例往
`diagnostics/` 里放一个密钥库、一个用户笔记、一个形状不对的目录，
断言清理之后**它们都还在**。

### ③ 同一秒内的第二次失败也要留证据

崩溃循环里一秒内失败两次是常态，而 `exportDiagnosticPackage` **不覆盖**
已有目录（那是对的）。不加去重后缀的话，第二次失败只会拿到
`DIAG_PACKAGE_EXISTS`，于是"第 2 到第 N 次崩溃没有证据"。

> 一个"同一秒内第二次失败就不留证据"的自动导出，
> 与一个"只在第一次失败时留证据"的自动导出，在崩溃循环里是同一个东西——
> 只不过前者会让人以为导出**一直在跑**。

所以同秒冲突加 `-2` / `-3` 后缀（上界与 `keep` 同源，不会无限加）。

### ④ 失败不换原因

这是本批**最要紧**的一条。诊断包出不来时：

```
✖ 启动失败（阶段：readiness）
  ✖ [team-hub] READINESS_TIMEOUT：原来的原因     ← 必须还在
  ⤷ 未留下诊断包：磁盘满了                        ← 只是附注
```

**退出码仍然是 5。** `runAutoExport` **永远不抛**（调用方正在处理一个
已经发生的故障，这里再抛一个只会把那个原因盖掉），导出失败时
`reason` 字段**原样带回**原始原因。

> 一个"出不了诊断包于是报了个诊断包错误"的启动，
> 与一个"真的就是诊断包坏了"的启动，
> 在用户读到的第一行上是同一个东西——
> 只不过前者会把一个**已经查明的**故障，换成一句**关于工具的**抱怨。

### ⑤ 家目录定不下来时**不猜**位置

猜出来的位置可能落在用户的别的东西上。而"把证据写到错的地方"比
"这次没有证据"更坏：后者只是没有，前者会污染。

### ⑥ 「读不出来」≠「目录是空的」

读基础目录失败 → `AUTO_BASE_DIR_FAILED`，并且**跳过清理**。
把它当成空目录的话，一个塞满的目录永远不被收缩。

### ⑦ 清理删不掉时不抛、也不报成故障

Windows 上文件被占用时 `rmSync` 会失败。删不掉就留着——
**清理失败不是启动失败的原因**（PRT-709 同一条纪律：删不掉时不要转而做更激进的事）。

## 3. 本批真的踩到的坑

### 3.1 变量定义插错了函数，于是**只在启动失败时才崩**

我按 `const fromConfig = ...` 定位插入点，而那一行在 `launcherOptionsFrom()` 里
也有一份。`autoDiagnostics` 定义在了那个函数里，`run()` 里引用它当场
`ReferenceError: autoDiagnostics is not defined`。

它**只在真的启动失败时才崩**——跑得通的运行完全看不出问题。

> 一个"只在出错路径上才崩"的变量引用，
> 与一个正确的实现，在**产品正常工作**的时候同形——
> 只不过前者会让"产品坏掉"这件事，表现成一句关于代码的报错。

### 3.2 探针 ㊲ 报「没咬住」，而它揭开的是用例的盲区

把清理方向反过来（删最新、留最旧）之后，我原本指望「崩溃循环」那条变红。
它**没红**：

- `left.length <= keep` —— 成立（删哪一头，写完之后总数都是 keep）；
- "最新那个在" —— 也成立（**刚写下去的那个永远是最新的**）。

所以这个探针的 `expectRed` 指错了，而更正之后它咬住了别的两条
（断言 `prune` 具体成员的那两条）。同时我**加强了**崩溃循环用例：
从"不超过三个"改成断言留下的**就是最后三个**。

> 一个"只断言份数上界"的用例，
> 与一个"断言了清理方向"的用例，看起来都在守清理——
> 只不过前者在方向反了的时候**照样是绿的**，
> 而方向反了的后果恰恰是"最有用的那份证据先没"。

### 3.3 夹具没给候选 → 读起来像"自动导出坏了"

第一版循环用例只给了 `{ productHome: dir }`，于是每次导出都拿到
`DIAG_EMPTY_PACKAGE`——因为 `defaultCandidates` 的候选全部来自
`logDir` / `productConfigPath` / `secretsFile`，而这三样都没给。

一个"没什么可收"的空包与一个"导出功能坏了"，在没有候选的时候报的是同一个错。

### 3.4 替身不完整、替身说谎

同一条用例里我先后犯了两次替身错误：

- `fs: { existsSync: () => true, ... }` —— **对所有路径都说"存在"**，
  于是导出模块的前置检查认为目标目录已存在并拒绝导出，用例红在
  `DIAG_PACKAGE_EXISTS` 上，而真正的原因是替身说谎。
- `fs: { existsSync, readdirSync, rmSync }` —— **少给了 `mkdirSync` /
  `writeFileSync`**，导出那一步拿到一个残缺的 fs，红在
  `DIAG_WRITE_FAILED：TypeError` 上。

现在的做法是 `{ ...await import('node:fs'), rmSync: <替换> }`：
替身**转发给真实实现**，只覆盖要模拟的那一个方法。

> 一个"少给几个方法的 fs 替身"，与一个"写入真的坏了"的产品，
> 报出来是同一个失败——只不过前者会让人去查导出模块。

### 3.5 `scan` 门拦下了四个新码

`AUTO_*` 是 SCREAMING_SNAKE 字面量，被规则 ③ 当成疑似 env 键。
按既定纪律补进 `product/config-schema.mjs` 的 `nonEnvLiterals`，
并逐个写明理由（它们是**输出**用的码，不是配置键）。

## 5. 诚实边界

1. **只接在启动失败那一条路上。** 体检失败（`--check`，退出 4）、
   布局失败（3）、配置失败（6）**不**触发自动导出——那几条路径上
   用户已经得到了明确的诊断，且它们都不是"产品跑过又坏了"。
2. **不自动外发。** 包只写在 `<产品家目录>/diagnostics/`，
   怎么发给别人仍然由用户决定。
3. **没有界面。** 保留份数与默认开关目前只能通过命令行参数改，
   配置文件里没有 `diagnostics.*` 键（与 PRT-709 的 `log.*` 有键不同）。
4. **保留份数是**按**份数**而不是**字节**计的。`keep: 3` 的最坏占用是
   3 × `maxTotalBytes`（64MB）≈ 192MB；真正的字节级配额要等
   PRT-709 那套 `minFreeBytes` 逻辑外延到这里（目前没有）。
5. **时间戳是本地时间**，跨时区/夏令时切换时同一秒可能产生两名
   （已由去重后缀兜住，但"最旧"的排序在那一个小时内可能不准）。
6. **`maxScan: 2000`** 意味着一个被塞了超过 2000 个条目的 `diagnostics/`
   目录只会被看到前 2000 个（按 `readdirSync` 的顺序，未排序）——
   清理可能漏掉一些旧包。不设上限的话，"留下证据"会变成卡住启动的原因。
7. **没有单实例保护。** 两个 Launcher 同时失败时可能同时写，
   去重后缀能避免覆盖，但两者都可能看到同一批旧包并各自清理。
8. **`planAutoExport` 的 `dirName` 上界**（`keep + 2`）是启发式的：
   同一秒内失败次数超过那个值时，最后一个会落到一个已被占据的名字上，
   于是那一次导出会以 `DIAG_PACKAGE_EXISTS` 失败（**不覆盖**是对的，
   但那一刻就是不留下证据）。
