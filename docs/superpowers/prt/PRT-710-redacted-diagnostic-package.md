# PRT-710 脱敏诊断包导出

> 本文记录 `product/diagnostics/redact-package.mjs` 与它的入口
> `legion --diagnostics=<dir>`。
>
> spec §6.7 把「诊断包」与提示词、日志、异常、审计、能力包并列，作为
> **密钥不得出现的地方**。§6.7 还有一条：诊断包**不得包含密钥**。
> 本模块就是那个导出点——在此之前，仓库里对"诊断包"只有**威胁描述**
> （`product/paths.mjs:291`、`product/config-schema.mjs:91`、
> `security/secrets/errors.mjs:45`、`team-hub/secret-admin.mjs:282`），
> 没有任何导出实现。

## 1. 四件被守住的事

这一节是本文的骨架。每一条都对应一个**真实会发生的误读**，而不对应一个"功能点"。

### ① 结构性排除优先于文本过滤

脱敏是**过滤器**：它只能拦下它认得出来的形态。而
`runtime/contracts/redact-patterns.mjs` 是一张**有限的**表——明天出现一种新的
密钥前缀，今天的过滤器会静默放它过去。

所以敏感**文件**不是"被脱敏后收进包里"，而是**根本不进包**：

| 规则 | 拦什么 | 为什么整类排除 |
| --- | --- | --- |
| `secret-store` | `secrets/` 目录下的一切，以及独立的 `secrets.json` / `secrets.db` | 密钥库本体：进包就等于把密钥发出去 |
| `credentials-yaml` | `*credentials.yaml/yml/json` | spec 附录 A.2 的明文凭证载体 |
| `raw-key` | `*.key / *.pem / *.p12 / *.pfx` | 私钥材料形态多变，脱敏认不全 |
| `auth-json` | `auth*.json` | 鉴权缓存通常整文件都是凭证 |
| `business-db` | `*.db / *.sqlite / *.sqlite3` | **业务库正文含提示词与业务数据**：诊断包是要发给别人的东西 |
| `env-file` | `.env` / `.env.*` | 该文件的惯例就是放密钥 |

**"不读"与"读进来再丢掉"是两回事。** 用例用一个会抛错的 `read` 钉住了这一点：
结构性排除发生在**读取之前**（破验证 ⑱①）。

### ② 「没包含」与「被排除」必须可区分

一份包里少了一个日志文件，与一份包**刻意**排除了密钥库，在收件人眼里长得一样：
都是"没这个东西"。所以清单里记的是**每一个候选**的去向——
`included` / `excluded`（附为什么）/ `skipped`（附原因）/ `oversized`（附原因），
四选一，没有第五种。

> 一份说不清自己排除了什么的诊断包，与一份漏收了文件的诊断包，
> 对排查者是同一个东西。

连"密钥库"这个候选也是**显式列出来再排除**的（`defaultCandidates` 里的
`push('secrets-store', …)`），而不是"忘了列"——后者在清单上只会显示成一个
不存在的条目。

### ③ 0 次脱敏命中 ≠ 「包是干净的」

`redactionHits` 只说**这张表认出了几个**。清单里始终带着 `redactionCaveat`，
成功文案在 0 命中时也明确写着"这不等于包是干净的"。真正的保证来自 ①。

### ④ 判定用的是**落盘之后读回来的字节**

写完包会**重新读回每一个文件**再审一遍。内存里那份是"我们以为写下去的"，
磁盘上那份才是发出去的东西——写错缓冲区这类 bug，恰好只有后者看得见
（破验证 ⑬ 用一个"偷偷把原文写下去"的 writer 量到了这一点）。

审出任何残留 → 包**作废**（连同目录一起删掉），而不是"发出去但附一句警告"：

> 一个**带着已知泄漏被发出去**的诊断包，比没有诊断包坏得多：
> 它已经离开了这台机器。

## 2. 入口：`legion --diagnostics=<dir>`

**位置是这段代码的全部要点**：它排在布局校验与配置校验**之前**。

诊断包最需要在什么时候拿到？**产品坏掉的时候。** 把它挂在"配置能解析、
布局合法才往下走"的流程后面，等于在最需要它的时候恰好用不了：

> 一个只在产品健康时才可用的诊断入口，与一个不存在的诊断入口，
> 在最需要它的那一刻是同一个东西。

所以 `diagnostics-cli` 套件里有两条专门的用例：**布局有 error 时照样出包**、
**配置是坏 JSON 时照样出包**。还有一条：它**不启动任何进程**。

退出码刻意把两类失败分开：

| 码 | 含义 |
| --- | --- |
| `0` | 包已生成并复检通过 |
| `8` | **复检发现残留，包已作废**——安全事件，必须一眼看得出与普通失败不同 |
| `9` | 其它导出失败（含"不覆盖已有目录"） |

**不覆盖已存在的目录**：诊断包的价值在于它是**当时**的证据，
悄悄覆盖掉上一次等于把"出事前的样子"毁掉。

## 3. 落地时发现的两个真 bug

两条都是**用例先红、实现后改**，不是设计时想到的。

### 3.1 `secret-store` 规则匹配不到密钥库

第一版手写了 `name === 'secrets.json'`，而产品用的是
`SECRETS_DIRNAME/SECRETS_FILENAME` = `secrets/credentials.json`
（`product/paths.mjs:64-65`）。于是那条**以密钥库命名**的规则**从来没匹配过密钥库**，
它只是碰巧被更宽的 `credentials-*` 规则接住了。

> 一条以某物命名、却匹配不到那个物的规则，与一条不存在的规则，
> 在「有没有保护到它」上是同一个答案。

处置：判定改为按**位置**（`secrets` 目录段）+ 两个独立的常见库文件名。
按位置比按名字强——换文件名它照样拦得住。

### 3.2 `credentials-*` 规则太窄

第一版是 `/^\.?credentials\.(ya?ml|json)$/`，于是 `x.credentials.yaml`
从缝里漏了过去。改成按**后缀**匹配，代价是 `notcredentials.yaml` 这类名字会被误排。

这个方向是对的：**少收一个日志文件只是信息少一点，多收一个凭证文件是泄漏**。
一条只认"标准写法"的排除规则，防的是规范，不是事实。

## 4. 变红验证：28 处，28 处红

覆盖：排除判定挪到读取之后、凭证后缀规则退回、独立库文件名那一支失效、
目录段兜底失效、`fullPath` 不传给规则、排除不登记、业务库不再按类型排除、
二进制当文本收进来、读不到就静默丢掉、read 抛出炸掉整次导出、
单文件/总上限失效、拿掉"0 命中≠干净"那句话、命中种类带原值、
成功文案说成"已验证干净"、复检审内存副本、复检失败只警告不作废、
读回复检失败算成功、写失败留半成品、复检清单只说 ok、
覆盖已存在的目录、缺布局时猜默认目录、空包当成功、
清单写入密钥库路径、包内文件名保留绝对路径、文件名长度上限失效、
默认候选不排序、默认候选不列出密钥库。

### 三轮"没咬"，三种不同的原因

| 探针 | 第一版瞄了什么 | 为什么没红 | 处置 |
| --- | --- | --- | --- |
| ⑱㉒ | `.slice(0, 60)` 长度上限 | 我给的 id 太短，**那道上限根本没被断言过** | 用例补一条长度断言；探针改瞄路径清洗，并**另立 ⑱㉕** 专打长度 |
| ⑱⑪ | `text.slice(0, 40)` | `text` 是 `redactText` 的**返回值**，原文已被替换，从它里面取不到原值——**探针意图对、变量错** | 改瞄 `bytes`（唯一还有原文的地方） |
| ⑱㉖ | 去掉 `name === SECRETS_FILENAME` 那一支 | `credentials.json` 同时被目录规则和 `credentials-*` 规则接住，删掉它**没有任何用例变红** | **不是改探针，是删掉那一支**——它本来就不是防线 |

⑱㉖ 是本文最值得记的一条：

> 一个删掉也不会让任何用例变红的判断，与不存在同形。

留着一个"看起来像防线、实际不改变任何输出"的分支，会让下一个人以为那里有保护，
从而不再在真正决定行为的地方加判断。这与 PRT-257 修复执行器里删掉的那道
死守卫是同一个形状（`PRT-257-repair-entrypoint.md` §6）。

## 5. 本模块**没有**解决的事

- **界面里没有按钮**。入口是 CLI（`--diagnostics=<dir>`），
  Workbench 上还没有导出诊断包的操作。属同一功能的前端一半。
- **`--diagnostics` 不在 Launcher 的启动流程里被调用**：它是一条独立的命令，
  不是"启动失败时自动出包"。自动出包需要先决定"包存到哪、留几份、
  什么时候清"——那是 PRT-709（日志轮转与磁盘保护）的范围，本批未做。
- **上限是定值**（8 MiB/文件、64 MiB/包、200 个文件），没有按可用磁盘空间自适应。
- **`business-db` 的排除意味着包不含业务数据**：这是有意的取舍，但也意味着
  纯数据库层面的故障排查拿不到现场。需要那类现场时应当走**单独设计**的
  最小导出，而不是把整库塞进诊断包。
