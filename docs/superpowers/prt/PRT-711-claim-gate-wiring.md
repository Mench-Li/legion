# PRT-711（后半）：把产品状态接到 Orchestrator 的认领决定上

> spec §6.3。「产品状态 → Orchestrator 行为」这张表，
> 在这一批之前**没有任何生产调用方**。

## §1 这一批要解决的问题

`product/runtime-state.mjs` 已经做全了 spec §6.3 那张表：六态总函数、
`mayClaimTasks`、`liftProductState`、`runtimeStatusReport`，30 例断言，
而且它自己那一行进度里就写着诚实边界：

> ⚠️ **本模块还没有调用方**——`mayClaimTasks`/`runtimeStatusReport` 判据完整
> 但 Orchestrator 的扫描循环尚未改成调用它，所以它是"可供接入"而非"已经接上"。

这句话本身就是这一批的全部理由：

> 一个「判据完整但没有调用方」的模块，
> 与一个「没实现的模块」，在真实运行里是同一个东西——
> 只不过前者在进度表上看起来是完成的。

当时的实际行为是：worker 只问「**我能不能执行**」（有没有 executor、阶段齐不齐），
从不问「**现在该不该执行**」。于是升级过程中、强制面没生效时、
Runtime 不可用时——只要引擎在、阶段齐，任务就会被领走并跑起来。

> 一个"引擎在、我就认领"的 worker，
> 与一个在升级过程中继续把任务领走并跑起来的 worker，
> 是同一个东西——只不过前者在"我能不能执行"这个问题上回答得完全正确。

## §2 接线结构

```
product/orchestrator/worker.mjs       ← 进程入口（保持"只有一层转发"）
        │  claimGateFromExecutor
        ▼
product/orchestrator/claim-gate.mjs   ← 判定：引擎状态 → 产品状态 → mayClaimTasks
        │
        ▼
orchestrator/worker/run.mjs           ← runWorkerProcess 把线插上
        │  createWorker({ claimGate })
        ▼
orchestrator/worker/main.mjs          ← tick() 里排在 hub.claim() 之前
```

**为什么判定逻辑不写在入口文件里**：入口自己的注释把「只有一层转发」写成设计约束
（清单冻结了入口路径，实现搬家不该动它）。判定住在 `claim-gate.mjs`，
入口只多一行 import 与一个参数。

**为什么是"从引擎状态推出闸门"的函数**（`claimGateFromExecutor`）而不是直接给一个 `claimGate`：
闸门要依据"引擎到底接上没有、自检过没过"定档，而这两件事要等 `executorProvider()`
（异步、可能被拒）跑完才知道。直接传 `claimGate` 的话，调用方就得在自己那一侧
把这段异步过程重做一遍。

### 两个容易搞错的地方

**① 闸门是函数，不是取值。** `tick()` 每轮重新问一次。
"正在升级""Runtime 变成不可用"都是**运行中**才发生的事；
只在启动时判一次，等于在升级开始的下一秒又开始认领。

**② 认不出来的处境不许落到 `ready`。** `ready` 是唯一会让 worker
领走任务的档。缺省档取 `unavailable`——不是"保守"，而是因为
"没问过"与"问过说可以"是两件事。

## §3 引擎状态 → 产品状态

| 执行引擎状态 | 产品状态 | 为什么 |
| --- | --- | --- |
| 已接线 | `ready` | 自检过了、强制面生效了，本进程具备全部能力 |
| 拒绝，码为 `EXECUTOR_SELF_CHECK_INCOMPATIBLE` | `incompatible`（经 `liftProductState`） | 强制面没生效。**进程都起来了不等于能力层生效了**（PRT-215） |
| 其它拒绝（缺宿主端口 / 接线错） | `unavailable` | 不是"不兼容"，是"现在干不了" |

判据用**执行引擎自己的回答**，不用推断。外部信号（`getOverrides()`）只可能把状态
**往上抬**（更保守）——这一点由 `liftProductState` 保证，调用方无法用它把状态"抬"成 `ready`。

## §4 闸门的行为纪律

| 情形 | 行为 | 为什么 |
| --- | --- | --- |
| 闸门说 `claim: false` | 不调用 `hub.claim()` | 闸门必须排在认领**之前** |
| 闸门**运行中**抛错 | **不认领** | *坏掉的判据不是通行证* |
| 闸门返回 `null`/`undefined` | **不认领** | "没给结论"不是"同意" |
| 要了闸门但**造不出来** | 退回**恒不认领** | 调用方的意图就是"要判定"，造不出来不能变成放行 |
| `claimGate` 传了个非函数 | **建实例就抛错** | *装了却从不被调用 = 没装* |
| **根本没要闸门** | 不装，照常认领，但状态写 `not-installed` | 见 §4.1 |

### 4.1 "没有闸门"的两种情形必须分开——以及一次真实的回归

这一节记录本批**自己犯的错**，因为它值得留下。

最初把"调用方没提供 `claimGateFromExecutor`"也兜底成"恒不认领"，
理由是那条我很喜欢的话：

> 一个"闸门没接上，所以照常认领"的兜底，
> 与一个"升级期间照常认领"的兜底，是同一个东西。

**这个兜底直接打挂了 CI。** `orchestrator/worker/run.mjs` 是**通用外壳**，
除了产品入口还有别的正当调用方——`orchestrator/worker/scripts/kill-drill-worker.mjs`
（强杀演练，PRT-312）调用它时不给闸门。于是那个演练的 worker
**静默地什么都不认领了**，整个套件卡到 300 秒被 CI 杀掉：

```
FAIL run-kill-drill: 套件超过 300s 被杀（已存在泄漏句柄或死锁）
✖ ① 在外部写边界**之前**强杀 worker：任务不丢… (15159ms)
```

> 一个"因为没接线所以什么都不干"的兜底，
> 与一个"接线漏了但看不出来"的兜底，是同一个东西——
> 只不过前者的表现是产品静默地不工作，而后者是产品静默地工作太多。

修法是把纪律**拆成两半，各自落在能负责的那一层**：

| 纪律 | 落点 | 怎么钉住 |
| --- | --- | --- |
| **产品不许没有闸门** | `product/orchestrator/worker.mjs`（产品入口，总是装一个） | 结构性断言：入口必须引入并传 `claimGateFromExecutor`（61⑨） |
| **要了闸门就得真的有** | `orchestrator/worker/run.mjs`（通用外壳） | 闸门构造失败 → 恒不认领（61⑥） |
| **没要闸门这件事看得见** | 状态文件 `claimGateMode=not-installed` | 61④ |

产品入口是"总会有闸门"的那一层，所以这条纪律放在那里；
通用外壳不该因为某个调用方没要闸门就自己停手。

### 4.2 "没装闸门"必须可见

状态文件里 `claimGateMode` 是 **三态** `installed` / `not-installed`，而不是布尔：

- `not-installed` 与 `installed ∧ true` 在"**为什么 claimed 一直是 0**"这件事上
  给出的答案完全不同；
- 合成一个布尔，等于把"没装闸门"与"闸门放行了"写成一个值——
  而那正是这块最容易被读错的地方。

`claimGate` 字段（最近一次裁决）里带的是**产品状态**而不是本进程状态：
运维要能一眼看出"不认领"是**产品级的决定**，不是本进程的故障。
`claim-blocked` 的日志文案也显式把运维推向产品状态（是否在升级 / Runtime 是否不可用），
而不是让他们去查网络或执行引擎。

## §5 验证

### 5.1 套件

- `orchestrator/worker/claim-gate.test.mjs`（**13 例**）：接线本身。
- `orchestrator/worker/worker.test.mjs`（34 → **38 例**）：`runWorkerProcess` 端到端接线。

最要紧的一条判据不是"闸门被调用了"，而是 **`hub.claim` 一次都没被调用过**：

> 一个"先认领再问闸门"的实现，
> 在"闸门被调用"这个计数上看起来是完全正确的。

### 5.3 探针过程本身暴露的三个问题（如实记录）

**① 锚点因 CRLF 而一次都没命中。** 61② 与 61⑥ 首轮报"锚点命中 0 次"。
仓库里有些文件是 CRLF（`orchestrator/worker/run.mjs`），有些是 LF；
脚本里模板字面量写的多行锚点含 `\n`，对 CRLF 文件**永远命中不了**。
危险之处在于**它的表现像"探针没效果"**，很容易被误读成"这条判据测不出来"。
现已在探针脚本里显式两种都试（`findOccurrences`），
并且汇总里把"锚点没命中"与"补丁无效"**分开报**。

**② 一条探针根本红不了，暴露的是断言太弱。** 61⑦ 原版把闸门里的
`o.satisfiedCapabilities ?? null` 改成 `?? []`——但
`mayClaimTasks('degraded', { satisfiedCapabilities: [] })` 同样返回 `claim: false`（长度 0），
所以 fail=0。原来只断言 `claim === false`，而 `null`（"没给判据"）与
`[]`（"给了但一个都没满足"）都满足它：

> 一个只断言布尔值的用例，
> 与一个"接线漏了也不报"的用例，是同一个东西——
> 只不过前者看起来测了 degraded 这一档。

测试补上"**断言理由的出处**"（`assert.match(noInfo.reason, /不给判据不等于判据都满足/)`）——
否则"调用方根本没接线"会被伪装成"接线了但没有能力可用"；
探针改瞄一个真的接线缺陷（61⑦，fail=4）。

**③ 结构性断言会被注释骗过去。** 61⑨ 首轮 fail=0：它把产品入口里的
`claimGateFromExecutor,` 注释掉，而我的正则**照样匹配**——因为那几个字
**还在注释里**。这是"把参数注释掉"这种"看起来删了、其实没删"的改法的真实漏洞。
修法：断言前先把注释剥掉（**先剥注释再匹配**），剥注释后 61⑨ fail=1。

## §6 诚实边界

- **`getOverrides()` 今天由调用方给**（默认 `() => ({})`），
  **没有**从 Launcher 或升级流程实时接过来。也就是说：
  **"正在升级"这一档在真实部署里还没有人把它置为 `true`。**
  闸门的机制、判定与兜底都在，缺的是那个置位的人——
  那是升级协调器那一侧的线（PRT-809/810）。
- `degraded` 的 `satisfiedCapabilities` 同理：判据在，喂给它的人还没有。
- `incompatible` 的真实来源仍缺"组合观测"的生产者（`COMPOSITION_UNOBSERVED`），
  当前只能由执行引擎自检给出。
- **闸门只在本进程内生效**：它管的是"这个 worker 认不认领"，
  不是服务端的强制。服务端的资格判定在 `team-hub/claim-policy.mjs`（PRT-304），
  两者是不同层的闸：一个在客户端决定"我要不要问"，一个在服务端决定"问了给不给"。
- **通用外壳（`runWorkerProcess`）今天仍然允许"没有闸门"**：这是刻意的（§4.1），
  代价是"产品入口之外的调用方没有闸门"这件事只由状态文件与告警暴露，
  没有被强制。产品入口那一条由结构性断言钉住。
- `renewLeasesIndefinitely` 仍没有消费者。
- 界面上还没有这张表的状态条。
- 本批**没有**改动 `product/runtime-state.mjs` 的任何判定——那 30 例仍然覆盖判定本身。
