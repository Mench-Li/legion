# PRT-712 最小系统指标（本地展示）

> spec §6.6 列了九个指标：队列深度、最老待办年龄、活跃 lease、租约过期率、
> Attempt 重试率、Dead Letter 数量、Runtime 可用率、模型错误率、升级结果。
>
> `product/metrics.mjs` 是它们的**读数与计算**；本地展示是 `renderMetrics`。
> 「商业 Alpha 默认仅本地展示」——远程那一半（显式选择加入的脱敏心跳）是 PRT-713。

## 1. 唯一真正要紧的那条纪律：「读不出来」不许显示成 0

一个仪表盘把读不到的指标画成 0，与一个把「着火了」画成绿色的仪表盘，
在「值班的人会不会去看一眼」上是同一个东西——**而且前者更糟**：
它看起来是**有读数**的，所以没人会去怀疑它。

> 一个把「我没有数据」渲染成 0 的仪表盘，
> 与一个把「一切正常」渲染成 0 的仪表盘，
> 在「值班的人能不能看出出事了」上是同一个东西。

所以每个指标有**三种**结果，在数据结构上就是三个不同的东西：

| 结果 | `value` | `display` | 含义 |
| --- | --- | --- | --- |
| 有读数 | 有限数（**包括真的 0**） | `0 个` / `3.0%` | 读到了 |
| 读不出来 | `null` + `reason` | `—` | 不知道；`reasonText` 说明为什么 |
| 不适用 | `null` + `reason: metric-not-applicable` | `—` | 这个指标此刻没有意义 |

「队列深度 0」与「队列深度读不出来」在数据结构上就分开了，
**渲染层没有机会把它们混起来**——这就是为什么 `known` 与 `display`
是模块自己算的，而不是交给调用方去 `v ?? 0`。

## 2. 比值的分母为 0：这是同一个坑的另一半

```
0 次失败 / 0 次尝试 = ?
```

填 `0%` 说的是「没有失败」；而事实是「**还没有观察过**」。
这正是「上线第一天，错误率 0%，一切正常」这句话的来历。

分母为 0 一律返回 `null`，`reason` 是单独的 `metric-no-observations`
（**不是** `metric-no-data`：一个是「还没有观察过」，一个是「读不到」），
并且文案要写明它**不是什么**。

容易出现的一个过头修正是「把 0% 一起防掉」——分子为 0 而分母不为 0 时
那**是**一个真的 0%，有用例专门钉住这一点。

另外两种情况也返回 `null` 而不是编一个数：

- **分子大于分母**：两个读数来自不同的时间窗或不同口径。硬算出 `>100%`
  会让人以为系统疯了，填成 `100%` 则是替它编一个数。
- **读数不是有限数**：`NaN` / `Infinity` / 字符串 / 布尔都算读不出来。
  `NaN` 尤其危险——它会一路静默传播。

## 3. 「此刻不适用」是第三种结果

队列为空时，「最老待办年龄」显示 `0 毫秒`会让人以为**刚有任务进来**。
它是不适用，不是 0。

**这一条还有一个更隐蔽的变体，是本轮量出来的真缺陷**：判据本身读不出来时怎么办？
`queue-depth` 未知 → 「队列为空吗」无从判断 → 但原来的实现会因为
`null === 0` 为假而**落到"有读数"那一支**，照样报 `0 毫秒`——即
「有一个刚进来的任务」。

修法是给定义加 `dependsOn`：判据依赖的字段读不出来时，这个指标也是未知
（`reasonText` 会说明它依赖谁）。**一个读数不明时替它编一个 0，
与一个把火灾报成绿灯的仪表盘是同一件事。**

## 4. 类别值不猜

「升级结果」是 `state` 类：`succeeded` / `failed` / `rolled-back` / `never-run`。
一个没见过的取值（比如 `partially-succeeded`）**不翻译成最接近的那一个**——
猜出来的「升级结果：成功」会让值班的人据此收工。

同样地，「读不到升级结果」与「从未执行」是两件事，前者是 `null`。

## 5. 一个坏掉的读数点不该让整个仪表盘消失

`readMetrics` 逐个容错：某个读数点抛错，**只有那一个**指标变成未知，
其余照常。那会让值班的人连「别的指标是好的」都看不到。

失败的读数点有**单独的诊断码** `metric-read-failed`，与「没有数据」
（`metric-no-data`）分开：**一个是坏了，一个是空的。** 排障时这两件事
的处置完全不同。

「此刻不适用」**不算告警**——那是正常状态，报出来只会让日志变吵。

## 6. 摘要只给数（PRT-713 的接缝）

`metricsSummary` 是给心跳用的：只取数与受控类别值，
**不含标签、路径、任务名**。一个「顺手带上上下文」的心跳是数据外流
最省事的通道：不需要谁犯错，只需要它存在。

读不出来的指标**不进**摘要，而不是填 0——远端收到一个 0 会把它当成真实读数，
而这正是本模块通篇要防的那件事。摘要带 `observedMetrics` / `totalMetrics`，
远端因此知道这份摘要有多完整。

## 7. 九个指标的计算口径

| 指标 | 分子 / 分母（比值类） |
| --- | --- |
| 租约过期率 | `leasesExpired` / `leasesTotal` |
| Attempt 重试率 | `attemptsRetried` / `attemptsTotal` |
| Runtime 可用率 | `upMs` / `observedMs` |
| 模型错误率 | `modelErrors` / `modelCalls` |

`computeMetrics(snapshot)` 是**纯函数**：算错了和读错了是两件事，
混在一起就分不清该修哪一头。`snapshot` 不会被改动，有用例钉住。

## 8. 变红验证：20 处，20 处红

重点：★ 缺读数时填 0 / 未知也渲染成 0 / 分母为 0 时算出 0% /
分子大于分母时截成 100% / 空队列时年龄报 0 毫秒 /
**判据依赖的字段未知时照样报读数** / 一个读数点抛错时整个仪表盘失败 /
摘要把未知指标填成 0。

第 ⑨ 处（`dependsOn`）不是"探针写错了"，而是**探针量出了一个真缺陷**：
它是在写测试时先红的，然后才去修实现。这与前面几批里
「补断言 → 发现实现没做到」的顺序一致。

## 9. 本批**没有**解决的事

- **没有真实的读数点**：`readMetrics` 接受一个 `source` 对象，而把
  team-hub 的表（`run_attempts`、`tasks`、`budget_reservations` …）
  接成九个读数点**还没有做**。当前模块是「读数与计算」，
  **读数的来源仍然是空的**。
- **没有 HTTP 路由**：spec §6.6 的「本地展示」最终要有一个
  `/api/metrics`，本轮没有加（加路由会动 `baseline-snapshot` 的路由基线）。
- **界面里没有仪表盘**：`renderMetrics` 给出的是文本行，
  Workbench 还没有把它渲染出来。
- **升级结果没有生产者**：`upgrade-result` 现在只能由调用方传入，
  产品里还没有一个升级流程会写它（与 PRT-711 的 `upgrading` 是同一个缺口）。
- **租约过期率与重试率的窗口口径未定**：当前是「调用方给两个累计数」，
  「过去 N 分钟内的比率」需要时间窗，而 `metric-bad-window` 这个码
  目前**没有任何调用方会产生**——它是为将来留的，这一点要写清楚，
  免得被读成"已经支持窗口了"。
