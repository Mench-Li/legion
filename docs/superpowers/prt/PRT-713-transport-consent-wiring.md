# PRT-713 收尾　真实的发送通道 + 同意采集 + Launcher 接线

> 状态：✅ 完成（2026-09-13）
> 依赖：PRT-713（心跳本体 `product/heartbeat.mjs`）、PRT-709（Launcher 接线方式）、PRT-710（配置与诊断纪律）
> 对应 spec：§6.7「默认关闭、显式选择加入的脱敏健康心跳」

## 0. 这一批补的是三条**互相独立**的缺口

PRT-713 本体的三道闸（策略 / 代际 / 已停掉）做得很细，命中率也高（变红 22/22）。
它的行里留着五条诚实边界，而其中三条各自都是一整条没修的路：

| 边界（原文） | 实际后果 |
|---|---|
| 「没有真实的 transport——它是注入的 `async (payload) => any`」 | **发不出去任何心跳** |
| 「没有同意流程（`consent` 由调用方传入……PRT-707 向导是它的位置）」 | "没同意就不发"那道闸**永久关闭** |
| 「没有接进 Launcher」 | 装配那个模块的**只有测试** |

而这三条有一个共同点——**它们都不让任何一条用例变红**：

- 注入式 transport 让所有"什么不许发"的用例都能跑绿；
- 一道永远拦着的闸让"没有同意就不发"也跑绿；
- 一个没有生产调用方的模块让全部单测跑绿。

> 一个"所有闸门都被测过、但门后没有路"的心跳，
> 与一个"真的能发出去"的心跳，在测试报告上是同一个读数——
> 只不过前者永远不会因为网络、超时、证书而失败，
> 所以它**也不会**因为那些原因被修好。

另外两条边界（`HEARTBEAT_INVALID_ENDPOINT` / `HEARTBEAT_PAYLOAD_REJECTED`
没有调用方、`timeoutMs` 没有生效）随这一批一起关掉。

## 1. 交付

### 1.1 `product/heartbeat-transport.mjs`（新）— 真实的 https 通道

| 导出 | 职责 |
|---|---|
| `MAX_PAYLOAD_BYTES` | 4096。不是"防大载荷"，是**允许名单被加宽时立刻失败** |
| `checkEndpoint(endpoint)` | 只认 `https:`，**这一层自己判** |
| `checkPayload(payload, max)` | 返回**那一串字节**，不是"校验过的对象" |
| `createHttpTransport(deps)` | 真的发 POST；`requestImpl` 可注入 |

三条纪律：

1. **`timeoutMs` 真的生效。** 用 `setTimeout` 按**墙钟**算，不用 `req.setTimeout`
   （后者的语义是套接字空闲超时，一个"连上了但不收响应体"的服务端可以让它永不触发）。
   超时先 `destroy()` 再 reject——不 destroy 的话套接字挂到进程退出，
   而"每 6 小时一次"会变成一堆僵尸连接。
2. **不重试。** 与 `createHeartbeat` 的"不会重试，等下一个周期"一致；
   这里再重试一次的话，"关掉"之后在路上的重试就是一个新的泄漏口。
3. **`https` 是这一层自己判的**，不假设调用方已经校验过——
   一道依赖"前面某行校验已经跑过"的闸，在有人把那行挪走的下午就失效了。

### 1.2 `product/heartbeat.mjs`（改）— 保留 transport 的具体码

`sendOnce` 的 catch 原来写死 `SEND_FAILED`，于是新产生的
`INVALID_ENDPOINT` / `PAYLOAD_REJECTED` 会在到达用户之前被抹成同一句话。
三种原因的**处置完全不同**：配错了（用户改一次）/ 代码错了（开发者动手）/
网络的事（下个周期再说）。

> 一个把"你配错了"和"我们发不出去"报成同一句话的上报通道，
> 会让用户反复检查自己那份没有问题的配置。

只透出**已知**的码（`Object.values(HEARTBEAT_CODES).includes`），
不认识的仍然落到 `SEND_FAILED`——否则任意异常码会变成用户可读的原因。

### 1.3 `product/heartbeat-consent.mjs`（新）— 同意记录的采集

产品里**唯一**能产生"同意"这个值的入口。四个状态分开：

| 码 | 含义 |
|---|---|
| `CONSENT_NEVER` | 从未同意过 |
| `CONSENT_REVOKED` | 同意过，后来撤回了 |
| `CONSENT_UNREADABLE` | 记录读不出来（损坏/权限） |
| `CONSENT_INVALID` | 记录不合法（缺 `who`/`at`） |

**为什么用文件 + 显式命令，而不是一个配置项**：同意是"谁在什么时候同意了"
这件事的记录，必须来自用户在某个具体时刻做的一个动作。放进配置文件有三个问题：

1. 配置文件会被复制、同步、模板化。一个跟着配置走的同意，到了第二台机器上
   就变成"这台机器也同意了"，而**没有人在那台机器上同意过**；
2. 它是可编辑的，于是"同意"退化成"这段文本存在"；
3. 撤回会变成"删掉一行 YAML"，而那与"从来没同意过"在记录上无法区分。

所以**撤回是写下一条新记录**（`revoked: true` + `revokedAt`），不是删文件：

> 一份被删掉的同意与一份从来没有过的同意，在事后排查时是同一个东西。

写是**原子**的（先写 `.tmp-<pid>` 再 rename）：写到一半断电会留下半截 JSON，
读出来是 `UNREADABLE`——用户**刚刚做过的一次同意**变成了"读不出来"。

### 1.4 `product/launcher/heartbeat-wiring.mjs`（新）— 接线

- `wireHeartbeat(deps)` → `{ok, heartbeat, policy}` 或 `{ok:false, code, message}`，**不抛**；
- `attachHeartbeat(wired)` → `{start, stop, status}`；两个动作都**不抛**；
- `createLauncherHeartbeat(deps)` → Launcher 只调这一个。

**consent 只认这台机器上的记录**：`config.mjs` 里根本不读 `heartbeat.consent`，
所以"配置说开着"与"这台机器同意过"是两件必须同时成立的事。

### 1.5 `product/config.mjs`（改）— `heartbeat.*` 四个键

`enabled` / `endpoint` / `intervalMs` / `timeoutMs`。此前仓库里**一个键都没有**，
于是这条任务唯一对外可见的入口是一行代码注释。

- 不补默认值（补了就有两份默认值，"哪一份生效"会成为排查问题）；
- **不读 `consent`**（见上）；
- 不合法的值**不进**策略，由 `validateHeartbeatPolicy` 去报——
  一个被静默纠正的配置，用户会以为它生效了。

### 1.6 CLI（改）

| 参数 | 作用 |
|---|---|
| `--heartbeat-consent=<who>` | 记录同意（谁） |
| `--heartbeat-revoke-consent` | 撤回同意（**与上面同用**，需要署名） |

同意命令排在**布局校验之前**：撤回是一个安全动作，
而"配置坏了所以撤不回"会让用户被困在一个他不想继续的选择里。

### 1.7 Launcher（改）

- 装配并起心跳排在**就绪之后**——在产品其实没起来时就开始发心跳，
  等于向服务端报告一个**不存在的运行实例**，而那种假信号比没有信号更坏；
- `stop()` **连带停掉心跳**（含 `supervisor === null` 那条早退路径）；
- `status().heartbeat` 与 `allDiagnostics()` 都带上心跳的读数；
- 装配失败**不影响启动**，但一定留一条诊断。

## 2. 本批真的踩到的五个坑

### 2.1 `attachHeartbeat` 把**累加器本身**冻住了

```js
diagnostics: Object.freeze(diagnostics),   // ✗ 冻住的是累加器
```

于是返回对象一造好，后面每一次 `start()`/`stop()` 里的 `note()` 都在 `push` 上抛
`TypeError: Cannot add property N, object is not extensible`。

这个 bug 的坏形态特别隐蔽：`attachHeartbeat()` 本身**不抛**，
装出来的对象看起来完全正常；它只在**第一次 start 或 stop** 时炸。

> 一个"在装配时一切正常、在用户按下启动时才炸"的字段所有权问题，
> 与一个正确的实现，在代码审查里长得一样。

### 2.2 `writeConsent` 的默认 fs 里漏了 `readFileSync`

撤回路径要先把当前记录读回来，于是**撤回永远失败**，报的是
「同意记录读不出来：`io.readFileSync is not a function`」——
一句关于文件系统的抱怨，而真正的原因是这次调用的依赖清单不完整。
更坏的是它**只影响撤回**：授予同意走另一条路，一切正常。

> 一个"只有撤回会失败"的同意流程，
> 与一个"同意之后撤不回来"的同意流程，在用户看来是同一个东西。

### 2.3 端点检查**排在另一道更宽的闸后面**（死代码）

`if (!endpointOk)` 原来排在 `validateHeartbeatPolicy` 之后，而策略校验自己
就会以 `BAD_POLICY` 拒掉同一个端点。断验证 ⑤⑩ 把它改成 `if (false)`：
**套件全绿**。

> 一个"永远排在另一道更宽的闸后面"的检查，
> 与一个不存在的检查，在"它到底拦不拦得住"上是同一个答案——
> 只不过前者的代码看起来是有的，所以没有人会去补。

已把端点检查**前移**，于是它真的会拦，而且给出的是**精确**的 `BAD_ENDPOINT`。

### 2.4 Launcher 的三条用例是**空转的**

夹具写的是 `installDir: dir` 且把 `data`/`ws`/`cache`/`log` 都放在 `dir` 下——
全都在安装目录**之内**，preflight 以 `WRITABLE_DIR_INSIDE_INSTALL_DIR` 挡下启动，
`start()` 根本没走到心跳那一段。而断言写在 `if (started.ok === true)` 后面，
所以用例是**绿的**。

断验证 ⑤⑮/⑤⑯/⑤⑰ 把 Launcher 里那三行分别改坏，**套件全绿**——这一幕才暴露出来。

> 一个"在代码根本没执行到的地方仍然断言通过"的用例，
> 与一个真的守住了那个行为的用例，在报告上是同一个读数——
> 只不过前者是在**什么都没跑**的时候绿着。

现在夹具用独立的 `install/` 子目录 + 合法密钥库路径，并且**强制断言 `start()` 成功**。

### 2.5 两处断言太宽 / 指错对象

- **端点那条**原来写 `[BAD_ENDPOINT, BAD_POLICY].includes(r.code)`，
  于是把端点检查整个删掉用例**照样绿**。

  > 一个"两码皆可"的断言，与一个"什么都没断言"的断言，
  > 在被检查的那道闸被删掉时是同一个读数。

- **"配置里没有 consent"那条**原来断言的是原始 `merged`——而 `merged` 是
  合并后的原始配置，当然包含文件里写的每一个键（连拼错的也在）。
  拿它判"有没有偷渡"是**判错了对象**；真正的契约是**派生的 `heartbeatPolicy`**。

  这个断言还有个坏后果：它**无论实现对不对都会红**，于是它会被删掉，
  而真正要守的那条纪律就跟着一起没了。

另外两个探针的问题（㊽ 编译不过 → 无效；⑤⑤/⑤⑰ `expectRed` 指错分支/指错用例）
都是**探针自己的错**，读数分别是"无效"与"没咬住"，已逐一更正。

## 4. 诚实边界

1. **没有跑过真实 HTTPS 请求。** 网络部分注入的是 `requestImpl`（套接字那一层），
   而 URL 解析、超时定时器、`destroy`、排空响应、状态码判定、不重试这些
   **全部真的被执行**。但"这台机器能不能连上某个真实端点"从未被验证过。
   （真跑一次真实网络请求的用例是**不可靠的**，而不可靠的用例会被跳过或删掉，
   于是"能发出去"这件事又变回没人守。）
2. **没有界面。** 同意只能通过 CLI 两个参数采集；`consent` 的采集点
   仍然是 PRT-707 向导该有的位置，向导本身没有 UI。
3. **`purpose`/`timeoutMs` 之外的空缺照旧**：`timeoutMs` 现在真的生效了，
   但它只覆盖**单次发送**，不覆盖 DNS/TLS 握手之外的连接建立阶段
   （那部分被 `request()` 自己处理，没有单独的闸）。
4. **一次失败只记一条诊断，不重试也不排队。** 下一个周期（默认 6 小时）
   才会有下一次尝试。产品没有"发送队列"，所以短暂的网络抖动等于丢掉一个周期。
5. **同意记录的署名不可验证。** `who` 是用户自己敲的字符串，
   产品不校验它是不是一个真人或一个有效身份——它只是"某个时刻有人写了这个名字"。
6. **没有并发保护。** 两个进程同时写同意记录时，原子 rename 保证文件不会是半截，
   但**后写的那次赢**，而先写的那次不会知道自己的记录被覆盖了。
7. **撤回不撤销已经发出去的心跳。** 撤回只保证此后不再发；
   已经离开这台机器的数据产品无法收回（也从未声称能收回）。
8. **心跳只接在 Launcher 的 `start()` 成功路径上。** `restart()`/熔断重试
   那条路不重新装配（它走的是 `start()`，所以实际上会重新装配并启动——
   但这一点没有专门的用例守住）。
