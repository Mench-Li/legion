## 1 一句话

把"保留日志/事件/产物"与"卸载时区分删程序、留数据、彻底删"从一个**返回 `ok` 的
动作**，变成一份**由磁盘上实际存在什么算出来的**去留清单。

---

## 2 为什么这两条任务共用一份台账

它们问的是同一个问题：**这份数据属于哪一类，因此该拿它怎么办？**
保留策略按类定上限，卸载按类定去留。

> 一个「保留策略按一张类表、卸载按另一张类表」的实现，
> 与一个「某一天卸载会删掉保留策略承诺保留的东西」的实现，是同一个东西——
> 只不过前者在任何单独一张表上都是自洽的。

所以 `data-classes.mjs` 是唯一的分类权威：9 个类，每类的 `onUninstall` 动作
**没有默认值**——一个"忘了写去留"的类会变成"卸载时什么都不做"，
而那与"保留"不可区分。

---

## 3 PRT-904：三个安静的坑

保留策略要同时表达**时间**与**容量**两个维度——只有时间时一次尖峰能写满磁盘，
只有容量时一条安静的旧日志会永远留着。

### ① 只对一个类做容量核算，却把结果当成总用量

> 一个「只对一个类做容量核算、却把结果当成总用量」的策略，
> 与一个「另外两类没有上限」的策略，是同一个东西——
> 只不过前者在报表上看起来是有上限的。

`usageTotal.bytes` 是**三类之和**，且 `usageTotal.unbounded` 会列出没有上限的类。
`assertRetentionBounded` 拦住"缺席"（忘了配）与"两维都不设上限"两种情况，
但允许显式 `null`（故意的）。探针 53⑧ 把总量改回"只算第一个类"→ 红。

### ② 删掉最新而不是最旧

> 一个「删掉最新日志来降低占用」的保留策略，
> 与一个「把排障需要的那部分删掉、留下最没用的那部分」的策略，是同一个东西——
> 只不过它在"用量是否下降"这个指标上是完全成功的。

排序写死为**最旧的在前**。探针 53① 把比较反号 → 3 条用例红。

### ③ ★ 删掉还被进行中 Run 引用的产物 —— **这是我第一版的真实 bug**

引用检查最初**只写在容量那一轮**，漏了**时间**那一轮：

```js
// 第一版（错）
if (p.maxAgeDays !== null) {
  for (const e of list) {
    if ((e.atMs ?? 0) < cutoff) { doomed.add(e.id); ... }   // ← 没有引用检查
  }
}
```

于是"超过 30 天的产物"照样被删，**哪怕它正被一个进行中的 Run 用着**。
失败会在那个 Run 的之后某一步出现，而原因与保留策略之间隔了很远。

> 一个「在两条删除规则里只有一条做了引用检查」的保留策略，
> 与一个「按时间清掉的正好是还在用那个」的策略，是同一个东西——
> 只不过它在容量那一条规则上是完全正确的。

用例把它打红了。修复：抽出 `isPinned`，两条规则共用；被钉住的条目**保留并报
`retention-pinned-by-active-run`**（"为什么这一条没被清掉"必须可解释，
否则下一个人会以为时间规则没生效）。探针 53② 就是把第一版的错改回去 → 红。

**另外**：删无可删仍然超限时报 `CAP_UNREACHABLE`（带 `remainingBytes`/`capBytes`），
不假装成功。探针 53⑤。

## 4 PRT-908：拒绝猜

判据**不接受"要删什么"作为输入**，而接受 `stores`——**磁盘上实际存在什么**。

因为"按清单删了几个路径、返回 ok"的失败方式是**漏掉一个落点时照样返回 ok**：

> 一个「按清单删了几个路径、于是报告成功」的卸载，
> 与一个「漏掉了 team-hub 的 team.db 与 whiteboard 的 rooms 目录、
> 于是数据还在磁盘上」的卸载，是同一个东西——
> 只不过前者在返回值上看起来是彻底干净的。

产出三类，而不是一类：

| 列表 | 含义 |
| --- | --- |
| `remove` | 这次要删的 |
| `keep` | 这次明确留下的（**逐条列出**） |
| `refuse` | 认不出类别、因此**拒绝**动的 |

`refuse` 是关键：认不出的落点，删它是数据丢失，留它是不彻底。
本模块选择**保留并报出来**——*"少删了一个"可以补救，"误删了"不能*。
未知卸载模式同样**什么都不删**（不猜 `purge`、也不猜 `program-only`）。

### 4.1 ★ "保留数据"与"把凭据留在磁盘上"是两件事

本仓库的布局让这件事**可做**：`secretsFile` 在 `productHome/.secrets/` 下，
**不在** `dataDir` 下（`product/paths.mjs:212`）。

| 模式 | 删 | 凭据 |
| --- | --- | --- |
| `program-only` | program, cache | **保留**（报表给警告） |
| `keep-data` | program, cache, **secret** | 删除 |
| `purge` | 除 workspace 全部 | 删除 |

三种模式**对凭据的表态必须不同**，且三种模式的实际删除集合**两两不同**——
台账自检里钉住这一点。*三个名字指向同一组动作，就等于只提供了一种选择。*

**分类器必须先判密钥、再判容器**：否则一个把密钥库配在 `dataDir` 下的用户
会被归成"业务数据库"，于是 `keep-data` 会**静默地留下凭据**。探针 53⑫ 专打这一条。

**工作区在任何模式下都不删**（台账动作 `never`）。两个表打架时（模式表要删、
台账说永不删）**以更保守的为准**，并报 `PROTECTED`。探针 53⑭。

## 6 ⚠️ 诚实边界

1. **本模块是判据，不是执行。** `planUninstall` 返回一份计划，
   `planRetention` 返回一份删除清单——**没有任何本仓库的代码路径会真的删文件**。
   真正的删除由安装器（PRT-809 卸载 / PRT-806 备份）执行，那部分不在本批。

2. **`stores` 是调用方给的。** "磁盘上实际存在什么"必须由调用方枚举。
   一个**不完整**的 `stores`（比如漏了 whiteboard 的 `WB_ROOMS_DIR`）
   会让 `purge` 报告"删干净了"，而本模块**没有机制发现它漏了**。
   这与 PRT-614 里 `legacyHighRiskTools` 是同一个边界——**那是信任边界，不是检查**。
   `NO_STORES` 只拦得住"一个都没找到"，拦不住"少找了几个"。

3. **不删工作区是刻意的一刀切。** 若用户把 workspace 配在 `dataDir` 下，
   而某次 `purge` 期望"数据全清"，工作区**仍然会留下**。
   这是保守方向（宁可留），但用户可能不喜欢——需要在 UI 上说清。

4. **保留策略没有真的执行者。** 没有调度器、没有定时任务、没有容量采样器。
   `planRetention` 是一个纯函数；谁在什么时候调用它、从哪拿到 `entries` 与
   `activeRefs`，本批**未接**。因此"日志不会写满磁盘"这句话目前**不成立**。

5. **`activeRefs` 由调用方给。** 一个过期的 `activeRefs`（Run 已结束但仍被列为
   活跃）会让产物永远清不掉；反过来一个缺失的引用会让产物被提前删掉——
   后者更糟。当前只依赖调用方。

6. **未覆盖**：PRT-905（备份/恢复/数据导出入口）、PRT-903（隐私与数据处理说明）、
   PRT-906（崩溃报告授权与脱敏）、PRT-907（诊断与故障处置手册）、
   PRT-909（发布检查清单）、PRT-910（内部与金丝雀验证，需真实用户项目）。
