# PRT-905：数据导出入口（备份 / 恢复 / 导出是三件事）

**spec**：§10 line 988
**状态**：✅ 已交付（判据与清单；写包见 §6）
**证据**：`.ci/prt-905/`

---

## 1 一句话

备份、恢复、导出被当成一件事的实现，会产出"一个 `.db` 文件被叫做导出"。

> 一个「把数据库文件复制一份」的导出，
> 与一个「用户拿到一个打不开的 .db」的导出，是同一个东西——
> 只不过前者在"导出成功"这个返回值上是完全正确的。

---

## 2 三个不同的目标

| | 目标 | 形态 |
| --- | --- | --- |
| **备份** | 能**原样恢复** | 字节保真、含 WAL 与索引、只有本产品打得开 |
| **恢复** | 能**回到某一时刻** | 内部机制 |
| **导出** | 能**被别人读** | 稳定 schema、通用格式、自描述 |

备份与恢复已由 `product/upgrade/backup.mjs`（PRT-806/812，阶段 8）实现。
本模块（`product/lifecycle/data-export.mjs`）补**第三件**。

**核心判据**：导出条目必须是**可移植格式**。

| 可移植（导出） | 不可移植（备份） |
| --- | --- |
| `json` / `ndjson` / `csv` / `text` | `sqlite` / `db` / `binary` / `wal` / `shm` |

两个集合**不相交**，有专门用例钉住。

---

## 3 ★ 四个会安静出错的坑

### 3.1 「导出成功」= 文件写出来了

写出了文件、但里面有密钥、或有别人的数据、或格式只有本产品能读——
这三种"成功"对用户是三种不同的伤害，而返回码是一样的。

### 3.2 导出会顺手改一下源

最常见的一次是"为了导出一致快照，先 checkpoint 一下 WAL"——
那是**对运行中的产品做了一次写操作**，而用户以为导出是只读的。

> 一个「为了导出得干净而先动一下源」的导出，
> 与一个「导出动作本身破坏了正在运行的实例」的实现，是同一个东西——
> 只不过前者的动机是好的。

所以 `openedForWrite === true` 的落点**直接拒绝**，且理由里写明这条动机。

### 3.3 部分导出不报

某一类因为权限/格式导不出来，静默少给一个类——用户以为拿到的是全部。

**工作区**是这一条的实例：默认不导出，**但必须报出来**。

> 静默漏掉一个类与故意排除一个类，对用户是不一样的。

`exclude`（program / cache 是**刻意**排除的）**不报** finding——
否则会把"设计决定"变成噪音；`confirm`（workspace）**必须报**。

### 3.4 没有清单的导出包

> 一个「把一堆 JSON 打个 zip」的导出，
> 与一个「接收方需要猜每一份文件是什么」的导出，是同一个东西——
> 只不过前者在文件数量上是完整的。

清单必须自描述：`format` + `productVersion` + `schemaVersion` + 逐类计数 + 条目数 + 每条目的类别/形式/哈希。

`assertExportReadable(manifest)` 的视角是**"我不是 Legion，我拿到一个 zip"**——
这正是"导出"这个动作的全部意义所在。

## 4 ★ 两张表必须覆盖同一批类

与 PRT-904/908 同一主题：导出/卸载是**两张不同的表**（一个问"要不要删"，
一个问"要不要、以什么形式交给他"），但必须覆盖**同一批 9 个类**。

漏掉一个类，那个类的数据就会在某一天**无声地不出现在导出包里**。
`DATA_EXPORT_CHECKED` 双向核对（漏报与多报都报），并逐条校验
handling 合法、有理由、`portable` 类真的声明了可移植格式。

**密钥类的处置必须是 `never`**——自检单独钉住这一条。

### 5.1 ★ 用例抓出来的真缺陷：导出体积

`counts.bytes` 第一版把 `reference-only`（产物）的字节也算进去了。
测试 `⑧` 用 `mk({bytes:100})` + `mk({classId:'artifact', bytes:10**9})` 断言
`bytes === 100`，实际得到 `1000000100`。

> 一个「把不复制的东西也算进体积」的读数，
> 与一个「告诉用户这次导出有 10 GB」的读数，是同一个东西——
> 只不过前者在加法上是完全正确的。

修复：拆成 `bytes`（会被真的写出去的）与 `referencedBytes`（只给清单的），
两个数分别由用例钉住。探针 57⑨ 就是把这一版改回去。

### 5.2 探针 57⑥ 的重瞄（记下来，因为它是一次探针缺陷）

57⑥ 第一版写的是 `if (false)` 关掉"认不出类别"的守卫。它**确实变红了**，
但 `thrown=1`——红的原因是 `policy.handling` 上抛 `TypeError`，**不是断言**。
按本项目的纪律，**崩溃式变红不算证据**。

改成人类真会写的那个 bug：给认不出的类别一个**兜底默认**
（`?? EXPORT_CLASS_POLICY.database`）。那样陌生落点会被当成"业务数据库"
正常导出，用例在 `entries.length === 0` 与 `CLASS_UNKNOWN` 两处**断言级**变红。

> 一个「让代码崩掉所以用例红了」的探针，
> 与一个「根本没打到那条判据」的探针，是同一个东西——
> 只不过前者在红/绿这一列上看起来是有效的。

## 6 ⚠️ 诚实边界

1. **没有写包代码。** `planExport` 产出计划与清单；**本仓库没有写 zip 的代码**，
   没有真正的字节复制、没有流式写出、没有 fsync。导出的"包"目前只是一份
   JSON 清单的**结构**。

2. **没有 CLI 入口。** spec line 988 说"提供入口"，而备份/恢复/导出**三者
   都没有接进** `product/launcher/cli.mjs`。阶段 8 的备份模块同样如此
   （其子代理已如实报告）。所以"入口"这一半**未完成**。

3. **`stores` 由调用方枚举。** 与 PRT-904/908/614 同一条边界：一份**不完整**的
   `stores` 会让导出报告"导完了"，而本模块**没有机制发现它漏了**——
   *那是信任边界，不是检查*。

4. **密钥扫描是调用方给的。** `scannedSecrets` 由调用方提供，
   本模块不自己扫内容。`EXPORT_CLASS_POLICY.secret` 挡得住"整个密钥库"，
   挡不住"凭据被抄进一份普通配置里"——那要靠调用方扫。

5. **哈希由调用方给。** 缺哈希会报 `ENTRY_UNHASHED`，但本模块**不计算**哈希，
   因此无法发现"哈希是假的"。

6. **格式可移植 ≠ 内容有意义。** 一份 `json` 格式但 schema 随版本变来变去的
   导出，接收方照样读不懂。`schemaVersion` 只是**声明**，没有对应的
   schema 定义文件，也没有版本兼容性检查。

7. **未覆盖**：导出加密、分包（大于单文件上限时怎么办）、断点续传、
   导入（把导出包读回来）——spec 只要求"导出入口"，本批严格照做。
