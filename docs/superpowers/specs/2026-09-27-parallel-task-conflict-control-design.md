# Legion 并行任务文件冲突治理设计

> 日期：2026-09-27
> 状态：待评审
> 范围：同一 Git 仓库内多个编码任务的写入调度、成果集成与冲突裁决
> 依赖：[Legion Product Runtime 产品化架构设计](2026-09-11-legion-product-runtime-design.md)

## 1. 摘要与设计目标

用户可以同时发布多个任务，Legion 应让互不影响的任务并行执行，让可能修改同一文件的任务有可解释的等待顺序，并确保每项成果在进入交付分支后仍满足验收条件。用户不需要知道 worktree、Git 冲突标记或手工合并命令，就能看清任务为什么等待、谁占用文件、哪项成果已经进入主版本，以及冲突需要自己决定什么。

本设计把问题拆为三个时刻：**开工前识别写入重叠；执行时隔离并监测实际改动；完成后按仓库串行集成并验证集成结果**。同一文件可以在不同任务的隔离工作区中安全编辑，但“彼此看不见的编辑”并不等于“可以同时交付”。因此默认对重叠写入排队；只读调研、评审和与该文件无关的任务继续并行。

成功标准：

1. 两个受管任务不会在同一个物理工作目录中同时写入；已知写入范围重叠时不会同时获得写入资格。
2. 后完成的任务不能因为先完成任务已合入而静默丢失、覆盖或误报自己的产出。
3. Git 自动合并成功之后，仍要在**集成后的代码**上验证任务验收条件；验证失败不得记为已交付。
4. 冲突、进程崩溃和用户本地未提交改动均保留可恢复产物，并给出明确下一步。
5. 任务卡区分执行、等待集成、待裁决、已交付，不再把“Agent 写完”当作“已经进入目标分支”。

首版针对绑定 Git 仓库的软件交付任务。非 Git 工作区只允许一个写入任务执行，直到引入可验证的版本快照与回滚机制；只读任务不受此限制。不在首版实现行级协同编辑、自动理解所有语义冲突、跨主机分布式锁或把用户的未提交改动自动 stash。

## 2. 依据与当前缺口

### 2.1 厂商做法

| 产品 | 公开机制 | 本设计吸收的原则 |
| --- | --- | --- |
| Claude Code | 桌面会话可选独立 worktree；Agent Teams 文档建议把不同文件交给不同成员，同文件编辑适合顺序处理 | 任务边界应在派工前可见，重叠任务默认串行 |
| Codex | 并行任务可在各自 worktree 执行，Handoff 将工作移回本地工作区 | 执行隔离与成果集成是两个独立的产品阶段 |
| Cursor | 后台 Agent 在隔离环境与独立分支完成工作，用户审查后合并 | 成果保留为可审查的交付物，集成应有明确边界 |

资料：[Claude Code Desktop](https://code.claude.com/docs/en/desktop)、[Claude Code Agent Teams](https://code.claude.com/docs/en/agent-teams)、[OpenAI 官方 Codex worktree 文档](https://learn.chatgpt.com/docs/environments/git-worktrees)、[Cursor Background Agents](https://docs.cursor.com/background-agent)。这些资料说明行业已普遍采用隔离工作区；以下调度和集成队列是 **Legion 的设计选择**，不声称厂商均已提供相同能力。

### 2.2 仓库现状

| 现有资产 | 现有行为 | 本设计处理 |
| --- | --- | --- |
| `orchestrator/workspace/index.mjs`、`plugins/src/workspace.ts` | 每任务独立 worktree；产品运行面要求 worktree 在仓库外 | 保留隔离，统一运行路径与身份；不另造工作区系统 |
| `tasks.fileDomain` | 切片任务可声明文件域，守护在合入前检测越域；为空时不拦 | 作为任务的**许可上界**继续使用；新增运行时写入意图和占用，不把二者混成一列 |
| `GET /api/overlaps` | 从已有 patch 记录回看同文件改动，在任务详情警示 | 保留历史审计；增加启动前与运行中的实时冲突视图 |
| `plugins/src/index.ts` 的 `autoPromote` | 对主工作区直接执行 `git merge`，失败后 abort 并保留任务分支 | 收敛为唯一集成服务；完成前验证集成结果 |
| `plugins/src/mediation.ts` | 对失败的 merge 调用 AI 调解员，并尝试提交结果 | 调解员产出候选解决方案；涉及需求取舍时由用户裁决 |
| `team-hub/run-store.mjs` | Task、Attempt、Lease、Run 分离；claim 与 epoch fencing 已存在 | 写入资格与集成租约由 team-hub 原子授予，复用 Attempt 身份和 epoch |

现有重叠提示依赖**已生成的补丁**，无法阻止两个任务同时开工；文件域越界检查发生在**合入前**。现有进程内 `mediating` 集合也不能充当多个守护进程之间的仓库锁。本设计不删除这些能力，而是把预防与交付阶段补齐。

## 3. 产品规则与任务生命周期

### 3.1 用户可见规则

- 创建编码任务时，规划器给出“预计修改范围”；用户可以查看、缩小或扩大。它是调度依据，不能被 Agent 的一句提示词替代。
- 未声明范围的任务可进入**只读探索**；第一次写入前必须提交具体范围。用户手工创建的旧任务也走同一路径，不默认独占整个仓库。
- 写入范围与活跃任务重叠时显示“等待任务 T-123 释放 `src/server.mjs`”，并说明当前任务仍可进行哪些只读工作。等待结束后，任务工作区从**最新目标提交**创建；若重试任务已有未交付 WIP，先在隔离工作区把最新目标版本纳入并验证，不能重置掉 WIP。
- 完成执行的任务进入“待集成”；只有集成验证与必要的人工验收都通过后，才显示“已交付”。
- 碰到语义选择时，界面展示两项任务目标、原始改动、AI 建议及验证结果；用户选择“采用 A／采用 B／要求重新修改”，产品记录裁决人和理由。
- 用户本地仓库有未提交改动时，任务可继续在 worktree 运行；对该仓库的自动集成暂停，界面点名需要处理的本地状态。

### 3.2 状态分层

不扩充 `run_attempts.state` 去表达 Git 交付。Attempt 的 `Completed` 仍表示一次执行已结束；新增 `task_deliveries` 作为**交付子状态**：

```text
范围待确认 → 等待写入资格 → 隔离执行 → 待任务验收
                                         ↓
                    待集成 → 集成验证中 → 已交付
                       ↓          ↓
                    待裁决 ← 验证失败
```

交付状态的存储值固定为 `awaiting-acceptance`、`ready`、`preparing`、`validating`、`needs-review`、`integrated`、`abandoned`。无人工闸门的任务可由执行验收直接从 `awaiting-acceptance` 进入 `ready`；人审任务须有批准记录。`needs-review` 可由裁决回到 `ready` 或进入 `abandoned`；`integrated` 与 `abandoned` 是终态，重做必须产生新 Attempt 和新 delivery。写入调度状态独立存储为 `unplanned`、`waiting-file`、`reserved`、`reconciling`、`released`，不能拿交付状态代替文件占用状态。

`tasks.status` 继续是看板状态：等待写入资格保留 `todo`，另设结构化 `schedulingState=waiting-file` 和阻塞者信息，不进入执行失败/重试通道；执行中为 `in_progress`；执行结束到集成完成期间为 `in_review`；**`done` 仅在交付子状态为 `integrated` 且任务原有验收条件通过后产生**。需要将军验收的岗位先在任务 worktree 中审阅，批准后入集成队列；打回时继续使用该任务的隔离工作区，不污染目标分支。历史任务的 `done` 不倒推为已验证集成，迁移时显示 `deliveryState=legacy-unknown`，避免制造假的成功证据。

## 4. 核心数据与权威边界

team-hub SQLite 是唯一调度事实源；Git 保存代码版本，Workbench 只展示和发起操作。仓库身份取规范化的 Git common-dir 实路径，不能只按空间 ID 判断，因为多个空间可能绑定同一仓库。首版一个受管仓库只绑定一个交付目标：该仓库绑定工作区当前检出的分支完整 ref（如 `refs/heads/main`）。若用户切换该工作区分支，集成先暂停并要求重新绑定；不在首版管理一仓库多个目标分支。

| 表 / 字段 | 关键内容 | 不变量 |
| --- | --- | --- |
| `task_write_intents` | `task_id, attempt_id, repo_id, target_ref, paths_json, revision, source, state, created_at_ms` | 规划期 `attempt_id` 可为空，claim 后绑定；路径是仓库相对的规范路径；`state` 为 proposed/reserved/released；当前行用 revision CAS 更新，每次变更另记只追加事件 |
| `write_reservations` | `repo_id, task_id, attempt_id, lease_epoch, paths_json, state, expires_at_ms, updated_at_ms` | 活跃 reservation 不得在同仓库覆盖相交路径；释放须核对 Attempt 和 epoch |
| `task_deliveries` | `task_id, attempt_id, source_commit, base_commit, target_ref, state, validation_id, integrated_commit, decision_id, version` | 一次交付唯一；状态更新用版本 CAS；已集成提交不可被另一 Attempt 覆盖 |
| `integration_jobs` | `id, repo_id, target_ref, delivery_id, expected_head, prepared_commit, state, lease_epoch, owner, updated_at_ms` | 同一物理仓库同时至多一个受管 Git 集成操作；队列由 team-hub 授权 |
| `integration_events` | job、actor、时间、前后状态、Git SHA、错误码、验证摘要 | 只追加；恢复与审计使用，不保存密钥或完整模型输出 |

`tasks.fileDomain` 仍表示**允许修改的最大范围**。`task_write_intents.paths_json` 表示本次真正计划写入的范围，必须是 `fileDomain` 的子集；无 `fileDomain` 的旧任务仍需在首次写入前申报 intent。最终 Git diff 必须同时满足许可上界和本次 intent。动态扩域必须重走预约事务，不允许事后以“实际已改到这里”为由自动扩大范围。

路径匹配使用文件与目录两种明确类型，不接受任意 glob。规范化先拒绝绝对路径、`..`、空路径、`.git`、符号链接越界，再按仓库配置处理 Windows 大小写差异。目录以路径段边界匹配，`src/a` 不得错误覆盖 `src/ab`。重命名同时占用旧路径和新路径；删除、生成文件及格式化器改动都算写入。一个宽泛目录可合法占用其子路径，但界面提示范围过宽及会阻塞的任务数。

## 5. 调度协议

### 5.1 开工前

1. 规划器只读探索，提出任务目标、验收条件与预计写入范围；用户可调整。
2. **team-hub 的 claim 事务同时授予 Attempt lease 与首次写入 reservation**：在同一个 `BEGIN IMMEDIATE` 事务内选择候选、读取仓库活跃 reservation、判断路径交集、创建 Attempt、写入预约并递增 lease epoch。任何一步失败都回滚，不能出现“已认领但没有写入资格”的半状态。
3. 文件被占用的候选暂时跳过，继续检查队列后续无冲突任务，避免队头阻塞全仓库。响应给界面的是结构化 `FILE_CONTENTION`、冲突路径和持有任务；等待不算执行失败，也不消耗重试额度。claim 的候选扫描应设有上限和稳定排序，避免长队列拖慢事务或高优先级任务永久饥饿。
4. 成功后在 RunRequest 中携带不可由模型修改的授权快照。Worker 在启动写工具前核对 Attempt epoch、intent revision 和 worktree 身份。旧版不支持该协议的 worker 不得认领已启用治理的仓库。

只读任务不申请 write reservation。若任务先读后写，先执行只读阶段，再以该 Attempt 的当前 epoch 原子申请资格；等待期间暂停写工具，而不是让 Agent 在共享目录继续尝试。取得资格后重读目标 HEAD：若与只读探索时不同，更新上下文并重新核对修改计划。

### 5.2 执行时

受管 Agent 只能在自己的 worktree 内写入。写工具的 `pre-execute` 检查路径、Attempt epoch、reservation revision 与授权范围；命令执行和生成器同样需要受控工作目录。工具无法可靠预知全部写入文件时，在隔离 worktree 内执行后立即检测 Git 状态：超范围改动不得进入验收/集成，保持现场并要求调整范围或撤销该次改动。权限强制层和实际 diff 复核共同构成边界；**事后 diff 不是实时文件锁的替代品**。

动态发现需要修改新文件时，Agent 提出扩域申请。team-hub 在事务内检查新增范围是否撞上其他活跃 reservation；成功后提升 intent revision 并更新执行授权；失败时暂停该写入步骤，保留现有产物。多个进程同时争用同一路径，数据库事务只给一个赢家。取消、重试、租约过期时先冻结旧 epoch；若旧执行进程或 Git 状态仍未确认结束，reservation 进入 `reconciling` 而非立即释放，防止迟到写入与新任务重叠。

## 6. 集成队列与交付协议

### 6.1 入队条件

任务分支已有稳定 `source_commit`；工作树未提交改动已显式保全；最终 diff 通过文件域检查；运行验收证据齐备；原有人审岗位已获批准。满足后写入 `task_deliveries.state=ready`。此时仍占用写入范围，直到交付完成或用户明确放弃，避免后续任务基于过期主版本先行写同一区域。

### 6.2 单仓库集成步骤

1. team-hub 以事务认领该仓库的 integration job，发放带 epoch 的租约。不同守护进程和公共调解员必须走同一个入口；进程内 `Set` 仅用于减少重复请求。
2. 读取目标 ref 的 SHA、源分支 SHA 与主工作区状态。目标工作区必须整体干净；若有任何未提交或未跟踪改动、Git 正处于其他 merge/rebase，或仓库身份不符，则暂停并给出可操作原因；不自动 stash 用户文件。
3. 在**临时隔离集成工作区**从 `expected_head` 生成候选合并提交，保留任务分支与原提交。Git 内容冲突进入待裁决；干净合并继续。
4. 在候选合并提交上运行任务指定验证及仓库规定的受影响回归。验证命令从仓库已登记的命令及参数列表中选择，受超时和资源限制，不能由模型把任意 shell 字符串写进配置。验证报告含命令、退出码、耗时、候选 SHA 和所用验收版本；失败时不改变目标分支。
5. 最终提交前重新确认目标 ref 仍为 `expected_head`、仓库主工作区仍安全、job epoch 未过期；若版本前进则丢弃**临时候选**并基于新 HEAD 重算、重验。限定自动重算次数，超出后进入待裁决，防止无限循环。
6. 候选提交以 `expected_head` 为第一父提交。在仓库级受管互斥区内，对干净的绑定工作区执行仅允许快进的集成，将已验证候选接到目标分支；不在用户工作区重新做一次可能产生不同结果的冲突调解。写入 Git 操作前后分别记录 `integration_jobs` 阶段和 SHA；完成后核对目标提交包含任务源提交，记录 `integrated_commit`，再推进 `task_deliveries=integrated` 和任务 `done`，释放写入 reservation。

**Git 与 SQLite 不能组成单一原子事务。** job 因此按 `prepared → applying → ref-updated → finalized` 留持久日志。崩溃恢复时读取 Git 目标 ref、源提交可达性和 journal，判定“未应用／已应用未记账／结果不明”；已应用未记账只补记，不重跑 merge。结果不明暂停集成并请求核查，不自动删除分支。外部 Git 进程不受 Legion 租约约束，故最终 Git 操作必须检测 HEAD 与工作区变化；检测不到确定安全状态时停止，不能声称零风险自动合入。

集成队列只串行**短暂的 Git 集成操作**；候选合并与必要验证在临时集成工作区完成，其他任务仍在各自 worktree 工作。在最终锁内发现 HEAD 变化就重新生成候选并重新验证，不复用过期的绿色结果。集成完成前不得删除源 worktree/分支；清理是可重试的后续动作，失败不回滚已交付事实。

### 6.3 冲突裁决

Git 冲突与语义冲突分开处理：

- **可机械解决**：例如独立段落或确定性的生成文件重建。AI 可提出候选，但必须重新运行集成后验证；是否自动接受由仓库策略决定，首版默认要求用户审查同文件冲突。
- **需求冲突**：两个任务修改同一接口行为、校验规则或配置默认值。AI 只展示差异、影响和建议，用户选择最终意图，再由 Agent 据此修订候选。
- **Git 无冲突但验证失败**：作为集成失败呈现，不能标记完成。界面提供“让原任务修复”“新建修复任务”“放弃本次交付”。
- **人工拒绝**：保留源分支、patch 和证据；释放或继续持有写入预约由明确操作决定。拒绝并放弃时才释放；打回重做继续持有。

## 7. Workbench 交互

任务中心增加交付徽标：`只读探索`、`等待文件`、`执行中`、`待验收`、`排队集成`、`集成验证中`、`待裁决`、`已交付`。任务详情的“改动 × 证据”保留历史重叠展示，同时新增**当前占用**、预计等待对象、集成目标和最近一次验证结果；历史重叠不能冒充实时占用。

用户点击“为什么等待”可看到冲突路径、持有任务及该任务状态，并可选择缩小本任务范围、让当前持有任务完成、打回重做或取消任务。默认不提供“强制同时写同一文件”按钮；需要并行推进的用户可把工作拆成只读调研或互不相交的文件任务。

冲突裁决面板以“原任务意图 → 两份改动 → 候选结果 → 验证证据 → 选择”排序，显示差异而非原始 Git 命令。所有操作通过 team-hub API 绑定当前 `delivery.version`；过期页面提交返回 409 并刷新，不覆盖其他人的裁决。审计记录是谁、何时、依据哪份候选版本做的决定。

## 8. API 与模块边界

| 组件 | 新增职责 | 主要接口 |
| --- | --- | --- |
| team-hub `write-intent-store` | 规范路径、事务预约、冲突查询、epoch fencing、释放与恢复 | `POST /api/tasks/:id/write-intent`、`POST /api/tasks/:id/reservation`、`GET /api/repositories/:id/contention` |
| team-hub `delivery-store` | 交付状态、集成 job 租约、CAS 裁决、只追加事件 | `POST /api/deliveries`、`POST /api/integration/claim`、`POST /api/integration/transition`、`POST /api/deliveries/:id/decision` |
| Orchestrator | 写入资格申请、运行中扩域、执行结束生成交付请求 | 通过 team-hub 客户端调用，不保存第二套任务状态 |
| Integration worker | 候选合并、验证、目标分支提交、恢复与清理 | 只接受 team-hub 授权的 job；不从界面直接执行 Git 命令 |
| Workbench | 范围编辑、等待说明、交付队列、冲突裁决与审计展示 | 消费 team-hub API 和现有审计 SSE |

API 路径是设计契约草案；实现时遵循现有路由模块风格。请求必须绑定 scope、task、Attempt/lease epoch、revision/version 和操作者；服务端从数据库解析仓库目录与目标 ref，不接受浏览器传来的任意绝对路径、shell 命令或 Git ref。权限沿用现有 F-02：范围修改、放弃交付、冲突裁决和手工集成分别授权并审计。

## 9. 失败、恢复与边界条件

| 情况 | 行为 |
| --- | --- |
| 两个 worker 同时申请同一路径 | `BEGIN IMMEDIATE` 内只有一个预约成功；另一任务等待且不消耗重试额度 |
| Agent 写到未申报文件 | 在 worktree 保留现场，阻止验收/集成；扩域成功后继续，否则打回调整 |
| 运行 lease 过期但进程未确认退出 | 冻结 reservation，进入 `reconciling`；旧 epoch 写入与结果上报被拒 |
| 集成期间目标 HEAD 前进 | 当前候选与验证作废，按新 HEAD 重算；超限后待裁决 |
| Git 自动合并成功但测试失败 | 目标 ref 不变；保存候选与报告，任务显示“集成验证失败” |
| 用户本地未提交改动 | 不 stash、不覆盖；暂停集成并指明仓库和路径，Agent worktree 产物保留 |
| 集成 worker 崩溃或重启 | journal + Git SHA 对账；确认已经应用则补记，无法确认则暂停并保留分支 |
| 任务取消或打回 | 取消后确认执行停止，再释放预约；打回重做保留预约与 worktree |
| 非 Git、Git 不可用或路径不能规范化 | 禁止并行写入；清晰提示降级原因，不默默退回共享目录并行写 |

同一仓库多个空间共用一个集成锁和路径占用池。不同仓库之间互不阻塞。同文件不同代码段在首版仍视为重叠，因为 Git 可自动合并不代表逻辑上兼容；后续只有在验证数据证明误阻塞明显时，才考虑符号或代码区域级放行。

## 10. 迁移与发布

1. **观察阶段**：保持旧执行行为，只计算预计范围、真实 diff、潜在等待关系和集成验证结果；不改变派工。用日志与界面区分“模拟判断”，收集真实误判和漏判。
2. **调度阶段**：新任务启用写入 intent 与服务端预约；旧任务无 intent 时先只读探索再补报。非 Git 空间单写入。目标指标是消除已知同文件并行写入。
3. **集成阶段**：按空间逐步把 `autoPromote` 和公共 `mediation` 接到唯一 integration worker；同仓库不得同时启用旧直合与新队列。先灰度自动无冲突任务，再纳入 AI 调解候选和用户裁决。
4. **收口阶段**：`done` 语义改为已交付；旧历史显示 `legacy-unknown`；移除 UI 中要求用户手工输入 `git merge` 的提示，保留诊断导出。

开关按仓库或空间配置，但同仓库共享一个模式；不可因两个空间选择不同模式而同时运行两个集成器。回滚只关闭**新任务的自动认领与集成**，不删除数据库记录、预约、分支或临时工作区；在制 job 对账后再切换旧路径。数据库迁移需可重复、可从旧库启动，并在升级前备份。

## 11. 验收与度量

### 11.1 必须通过的场景

1. 两个独立进程同时申请同一文件，只产生一个活跃写入者；不同文件可同时执行。
2. `src/a` 与 `src/ab` 不误判，Windows 大小写别名、目录子路径、重命名两端正确判重。
3. 已认领任务动态扩域撞上其他任务，写入被暂停且现有 worktree 产物不丢。
4. 两任务在不同 worktree 修改同一文件，后者等待前者交付后基于新的目标版本继续；最终两个任务的要求都经验证。
5. Git 无冲突但集成后测试失败，目标分支保持原 SHA，任务不进入 `done`。
6. 集成前、更新 ref 后、落库前分别杀死 worker；恢复后每个 source commit 最多集成一次，不能丢产物或重复推进任务。
7. 用户在主工作区留有未提交改动时，自动集成暂停且这些字节不变。
8. 人审岗位打回后，目标分支不含其未批准改动；再次提交沿用原任务的反馈与隔离成果。
9. 多空间绑定同一仓库、多 worker 同时运行时，预约与集成仍遵守同一仓库权威。

关键指标按仓库与版本记录：同文件写入阻止次数、等待时长 P50/P95、集成冲突率、集成后验证失败率、人工裁决率、集成恢复成功率、误阻塞申诉数。指标不可读时显示“暂无读数及原因”，不展示为零。发布门槛：上述场景全通过；灰度期间无任务产物丢失、无未经授权覆盖用户工作区、无任务被错误标为已交付。

## 12. 实施切片与待评审决策

| 顺序 | 切片 | 可独立验证的交付 |
| --- | --- | --- |
| 1 | 路径规范化与冲突判定纯函数 | 文件/目录、Windows 大小写、重命名、越界判据 |
| 2 | team-hub intent 与 reservation 事务 | 跨进程争用、epoch fencing、崩溃恢复 |
| 3 | Orchestrator 认领和运行中扩域接线 | 等待不烧重试、队列不被单个冲突任务堵死 |
| 4 | delivery store 与单仓库集成 worker | 干净合入、HEAD 变化、Git/DB 对账、集成后验证 |
| 5 | Workbench 等待与裁决界面 | 用户能处理冲突，无需执行 Git 命令 |
| 6 | legacy 调解迁移和灰度收口 | 同仓库只有一个集成入口；历史状态如实展示 |

首版产品策略确定为：**不提供同文件强制并行写入**；每个受管仓库必须配置至少一项可执行的集成验证，且任务自身验收条件必须通过。未配置仓库验证命令时，任务可执行并保留交付候选，但停在 `needs-review`，由用户补充验证配置并重验后才允许进入目标分支；界面不得提供“跳过验证并标记已交付”。这两项是本设计的默认决策，评审可修改，但实现不得自行放宽。
