# Legion 桌面端自动更新设计

> 日期：2026-10-02
> 状态：待评审，尚未实施
> 范围：Windows x64、当前用户安装、自动检查更新、用户主动下载和安装、静态更新文件托管
> 依赖：[独立桌面应用设计](2026-09-27-legion-desktop-design.md)、[Product Runtime 产品化架构设计 §9](2026-09-11-legion-product-runtime-design.md)

## 1. 目标与核心决策

用户安装 Legion 后，无需重新寻找安装包或使用终端即可获知新版、查看发布说明、下载并完成升级。检查更新不影响当前工作；安装必须由用户确认，业务数据和用户工作空间不放入被替换的程序目录。

首期采用以下方案：

- 公开 HTTPS 静态文件托管存放签名版本清单、发布说明和更新包；无需更新 API、数据库或自建服务器。
- 产品发行地址在打包时写入客户端，测试与生产分离；具体域名、存储供应商由部署时填写。
- 启动后自动检查，运行中定期检查，设置页提供立即检查。
- 自动检查、用户确认下载、用户确认安装是三个独立动作。退出应用不自动安装。
- Electron 负责桌面交互；更新服务负责网络发现和下载；Product Launcher 负责停止任务与服务；独立更新 helper 负责程序切换和恢复。
- 延续 `product/upgrade/` 的版本清单、备份、迁移和切换约束，避免安装器绕过产品升级事务。
- 默认 stable 通道；internal/canary 用于开发与明确选择的测试用户。首期不做强制升级、自动后台下载或按用户比例灰度。

本设计针对 Legion 自身发行。DSH Desktop 的更新与 Legion 更新相互独立；Legion 所管理的 DSH Runtime 只按目标产品清单中的精确版本准备，不自行追踪 DSH 最新版。

## 2. 当前基础与新增范围

现有 `product/upgrade/` 包含 manifest、package、preflight、backup、migration、switchover、channels、audit 和升级编排模块，可以作为接入基础。它们的存在不表示真实安装、网络更新、Windows 文件释放或崩溃恢复已完成。

现有桌面设计采用独立 Electron 壳和唯一服务所有者 Product Launcher。当前工作区的桌面实现处于变动状态，本文件按该架构定义目标，不恢复或修改桌面代码。

新增范围包括网络版本发现、可信发布协议、下载缓存、更新界面、跨进程升级事务、发布脚本及真实安装包验收。

不改变任务状态机、权限策略和数据库领域模型；数据库迁移调用现有受控入口。首期不承诺 macOS/Linux、离线首次安装、任意历史版本直升、断点续传或差分下载。

## 3. 总体架构

```text
发布机器 / CI
  └─ 构建 → 签名 → 验证 → 上传不可变发布目录 → 最后替换通道清单
                            │
                            ▼
                  HTTPS 静态托管 / 可选 CDN
                    清单、发布说明、完整更新包
                            │
                            ▼
Electron 主进程 ── 更新发现和下载服务 ── CacheDir
       │                 签名/哈希校验、进度
       │ 用户确认安装
       ▼
desktop bridge → Product Launcher
                    停止认领、等待任务、写锁、备份、停止服务
       │
       ▼
独立更新 helper → 程序版本切换 → 新 Launcher 迁移和健康检查
       └─ 提交成功 / 恢复旧版本 / 停留在恢复界面
```

helper 位于本次事务的独立受控目录，由随包 Node 运行，启动前核对程序摘要。它及所需 Node 文件不属于本次待切换的目录。不得由已退出的 Electron 进程承担恢复责任。

首期不直接用 `electron-updater.quitAndInstall()` 代替升级事务。DSH 的更新器可参考调度、进度和下载体验，但 Legion 还需协调多服务、数据备份、数据库迁移与原子版本指针。若后续引入该库作为传输适配器，仍必须保持唯一升级事务所有者。

## 4. 托管部署与目录

只需能公开读取文件的 HTTPS 托管。对象存储可直接提供入口；有稳定自定义域名时，迁移存储供应商无需改变已安装客户端。CDN 是可选项，首期成本主要来自存储与下载流量。

```text
https://<待配置的生产更新域名>/legion/
  feeds/stable/win-x64.json
  feeds/canary/win-x64.json
  feeds/internal/win-x64.json
  releases/<releaseId>/manifest.json
  releases/<releaseId>/notes.zh-CN.txt
  releases/<releaseId>/legion-win-x64.zip
  releases/<releaseId>/Legion-Setup-win-x64.exe
```

ZIP 用于已安装客户端的升级，包含产品文件闭包和目标产品版本清单；EXE 用于首次安装和人工修复。两者必须从同一已验证发行目录产生，不能分别解析不同依赖版本。DSH 仍遵循桌面设计的首次联网、精确版本安装路线，其目标运行时准备纳入本次升级验收。

- `releaseId` 唯一且不可覆盖；同版本不同字节也必须使用不同 releaseId，并禁止客户端把它当成常规同版本更新。
- 发布目录可长期缓存；通道清单使用 `Cache-Control: no-store`，且客户端请求禁用缓存。CDN 配置必须实际验收。
- 客户端仅需读取权限。上传权限只在发布端，不进入安装包。
- 测试部署使用独立 origin、存储前缀和签名信任配置，不依赖难以猜中的路径代替隔离。
- 旧发布保留到升级支持窗口结束；本地成功备份按产品架构保留最近 3 份和 30 天，取更大者。

## 5. 清单协议与信任

现有产品版本清单描述精确组件版本；新增发行清单描述产物和升级路径，不替换现有格式。通道清单和发行清单均使用签名 envelope：

```json
{
  "payload": {
    "format": "legion/update-feed@1",
    "channel": "stable",
    "platform": "win32",
    "arch": "x64",
    "sequence": 42,
    "issuedAt": "2026-10-02T00:00:00Z",
    "expiresAt": "2026-10-09T00:00:00Z",
    "releaseId": "example-release-id",
    "productVersion": "1.2.0",
    "manifestPath": "releases/example-release-id/manifest.json",
    "manifestSha256": "<64位十六进制摘要>"
  },
  "keyId": "release-2026-a",
  "signature": "<Base64 Ed25519签名>"
}
```

示例仅说明字段，不是有效发布文件。签名覆盖固定前缀 `legion-update-envelope@1\n` 加 `canonicalJson(payload)` 的 UTF-8 字节，keyId 从客户端内置信任表选择公钥；验证器拒绝重复 JSON 键、非法数字、未知格式、超大输入和不满足 schema 的字段。现有 canonicalJson 需经过跨发布端/客户端的固定向量验证后才复用。

发行 payload 使用 `legion/update-release@1`，至少包含：

| 字段 | 用途 |
| --- | --- |
| releaseId、productVersion、channel、platform、arch | 与通道清单一致，锁定一次发行 |
| productManifest、productManifestSha256 | 现有产品版本清单及其摘要，钉住 Legion、DSH、补丁和契约版本 |
| supportedFromVersions | 明确允许升级的当前产品版本集合，首期只验证当前 stable 的 N-1 → N |
| minWindowsBuild、requiredFreeBytes | OS 及空间预检；空间仍需按实际下载、解压、运行时和备份预算计算 |
| package.path、sizeBytes、sha256 | 完整 ZIP 的地址、准确大小和内容摘要 |
| installer.path、sizeBytes、sha256 | 人工安装产物 |
| notes.path、sizeBytes、sha256 | 纯文本发布说明，避免运行外部 HTML |
| migrationPlanDigest、rollbackPolicy | 固定迁移计划及是否允许仅回退程序 |
| issuedAt、expiresAt | 可信元数据有效期 |

路径为固定 origin 下的相对路径，禁止绝对地址、父目录穿越、编码绕过和跨 origin 重定向。HTTPS 保护传输，独立签名防止托管被改写时客户端信任伪造清单；包摘要保护完整性，Windows Authenticode 验证发布者身份。

客户端持久化每个通道/平台的最高已接受 sequence；低于该值拒绝，同 sequence 只允许完全相同摘要。sequence 提升不授权安装更旧版本。过期清单不授权新的下载或安装；时钟明显异常时提示校正时间。发布系统定期重新签发指向同一版本的新清单，防止长期无新版时清单失效。

换密钥需先通过旧信任根签名的客户端更新预置新公钥，再切换发布签名。首期不提供远程任意替换信任根的入口；签名私钥泄漏后的紧急恢复保留人工下载可信安装包路径。

## 6. 检查与下载策略

启动达到桌面可交互状态后延迟 30～90 秒首次检查；之后以 6 小时为基准、±20% 抖动检查。恢复前台或系统唤醒时，仅在到期后补一次，不累计执行错过的周期。

手动检查立即执行，并与已有检查共享一次网络请求。失败按 15 分钟、30 分钟、1 小时逐步退避，最终上限 6 小时，加入抖动；成功恢复正常周期。请求空闲超时 60 秒，清单整体超时 30 秒，清单上限 256 KiB。自动检查失败只留脱敏日志；用户手动检查显示错误和重试按钮。

读取并验证通道清单 → 获取固定摘要的发行清单 → 验证兼容性 → 得到候选版本。按 SemVer 比较，不能按字符串排序；现有比较函数对预发布标识采用字典序，接入 canary/internal 前必须修正或使用已验证的 SemVer 实现。

候选以 releaseId、版本和发行摘要共同标识。用户确认绑定该身份；发布端变更清单不替换正在下载或已下载的目标。

下载写入 CacheDir 的 `.part` 文件，流式限制大小并计算摘要；下载完成及签名检查通过后原子改名。首期中断后重新下载完整包，不承诺续传。用户可取消下载，取消不影响当前程序。重启后保留有效缓存，重新校验后复用。

压缩包解压前后校验闭包；拒绝越界路径、软链接/重解析点、重复目标、解压炸弹及未知可执行文件。安装前再次验证包、发行清单有效期和目标身份。目标清单已过期时重新检查；新版目标变化需重新确认，不能悄悄安装另一个版本。

## 7. 用户界面与接口

设置 → 关于 Legion 显示当前版本、通道、上次成功检查时间及“检查更新”。发现新版后展示版本、发布说明、“下载更新”和“稍后”。稍后仅收起提醒，设置页仍可见；同一发行默认 24 小时内不重复主动提醒。

下载页显示真实字节进度和取消；校验阶段显示“正在验证更新”。就绪后提供“安装并重启”和“稍后安装”。关闭窗口、退出或托盘退出均不自动安装。

安装确认显示是否有在途任务。默认等待任务结束；超时回到可选择界面，不默认强杀。需要取消任务时使用已有取消机制，说明影响并另行确认，不把中断外部写操作当成可安全自动重试。

Electron preload 只暴露以下有界操作，主进程校验窗口来源和输入：

| 操作 | 输入及行为 |
| --- | --- |
| update.status / update.check | 无任意 URL、路径或 shell 参数 |
| update.download | releaseId + manifestDigest，匹配已验证候选 |
| update.cancelDownload | 当前下载操作 ID |
| update.install | releaseId + manifestDigest，匹配已就绪包与用户确认 |
| update.subscribe | 脱敏状态、阶段、字节进度、错误码；不含凭据 |

升级控制走 Electron → bridge 的私有协议；网页不能直接触发迁移或程序切换。升级 helper 使用受限的一次性事务凭证和固定事务文件位置，不信任网页输入的包路径。

## 8. 安装事务、恢复与数据边界

主状态机为 `idle → checking → available → downloading → verifying → ready → waiting-for-tasks → preparing → installing → validating → committed`。网络与准备失败进入可重试状态；程序切换后失败进入 `rolled-back` 或 `recovery-required`。检查失败不能覆盖已经准备好的更新状态。

安装事务按以下顺序执行：

1. 取得更新事务锁，记录当前/目标发行、摘要及持久化事务 ID；重新检查兼容性、签名和空间。
2. 下载并准备目标 DSH 精确版本及对应补丁，不改变当前运行时活动指针；网络失败在此停止。
3. Launcher 停止认领，等待在途任务结束；未完成外部操作按现有恢复协议记录，禁止盲目重放。
4. 建立覆盖所有写入入口的维护屏障并刷新数据；使用 SQLite backup API 或关闭数据库后的完整一致快照，禁止复制孤立的 WAL 主文件。
5. 备份数据库、配置和恢复所需元数据，记录附件的一致性边界；备份验证失败立即停止。密钥按既有安全存储策略处理。
6. 停止受管服务、bridge 和 Electron；helper 校验退出身份与进程树，句柄未释放则安全中止。
7. 解压并验证目标版本目录，在同一卷内原子切换活动指针；稳定入口启动目标程序，不能原地覆盖运行中的 EXE。
8. 新 Launcher 保持维护模式，运行固定迁移计划、运行时补丁自检和服务健康验证。此阶段不开放业务写入或自动认领。
9. 验证成功后刷盘提交事务，再解除维护屏障、恢复认领并显示成功。保留旧版本和有效备份，按策略清理。

版本目录包含本次需要切换的 Electron、Launcher 和产品资源，固定入口与 helper 的自更新另设经过验收的引导兼容流程。首期正常更新不得改变引导协议；需要变更引导层时引导用户使用已签名安装器。

事务日志位于 DataDir，由 helper 独占；每个不可逆动作前写意图、完成后写结果并刷盘。新旧 Launcher 均识别未完成事务，在恢复结束前禁止正常业务启动。断电或 helper 崩溃后的恢复依据磁盘活动指针、事务日志、备份摘要和数据库实际 schema，不只依赖最后一条 UI 状态。

| 失败位置 | 恢复规则 |
| --- | --- |
| 下载、校验、预检、备份或任务等待 | 当前版本继续运行；不改变活动指针 |
| Windows 文件占用、切换前退出失败 | 保留旧版本，恢复维护状态并提示重试 |
| 切换后、未改数据库 | 回到旧版本，验证成功后恢复工作 |
| 向前兼容迁移后健康失败 | 仅在旧版本兼容性已被证明时自动回退程序 |
| 不兼容迁移、恢复证据不足或恢复失败 | 保持维护模式；提供向前修复或明确的数据备份恢复入口 |

自动恢复备份仅限已证明维护屏障期间没有业务写入的未提交事务。提交后恢复旧备份可能丢失新写入，必须明确告知并取得用户确认。用户工作空间永远不作为安装覆盖或自动恢复目标。

## 9. 发布与撤回流程

1. 冻结精确组件清单和迁移计划，在干净 Windows 用户环境生成 ZIP 与签名安装器。
2. 校验文件闭包、签名身份、包大小/摘要和 N-1 → N 升级恢复证据。
3. 生成并签名发行清单，上传全部不可变发布文件，公开回读验证字节与签名。
4. 对通道发布加锁；生成更大的 sequence，最后通过单对象替换通道 envelope。
5. 从公网回读通道清单并用真实旧客户端检查、下载、安装；保留审计记录。

上传失败不得推进通道指针。通道清单只有一个带签名对象，避免正文与旁路签名不同步。上传凭据、签名私钥和 Windows 签名凭据保存在发布机或 CI 密钥存储。

撤回坏版本时签发更高 sequence 的清单，指向当前安全版本；它用于停止新安装，不使已升级用户自动降级。已下载目标安装前必须重新检查通道；目标被撤回时禁止安装。撤回清单允许取消旧候选，但不能授予降级权限。已安装坏版本优先发布更高版本修复。

签名清单定期续签可由 CI 定时任务执行，但本设计不创建任何实际自动化或云资源。

## 10. 验收与实施阶段

| 场景 | 验收结果 |
| --- | --- |
| 无更新、离线、超时、CDN 返回旧清单 | 现有工作不受影响；无错误更新提示；手动检查有准确结果 |
| 清单伪造、未知 keyId、过期、sequence 回退 | 拒绝授权下载或安装，保留脱敏原因 |
| 包被替换、错误签名、错误平台、磁盘不足、ZIP 越界 | 不触发安装，不修改当前程序或用户数据 |
| 重复点击、多个窗口、下载中发现新版 | 一次网络/安装事务；确认目标保持一致 |
| 有任务运行、不能安全取消、服务拒绝退出 | 不强制切换，任务状态可恢复 |
| SQLite WAL、附件写入、迁移失败、补丁失效 | 快照一致；新版本未验证前不开启业务写入 |
| 切换或迁移期间断电、helper 崩溃、指针损坏 | 下次启动先恢复；不能把未知状态显示成升级成功 |
| 错误发布撤回、清单续签、公钥轮换 | 旧客户端正确消费；已下载撤回包被阻止安装 |
| 干净机器首次安装及 N-1 → N | 无开发环境依赖，重启后数据、配置、工作空间和任务一致 |

实施拆为四个可验收阶段：

- A：协议 schema、签名固定向量、发布产物闭包、静态托管与公网回读脚本。
- B：检查调度、下载缓存、桌面状态与用户确认流程；此阶段不执行真实切换。
- C：Launcher 维护屏障、独立 helper、事务持久化、迁移和恢复接入。
- D：签名真实安装包，完成干净机器、文件占用、断电故障注入与撤回演练，满足门禁后开放 stable。

每阶段记录实际证据；测试替身通过不能替代 Windows 真机升级验收。

## 11. 部署时填写与实施前验证

设计默认采用静态 HTTPS 托管、完整包升级和用户确认，不因暂缺云账号而阻塞协议开发。正式发布前需填写生产/测试 origin、存储供应商与区域、签名发布者、公钥及责任人，并验证实际预算和下载可达性。

实施前必须确认现有升级编排是否提供真实的跨进程事务、写入屏障、一致备份及可替换 Windows 版本目录；缺失部分按本文件补齐，不能仅接一个“检查更新”按钮后宣称完成。当前桌面/运行时分发设计若发生变更，应同步本文件的 ZIP 闭包、helper 引导兼容范围与 DSH 准备方式。
